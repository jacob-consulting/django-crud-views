## Implementation Decisions

### Parent precedence — explicitly selected

- **D-01:** For object destinations, derive the actual parent from the object and prefer it over the hosting
  page's parent kwargs. A Book belonging to Publisher B links under B even when rendered on a page under A.
- **D-02:** An explicit caller-supplied parent override that conflicts with the object's actual parent raises
  an error. Do not silently discard the override or build a knowingly mismatched object URL.
- **D-03:** Collection destinations keep the hosting page's parent scope when it exists. A Back to Books link
  on Publisher A's page remains under A even if a supplied Book belongs to B. Do not apply D-01 indiscriminately
  to collection links.
- **D-04:** When the page URL supplies no parent scope, a collection link may derive its parent from a supplied
  object. An explicit parent is not required merely because the destination is a collection.

### Missing or ambiguous parents — explicitly selected

- **D-05:** M2M nesting requires parent context: an explicit parent or the page's parent kwargs. Without it,
  strict URL generation raises. Never automatically choose a related parent, even if exactly one exists.
  This permits explicitly scoped M2M links; the issue's shorthand "M2M builders raise" must not prohibit them.
- **D-06:** A null single-parent relation cannot be replaced by a page or caller parent. For an object detail
  destination this is unavailable: strict generation raises, while optional displays such as delete previews
  retain plain text under the optional-link contract below.
- **D-07:** Resource rows accept an explicit parent object or parent kwargs; view-based Resource links may use
  page parent kwargs. Do not infer relationships from arbitrary Resource row attributes. Preserve Resource
  ViewSets' existing leaf-only constraint.
- **D-08:** Do not query M2M membership during URL generation. Build from supplied parent context and leave
  membership/scope enforcement to the destination request. A generated URL certifies neither membership nor
  access. This does not remove existing destination validation performed separately by protected previews.

### Guardian link visibility — explicitly selected

- **D-09:** If the access helper cannot resolve a supplied object's parent, retain the existing child-access
  result. In particular, do not hide valid M2M links merely because the classmethod has no page kwargs. The
  destination request still checks parent permission; some displayed links may return 403 in this case.
- **D-10:** If no object is supplied, retain existing view-access behavior rather than requiring new parent
  context. The motivating case is a list page's own toolbar. Do not describe this fallback as proof that an
  arbitrary request-free caller has passed a parent gate.
- **D-11:** Missing configured Guardian permissions hide or disable the link according to the existing
  inaccessible-action policy. Direct requests raise a clear configuration error. Core permission-required
  views keep their existing request assertion and migration hint; their undeclared-permission links are hidden
  or disabled rather than treating an empty permission tuple as access.
- **D-12:** Unexpected parent-resolution errors propagate, including bugs in custom properties. Only recognized
  missing or ambiguous parent cases use the unresolved-parent fallback. Do not blanket-catch custom-code errors.

### Public URL helper contract — explicitly selected

- **D-13:** The request-free `ViewSet.get_url()` is strict by default: return a URL or raise. Its `strict=False`
  mode returns `None` for recognized unavailable destinations. Do not introduce a separate `try_get_url()` as
  the optional-link API. Unexpected programming errors still propagate.
- **D-14:** Conflicting explicit parents and wrong-model object inputs always raise, including with
  `strict=False`. Missing parent context and null relations are examples of expected unavailability that may
  return `None`; caller mistakes are not silently converted to missing links.
- **D-15:** Use existing exception types: `ValueError` for invalid or unresolved parent inputs and Django's
  `NoReverseMatch` when a route cannot be reversed. Document the distinction. Do not add a dedicated public
  URL-resolution exception. Keep unexpected custom-code errors unchanged.
- **D-16:** Release the changed precedence and conflicting-override behavior with a `### Breaking` changelog
  entry and a migration guide in `docs/migrating-1.0.md`. Include concrete caller changes. This explicitly
  supersedes #311's recommendation to use Changed only. Access fixes may also have their own Fixed entries.

### Carried-forward scope and preservation

- Reuse one parent-chain rule across URL and Guardian integrations. The issue proposals name
  `ViewSet.get_parent_pks()`, `ViewSet.get_url()` and `cv_guardian_has_parent_access()`; settle and document the
  public surface before handing it to Phase 7. Do not create separate competing relation resolvers.
- Preserve request-side queryset scoping, parent permission checks, inactive-actor handling and existing create
  semantics. A configured None parent-permission key still skips that permission evaluation only. Core nesting
  enforces parent scope, not a newly introduced parent permission requirement.
- Preserve `cv_get_parent_object()` as the parent of the current URL and sibling-collection navigation that
  intentionally reuses the current parent chain. Do not extend this phase into cancel history or save redirects.
- Phase 06.9's protected-preview contract remains: visibility filtering precedes URL work, hidden labels/URLs
  stay hidden, unavailable or inaccessible destinations stay plain text, and the exact resolved destination is
  checked. Keep the public `cv_get_related_object_url()` override hook and cascade behavior. Merely returning a
  URL from the new helper is not a replacement for protected-preview authorization.
- Preserve default markup, translations, escaping, action states, protected-blocker ordering and blocked-page
  form omission. Keep the stock/custom-template verification scope from prior phases; no external-application
  certification is implied.
- Existing project quality gates apply, including multicore pytest for broad runs, JavaScript tests, strict docs,
  Ruff checks and format checks. No product code was changed or product tests run during this discussion.

### Implementation latitude and research obligations

Resolve the following through code-grounded research and express them explicitly in the plan:

- Build a precedence matrix for object versus collection destinations, page kwargs, explicit kwargs,

### Public surface and internal composition

Recommend these signatures as implementation details delegated to research; they are proposed APIs, not existing definitions. [CITED: D-13–D-15; implementation latitude]

~~~python
def get_parent_pks(self, obj=None, *, parent_obj=None, kwargs=None) -> dict: ...
def get_url(self, key, obj=None, *, parent_obj=None, kwargs=None, strict=True) -> str | None: ...

@classmethod
def cv_guardian_has_parent_access(cls, user, parent_obj) -> bool: ...
~~~

Public kwargs mean explicit caller context. Pass page kwargs separately through a private view adapter. Internally return ordered coordinates, any materialized parent instances, source information and a recognized-unavailable reason. Strict wrappers turn a missing result into ValueError; optional wrappers return None. No new public exception and no try_get_url API. [CITED: D-12–D-15]

Own-model input means destination row. Accept unambiguous compatible parent instances as parent context; parent_obj explicitly disambiguates the role, including self-nesting. An object destination still requires its own row. Keep implementation in ViewSet plus at most one private relation module, with adapters in existing view/Guardian/delete owners. ### Precedence matrix

O = object-derived chain; W = page coordinates; E = explicit kwargs; P = explicit parent object and ancestry. Classify target with cv_object, not operation-name guesses. [CITED: src/crud_views/lib/view/base.py:589-605]

| Inputs/destination | Selected parent scope | Outcome |
|---|---|---|
| Object, O known, W agrees/differs | O throughout known single-parent chain | Ignore conflicting page chain |
| Object, E/P agree with O | O, explicit context at unresolved boundaries | Validate every known supplied coordinate |
| Object, E/P conflict with O | None | ValueError in both modes |
| Collection, W exists, child O differs, no E/P | W | Preserve Back/Home under page parent |
| Collection, no W/E/P, child O known | O | Derive without requiring explicit parent |
| Collection, explicit E/P | Explicit scope | Validate E against P and its known ancestry |
| Collection, explicit E/P plus conflicting own-child O | None | Conservative D-14 interpretation: reject explicit known conflict; intentionally different collection callers omit obj |
| Object, null single-parent relation | None | Unavailable; W/E/P cannot repair it |
| Collection with independent W, supplied child relation null | W | Collection scope does not require that child's relation |
| M2M, supplied E/P or W | Supplied scope at M2M boundary | No membership query |
| M2M, no supplied scope | None | Unavailable even with exactly one related parent |
| Resource row, supplied E/P or W | Supplied scope | No ancestry inference from arbitrary attributes |
| Resource row without required context | None | Unavailable |
| Non-nested destination | No parent chain | Preserve ordinary reverse/extra kwargs |

[CITED: D-01–D-08,D-14; implementation latitude]

Select coherent chains, not independent per-key winners. Changing an explicit immediate parent must not retain unrelated page ancestors. Derive from that parent instance; when only partial context exists and coherence cannot be established, report missing context. A complete explicit chain without object evidence remains coordinates rather than a membership certificate. Validate known single-valued segments around M2M boundaries without querying membership. [CITED: D-08 and multilevel research obligation]

cv_get_child_url's obj is the destination's direct parent: pass it as parent_obj and derive its ancestors. Preserve ordinary detail-page child URLs, cv_get_parent_object's URL-parent meaning and SiblingContextButton's current-chain navigation. [CITED: base.py:985-1035; buttons.py:255-302]

## Common Pitfalls

- Per-key precedence mixes unrelated ancestors: test two disagreeing full chains and partial overrides. [CITED: context multilevel obligation]
- A raw FK value can be a non-PK target: test to_field and registered model PK extraction. [CITED: Django fields reference]
- Optional mode masks bugs: inject ValueError, AttributeError, ObjectDoesNotExist and NoReverseMatch from custom hooks/properties. [CITED: D-12–D-15]
- New parent gate breaks create or checks the wrong state object: preserve parent-only creates and child-state checks. [CITED: guardian/lib/views.py:298-341; mixins.py:375-382]
- No-object fallback hides missing configuration: test D-10 and D-11 together. [CITED: context]
- Cached environment tests an old installed wheel: source-bind and record imported module locations. [CITED: 06.9-VERIFICATION.md:44-51]
- Prior browser evidence is mistaken for current: source hashes change; refresh affected cases and report limits. [CITED: 06.9-VERIFICATION.md:58; protected-delete.cjs:37-39,69-73]
