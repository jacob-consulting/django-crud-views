`DEFAULT_BUTTON_CLASSES` in `src/crud_views/lib/button_classes.py` remains the unchanged 88-key core table.
With only workflow's contribution installed there are 98 effective defaults; other installed extensions can
contribute more. Imports of workflow alone do not activate its defaults, and core never imports workflow to
discover them. The declaration attribute is an app-provider seam, not a replacement theme registration API.
`_get_default_button_classes()` and its caches remain private implementation details.

Declarations are static mappings, immutable by convention. First lookup after app discovery merges core and
active AppConfig declarations without mutating provider maps. A non-mapping declaration, non-string key, or
collision with core or another app's declared key raises `ImproperlyConfigured`; app ordering does not permit
default collisions. Values retain the established `str | None` contract and E361 validation.

The precedence is core defaults + installed-app defaults < theme registrations < `CRUD_VIEWS_BUTTON_CLASSES`.
Themes use the existing `register_button_classes()`; later registrations override earlier ones. A theme
registering workflow keys checks `apps.is_installed("crud_views_workflow")` inside `AppConfig.ready`, after app
discovery, retaining non-workflow registrations when workflow is absent. Project workflow settings assume it
is installed. Present `None`/empty values stop fallback; complete string whitespace remains literal.

Before apps are ready, lookups use core defaults without retaining a partial effective snapshot. Once ready,
default and resolved caches are bound to the active app-config map identity: replacement/restoration, including
direct registry operations and lookups before setting signals, invalidate both. Warm lookups do not enumerate
apps again. `reset_button_classes_cache()` clears both snapshots; in-place mutation of static declarations is
not a supported configuration lifecycle. Setting and theme registration cache resets remain established paths.

## Key grammar and existing diagnostics

When workflow is installed, `workflow:badge-<colour>` accepts exactly one nonempty colour segment containing
neither whitespace nor colon. Custom colours such as `workflow:badge-purple` need not appear in the default
mapping. No badge, wrapper or table key accepts a label-mode suffix. `workflow:badge-`,
`workflow:badge-pur ple` and `workflow:badge-purple:icon` warn. When workflow is absent, workflow keys supplied
by theme/settings warn, including standard defaults and custom colours.

`crud_views.W362` applies to those unknown keys and preserves its existing heading-location/action-mode
exceptions and specific invalid-mode warning. `crud_views.E361` applies to non-string, non-None values,
independently of W362. No new check IDs, colour formatter, template evaluation or helper API were introduced.

## Model API and additive badge context

`BadgeEnum`, `STATE_BADGES`, `STATE_BADGE_DEFAULT`, `get_state_badge(state)`, `state_badge`, and history consumption
through `workflow_data` retain their APIs. An unmapped state first chooses `STATE_BADGE_DEFAULT` (INFO by
default); a chosen colour with no registry entry instead keeps its own Bootstrap construction, for example
`badge rounded-pill text-bg-purple`. These are separate fallback decisions.

| Context name | Meaning |
|---|---|
| `state` | Existing raw state value |
| `name` | Existing display label |
| `class` | Existing selected colour, not the new complete classes |
| `badge_class` | Additive complete resolved classes; `None` is the missing-entry sentinel; `""` is normalized disabled output |

The retained leaf is `crud_views_workflow/badge.html`. It falls back to original Bootstrap construction only
for missing/sentinel `badge_class`, including direct rendering with old context. A present `None` or empty
registry value becomes `badge_class=""`, preserving visible escaped text without classes. Invalid values also
normalize to empty at render time and remain diagnosed by E361. Strings, labels and class attributes are
escaped and never evaluated as templates. Current and historical badges use the same request-free renderer.
Copied legacy badge leaves still receive old context and render their chosen markup; removing a redundant
copy enables registry rendering, while a retained copy must explicitly consume the additive field.

## Template composition and ownership

| Retained path | Contract |
|---|---|
| `crud_views/snippets/form_frame.html` | Existing `cv_form_frame` surrounds `cv_form_body`; stock is undecorated; theme owns modal decoration |
| `crud_views_workflow/view_workflow.action.html` | Now extends the shared frame, filling `cv_form_body` around the entire choices/empty branch |
| `crud_views_workflow/view_workflow.history.html` | History heading then a direct div/table wrapper; whole section omitted for empty `object.workflow_data` |
| `crud_views_workflow/view_workflow.content.html` | Includes history before action, keeping history outside the action frame |
| `crud_views_workflow/view_workflow.html` | Retains full-page routing and host extension |
| `crud_views/view_custom_form.content.html` | Retains supported workflow modal routing and its generic form, including no-choice cases |

With `has_workflow_choices`, both the existing level-5 “Workflow Action” heading and the page-owned `cv-form`
live inside the frame. The form retains method POST, implicit current-page target, `novalidate`, one CSRF input,
`form.non_form_errors` and `cv_render_form`. With no choices, only the existing translated no-transitions message
is framed: no action heading, form, CSRF input or controls. Copied action templates must adopt the inheritance
and body block to participate. Modal adapters must not substitute the full-page workflow branch.

History's `workflow:history-wrapper` class is on the div directly wrapping only the semantic table, whose class
comes independently from `workflow:history-table`. The heading is outside the scroll region; horizontal
scrolling belongs immediately below the table. Existing columns, heading level, history querying and full-width
table behavior remain. `None`/empty classes omit styling without removing either structural element. No broad
container overflow rule, fixed height, fixed row width or additional data query is introduced.
