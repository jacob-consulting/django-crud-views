## 06.12-01

### Summary
The plan composes the existing registry and renderer correctly: membership-before-normalisation, retained `state/name/class` context with an additive `badge_class`, and an installed-app default layer below theme and settings. The lifecycle design is sound against the Django registry code, but it carries more mechanism than the maintainability rule asks for, and its collision handling chooses an exception where the codebase convention is a system-check message.

### Strengths
- **Correct fallback distinction.** `get_button_class()` cannot tell absent from disabled (`button_classes.py:169-170`); the plan tests `key in get_button_classes()` first, which the merged dict preserves (`:154`). D-02/D-03 are achievable exactly as described.
- **One renderer, both badges.** History rows call `get_state_badge()` for old and new states (`mixins.py:75-76`); no second resolver is needed, and the plan does not add one.
- **Legacy copied leaves survive.** Keeping `class` as the colour and testing `badge_class is None` in the leaf lets a copied `badge bg-{{ class }}-lt` leaf keep working. In `{% if %}` an unresolvable variable evaluates to `None`, so direct legacy rendering with only the three original keys falls into the stock branch as claimed.
- **Identity-keyed invalidation is grounded.** `set_installed_apps`/`unset_installed_apps` swap the `app_configs` object, which is exactly what the snapshot keys on.
- **Inventory tests named precisely.** The plan correctly identifies `test_button_classes_checks.py:260` and `test_button_classes_templates.py:57` as the two assertions that conflate core and effective defaults.

### Concerns
- **MEDIUM — Collision rejection raises from a render path.** The plan rejects a duplicate core/app key with `ImproperlyConfigured` inside `_get_default_button_classes()`. That getter feeds `get_button_classes()`, which is called by the `cv_button_class` template tag (`templatetags/crud_views.py:664-667`) and by `button_class_check_messages()` (`button_classes.py:291`). A collision would therefore appear as a 500 on first render, or as an uncaught traceback in `manage.py check`, instead of an `E36x` message like every other table defect (`E360`–`E365`, `:285-329`). Prefer a deterministic merge (core wins, then first app) plus a check Error.
- **MEDIUM — Redundant invalidation mechanisms.** The plan requires an identity-keyed snapshot *and* a new `setting_changed` handler for `INSTALLED_APPS` *and* a pre-ready guard. Since `override_settings(INSTALLED_APPS=...)` swaps the registry object before the signal fires (the research itself notes this), the signal handler adds nothing the identity check does not already catch. Under the CLAUDE.md maintainability rule, one mechanism with one test is preferable.
- **MEDIUM — Theme coupling introduced by active-only W362 grammar.** Accepting `workflow:badge-<colour>` only while workflow is installed forces every theme to make its registration conditional on `apps.is_installed("crud_views_workflow")` (Plan 03 does this). That is a new obligation on all downstream themes, and Plan 04's recipe text does not currently promise to document it.
- **LOW — Registry isolation in `tests/test1/test_workflow.py`.** The tracer registers theme classes, but that file has no `_isolate_registry` fixture; only the button-class test modules do (`test_button_classes.py:98-105`, `test_button_classes_checks.py:12-19`). Without a snapshot/restore fixture, theme registrations leak into later tests in the same xdist worker.
- **LOW — `test_every_literal_slot_in_templates_is_a_default_key` changes only become observable in Plan 02.** Plan 01 lists the file, but the new literals land in Plan 02's history template. The union assertion written in Plan 01 is forward-looking; make sure it unions the AppConfig mapping, not a hard-coded list.

### Suggestions
- Replace the `ImproperlyConfigured` collision path with a deterministic merge and a new check id reported next to E361.
- Drop the `INSTALLED_APPS` `setting_changed` branch; keep identity keying and the "no pre-ready retention" rule, and test both explicitly.
- Add the registry snapshot fixture to `test_workflow.py` for the new badge tests.
- State in the plan that the leaf condition is `{% if badge_class is None %}` so missing-context and present-empty are visibly distinct.

### Risk Assessment
**MEDIUM.** Behavioural design is correct against source; the risk is over-building the lifecycle seam and surfacing a configuration error through the wrong channel.
