## 06.13-01

### Summary

Plan 01 is a well-grounded test plan. Its seven cases map one-to-one onto D-01 through D-12, every state-changing path it describes exists in source at the lines the plan cites, and the tracer-first ordering (one real permitted POST from URL to history before any negative case) is the right shape for a documentation-and-tests phase. The isolated `WorkflowRequest` model avoids touching Campaign. The one factual slip is a claim about how the custom permission must be granted, which does not break the plan but makes it slightly more complicated than necessary.

### Strengths

- **Same-source forgery is correctly distinguished from wrong-state forgery.** The existing test at `tests/test1/test_workflow.py:581-594` posts `wf_done` from `NEW`, which the plan correctly identifies as insufficient for D-09. Two transitions from `NEW` with different `permission=` rules is the only way to prove permission filtering, and `Transition.has_perm` (above) shows the mechanism will behave as the plan assumes.
- **The execution-recheck test is genuinely independent of choice validation.** Since `workflow_has_transition` has exactly one caller (`views.py:98`), a spy returning False proves `cv_form_valid` was reached by a choice that passed `ChoiceField` validation. The plan's demand to bind the real form first and to record `(self.pk, user.pk, transition)` is exactly the right evidence.
- **The optional-hook test checks the server gate, not only the DOM.** `base.py:1077-1087` makes `cv_action_enabled` a request gate; the plan tests direct GET and POST for 403 plus the disabled sibling control, and the positive permitted path. `tests/test1/test_action_enabled.py:46-57` is a proven analog of the same monkeypatch-plus-403 pattern.
- **Rejection evidence is scoped correctly.** Using `get_workflow_info_queryset()` (pk plus content type) instead of global counts prevents false passes from unrelated history rows under xdist.
- **Isolation is cheap and reversible.** Monkeypatching only `WorkflowRequestWorkflowView.cv_action_enabled` and `cv_inaccessible_actions` mirrors `tests/test1/test_inaccessible_actions_context.py:59-65` and leaves Campaign and production untouched.

### Concerns

- **LOW (factual inaccuracy): the custom permission does not need a content-type-scoped lookup.** Task 01-01 says to use "content-type-scoped Permission lookup for the custom grant" because the plan assumes `viewset.permissions` only maps default actions. `src/crud_views/lib/viewset/__init__.py:461-467` iterates every `Permission` for the model's content type and strips the `_<model>` suffix, so `process_workflowrequest` lands in the map as key `"process"`. The existing helper `tests/lib/helper/user.py:1-8` therefore works unchanged: `user_viewset_permission(user, cv_workflowrequest, "process")`. The planned approach still works, it is just more code than needed and contradicts the plan's own "no new helper" stance.
- **LOW (ambiguous instruction): "use existing generic views without a new table/helper abstraction" may send the executor to a plain `ListViewPermissionRequired`.** That is valid (`src/crud_views/lib/views/list.py:58-59`, `GenreListView` at `tests/test1/app/views.py:472` is a precedent, and `view_list.content.html` renders a bare table). But the plan also says "make home/success/cancel destinations resolve to those registered views", and following the 302 to a plain list page is fine. The ambiguity is whether a Campaign-style `Table` subclass counts as a forbidden "table abstraction". Say explicitly that either the plain list view or a three-column `Table` like `CampaignTable` (`views.py:601-604`) is acceptable.
- **LOW: `cv_list_actions` default includes unregistered keys.** `ListView.cv_list_actions = crud_views_settings.list_actions` defaults to `["detail","update","delete"]` (`src/crud_views/lib/settings.py:86`). Unregistered keys are skipped at render time via `ViewSetKeyFoundError` (`base.py:674-680`), so this is harmless, and the plan already says to set actions explicitly. No change needed; noted so the executor does not treat the skip as a bug.
- **LOW: D-03's object/parent layer has no test.** The plan explicitly scopes this out ("this isolated root-model recipe does not claim a Guardian or nested-policy test matrix") and D-03 only asks that the layers be explained. Acceptable, but WFP-01's wording ("cannot bypass page or applicable object/parent access checks") is broader than what will be proven. Plan 02's docs must carry that boundary honestly.
- **LOW: `test_page_permission` for POST.** For a step-only actor, POST hits `has_permission` before `post()`, so no form is built and the 403 comes from `PermissionRequiredMixin.handle_no_permission`. That matches `tests/test1/test_workflow.py:706-717`. Fine; just be aware the "transition rule permits them" precondition must be asserted by calling `obj.workflow_has_transition(user, "wf_process")` directly, which the plan does say.

### Suggestions

- Replace the content-type lookup instruction with `user_viewset_permission(user, cv_workflowrequest, "process")`, and add one assertion that `cv_workflowrequest.permissions["process"] == "app.process_workflowrequest"` so the suffix-stripping contract is pinned.
- State that the list sibling may reuse the Campaign `Table` pattern; it is three lines and avoids the executor second-guessing the plain list template.
- In `test_execution_recheck`, also assert `WorkflowInfo` count on the scoped queryset is unchanged **and** that `obj.state == NEW` after refetch; the plan says "compare state/history" which covers it, but naming both avoids a count-only check.
- For `test_optional_hook_denies_empty`, select the control with `'[cv-context-container] [cv-key="workflow"]'` exactly as `test_inaccessible_actions_context.py:47` does; the base template `tests/test1/app/templates/app/crud_views.html:24` renders that toolbar on every page, including a core `DetailViewPermissionRequired`.

### Risk Assessment

**LOW.** No production code changes, all mechanisms verified in source, and the verification commands reference executables that exist. The only correction is cosmetic.
