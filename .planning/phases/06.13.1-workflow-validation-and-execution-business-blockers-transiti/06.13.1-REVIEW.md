## Narrative Findings (AI reviewer)

### Summary

Three independently reproduced blockers remain: metadata lookup ignores the selected FSM source state, the
public helper leaks the view's private refusal marker across execution boundaries, and late refusal recovery
breaks the shipped Guardian object-permission mixin. These affect required-comment enforcement, truthful
post-commit responses and authorized invalid-form recovery respectively.

Review followed the public lazy export through the execution engine, WorkflowForm, WorkflowView, generic form
processing, crispy helper/widget rendering, Django transaction callbacks and Guardian object loading. The
installed django-fsm implementation was inspected to verify stacked-decorator selection. The explicit same-alias
support policy, unsupported replica inputs, custom-renderer boundaries and documented concurrency limits were
respected; none is reported as a defect. No structural pre-pass or external reviewer evidence was supplied.

### Critical Issues

#### CR-01: Source-independent metadata lookup bypasses required comments

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/execution.py:75-80`
**Related file:** `/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/forms.py:118-132`

**Issue:** A method can have stacked Django FSM transitions for different source states, each with its own
`custom` metadata. Availability and existing form choices correctly select the transition for the current
state. Execution instead takes the **first** matching method from `get_all_state_transitions()`, including
entries for other states. Consequently a current REQUIRED action can execute through `run_transition` with
no comment when an earlier source uses NONE. Reversing the policies makes a valid OPTIONAL form submission fail
with an unexpected required-comment error. The new button help lookup has the same source-selection defect:
its dictionary takes the **last** entry by name and can display another state's help beside the current label.

**Reproduction:** In the existing in-memory Campaign fixture, add a second decorator to `wf_activate`:

```python
transition(
    field=Campaign._meta.get_field("state"),
    source=CampaignState.ACTIVE,
    target=CampaignState.SUCCESS,
    custom={"label": "Complete", "comment": WorkflowComment.REQUIRED,
            "help_text": "ACTIVE guidance"},
)(Campaign.wf_activate)
obj = Campaign.objects.create(name="stacked", state=CampaignState.ACTIVE)
print(obj.workflow_get_form_kwargs(actor)["transition_comments"]["wf_activate"])
info = run_transition(obj, "wf_activate", user=actor, comment=None)
print(info.state_old, info.state_new, info.comment, WorkflowInfo.objects.count())
```

Observed: the offered policy is REQUIRED, but execution returns `active success None 1`. Both actors and
objects were saved on `default`; no unsupported routing or stale-object scenario is involved. A second run
with NEW=REQUIRED and ACTIVE=OPTIONAL returned HTTP 200 with `comment: Comment is required for this transition`
for an empty-comment ACTIVE POST. A NEW button rendered `ACTIVE guidance` rather than its own `NEW guidance`.

**Fix:** Obtain comment/help metadata from the transition selected for the current source state, preserving
Django FSM's exact-source/wildcard selection and the existing availability-before-business ordering. For
example, use the current available-transition iterator when selecting metadata, rather than the all-state
iterator; keep the existing execution permission recheck. Add stacked-decorator regressions for helper and
POST with both policy orderings, plus current-state help rendering. No new public API or routing abstraction
is needed.

#### CR-02: Nested public helper refusals are mistaken for the primary view's own validation

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/execution.py:43-51`
**Related files:** `/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/views.py:92-105`,
`/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/views.py:123-128`

**Issue:** `run_transition()` exposes `_WorkflowRefusal` unchanged. Although this satisfies `isinstance(error,
ValidationError)`, that private type also controls the primary view's recovery. When application execution or
`on_transition` calls the public helper for another object and it is blocked, the primary view catches that
nested failure and reports it as its own transition/comment field error. This violates the documented
exception-origin boundary. If that helper call occurs in `cv_on_commit`, Django invokes the callback after
the primary transaction commits but before `cv_form_valid_process` returns (without an enclosing request
transaction). The same catch then renders an invalid form despite already committed primary state/history.

**Reproduction:** With two saved Campaign objects and a saved superuser on `default`, make the business hook
raise `ValidationError("Dependent blocked")` only for the second object. Set these callbacks in separate runs:

```python
# First run: an ordinary database follow-up.
CampaignWorkflowView.on_transition = lambda view, info, *args: run_transition(
    dependent, "wf_activate", user=actor
)

# Second run: reset on_transition to no-op and use the commit callback.
CampaignWorkflowView.on_transition = lambda *args: None
CampaignWorkflowView.cv_on_commit = lambda view, context: run_transition(
    dependent, "wf_activate", user=actor
)
```

POST `transition=wf_activate&comment=` for the primary through the real Django client. Observed results:

```text
ON_TRANSITION 200 {'transition': ['Dependent blocked']} history 0
ON_COMMIT     200 {'transition': ['Dependent blocked']} history 1 persisted state active
```

The first failure should propagate after rollback; the second must propagate as a post-commit failure,
not enter the primary refusal redisplay path or imply its write was refused.

**Fix:** Keep the private marker private at the public helper boundary. A bounded option is to catch
`_WorkflowRefusal` in `run_transition` and raise a plain `ValidationError(refusal)` from it, preserving the
sanitized error leaves, codes, order and cause. The view's direct private-engine path can retain the marker
for its own checks. Add regressions for nested helper refusals from a transition/`on_transition` and from
`cv_on_commit`, asserting propagation and the correct rolled-back versus already-committed state. Do not
broaden the view's catch to general `ValidationError`.

#### CR-03: Late refusal recovery crashes with Guardian object permission composition

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views_workflow/lib/views.py:99`
**Related file:** `/home/alex/projects/alex/django-crud-views/src/crud_views_guardian/lib/mixins.py:74-82`

**Issue:** Recovery now calls the polymorphic `self.get_object(queryset=...)` method. The package's
`GuardianObjectPermissionMixin.get_object()` accepts only `self`, so a workflow using that object-permission
mixin raises `TypeError` after an expected late refusal. Initial authorization/loading and form validation
succeed; the failure appears only when the new recovery path reloads. This prevents the promised bound
200/422 response and loses the user's normal recovery flow.

**Reproduction:** Dispatch a saved superuser's valid POST through this ordinary mixin composition, with
`cv_viewset` assigned to the existing Campaign ViewSet after defining the test class:

```python
class GuardianWorkflow(GuardianObjectPermissionMixin, CampaignWorkflowView):
    def cv_form_valid(self, context):
        executing[0] = True
        return super().cv_form_valid(context)

GuardianWorkflow.cv_viewset = cv_campaign
```

The business hook returns during form validation and raises `ValidationError("Late business blocker")`
when `executing[0]` is true. A real `RequestFactory`/`as_view()` dispatch produced:

```text
TypeError GuardianObjectPermissionMixin.get_object() got an unexpected keyword argument 'queryset'
history 0 state new
```

**Fix:** Make the Guardian override follow Django's cooperative signature,
`get_object(self, queryset=None)`, and forward `queryset=queryset` to `super().get_object()` before applying
its existing object-permission and action-enabled checks. Retain the pinned alias and scoped queryset in
workflow recovery; do not bypass the Guardian loader with an unrestricted manager. Cover late page/modal
refusals on this composition and verify that reload still enforces object permission.
