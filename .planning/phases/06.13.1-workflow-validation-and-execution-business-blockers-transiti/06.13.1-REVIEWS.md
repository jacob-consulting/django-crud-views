## 06.13.1-01

**Summary.** The plan extracts the write sequence that genuinely lives in one place today (`src/crud_views_workflow/lib/views.py:85-135`), adds the locked hook/helper, and recovers late refusals with the same catch-after-unwind shape DeleteView already uses. The seams it names exist and behave as described. Two things are under-specified: which database alias the view pins, and how the form behaves when it has no owning view.

**Strengths.**
- The "do not call `workflow_has_transition` from form validation" rule is necessary, not stylistic. `tests/test1/test_workflow_permissions.py:246-253` asserts exactly one call `[(obj.pk, actor.pk, "wf_process")]` and HTTP 400. Any extra call during `clean()` breaks a locked WFP-03 regression.
- The "return after add_error still redirects" pitfall is real: `src/crud_views/lib/views/mixins.py:44-46` redirects unconditionally once `cv_form_valid_process` returns, and `on_commit` is registered at line 60 only after `cv_form_valid_hook`. A raised private marker is the only way to skip both without touching the core mixin.
- The recovery precedent is exact. `src/crud_views/lib/views/delete.py:357-362` catches `_NativeDeleteBlocked` (defined at `src/crud_views/lib/deletion.py:251`) around `cv_form_valid_process`, outside all atomics. `MessageMixin.cv_form_valid_hook` (`mixins.py:140-144`) runs after `cv_form_valid`, so a refusal raised inside `cv_form_valid` queues no success message.
- Lazy export mechanism is in place (`src/crud_views_workflow/lib/__init__.py:24-41`), and `tests/test1/test_import_safety.py:143-165` already shows the subprocess pattern to extend.
- Protected-FSM reload concern is confirmed: `django_fsm/__init__.py:329-331` rejects assignment when the attribute already exists, so `refresh_from_db()` on a protected field raises. A fresh fetch is the right recovery.

**Concerns.**
- **MEDIUM — alias pinning policy is unspecified and diverges from the delete precedent.** `CrudView.cv_get_db_alias` (`src/crud_views/lib/view/base.py:278-280`) routes on the model with no instance hint, whereas `DeleteView.cv_get_db_alias` (`delete.py:147-148`) passes `instance=self.object`. Django's router returns `instance._state.db` only when the hint is given (`django/db/utils.py:230-231`). A consumer whose `get_queryset()` uses `.using("shard")` without routers today gets a silent split (object saved to shard via `self.object.save()`, history to default). Plan 02's "object alias mismatch rejects" would turn that into `ImproperlyConfigured`. Plan 01 must decide the pin source; the instance-hinted delete precedent is the better default because the pin then agrees with the loaded object.
- **MEDIUM — form business check with no owning view.** `CrispyFormMixin.__init__` (`src/crud_views/lib/crispy/form.py:40-42`) accepts `cv_view=None`, and `get_cancel_button` (`form.py:93-96`) already handles that case. The plan's `clean()` reads `cv_view.object` and `cv_view.request.user`. "Document as unsupported" is not enough; a bare form must still validate choices/comments without an AttributeError. No acceptance criterion covers it.
- **LOW — `add_error` removes the field from `cleaned_data`.** Capture `transition` before adding business errors (the current code already does this at `forms.py:64`), and still run the required-comment check so both errors coexist per D-08.
- **LOW — estimate.** 35k tokens for three TDD tasks across five source files plus a new test module, with a new `post()` override and alias pinning, is optimistic; confidence is correctly marked low.

**Suggestions.**
- State explicitly that `WorkflowView.cv_get_db_alias()` pins `router.db_for_write(type(self.object), instance=self.object)` once per request, mirroring `delete.py:147-156`.
- Add a `TestWorkflowTracer` case constructing `WorkflowForm(cv_view=None, ...)` to prove choice/comment validation still works and the hook is skipped.
- Have `clean()` call the same private check helper the engine uses and translate `_WorkflowRefusal` into `add_error(refusal.field, refusal)`, so there is one check implementation.

**Risk Assessment.** MEDIUM. The design matches the code; the alias decision must be made here because plan 02 builds rejection logic on it.

## 06.13.1-02

**Summary.** The plan addresses a real gap: the current block opens `atomic(using=alias)` but saves and creates history through unbound managers (`views.py:105-129`), and the only "routed" test observes the default alias (`tests/test1/test_transactions.py:706`). The binding mechanics it proposes are correct Django. The "detect explicit split routing" ambition is where it risks hidden coupling.

**Strengths.**
- `ContentType.objects.db_manager(alias).get_for_model()` is correct: the manager cache is keyed by `self.db` (`django/contrib/contenttypes/models.py:20,33`), so content-type IDs cannot leak across aliases.
- The actor pre-check preempts a confusing failure: Django's forward FK assignment calls `router.allow_relation` (`django/db/models/fields/related_descriptors.py:300-313`) and raises a generic `ValueError` on cross-database objects.

**Concerns.**
- **MEDIUM — "explicit split" detection has no clean API.** `ConnectionRouter._route_db` returns `DEFAULT_DB_ALIAS` both when no router has an opinion and when one explicitly chooses default (`django/db/utils.py:217-233`). Distinguishing them means iterating `router.routers` yourself. That is the kind of hidden coupling CLAUDE.md's maintainability rule warns against, for a case no consumer has reported. The simpler bounded policy is: all participating writes use the selected alias, period; document that history lives with the object's database.
- **MEDIUM — spy target drift.** `test_transactions.py:701` patches `crud_views_workflow.lib.views.transaction.atomic`. If `views.py` stops importing `transaction`, the monkeypatch path raises `AttributeError`; if the engine uses `from django.db.transaction import atomic`, the spy misses it. Specify `from django.db import transaction` plus `transaction.atomic(...)` in the engine and retarget the spy to the engine module.
- **LOW — readback alignment.** `get_workflow_info_queryset` (`src/crud_views_workflow/lib/mixins.py:62-72`) should use `self._state.db`, which is `None` for unsaved instances; guard it.
- **LOW — multi-database marker.** New shard tests need `django_db(databases=[...])` on both aliases; the plan implies but does not state it.

**Suggestions.**
- Drop explicit-split detection from scope. Keep the saved-object and actor-alias checks, which are cheap and have a concrete failure mode.
- Name the exact spy retarget in 02-02's action text.

**Risk Assessment.** MEDIUM. Correct mechanics; trim the routing-detection ambition to stay within D-17.

Execution-time recovery is specified; the form path is not.
