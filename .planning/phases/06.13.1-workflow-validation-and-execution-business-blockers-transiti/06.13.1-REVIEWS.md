## 06.13.1-02

**Summary.** The plan drops router introspection, binds every workflow write and the history readback to one selected alias, uses scalar FK ids for the history row, and tests real shard rows. That is the right bounded contract for D-14 to D-17. The one predicate it adds on top, "loaded database must equal the selected alias" for both object and actor, is stricter than the project's own delete contract and breaks the most common Django multi-database layout.

**Strengths.**
- R6 disposition is sound and verifiable: `ContentType.objects.db_manager(alias).get_for_model()` and `WorkflowInfo.objects.using(alias).create()` make the aggregate router's opinion irrelevant for those rows. No `router.routers` iteration is needed.
- Passing `user_id=user.pk` and `workflow_object_content_type_id=content_type.pk` is correct for the stated reason: forward FK assignment on an unsaved instance consults `router.allow_relation`, whose fallback compares `_state.db` of both instances (`django/db/utils.py:240-251`). Scalar ids bypass that check entirely.
- The current gap is real: `views.py:105-128` opens `atomic(using=self.cv_get_db_alias())` but saves and creates history through unbound managers, and `mixins.py:69-72` reads history through the default manager.
- The existing routed test only observes the default alias (`test_transactions.py:706`); the plan correctly refuses spy-only evidence.

**Concerns.**
- **HIGH, R19 (new, arises from the R4/R6 resolution):** 02-01 says "Require saved object and actor with matching loaded database and reject mismatches using ImproperlyConfigured" and 01-01 says the same. Trace against Django:
  - A primary/replica router returns the replica from `db_for_read` and the primary from `db_for_write`. The workflow object is loaded through `get_queryset()` and the actor through `UserModel._default_manager.get(pk=...)` (`django/contrib/auth/backends.py:232`), so both carry `_state.db == "replica"`.
  - `router.db_for_write(type(obj), instance=obj)` returns the router's choice, "primary", before ever looking at `instance._state.db` (`django/db/utils.py:218-233`; the instance fallback applies only when no router answers).
  - The plan's predicate then sees `"replica" != "primary"` and raises `ImproperlyConfigured` on every view POST and every `run_transition()` call. Today this configuration works, because `self.object.save()` and `WorkflowInfo.objects.create()` both route writes to the primary.
  - This contradicts the shipped delete contract: `cv_get_delete_db_alias` (`delete.py:150-161`) requires only a saved target and a configured alias string, and `docs/reference/request_lifecycle.md:140` states "Explicit selection can target the same model/PK on a different alias from the loaded instance."
  - The planned matrix cannot observe this: the `database_routes` fixture defines `db_for_write` as `db_for_read` (`tests/test1/conftest.py:147-157`), so read and write aliases never differ in any planned case.
  This violates D-17 ("preserve proven paths") and D-15 ("existing transaction semantics must not weaken"), and the changelog classification in 05-02 ("loaded-identity mismatch rejection") would publish the regression as intentional.
- **MEDIUM (part of R19):** the hazard the equality check was meant to prevent is real but has a cheaper, precedent-aligned guard. `Model.save(using=alias)` on an alias lacking the row silently falls through from UPDATE to INSERT (`django/db/models/base.py:1126-1145`), which would create a colliding row. `save(using=alias, force_update=True)` raises `DatabaseError("Forced update did not affect any rows.")` at `:1141-1142`, or one `exists()` query on the selected alias gives a friendly diagnostic before dispatch.
- **LOW:** "Distinct actors sharing a PK across databases" cannot be distinguished from replica copies by any code; the plan should state this as the D-16 documented limit rather than a detected condition.

**Suggestions.**
- Adopt the delete predicate verbatim: saved object (`pk` set, not `_state.adding`), saved actor, selected alias is a configured string; do not compare `_state.db`.
- Bind all writes explicitly as planned; guard the object write with `force_update=True` or an existence check on the selected alias, and check actor existence on that alias with one query if a friendly `ImproperlyConfigured` is wanted.
- Replace the "unaligned override fails" case with "row missing on the selected alias fails before dispatch", and add one read-replica case: router reads from `shard` (a copy with the same PKs), writes to `default`; the POST and the helper must succeed and write to `default`.
- Keep the actor/content-type identity assertions, but assert them against the selected alias's rows.

**Risk.** HIGH until R19 is resolved; MEDIUM afterwards.

Fable's HIGH nevertheless remains counted because it is a source-cited judgment-class concern: the consensus gate does not require corroboration or permit a majority vote to suppress it.
