## Form Ownership, Accessibility and Theme Contract

Reuse the shared cv_form_frame/cv_form_body and cv_render_form boundaries. The normal workflow action owns its
single POST form and token; the modal retains its generic owner/action/enctype conventions. Keep all controls
inside or explicitly associated with the correct owner. Count forms/tokens within that owner, excluding sibling
language/action forms. Do not nest a widget form or duplicate CSRF tokens.

Normal invalid POST returns the existing 200 response; modal invalid POST returns the existing 422 response.
No-transitions GET retains its existing normal/modal branch and optional request-level denial behavior. An empty
modal must not gain an implicit executable transition. Do not pull page history into the modal.

In button mode, give the transition group its existing field label through native group semantics or a correct
accessible association. General guidance precedes the action group. Each action has an accessible name that
includes its full caption; required actions also expose Comment required without relying on the asterisk.
Use the existing hidden-text utility for the nonvisual equivalent; hide a purely decorative asterisk from AT.
Keep the conditional visible legend outside individual captions so it is not repeated for every action.

Associate each action with its own help, blocker messages and applicable transition field errors using
aria-describedby. Every referenced ID must exist exactly once in the document, including simultaneously rendered
page/modal instances and multiple forms. IDs derive from an owning instance/prefix plus a stable safe action suffix;
do not derive IDs from translated labels. Preserve existing describedby tokens when adding new ones.
Do not assume the default unprefixed Django field ID alone is unique across repeated forms.

Render blocker messages as an ordered sequence of semantic list items. The visual treatment may use existing
list styling; list position and DOM order preserve the hook's order. Do not truncate, merge, deduplicate or
replace reasons with hover-only content. A disabled button is skipped by normal Tab navigation, so its nearby
readable reasons must remain discoverable as document text without focusing that button. No synthetic tabindex
or new live-region protocol is required. All-enabled buttons remain natively keyboard operable with visible focus.

After invalid POST, expose transition and comment field errors through the ordinary renderer and proper field
associations. An expected late refusal rebuilds current button states and descriptions from persisted object data;
the original bound data/errors remain visible. Do not show stale state badges/history or a success alert.

Escape labels, help, blockers and submitted comments; do not evaluate user text as templates or adopt mark_safe
for the new presentation. Exercise HTML-looking strings in each of these surfaces. Library-added copy is translated.
No workflow-specific JavaScript, tooltip plugin, asynchronous validator or optimistic state change is required.

Keep radio custom constructors, fields, clean() inheritance, layout customization and submit_label overrides.
In supported button custom forms preserve legitimate extra fields and Cancel while suppressing only the default
generic workflow submit. Never clear an entire custom helper/layout to obtain button rendering. A fully replaced
custom renderer that bypasses the selected transition widget must explicitly adopt the documented seam; document
this boundary instead of promising arbitrary rewritten markup compatibility.

Implementation recommendation: a workflow ChoiceField widget/layout seam shared by page and modal is smaller
than a page-only alternate form. Keep existing constructor kwargs and use the established owner context.
Private widget/context/class-key names remain planner choices; document any new public theme seam explicitly.

## Acceptance Contract

Verify the complete normal-page flow in a real browser with JavaScript disabled, using at least two available
actions so that incorrect default dispatch is observable. Submit each chosen name, test missing/whitespace-required
comments, initial/POST/late blockers, retained bound values, then an allowed success with corresponding server history.
Exercise navigation Cancel according to its existing native-link eligibility. Modal acceptance uses the established
JavaScript modal lifecycle separately; no-JS modal support is not promised.

Use normal and narrow stock layouts, including 375px and 1440px viewport widths, with many actions, multiple
blockers, long translated sentences and a long unbroken token. New workflow content must wrap without clipping
labels/reasons or creating horizontal overflow; use a bounded local wrapping rule if existing classes cannot do so.
Long content uses ordinary page/modal scrolling, not a new inner scroll region. This is a phase-local acceptance
default, not a universal restyling requirement for inherited chrome or every third-party theme.

Inspect page/modal DOM for owner/token counts, no competing transition inputs, all-none wrapper absence,
conditional legend, full ordered reasons, unique IDs and resolvable describedby relationships. Repeat with
prefixed forms and simultaneous form instances to expose ID collisions. Test native keyboard focus and activation,
including disabled reasons read as ordinary content. Automated accessibility attributes do not establish human
screen-reader or translated-copy acceptance; report the actual checks and limits.

Extend existing workflow/theme request tests for custom constructor/clean/layout forms and radio compatibility.
Preserve WFP-01–WFP-05: page change default, opt-in transition permissions, basic no-step GET, optional denied
request and execution recheck. Verify unexpected exceptions remain errors and expected refusal has no success
redirect/message/history/state/commit callback. Backend rollback and helper parity belong in the backend plans.
No new browser fixture or implementation test has run as part of this specification.
