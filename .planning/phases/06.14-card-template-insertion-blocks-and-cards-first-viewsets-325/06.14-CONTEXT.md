<decisions>
## Implementation Decisions

### Card template extension points

- **D-01:** Add empty `card_root` and `card_header` blocks to `crud_views/tags/card.html`.
  `card_root` is the first child of the card root, before the body. `card_header` is inside the body,
  before the heading; its content must not become part of the heading.
- **D-02:** Preserve `card_title`, `card_content`, `card_actions`, and existing action rendering.
  Unused new blocks preserve existing rendering. Inherited inline/overflow actions and hidden POST forms
  must continue to render correctly without consumers repeating their plumbing.
- **D-03:** Document the placement of all five blocks and provide a small inheritance example that inserts
  content at the new extension points. Explain that replacement theme templates must expose the new blocks;
  upstream changes cannot update a shadowing template automatically.

### Cards-first recipe using existing configuration

- **D-04:** Publish a complete recipe in `docs/reference/card-list-view.md` with two list presentations
  on one ViewSet. The card view uses `cv_key = "list"`, `cv_path = ""`. The table view uses
  `cv_key = "table"`, `cv_path = "table"`, `cv_home_key = "list"`.
- **D-05:** Include the appropriate table mixin/table configuration and context actions for switching
  presentations. Explain action labels and `cv_icon_action` using existing icon support, without requiring
  a downstream theme. Demonstrate existing switching behavior; do not introduce new switching behavior.
- **D-06:** Explain and test home/breadcrumb targets, default successful-save redirects, and static Cancel
  fallback. Distinguish these from existing origin-aware Cancel, which may return to the originating table.
  Preserve navigation, permissions, and query-state behavior; successful redirects and Cancel remain independent.
- **D-07:** Explain the difference from the existing card-only `list` to `card` fallback. Preserve that fallback
  and conventional table-first configurations. The recipe does not change class defaults or registered keys/paths
  for applications that do not opt into this configuration.

### Acceptance and boundaries

- **D-08:** Focused integration tests must exercise both URLs, presentation switching, and the documented
  home/breadcrumb/default success/static Cancel targets. Verify the new template insertion positions,
  unchanged unused-block rendering, inherited actions/forms, and preserved existing navigation behavior.
- **D-09:** Keep the change additive and bounded. No routing redesign, `cv_default_list` API, new icon registry
  API, general card layout framework, or downstream theme implementation belongs in this phase.
- **D-10:** Apply developer maintainability as a hard constraint. Reuse established templates, ViewSet
  configuration, and focused regression patterns. Use multicore pytest for broader verification and report
  actual checks and limitations. Add the required public-surface changelog entry; any Breaking entry also
  requires a corresponding `docs/migrating-1.0.md` update under the project convention.

### Planner discretion

- **D-11:** Implementation details and test organization are explicitly delegated to the planner by the
  issue's GSD handoff. Example names/content, labels, icon/text presentation, snippet organization, fixture
  layout, and exact verification commands are implementation choices within the agreed acceptance criteria.
  No particular alternative from the assistant's initial discussion menu was selected by the user.
- **D-12:** Do not reopen approach selection. Ask only if code inspection exposes a concrete contradiction
  or a missing decision necessary to meet the acceptance criteria. Inspection so far has found no such blocker.

## Existing Code Insights

### Reusable Assets

- `src/crud_views/templates/crud_views/tags/card.html` currently provides the three existing blocks,
  resolves the action group, renders menu forms, and includes the shared action container.
- `tests/test1/test_card_blocks.py` already exercises template inheritance while retaining inline/overflow
  actions and hidden forms, comparing against stock rendering with masked CSRF values normalized.
- `tests/test1/test_card.py` and existing action/navigation tests provide nearby regression coverage.
- `examples/bootstrap5/card_view/views.py` demonstrates a card-only landing page; it is distinct from
  the new two-presentation recipe and need not be redesigned.

### Established Patterns

- `src/crud_views/lib/views/card.py` defaults to key/path `card`; `src/crud_views/lib/views/list.py`
  defaults to key `list` and an empty path. Both expose existing action labels and icons.
- `src/crud_views/lib/view/base.py` owns home/success/Cancel configuration and origin handling.
  Existing settings allow the recipe without a new default-list abstraction.
- Existing card documentation encourages inheritance so projects avoid copying action plumbing;
  replacement themes currently retain three block names and need guidance for all five.

### Integration Points

- Add the empty blocks in the existing card template and extend its focused inheritance tests.
- Add the complete recipe and regression fixtures using existing view/table/URL APIs.
- Hand the two new public block names to Phase 7's theme-surface inventory; keep downstream adaptation separate.
