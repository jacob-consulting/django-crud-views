### WR-01 (resolved): Inline template captions are invisible to normal message extraction

**Classification:** WARNING (resolved; excluded from current counts)

**Original file:** `/home/alex/projects/workspaces/cv-phase-06-14/django-crud-views/docs/reference/card-list-view.md:114-115`

**Original issue:** The complete recipe is intended to be copied into `views.py`, but its `Table` translation tags are
embedded inside Python string literals. Django's `makemessages` processes `.py` files as Python without
template preprocessing, so these tags do not create catalog entries. The example has no Python gettext
extraction markers for either caption. A developer following the normal extract/translate/compile workflow
therefore cannot discover the new `Table` message from this recipe, despite lines 147–148 describing translated
captions. `Cards` happens to work in German because the library already supplies that message; `Table` does not.
This is a localization/documentation gap, not a routing or permission defect.

**Original evidence:** A fresh Django 5.2 process compiled and executed the exact marked recipe. Rendering its short-label
template code under `translation.override("de")` produced `['Karten', 'Table']`. The package German catalog
contains `Cards` but no `Table` entry. A separate read-only probe of Django's installed `BuildFile` confirmed
`is_templatized == False` for `views.py`; the command passes these files to `xgettext --language=Python`.
AST inspection of the exact fence found no `_`, `gettext`, `gettext_lazy` or `gettext_noop` calls marking the
captions. GNU gettext is unavailable in this runtime, so a complete `makemessages` invocation was not run.

**Recommended fix:** Keep the existing runtime template tags, but add explicit extraction markers to the recipe and explain
that applications translate these entries in their own catalogs, for example:

```python
from django.utils.translation import gettext_noop

# Inline template code is not scanned as a template by makemessages.
gettext_noop("Cards")
gettext_noop("Table")
```

Alternatively, move the two label snippets into real application templates, which `makemessages` already scans.
The extraction-marker option preserves the recipe's single-fence structure and requires no new library API.

**Resolution:** Commit `3caf6bb6` adds the `gettext_noop` import and literal markers for both captions, and tells
consumers to translate those entries in their own catalogs. Independent re-review confirmed that Django's
installed `makemessages` recognizes `--keyword=gettext_noop`; a fresh probe verified the import and both exact
markers, successful compilation, and the markers' unchanged runtime return values. Removing only the new
import/marker statements from the parsed fence produces an AST identical to the pre-fix recipe, establishing
that view configuration and runtime template code remain unchanged. The new catalog guidance is present.
No full `makemessages` run is claimed because GNU gettext is unavailable. The parent separately reports
24 recipe cases and strict documentation build passing; broad suites were not repeated for this correction.
