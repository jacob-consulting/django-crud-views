<decisions>
## Implementation Decisions

### Default selector labels — settled in issue #326

- **D-01:** Use Django's `capfirst` on the model verbose name or equivalent content-type label. Capitalize
  the first character while preserving remaining casing, acronyms, and translation behavior.
- **D-02:** Preserve choice IDs, order, include/exclude filtering, custom form support, permissions, and
  redirect/cancel behavior. Reuse discovered models/content types; do not add a database lookup per label.

### Declarative model-to-groups configuration — settled in issue #326

- **D-03:** Accept both the existing group list and a model-class-to-group-list mapping in
  `cv_property_display`. Mapping values use the existing group-list format, including dict and
  `PropertyGroupConfig` forms. No separate public configuration object or duplicated parser/resolver.
- **D-04:** Select a mapping entry by exact `type(self.object)` after object resolution. Base and proxy
  instances need their own exact entry when served. Do not introduce superclass/MRO matching, default
  keys, fallback values, or automatic subtype discovery.
- **D-05:** An unmapped actual type raises a clear configuration error identifying the model and view.
  Never silently return an empty detail or another model's groups for a missing entry.
- **D-06:** After selection, reuse existing parsing, resolution, layout, and rendering. Keep selections
  request-local; do not mutate class configuration or cache one request's groups on the class.
- **D-07:** Existing list configuration and working `property_display` overrides continue to work.
  Preserve the property as an escape hatch for genuinely request/object-dependent groups. Mapping support
  addresses the demonstrated subtype use case; redesigning dynamic-hook validation is outside this phase.

### Startup checks and validation boundaries — settled in issue #326

- **D-08:** Accept both configuration forms. Validate mapping keys as Django model classes and inspect
  every declared value, including entries other than the first. Invalid keys and values must yield useful
  diagnostics instead of crashing the check runner.
- **D-09:** Reuse structural and icon checks. Mapped diagnostics identify the affected model and, where
  applicable, group/property location. Preserve missing-configuration detection, static-list checks,
  icon-prefix warnings, and inherited view checks.
- **D-10:** Checks inspect declared class configuration. They must not instantiate views/models, evaluate
  request/object-dependent properties, or query objects to select a configuration.
- **D-11:** Structural checks do not prove property-path resolution or coverage of all possible subtypes.
  Document that limit and verify representative real objects plus unmapped-type failures separately.
  Runtime parsing is not a substitute for checking every declared entry at startup.
- **D-12:** Keep mapping support in the object-detail configuration path. Ordinary Django model keys
  must not require the optional django-polymorphic package. Avoid extra queries on established paths.

### Required downstream adoption — settled in issue #326

- **D-13:** Remove only the label-rewriting workaround from `ProductContentTypeForm`. Retain the useful
  form subclass, `submit_label = "Continue"`, and `Row(Column4("polymorphic_ctype_id"))` layout.
- **D-14:** Set `ProductDetailView.cv_property_display = PROPERTY_DISPLAY`; remove the dummy Beans
  assignment and redundant `property_display` override. Keep application-owned groups, Commerce/About
  helpers, breadcrumbs, and existing supported view composition.
- **D-15:** Verify Beans, Equipment, and Subscription selector/detail behavior, shared groups,
  subtype-specific fields, stock visibility, typed forms, and permissions. Add regression coverage for
  selector labels and startup checks using the actual mapping.
- **D-16:** Update the downstream findings report for findings 10–11, linking #326 and recording the
  resolution only after implementation and verification. Preserve unrelated findings and pre-existing edits.
  Both repositories' changes and validation must be attributable; downstream delivery is mandatory.

### Documentation and completion — settled issue and project rules

- **D-17:** Document list and mapping forms, exact-type lookup, missing-entry errors, model-specific
  diagnostics, structural-validation limits, and the dynamic property escape hatch. Include a complete
  mapping recipe using `ObjectDetailMixin, PolymorphicDetailViewPermissionRequired` in that order.
  Use generic public examples consistent with project documentation hygiene; concrete downstream names
  here identify the explicitly authorized cross-repository work.
- **D-18:** Extend existing bounded paths under the developer-maintainability rule. Do not create a
  general configuration framework, change unrelated public behavior, or add dependencies for convenience.
  Add the required changelog entry; if classified under Breaking, also update `docs/migrating-1.0.md`.
- **D-19:** Completion requires upstream coverage and passing downstream catalog tests and warning-level
  system checks against the actual changed upstream checkout, plus docs/report updates. Use multicore
  pytest for broad upstream runs and report actual runtime coverage and limitations.

### Planner discretion — explicitly delegated by issue #326

Choose the smallest internal helper arrangement, type annotations, check IDs/message wording,
configuration-error exception, and fixture organization consistent with these contracts. Handle empty/invalid
mapping diagnostics consistently with the existing configuration API and document the result; do not add
fallback semantics. Select appropriate focused/broader verification and isolated cross-repository wiring.
These are delegated implementation choices, not unanswered product questions.

## Existing Code Insights

### Reusable Assets

- `PolymorphicCreateSelectView.get_form()` currently builds `(ct.id, ct.name)` choices after include/exclude
  filtering and passes them into the configured form. The custom-form and cancellation paths already exist.
- `ObjectDetailMixin.property_display` returns `cv_property_display`. `get_property_display()` reads the
  property, accepts an already parsed list by inspecting its first entry, or calls `parse_property_display()`.
  `get_context_data()` then calls `resolve_all()` and supplies existing layout/identity context.
- `checks()` validates the static attribute and delegates group/property checks before `super().checks()`.
  `_checks_property_group()` already handles typed groups and icon warnings; `_checks_group_properties()`
  checks property-entry shapes. Extend these paths without duplicating them for each model.

### Established Patterns and Bounded Planning Notes

- Tests explicitly preserve the property adapter, E240, base view check chaining, typed groups, and icon warnings.
  Some list-based tests use `get_object_for_detail()` without setting `self.object`; the mapping's exact-object
  requirement must not impose a new object lookup on existing list configuration.
- The runtime parser's first-entry shortcut differs from the per-entry startup checker. Plan support for the
  issue's existing raw/typed group forms deliberately; do not infer runtime support merely from a passing check
  or use this as justification for an unrelated parser framework.
- The repository uses request-local CBVs, declarative class configuration, Pydantic group/property objects,
  and optional extension packages. Preserve their boundaries and avoid class-level selection state.
- The downstream code confirms the issue: only Beans groups are declared statically while the override
  selects every concrete subtype at runtime; label capitalization currently lowercases the remainder.
- Prior phase contexts preserve defaults, navigation/permissions, bounded opt-in changes, and evidence-based
  completion. They do not add workflow or deletion requirements to this phase.
