### CR-01: Default-producing mappings bypass missing-type errors and mutate class configuration

**Classification:** BLOCKER  
**File:** `/home/alex/projects/workspaces/cv-phase-06-15/django-crud-views/src/crud_views_object_detail/lib/mixins.py:47-55`  
**Issue:** The public configuration accepts `collections.abc.Mapping`, but selecting with `raw[model]` and relying exclusively on `KeyError` does not establish that the actual type has a declared entry. A normal `collections.defaultdict` invokes its factory instead. For example, `defaultdict(list, {User: user_groups})` passes startup checks; rendering an unmapped `Group` returns an empty group list and inserts `Group: []` into the class-level mapping. A factory returning groups similarly renders undeclared fallback groups. Later requests and checks see the newly inserted entry.

This violates the documented exact-entry error and no-fallback/no-class-mutation guarantees (D-04–D-06). It is not limited to a custom application override: `defaultdict` is accepted directly by the new mapping API.

**Evidence:** A fresh process using this worktree's source and the existing Django 5.2.18 interpreter produced:

```text
DEFAULTDICT_CHECKS []
DEFAULTDICT_KEYS_BEFORE ['auth.User']
DEFAULTDICT_RESULT []
DEFAULTDICT_KEYS_AFTER ['auth.User', 'auth.Group']
```

The probe used the real `ObjectDetailMixin.get_property_display()`, a class-level `defaultdict(list, {User: [{"title": "Users", "properties": ["username"]}]})`, and `view.object = Group(name="Unmapped")`. No database or request mutation was needed.

**Fix:** Establish membership in the mapping's declared keys before invoking its lookup, and raise the existing named `ImproperlyConfigured` error when the exact class is absent. Do not allow `__missing__`/default factories to stand in for a declaration. For arbitrary `Mapping` implementations, inspect the iterated keys rather than assuming their `__contains__` cannot perform a lookup. Add regressions for empty and populated `defaultdict` declarations asserting the missing-type exception, zero factory calls and unchanged class keys; preserve successful exact entries.

### CR-02: The bare Django Model class crashes all-entry startup validation

**Classification:** BLOCKER  
**File:** `/home/alex/projects/workspaces/cv-phase-06-15/django-crud-views/src/crud_views_object_detail/lib/mixins.py:87-90`  
**Issue:** `django.db.models.Model` itself satisfies both `isinstance(model, type)` and `issubclass(model, Model)`, but it has no `_meta` attribute. Supplying this class as a mapping key therefore raises `AttributeError` while constructing the location string, before E247 is yielded. This terminates startup checks and hides malformed values and later mapping entries instead of reporting an invalid key. The new checker explicitly promises safe diagnostics for invalid keys and traversal of every declared value (D-08–D-10).

**Evidence:** In a fresh Django 5.2.18 process, a view inheriting the real mixin with:

```python
cv_property_display = {
    User: [],
    Model: [],
    Group: ["malformed"],
}
```

raised:

```text
MODEL_KEY_EXCEPTION AttributeError type object 'Model' has no attribute '_meta'
```

during `[m for check in view_class.checks() for m in check.messages()]`. Neither E247 for the bare base class nor E242/E243 for the following group was emitted.

**Fix:** Reject the bare `Model` base before accessing model metadata, retaining the safe entry/type location and continuing value validation and subsequent entries. The minimum bounded guard is:

```python
valid_model = (
    isinstance(model, type)
    and issubclass(model, Model)
    and model is not Model
)
```

Add a regression containing a valid first entry, the bare `Model` with a malformed value, and a malformed later entry. Assert E247 plus the value/group diagnostics, no exception, and inherited checks still running.
