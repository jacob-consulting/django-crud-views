<decisions>
## Implementation Decisions

### Choice labels — issue D12

- **D-01:** Add `choices_display: bool = True` to `PropertyConfig`, available through `x()` and the
  existing dictionary form. Plain choice-field paths show readable labels by default, retaining
  automatic `verbose_name` titles and explicit `title` overrides. `choices_display=False` restores
  raw-value presentation. No project/view choice-display setting is requested.
- **D-02:** Support scalar model fields with choices, including string/integer choices and terminal
  fields reached through single-object FK/O2O paths. Use the terminal model's display-method semantics,
  including Django's unknown-code fallback. Missing related objects remain empty without invoking
  a display method on `None`. Collection paths retain existing behavior, even with one member.
- **D-03:** Preserve ordinary non-choice fields, model methods/properties, and view-callable fallback.
  Do not infer choice metadata for arbitrary computed values. Apply property options after existing
  group selection, through the shared parser, for list/mapping/dynamic configurations from Phase 06.15.
- **D-04:** Badge color maps/functions and label maps continue to receive stored codes. Explicit badge
  labels take precedence over automatic choice labels; preserve existing lookup/fallback semantics.
  A raw-value opt-out does not cancel an explicit badge-label override. Links continue to receive raw values.

### Help-text policy — issue D13

- **D-05:** Add project setting `CRUD_VIEWS_OBJECT_DETAIL_SHOW_HELP_TEXT`, default `False`, and view
  attribute `cv_object_detail_show_help_text`, default `None` to inherit the project policy; a boolean
  view value overrides it. `True` at project level restores automatic model help text globally.
- **D-06:** Property `detail` has this exact precedence and meaning:

  | Property detail | Result |
  |---|---|
  | Omitted or `None` | Inherit view → project → `False` |
  | `True` | Use terminal field help text, or no text if absent |
  | `False` or `""` | Suppress detail regardless of inherited policy |
  | Non-empty string or supported lazy translation string | Use explicit text regardless of policy |

  Booleans are instructions, never the rendered words “True” or “False”. Preserve lazy descriptions
  and explicit empty-string suppression. Accept booleans without coercing unrelated values into them;
  do not broaden unrelated configuration validation.
- **D-07:** Automatic help text comes only from terminal field metadata. A related path such as
  `customer__country` uses `country.help_text`; do not leak intermediate relationship help text when
  terminal metadata/help text is absent. Computed paths have no automatic model help text but retain
  explicit descriptions.
- **D-08:** Apply the policy through the shared resolver. Normal views and raw `property_display`
  template tags with a view use that view's policy. Direct resolver/tag use without a view uses the
  project setting. Already-resolved properties retain resolved detail text when rendered under a
  different context. No extra queries or layout-specific policy switches.

### Empty text — issue D14

- **D-09:** Stock `char`, `text`, and fallback `default` value templates use the existing muted em dash
  for both `None` and `""`. Keep the property row, label, and explicitly configured detail text.
- **D-10:** Preserve `0` and `False` as real values and whitespace-only strings as text. Do not use a
  broad falsy check or trim whitespace. Preserve normal escaping and non-empty text newline formatting.
  Custom templates retain output control. No new badge/relation/collection empty-value policy.

### Composition — issue D16

- **D-11:** Document that `ObjectDetailView` and `ObjectDetailViewPermissionRequired` already include
  `ObjectDetailMixin`; consumers subclass complete views directly. Put the explicit warning beside
  the existing composition recipe. Mix `ObjectDetailMixin` before core `DetailViewPermissionRequired`,
  `GuardianDetailViewPermissionRequired`, or `PolymorphicDetailViewPermissionRequired` only when the
  base does not already include it. Guardian composition uses a GuardianViewSet.
- **D-12:** Finding 16 is documentation-only. No class-hierarchy refactor, MRO detector, or system check:
  Python rejects the invalid class before Django checks could inspect it.

### Conservative implementation defaults — delegated by the issue

These constrain drafting without inventing additional maintainer-selected APIs.

- **D-13:** Preserve `ResolvedProperty.value` and custom-template `value` as raw values. Expose any
  additional display information separately using the smallest representation/name; document it if
  public. Keep existing badge/custom-template dispatch precedence and custom-template ownership.
- **D-14:** Stock choice labels are text, including integer/boolean choices; do not pass labels through
  number/boolean formatting. Explicit `type` does not silently disable choice display; the escape hatch
  is `choices_display=False`. Choice display precedes text-placeholder selection: a non-empty declared
  label for a blank choice remains meaningful text, while a missing relationship stays empty.
- **D-15:** Preserve translation and escaping. Do not mark new choice labels or descriptions safe
  merely because they originate in model metadata. Preserve existing badge fallback semantics,
  including empty label-map results, instead of broadening the label-map contract.

### Documentation, validation, and boundaries

- **D-16:** Extend public documentation with the examples, help-text precedence table, choice support
  boundary/raw escape hatch, empty-value policy, and composition warning. Record breaking/default
  changes in both `CHANGELOG.md` and `docs/migrating-1.0.md`, including global help-text restoration,
  per-property raw choices, and copied/custom value-template migration where relevant.
- **D-17:** Cover issue #327's full acceptance criteria with appropriate config/resolver/template/view
  regressions and documentation checks. Include string/integer and boolean choice presentation,
  unknown codes, missing relations, single-object versus collection paths (including one-member
  collections), raw badge/link inputs and custom-template ownership, translations/escaping, all
  help-text precedence cases and resolution entry points, and preserved empty-text distinctions.
  Preserve optional-app behavior and ordinary-path query costs; use multicore pytest for broad runs.
- **D-18:** Maintainability is a hard constraint. Reuse existing parsing/resolution/rendering paths;
  no general display pipeline, resolver rewrite, new collection mapping, or visibility system.
  Preserve Phase 06.15's exact-model group selection, static checks, and dynamic escape hatch.
- **D-19:** This is independently deliverable from #328 and #329. Downstream findings motivate the
  work, but downstream adoption/commits are not completion dependencies. Do not automatically remove
  application-owned group filtering or custom templates. Phase 06.15's downstream delivery obligation
  is specific to that completed phase and does not carry forward here.
- **D-20:** Do not reopen settled defaults, configuration levels, raw-code support, collection support,
  hiding empty rows, or class hierarchy. Ask only if new code evidence exposes a material conflict;
  identify the evidence and affected decision. Internal helpers, annotations/validation details,
  exception wording, fixture organization, and focused tests are delegated to the builder.

### Reusable Assets

- `PropertyGroupConfig.normalize_properties()` accepts strings, typed properties, and dictionaries;
  `parse_property_display()` preserves typed group identity. `x()` directly constructs `PropertyConfig`.
- `resolve_property()` separately gathers metadata, resolves raw values, and feeds raw values into
  `_resolve_link_url()`, `_resolve_badge()`, and `_resolve_badge_label()`. `resolve_group()`/`resolve_all()`
  already forward `view`. Preserve these bounded entry points.
- `ObjectDetailMixin.get_property_display()` already selects exact model keys before shared parsing.
  `get_context_data()` forwards `self` to resolution. The raw template-tag path also forwards context `view`;
  pre-resolved `groups` bypass resolution. These are the existing help-policy integration seams.

### Established Patterns and Planning Notes

- `_resolve_field_meta()` currently retains the last non-empty help text seen along traversal. D-07
  requires terminal-only metadata so relationships cannot leak descriptions into terminal/computed values.
- `_resolve_value()` retains collection identity through metadata `is_many`; a one-member collection
  does not become scalar. Preserve that boundary while obtaining terminal owners for choice display.
- `PropertyConfig.detail` currently accepts `LazyStr | None`; `LazyStr` rejects booleans and preserves
  Django `Promise` values. Add boolean instructions locally without weakening unrelated string validation.
- `render_property_value()` currently gives resolved badges precedence over explicit custom templates,
  then chooses type/fallback templates. It always supplies raw `value=prop.value`. Choice display must
  respect that contract while preventing numeric/boolean formatting of translated choice labels.
- The three stock text templates currently check only `value is None`; text formatting uses the existing
  `property_text_newline` setting. Preserve the markup and formatting for unaffected values.
- Extension settings currently use cached properties. The OD autouse fixture refreshes settings references
  in `conf` and template tags; account for any additional bound reference during test planning. This is a
  test-isolation consideration, not permission to redesign the settings infrastructure.
- Existing resolver tests expect inherited help text. Update their expectations deliberately for the new
  default and retain explicit opt-in coverage; do not interpret those old expectations as conflicting decisions.

### Integration Boundaries

- Extend existing docs and tests; no new runtime dependency or core-view hierarchy changes are needed.
- Preserve ordinary request/query behavior and optional Guardian/polymorphic boundaries.
- No source, downstream environment, or application code was changed by this discussion.

<specifics>
## Specific Examples from the Issue

- A field `process` storing `"natural"` displays `"Naturally processed"` with its automatic title;
  `x("process", choices_display=False)` displays `"natural"`.
- `BadgeConfig(color_map={"natural": "success"})` uses the stored code for color and the choice label
  for stock text; adding `label_map={"natural": "Natural"}` makes the explicit label win.
- `x("country", detail=True)` uses the field's help text even when global/view policy disables it;
  `detail=False` or `detail=""` suppresses it, while `detail="Used for invoices."` supplies explicit text.
- Empty `phone=""` and `notes=None` retain their labeled rows with an em dash.
- Complete detail views are subclassed directly; a Guardian detail base composes as
  `ObjectDetailMixin, GuardianDetailViewPermissionRequired` with a GuardianViewSet.
