## Implementation Decisions

### Choice labels — issue D12

- **D-01:** Add `choices_display: bool = True` to `PropertyConfig`, available through `x()` and the
  existing dictionary form. Plain choice-field paths show readable labels by default, retaining
  automatic `verbose_name` titles and explicit `title` overrides. `choices_display=False` restores
  raw-value presentation. No project/view choice-display setting is requested.
- **D-02:** Support scalar model fields with choices, including string/integer choices and terminal
  fields reached through single-object FK/O2O paths. Use the terminal model's display-method semantics,
  including Django's unknown-code fallback. Missing related objects remain empty without invoking
  a display method on `None`. Collection paths retain existing behavior, even with one member.
- **D-03:** Preserve ordinary non-choice fields, model methods/properties, and view-callable fallback.
  Do not infer choice metadata for arbitrary computed values. Apply property options after existing
  group selection, through the shared parser, for list/mapping/dynamic configurations from Phase 06.15.
- **D-04:** Badge color maps/functions and label maps continue to receive stored codes. Explicit badge
  labels take precedence over automatic choice labels; preserve existing lookup/fallback semantics.
  A raw-value opt-out does not cancel an explicit badge-label override. Links continue to receive raw values.

### Help-text policy — issue D13

- **D-05:** Add project setting `CRUD_VIEWS_OBJECT_DETAIL_SHOW_HELP_TEXT`, default `False`, and view
  attribute `cv_object_detail_show_help_text`, default `None` to inherit the project policy; a boolean
  view value overrides it. `True` at project level restores automatic model help text globally.
- **D-06:** Property `detail` has this exact precedence and meaning:

  | Property detail | Result |
  |---|---|
  | Omitted or `None` | Inherit view → project → `False` |
  | `True` | Use terminal field help text, or no text if absent |
  | `False` or `""` | Suppress detail regardless of inherited policy |
  | Non-empty string or supported lazy translation string | Use explicit text regardless of policy |

  Booleans are instructions, never the rendered words “True” or “False”. Preserve lazy descriptions
  and explicit empty-string suppression. Accept booleans without coercing unrelated values into them;
  do not broaden unrelated configuration validation.
- **D-07:** Automatic help text comes only from terminal field metadata. A related path such as
  `customer__country` uses `country.help_text`; do not leak intermediate relationship help text when
  terminal metadata/help text is absent. Computed paths have no automatic model help text but retain
  explicit descriptions.
- **D-08:** Apply the policy through the shared resolver. Normal views and raw `property_display`
  template tags with a view use that view's policy. Direct resolver/tag use without a view uses the
  project setting. Already-resolved properties retain resolved detail text when rendered under a
  different context. No extra queries or layout-specific policy switches.

### Empty text — issue D14

- **D-09:** Stock `char`, `text`, and fallback `default` value templates use the existing muted em dash
  for both `None` and `""`. Keep the property row, label, and explicitly configured detail text.
- **D-10:** Preserve `0` and `False` as real values and whitespace-only strings as text. Do not use a
  broad falsy check or trim whitespace. Preserve normal escaping and non-empty text newline formatting.
  Custom templates retain output control. No new badge/relation/collection empty-value policy.

### Composition — issue D16

- **D-11:** Document that `ObjectDetailView` and `ObjectDetailViewPermissionRequired` already include
  `ObjectDetailMixin`; consumers subclass complete views directly. Put the explicit warning beside
  the existing composition recipe. Mix `ObjectDetailMixin` before core `DetailViewPermissionRequired`,
  `GuardianDetailViewPermissionRequired`, or `PolymorphicDetailViewPermissionRequired` only when the
  base does not already include it. Guardian composition uses a GuardianViewSet.
- **D-12:** Finding 16 is documentation-only. No class-hierarchy refactor, MRO detector, or system check:
  Python rejects the invalid class before Django checks could inspect it.

### Conservative implementation defaults — delegated by the issue

These constrain drafting without inventing additional maintainer-selected APIs.

- **D-13:** Preserve `ResolvedProperty.value` and custom-template `value` as raw values. Expose any
  additional display information separately using the smallest representation/name; document it if
  public. Keep existing badge/custom-template dispatch precedence and custom-template ownership.
- **D-14:** Stock choice labels are text, including integer/boolean choices; do not pass labels through

- **D-15:** Preserve translation and escaping. Do not mark new choice labels or descriptions safe

### Terminal metadata and terminal owner

**Observed:** metadata currently remembers the last nonempty help text via `if help_text: detail = str(help_text)`; computed segments terminate metadata traversal. Runtime traversal uses a list for fan-out and collapses only under `if not is_many and len(current) == 1:`. [VERIFIED: src/crud_views_object_detail/lib/resolvers.py:146-168,220-255]

**Recommendation:** return the terminal field alongside existing metadata, clearing terminal metadata when traversal cannot reach a genuine terminal model field. Derive automatic help text from that field only. Preserve existing label/type inference for computed paths; do not accidentally clear those unrelated outputs while fixing help text.

For choice display, record the scalar owner immediately before the final segment in the existing traversal. Use one local owner variable, not an owner list, second relation walk, or general result-tree abstraction. A small private tuple return is enough. Keep fan-out expansion, missing-first-segment behavior, callable invocation, and collection output shape unchanged. Only use the owner when metadata proves a scalar field with choices and no collection segment. Guard the actual owner, not merely the raw value: a real blank value can have a declared label, whereas a missing relation has no owner. [VERIFIED: 06.16-CONTEXT.md:30-39,89-98; src/crud_views_object_detail/lib/resolvers.py:220-255]

Call the terminal owner's public display method. Django documents the method and its override behavior; installed source additionally shows unknown-value fallback and lazy-string evaluation at call time. The probe returned a declared blank label, the unknown raw code, an unknown integer unchanged, and the explicitly overridden display result. [CITED: https://docs.djangoproject.com/en/5.2/ref/models/instances/#django.db.models.Model.get_FOO_display] [VERIFIED: installed Django 5.2.18 django/db/models/base.py:1293-1299; django/db/models/fields/__init__.py:958-968; session probe]

Do not flatten choices yourself: calling the public method preserves application overrides, grouped choices and Django's fallback. Keep both explicit-title precedence and normal method/view fallback intact. Query-count tests should compare loaded and uncached ordinary relations as well as choice relations; do not claim all custom display methods are query-free, since application overrides can perform their own work. [CITED: https://docs.djangoproject.com/en/5.2/ref/models/instances/#django.db.models.Model.get_FOO_display]

### Separate raw and display values

The existing contract supplies `"value": prop.value` to templates and calls badge/link functions before constructing the resolved property. Its badge order is `if prop.badge_css`, then `elif prop.template`, then typed fallback. Preserve it exactly. [VERIFIED: src/crud_views_object_detail/templatetags/crud_views_object_detail.py:94-115; src/crud_views_object_detail/lib/resolvers.py:197-216]

**Recommendation:** add one optional separate choice-label result with absence distinct from an empty string. An optional choice-label field with identity-based absence checks is sufficient for Django's string-label contract; expose the effective display value separately to stock templates if that simplifies them. Name and document whichever public field/context entry is selected. Existing manually constructed resolved properties must keep working with defaults. Do not change raw `value`, or turn a display label into a type discriminator.

Dispatch order remains resolved badge → explicit property template → choice text → existing type/fallback. A choice text branch must precede ordinary type selection even when an explicit type was configured. Choose the existing text-compatible leaf rather than adding a renderer framework. Non-choice text retains its newline branch. Custom packs and explicit templates retain raw context and can opt into the documented new display field. [VERIFIED: 06.16-CONTEXT.md:89-105]

Badge label-map lookup remains separate and raw-keyed. The stock template currently uses `{% if prop.badge_label %}`, so empty mapped labels fall through; preserve that truthiness contract, then use automatic choice text before raw text in the fallback. Do not promote a mapped label into ordinary output when no badge color resolves. Preserve the badge's raw-None check rather than applying the new empty-string placeholder policy to badges. [VERIFIED: src/crud_views_object_detail/lib/resolvers.py:104-127; src/crud_views_object_detail/templates/crud_views_object_detail/types/default/badge.html:1; docs/reference/object_detail_badges.md:43-67]

### Help-text policy and cached settings

Use the proposed local annotation `detail: LazyStr | StrictBool | None = None`. The existing definition is `detail: LazyStr | None = None`, while `LazyStr = Annotated[str, PlainValidator(_validate_lazy_str)]` accepts only string/Promise without coercion. Do not weaken that shared validator. [VERIFIED: src/crud_views_object_detail/lib/config.py:31-40; src/crud_views/lib/lazy.py:7-16] [CITED: https://docs.pydantic.dev/latest/api/types/#pydantic.types.StrictBool]

The session probe of that union preserved identity for None, booleans, ordinary strings and Promise; rejected integers zero/one, bytes and lists; and kept the literal string “False” as text. Test these boundaries in the existing configuration suite. [VERIFIED: session Pydantic TypeAdapter probe, 2026-11-06]

Implement a small help-policy helper in the resolver: explicit string/Promise first, exact boolean instructions next, then view override if non-None, else project default. A true instruction selects terminal help text; false suppresses it. Preserve lazy metadata without `str(help_text)`; resolve language at render/request time. Only the detail field gains boolean instructions; titles and descriptions retain existing validation. [VERIFIED: 06.16-CONTEXT.md:43-65; src/crud_views/lib/lazy.py:7-16]

Read the settings singleton through the conf module in the resolver rather than binding another copy with a from-import. Existing settings are cached properties, and the OD autouse fixture currently rebinds conf and template-tag references separately. Module access avoids a third stale reference; no production settings redesign is needed. Tests that change settings twice in one test must refresh the singleton/cache between resolutions. Resolved-group rendering must retain already selected text. [VERIFIED: src/crud_views_object_detail/lib/conf.py:13-30; tests/test1/od/conftest.py:8-15; src/crud_views_object_detail/templatetags/crud_views_object_detail.py:27-30]

## Common Pitfalls

1. **A collection with one element appears scalar.** Keep the metadata collection flag authoritative, including reverse relations. Add empty/one/many-member cases; never infer support from result length alone. [VERIFIED: src/crud_views_object_detail/lib/resolvers.py:160-168,236-238]
2. **Intermediate help text leaks into computed/blank terminal fields.** Select terminal field help only, including a terminal field whose help is empty. [VERIFIED: src/crud_views_object_detail/lib/resolvers.py:146-157]
3. **False/zero choice labels disappear or become icons.** Use absence identity rather than truthiness for choice display, and choose the text leaf ahead of integer/boolean formatting. [VERIFIED: 06.16-CONTEXT.md:92-98]
4. **Blank choice labels are hidden by raw-empty handling.** Determine choice display before char/text/default placeholder selection; distinguish missing owner from a present blank field. [VERIFIED: 06.16-CONTEXT.md:92-95]
5. **Badge overrides silently change semantics.** Empty mapped labels still fall through; unresolved colors do not create badge presentation; explicit property templates win only after badge resolution fails. [VERIFIED: docs/reference/object_detail_badges.md:43-67; stock badge template:1]
6. **Settings tests pass alone but fail together.** Avoid a new bound singleton reference; run multiple inheritance cases in one process with explicit cache resets. [VERIFIED: tests/test1/od/conftest.py:8-15]
7. **Direct OD-path pytest never reaches tests.** OD conftest imports tags before Django's parent pytest_configure hook; current gettext_noop use then requires settings. Use parent-directory collection and filename selection below. [VERIFIED: session failed command output; tests/test1/od/conftest.py:1-5; tests/test1/conftest.py:43-51]
