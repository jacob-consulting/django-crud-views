### CR-01: Automatic numeric choice fallback still undergoes locale number formatting

**Classification:** BLOCKER  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views_object_detail/templates/crud_views_object_detail/types/default/char.html:1`  
**Related files:** `/home/alex/projects/alex/django-crud-views/src/crud_views_object_detail/templates/crud_views_object_detail/types/default/badge.html:1`; `/home/alex/projects/alex/django-crud-views/src/crud_views_object_detail/templatetags/crud_views_object_detail.py:102-123`  
**Issue:** The choice branch selects a textual template, but passes a potentially numeric `choice_label` unchanged to `{{ display_value }}`. Django's ordinary variable renderer localizes numbers even in char.html. Django's public display method deliberately preserves an unknown integer code as an integer, so a host using the supported `USE_THOUSAND_SEPARATOR=True` setting displays code `10000` as `10,000` in English or `10.000` in German. The automatic badge fallback has the same problem. This violates D-14's text presentation/no-number-formatting rule and plan 01 task 3's explicit requirement that unknown numeric codes avoid number formatting while choices are enabled. Changing the chosen template from integer to char does not itself enforce that rule.

**Evidence:** Read-only Python 3.12 / Django 5.2 probe bound to this checkout, using the existing test configuration and ChoiceValue fixture (no database or source changes):

```python
from django.test import override_settings
from django.utils.translation import override
from crud_views_object_detail.lib.config import x
from crud_views_object_detail.lib.resolvers import resolve_property
from tests.test1.od_app.models import ChoiceValue
from tests.test1.od.test_choice_display import render_value

with override_settings(USE_THOUSAND_SEPARATOR=True):
    for language in ("en", "de"):
        with override(language):
            for badge in (None, "info"):
                prop = resolve_property(ChoiceValue(rank=10000), x("rank", badge=badge))
                print(language, badge, prop.value, prop.choice_label, repr(render_value(prop)))
```

Observed:

```text
en None 10000 10000 '10,000\n'
en info 10000 10000 '<span class="badge text-bg-info">10,000</span>\n'
de None 10000 10000 '10.000\n'
de info 10000 10000 '<span class="badge text-bg-info">10.000</span>\n'
```

The existing test `test_choice_display_uses_text_despite_inferred_or_explicit_type` checks unknown `10000` only with default separator settings, so it misses this branch. Installed Django source confirms `Model._get_FIELD_display()` uses `force_str(..., strings_only=True)`, which preserves numeric unknown codes.

**Fix:** Disable localization specifically for automatic choice output in the stock text and badge-fallback leaves, or convert only that output to plain text before template localization. Preserve `prop.value`, `prop.choice_label`, and the documented raw/custom-template context; preserve ordinary numeric formatting and existing explicit badge-label precedence. Update published copied-template recipes where needed. Add a small regression crossing separator-enabled English/German rendering with ordinary choice text and automatic badge fallback, asserting `10000` remains ungrouped and raw metadata remains numeric.
