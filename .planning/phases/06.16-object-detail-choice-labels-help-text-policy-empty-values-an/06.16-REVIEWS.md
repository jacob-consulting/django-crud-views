### Strengths

- **Additive field placement is safe.** `ResolvedProperty` fields after `value` all have defaults (`resolvers.py:49-57`), and the positional-constructor test at `test_badge_semantics.py:98` pins ordering. Appending `choice_label` at the end is the only safe spot and the plan says so.

- **Dispatch order claim is accurate.** `crud_views_object_detail.py:95-107` is `badge_css` → `template` → typed fallback. Inserting a choice branch between `elif prop.template` and the `else` matches D-13 precedence without reordering existing branches.
- **Collection guard exists.** `_resolve_value` collapses only under `not is_many and len(current) == 1` (`resolvers.py:236`), so using metadata `is_many` as the owner gate is consistent with existing semantics.
- **Test analogs are real.** `isolate_apps` is used at `test_polymorphic_docs.py:12,56`; locmem template overrides at `test_badge_semantics.py:23-30`; `django_assert_num_queries` at `test_object_detail_view.py:331-345,422-441`. Nothing new in harness terms.

### Concerns

- **MEDIUM — Deep missing reverse one-to-one resolves to `[]`, not `None`.** `_step()` at `resolvers.py:250-255` drops a missing attribute; Django's `ReverseOneToOneDescriptor` raises `RelatedObjectDoesNotExist`, an `AttributeError` subclass, which `getattr(obj, segment, _MISSING)` swallows. `current` becomes `[]`, line 236's `len(current) == 1` is false, and the raw value is `[]` with type `char`. First-segment misses behave differently: `resolvers.py:228-230` returns `_MISSING`, then view fallback yields `None`. The plan should either state that this quirk is pre-existing and out of scope, with the test asserting the actual `[]`, or decide to fix it. Leaving it implicit will produce a test that passes for the wrong reason or a silent scope widening.
- **MEDIUM — Existing test-app view flips output, no regression named.** `tests/test1/app/views.py:613-623` (`CampaignDetailView`) displays `"state"`, an `FSMField` with `choices=CampaignState.choices` (`tests/test1/app/models.py:100-122`). - **LOW — Terminal "field" can be a `ForeignObjectRel`.** `_resolve_field_meta` navigates `OneToOneRel`/`ManyToOneRel` at `resolvers.py:162-166`; those are not `Field` instances and already need `getattr(field_obj, "help_text", None)` at line 155. - **LOW — Task 1 is heavy for a tracer.** It touches five files and introduces two public names. Acceptable given D-13, but the `estimate.confidence: low` is honest and the executor should expect this task to be the longest.

Plan `06.16-01` introduces per-property `choices_display: bool = True` on `PropertyConfig`, resolves scalar model choice labels via the terminal owner's `get_FIELD_display()` into an additive `ResolvedProperty.choice_label` field, and passes `display_value` to templates while keeping `ResolvedProperty.value`, template `value`, and badge/link inputs raw. The overall design adheres to the developer-maintainability constraint by extending the existing `_resolve_field_meta` → `_resolve_value` → `render_property_value` pipeline rather than introducing a new display subsystem, though two concrete source-level hazards in `src/crud_views_object_detail/lib/resolvers.py` and `tests/test1/od/test_object_detail_view.py` need attention during implementation.

### 2. Strengths
- **Preserves raw value ownership across badges, links, and custom templates (`src/crud_views_object_detail/lib/resolvers.py:198-217`, `src/crud_views_object_detail/templatetags/crud_views_object_detail.py:94-116`):** By keeping `ResolvedProperty.value` raw and feeding `value` into `_resolve_link_url` (line 198), `_resolve_badge` (line 201), and `_resolve_badge_label` (line 202), existing `color_map`, `color_fn`, and `label_map` configurations keyed by stored choice codes continue to work without change.
- **Additive dataclass field preserves positional construction (`src/crud_views_object_detail/lib/resolvers.py:45-58`, `tests/test1/od/test_badge_semantics.py:97-103`):** Appending `choice_label: Any | None = None` after `badge_pill: bool = False` at line 57 preserves existing positional `ResolvedProperty(...)` calls such as `test_badge_semantics_preserves_positional_constructor` (`tests/test1/od/test_badge_semantics.py:98`).
- **Precedence-preserving template dispatch (`src/crud_views_object_detail/templatetags/crud_views_object_detail.py:95-108`):** Inserting the `prop.choice_label is not None` branch after `if prop.badge_css:` (line 95) and `elif prop.template:` (line 100) but before `prop.type` (line 104) prevents integer and boolean choice labels from being routed to `types/default/integer.html` or `types/default/boolean.html` (`fa-circle-check` / `fa-circle-xmark` icons at `src/crud_views_object_detail/templates/crud_views_object_detail/types/default/boolean.html:1`), even when `config.type` is explicitly set.
- **Compatibility with `badge.html` truthiness and null guards (`src/crud_views_object_detail/templates/crud_views_object_detail/types/default/badge.html:1`):** Replacing only the final `{{ value }}` fallback with `{{ display_value }}` inside `{% if value is None %}...{% else %}<span class="badge {{ prop.badge_css }}">{% if prop.badge_label %}{{ prop.badge_label }}{% else %}{{ display_value }}{% endif %}</span>{% endif %}` preserves the raw-`None` dash, truthy `badge_label` priority, and empty-string `label_map` fallback tested in `tests/test1/od/test_badge_semantics.py:105-120`.

### 3. Concerns
- **HIGH — Absent reverse `OneToOneRel` traversal raises uncaught `ObjectDoesNotExist` (`src/crud_views_object_detail/lib/resolvers.py:228,254`):** Task 2 `<behavior>` specifies: *"FK/O2O terminal owners supply the label; absent nullable/reverse-one-to-one owners do not invoke a display method"*, while Task 2 `<action>` says *"Preserve `_MISSING` handling, `_expand`/`_step` behavior and normal exception propagation."* In Django, accessing an absent reverse `OneToOneRel` descriptor (e.g., `info.report` on `Info` at `tests/test1/od_app/models.py:7,23` when no `Report` references `info`) raises `Report.DoesNotExist` (`django.core.exceptions.ObjectDoesNotExist`), which does **not** inherit from `AttributeError`. Consequently, `getattr(instance, segments[0], _MISSING)` at `resolvers.py:228` and `getattr(obj, segment, _MISSING)` at `resolvers.py:254` do not catch it and will crash instead of resolving to `None` (compare `src/crud_views_guardian/lib/views.py:292-295`, which explicitly catches `ObjectDoesNotExist` around `getattr`).
- **MEDIUM — Changing `_resolve_value` return signature directly will break an existing test outside Wave 1's `-k` filter (`src/crud_views_object_detail/lib/resolvers.py:220`, `tests/test1/od/test_object_detail_view.py:202-212`):** The plan notes *"Private helper signatures may change locally to retain terminal metadata/owner"* and `06.16-RESEARCH.md:161` suggests *"A small private tuple return is enough."* However, `test_resolve_value_returns_list_when_single_path_fans_out_to_nothing` (`tests/test1/od/test_object_detail_view.py:207,210`) imports `_resolve_value` directly and asserts `value == []`. Because none of the three `<verify>` commands in `06.16-01` include `test_object_detail_view`, changing `_resolve_value` to return a tuple `(value, owner)` would pass all Wave 1 task checks and fail later in Wave 2.
- **MEDIUM — Intermediate `field_obj` retention on `FieldDoesNotExist` or non-relation hops in `_resolve_field_meta` (`src/crud_views_object_detail/lib/resolvers.py:146-168`):** In `_resolve_field_meta`, if segment 0 is a model field (or FK/O2O) and a subsequent segment raises `FieldDoesNotExist` (lines 149-152, e.g., `owner__get_full_name` or `info__custom_method`), the loop executes `break` while the local variable `field_obj` still holds the previous segment's `Field`. Similarly, if a path has a segment after a non-relation `Field` (where neither `if` nor `elif` at lines 162-166 matches), `current_model` currently remains the previous model instead of becoming `None`. If `terminal_field` is not explicitly cleared to `None` on `FieldDoesNotExist` and when traversing past a non-relation field, metadata from an earlier segment can leak into terminal field detection.
- **LOW — Nullable choice fields with `None` value and `get_FIELD_display()` (`src/crud_views_object_detail/lib/resolvers.py:191-217`):** When a nullable choice field (e.g. `CharField(choices=..., null=True)`) has runtime value `None` and `None` is not a key in `choices`, Django's `Model._get_FIELD_display` (`force_str(..., strings_only=True)`) returns `None`. The resolver should ensure that when `value is None` and `None` is not a declared choice label (so `get_FIELD_display()` returns `None`), `choice_label` remains `None` so stock templates render the muted em dash.

### 4. Suggestions
- In `src/crud_views_object_detail/lib/resolvers.py:228,254`, use a small helper around `getattr` that catches `ObjectDoesNotExist` and treats an absent reverse `OneToOneRel` as `None` (not `_MISSING`, so a missing related object on a valid model relation does not trigger the view-callable fallback at `resolvers.py:193-195`).
- Keep `_resolve_value(instance, segments, is_many)` returning `value` unchanged (so `tests/test1/od/test_object_detail_view.py:210` remains valid) and either factor the shared loop into `_resolve_value_and_owner(instance, segments, is_many) -> tuple[Any, Any]` or add `test_object_detail_view` to Task 2's `<verify>` selection.
- In `_resolve_field_meta` (`src/crud_views_object_detail/lib/resolvers.py:146-168`), track `terminal_field = None` on each iteration before `get_field(segment)`, set `terminal_field = field_obj` only when `get_field` succeeds, and set `current_model = None` when `field_obj` is not a relation so any subsequent segment cannot resolve against the parent model's `_meta`.

### 5. Risk Assessment
**MEDIUM** — The architectural scope is tight and well-bounded, but the uncaught `ObjectDoesNotExist` on reverse one-to-one traversal (`resolvers.py:228,254`) and the direct `_resolve_value` caller in `test_object_detail_view.py:210` will cause test failures during execution if not addressed explicitly.
