# Phase 06.18 Plan 01: Prove one nested request and strict policy ownership Summary

**A shared request-local ancestor guard in `CrudView.dispatch` now authorizes a plain nested Book list/create against its core Publisher's model permissions (resolve outermost inward through the ancestor ViewSet queryset, gate each level before the next lookup), backed by strict `AncestorPolicy`/`AncestorPermissions` values, validated `CRUD_VIEWS_ANCESTOR_*` settings and pre-registration ViewSet policy validation.**

## Evidence scope

The behavioral evidence of this plan is limited to **one composition**: a registered *plain* (`ListView` / `CreateView`, no endpoint-local permission gate) nested Book ViewSet under a core Publisher ViewSet, requested through real URLs with database-backed model grants. Permission-required, Guardian, manage, Resource, card/ordered/redirect/polymorphic-selector and custom compositions, and the early-actor ordering of the permission-required/manage MROs, are proven by later plans (02 families, 03 Guardian, 04 MRO ordering, 05 Resource/scoping). This plan does not seal the phase and makes no green-suite or release claim.

## Accomplishments

- `crud_views.lib.ancestors`: one engine — bounded ancestry walk (missing/cycle → `ImproperlyConfigured`), operation pair (exact `actions` entry, else family pair from the ViewSet override or the global setting), full/nearest selection of protected levels (`provider="none"` passes through without consuming the nearest position), actor admission, scoped outermost-inward resolution constrained to the URL PK and the resolved outer ancestor, interleaved gates, request-local `_AncestorState`.
- `CrudView.dispatch` runs `_cv_ancestor_guard()` after cancel restoration and before downstream dispatch; modal `Vary` handling is preserved for guard responses too. `cv_get_parent_object()` reuses the resolved immediate parent (one Publisher read per nested create POST).
- `AncestorPolicy` / `AncestorPermissions` (strict, extra-forbid, exact non-empty unpadded keys, complete pairs) exported from `crud_views.lib.viewset`; `ViewSet.ancestor_policy` is a fresh default per ViewSet; `ViewSet._ancestor_provider = "model"` and `ViewSet._ancestor_has_permission(user, permission, obj, *, view)`.
- `CRUD_VIEWS_ANCESTOR_PERMISSION_CASCADE=True`, `..._READ_PERMISSIONS={"nearest": "view", "higher": "view"}`, `..._WRITE_PERMISSIONS={"nearest": "change", "higher": "view"}` captured and validated (`validate_default`) when the settings singleton is built; the settings module imports only the dependency-light policy module.
- Owning-ViewSet validation in `register()` before registry insertion/manage creation: core `provider="guardian"`, ineffective `accept_global_perms=True`, and top-level non-None `cascade`/`read`/`write` or nonempty `actions` raise a Pydantic `ValidationError` naming the ViewSet and field; the same name can be retried; forward parents and not-yet-registered action keys stay valid.
