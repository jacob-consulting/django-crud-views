# Phase 06.18 Plan 02: Bound ancestry walks and classify exact endpoint operations Summary

**Every ancestry walk now goes through one bounded metadata walk (cycles and missing parents raise a named-chain `ImproperlyConfigured` at URL construction, helpers and requests, with no database access), declared relationships are validated from model metadata, operations come from a finite class-based family table with exact literal-key `actions` entries, and a URLconf completion barrier lets the new viewset.E266/E267/E268 checks run without premature missing-key errors; the 18 H1-core fixture rows are closed with exact Publisher grants and independent denial controls.**

## Accomplishments

- **Bounded walks (Task 1).** `_walk_ancestors` (visited ViewSet names, `first_only`) is the only ancestry walk of `get_parent_url_args`, `get_parent_attributes`, `get_path_parent`, `get_queryset` and the request guard. `urlpatterns` first validates a finite, resolved, Resource-free chain, so an imported URLconf fails boundedly; a child declared before its parent still routes. `ViewSet.checks()` no longer crashes on a missing parent (E261 is skipped; E266 reports it).
- **Relationships (Task 1).** `_validate_relationship` accepts one forward FK/one-to-one, reverse relation or many-to-many pointing at the ancestor model, and a `many_to_many_through_attribute` only when both sides are many-to-many to each other; it rejects missing/non-relational/generic fields, `__` paths and other targets. The request guard runs it before actor, lookup or permission work.
- **Families and exact keys (Task 2).** `_operation_family`: list/card/detail (incl. rich ObjectDetail and polymorphic detail)/RedirectChildView/manage are Read; create/update/delete (incl. polymorphic)/ordered up/down are Write; the polymorphic type selector carries `_cv_ancestor_operation = "write"`; Django's generic DetailView is not a family. `_operation_requirements` uses the literally registered key and raises for an unclassified nested endpoint without an entry. `_validate_action_declarations` rejects unregistered `actions` keys; Card's `list` alias never validates or selects a `list` entry.
- **Checks and barrier (Task 2).** `check_ancestor_declarations` imports the configured ROOT_URLCONF and every included URLconf through Django's resolver (each resolver visited once) before snapshotting the registry, then reports E266/E267/E268. No ROOT_URLCONF, a failed import or a check run during URLconf import defers only the completion-dependent messages; nothing is remembered between calls.
- **Fixtures (Task 3).** Shared `user_book_view` + Publisher view; `user_book_add/change/delete` + Publisher change; the local Book/Contract reader and Contract reader + Publisher view; the Genre-create actor + Publisher change (Genre add kept). New controls: child-only and parent-only readers, parent-view-only editors (create/update/delete GET), parent-change-only actors, local readers without Publisher view, and Genre-add-only / Publisher-change-only creates that leave no save, attachment, hook or on_commit event.
