# Phase 06.18 Plan 03: Guardian ancestry and legacy parent-policy removal Summary

**A `GuardianViewSet` ancestor is now a strict object-permission gate inside the shared ancestor engine (configured content types, direct/group grants, model fallback only from the ancestor's own `accept_global_perms`); the Guardian dispatch bridge runs that one traversal before any object/queryset/state work, every Guardian helper uses a bounded immediate-parent rule, and the old `cv_guardian_parent_*` fields are removed and rejected before registration.**

## Accomplishments

- **Guardian provider (Task 1).** `GuardianViewSet._ancestor_provider = "guardian"`; `_ancestor_has_permission` delegates to `_guardian_ancestor_has_permission` (or to the model gate for an explicit `provider="model"`). It denies anonymous/inactive actors before any shortcut, accepts `user.has_perm(permission)` only with the ancestor's own `ancestor_policy.accept_global_perms`, otherwise uses Guardian's `ObjectPermissionChecker` (content type from `guardian.ctypes`, group grants, active superusers), cached on the requested view.
- **Bridge (Task 1).** `GuardianParentPermissionMixin.dispatch` keeps composition `ImproperlyConfigured`, the configured anonymous 302/403/404 and inactive 403, then calls `_cv_ancestor_guard()`; the old `_guardian_check_parent` lookup is gone (one Publisher read per request, proven by query capture). The create/list state gate uses `cv_get_parent_object()`, i.e. the guard's object. `has_permission()` still bypasses the model permission for nested Guardian views (no child-add requirement); E001 and the runtime composition guard are unchanged.
- **Helpers (Task 2).** `_immediate_parent_access` replaces `_guardian_user_has_parent_perm` in child-collection links, `cv_create_has_access`, nested create `cv_has_access` and cancel availability: immediate parent's provider/fallback with the target's nearest key, no farther ancestor, no lookup, `None` → False, provider `none` → True, invalid key → `ImproperlyConfigured`, request-resolved identity reused.
- **Removal (Task 3).** Both fields are gone; constructor keys and annotated/inherited/ClassVar/mixin declarations fail as `ValidationError` naming the replacement scopes, before registration (no DB). The removed ViewSet-level `cv_guardian_accept_global_perms` error stays. Manage shows `parent_viewset (ancestor provider: …)` and `ancestor_policy.provider` / `accept_global_perms`; per-view local fallback applicability is now object/queryset views only. The shared Guardian Book uses the default policy.
