# Phase 06.18 Plan 04: Early actor admission and interleaved ordering across shipped MROs Summary

**Permission-required and manage endpoints now enter the shared ancestor guard at their first `dispatch`, before Django's `PermissionRequiredMixin` runs a child-, state- or group-loading `has_permission()`; actor admission goes through one small private adapter per family (protected ancestry: anonymous → endpoint response, inactive → 403; all-none: the endpoint's own early rule only), and a 43-entry composition inventory proves the static → actor → interleaved ancestor → local order with poison spies.**

## Accomplishments

- **Bridge (Task 1).** `CrudViewPermissionRequiredMixin.dispatch` calls `_cv_ancestor_guard()` before `super().dispatch()`. Before, `PermissionRequiredMixin.dispatch` ran `has_permission()` first, which loaded the child object or parent and checked action state ahead of ancestry (proven by RED: child queryset before Publisher queryset; 403 instead of 404 for a missing parent). Every permission-required family (core, card, ordered, rich detail, Resource, polymorphic, workflow, custom forms/actions) inherits it.
- **Actor adapters (Task 1).** `_authorize_ancestors` now calls `view._cv_ancestor_actor_response(protected=bool(selected))` before the first lookup. `CrudView`: protected rule only (plain endpoints are public under all-none). `CrudViewPermissionRequiredMixin`: under all-none, anonymous/inactive actors are admitted only by the model permission (`PermissionRequiredMixin.has_permission`), so an anonymous-granting backend still works; active actors go straight to ancestry. Guardian object/queryset/parent mixins: configured anonymous behavior and inactive 403 in both modes (one `_guardian_actor_response` helper, also used by the parent mixin's dispatch).
- **Manage (Task 2).** `ManageView.dispatch` runs the guard before `PermissionRequiredMixin`; its adapter keeps the actual `yes`/`debug_only` admission (`_cv_manage_public`) and denies only anonymous actors early under all-none; group membership stays the local gate after ancestry. `GuardianManageView` inherits it.
- **Inventory (Task 2).** `INVENTORY` in `test_ancestor_ordering.py` names 43 compositions with their guard entry (`CrudView.dispatch`, `CrudViewPermissionRequiredMixin.dispatch`, `GuardianParentPermissionMixin.dispatch`, `ManageView.dispatch`) — including `GuardianManageView` and `RedirectChildView` — and runs outer-denied / nearest-denied / reached-404 / local-reached scenarios, nearest-only and all-none variants, denied and authorized writes (`django_capture_on_commit_callbacks`, persisted rows), and a Guardian-ancestor chain. Spies on deeper querysets, local permission, `get_object`, `get_form`, state hook, render, fragment render, Resource loader and manage gate raise when reached in a denial scenario.
- **H1-fragment closed (Task 2).** `test_fragment_authorization.py`: the three failing/masked Guardian child cases and `test_ungranted_guardian_child_update_fragment_denied` grant Publisher change; the mismatch case asserts the child lookup was reached (404), the child-ungranted case asserts denial after ancestry, the disabled create records the resolved Publisher in the state hook; new `test_parent_view_only_guardian_child_fragments_denied_before_child_work` denies update/create fragments with parent view only and no child lookup, state call or render.
