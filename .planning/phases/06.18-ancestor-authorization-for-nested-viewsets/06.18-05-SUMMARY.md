# Phase 06.18 Plan 05: Scoped ancestry and structural-parent identity Summary

**A reached nested ORM child object must now belong to the request's resolved immediate parent (`CrudView.get_object` → `_validate_child_parent`, 404 before any state hook), and nested lists are scoped to that parent where they consume `object_list` (`_scope_child_queryset`), so a `get_queryset` override that drops the parent filter can no longer leak another parent's rows. The higher-chain create control reuses the request-resolved ancestor, and Resource leaves are proven to be authorized before their application-owned loaders run.**

## Accomplishments

- **Leaf object membership (Task 1).** `CrudView.get_object` calls `ancestors._validate_child_parent(view, obj)` after Django's lookup. For a guarded nested ORM request, a forward FK/one-to-one compares the stored key with the resolved parent (no query); an M2M or reverse relation checks this row's membership with one `exists()`. A mismatch is a 404. Because `cv_get_action_object`, Guardian's object gate and the view body all go through `get_object`, the check runs before state hooks, forms and writes.
- **Collection scoping (Task 1).** `CrudView.get_context_data` passes `object_list` through `ancestors._scope_child_queryset` before Django's pagination and django-tables2 read it. That covers plain, table, filter and card lists. The default ViewSet queryset already has the filter, so its rows stay the same.
- **Identity reuse (Task 1).** `CreateView._cv_action_enabled_for_rendering` reuses the request-resolved ancestor (`_resolved_ancestor`) when a create control targets a parent higher in the chain, so the state hook gets the same object without another query. Outside a guarded request it still does its one bounded lookup. FK/M2M create, through defaults and provider-`none` structural parents already reused the guard's object; tests now prove it.
- **Already in place, now proven (Task 1).** Ancestor lookups get the actual child view, request and kwargs. Manager/ViewSet scope exclusions are 404 without a retry. Explicit `pk_name`, int and UUID keys, and deep mismatches all hold, and a create is refused before any form is built.
- **Resource leaves (Task 2).** No production change was needed: the plain and permission-required bridges from 04.1 already run the ORM chain before `cv_get_items`/`cv_get_item`. A mutation check (guard disabled for Resource leaves) makes 37 of the 39 new cases fail. The 2 that still pass are the Resource-parent and top-level controls, which do not depend on the guard.
- **H1-resource closed (Task 2).** The four nested `PublisherFile` cases now use a module-local `client_user_publisher_file_view` fixture: the shared Resource-only actor plus Publisher view, granted with `user_viewset_permission`. Two new controls cover the other actors. The Resource-only actor is denied by the Publisher gate, and its poisoned loaders are never called. A fresh Publisher-view-only actor gets a 404 for a missing Publisher and a 403 from the local Resource permission, and nothing is loaded.

## Known limits (documented, bounded)

- Collection scoping covers `QuerySet`s of the ViewSet's model. A sliced, combined (`union`) or non-queryset collection from a custom `get_queryset` is not filtered: a sliced queryset raises Django's own `TypeError` on filter, and a non-queryset passes through unchanged as application-owned data.
- A custom `get_object` that does not call `super()` bypasses `_validate_child_parent`, as it bypasses Django's own lookup.
- Nested M2M/reverse detail requests run one extra `exists()` per `get_object` call. The permission phase and the body each call it, so that is two per object request. FK edges add no query.
