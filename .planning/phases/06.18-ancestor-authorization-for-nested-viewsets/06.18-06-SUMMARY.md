# Phase 06.18 Plan 06: Reject reached nondefault nested data and write routes Summary

**Nested ViewSet requests now refuse any database other than `default` at the point where it is reached. That covers ancestor querysets, child querysets and list collections, the delete-preview alias, and every write route: the transaction alias, the written instance's route, and the FK/M2M parent attachment. Writes are refused before any hook, action, transition or commit callback, with `cv_atomic` on or off, and no selection is ever stripped, forced or retried. The new code is a small inspect-and-refuse module, `crud_views.lib.ancestor_db`. Top-level ViewSets keep their routed behaviour.**

## Accomplishments

### Task 1: reached querysets and the delete preview

- **Ancestor lookups.** `_resolve_ancestor` checks `queryset.db` before `.first()`. This is the effective alias: an explicit `.using()` first, otherwise the router with the queryset's hints. Nothing is evaluated.
- **Child data at its consumers.**
  - `CrudView.get_object` builds the queryset Django would build and checks it before the lookup. This covers the default, view `get_queryset` overrides and Django's `queryset` attribute path.
  - `CrudView.get_context_data` checks the collection Django will paginate, including a keyword `object_list` from django-filter.
- **Delete preview.** `DeleteView.cv_get_delete_db_alias` keeps the existing instance-aware `cv_get_db_alias` selection and its pinning, but now refuses a nondefault alias, whether newly selected or pinned. Nested `DeleteView.get_context_data` consults it before `cv_check_delete_protection`, `inspect_deletion`, `cv_get_delete_preview` and any related-object query.

### Task 2: form and delete writes

`CrudView._cv_check_nested_write(context)` calls `ancestor_db._check_nested_write`. It checks three things, all recomputed on every call:

- the view's write alias (`_cv_write_alias()`: `cv_get_db_alias`, the delete alias for delete views);
- the written instance: the form's model instance or `self.object`, both its loaded database and `router.db_for_write(model, instance=...)`;
- the parent attachment from `CreateViewParentMixin._cv_attachment_routes()`: the FK assignment routed with the parent as hint, or the M2M through write hinted by the parent.

It runs in two places:

- **In each POST, before the first hook:** in `CrudViewProcessFormMixin.post` and `DeleteView.post`, after object and form-instance resolution and before `cv_post_hook`.
- **At the write wrapper:** again at the start of both `cv_form_valid_process` implementations, before the transaction. A guard only in `cv_get_atomic` would not be enough.

### Task 3: action, ordered and workflow writes

- **Actions.** `ActionView.post` checks right after `get_object`, before `get_context_data`. `cv_action_process` checks again. Ordered up/down inherit this wrapper, and `action_ordered.py` is unchanged.
- **Workflow.** `WorkflowView.post` checks before context, hooks and transition, and its own `cv_form_valid_process` checks again. `_cv_write_alias` returns the existing pinned `_cv_get_workflow_db_alias()`, which is validated and never replaced.
- **Core write selector.** `CrudView.cv_get_db_alias` passes the resolved object as instance hint for nested ORM requests, so the transaction alias equals the object's own `save()` route. Top-level selection stays model-only.

## Decisions Made

See `key-decisions` in the frontmatter. In short:

- The boundary inspects the alias each consumer already selected, at the consumer: `queryset.db`, the real instance hints, and the attachment routes Django uses.
- It refuses with `ImproperlyConfigured`, and never selects or reroutes.
- The nested core write selector now uses the instance hint so the transaction alias matches the actual save route. Plan 12's release notes own the paired Breaking/migration entry for this.

- **Logged:** in `deferred-items.md` and in `.planning/WINDOWS.md` (kind `unmet-truth`). The proposed fix is one line: scope `kwargs["object_list"]` too.

## Known limits (documented, bounded)

- The check covers the consumers listed in the `ancestor_db` docstring. Some code paths bypass them:
  - a custom `get_object` that does not call `super()`;
  - a `ListView` with `allow_empty = False`, whose `exists()` runs before `get_context_data`;
  - inline formset child rows (their own models' routes);
  - application code inside hooks.

  None of these is validated.
- The pre-hook form check sees the form instance before validation. Values that change a router's answer only after `is_valid()` are caught by the second check, at `cv_form_valid_process`, which still precedes `cv_form_valid`, `cv_form_valid_hook` and commit callbacks. `cv_form_is_valid` itself runs between the two checks.
- Nested workflow POSTs now select and pin the workflow alias right after object resolution, instead of after form validation. It is still one selection with the same instance hint.
