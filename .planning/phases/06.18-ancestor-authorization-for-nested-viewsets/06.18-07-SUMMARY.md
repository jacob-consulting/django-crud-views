# Phase 06.18 Plan 07: Apply the default-database boundary to reached authorization consumers Summary

**Every permission check that a nested ViewSet request reaches now refuses authorization records outside `default`. The check runs before it reads its permission map (cached or not) and before any backend shortcut such as an active superuser or model fallback. This covers the selected ancestor gates, Guardian's local object gates and list filters, core permission-required checks (including the all-none early admission) and nested manage pages. It is one small helper, `ancestor_db._check_nested_auth`, with the Guardian grant-table list kept in the extension. Nothing is rerouted, a nearest-only higher gate is never touched, and top-level ViewSets keep their routing. Filtered nested lists are also scoped to the resolved parent now, as the directed Rule 1 fix.**

## Accomplishments

### The helper (`crud_views.lib.ancestor_db`)

`_check_nested_auth(view, *, actor, model, obj=None, provider="model")` returns at once for top-level views. For a nested view (or view class, for access helpers) it checks, in order:

1. the actor's own database (a saved user loaded from another database never authorizes);
2. the object's database;
3. every table from `_auth_tables(model, provider)`: the selection of its managers (an explicit manager alias, otherwise the router) and the router's answer with the actor as instance hint, and for Guardian checks also with the object as hint, which is how Django's related managers route.

`_auth_tables` reads metadata only. For `"model"` it returns Django's ModelBackend tables: user, group, permission, content type, and the user-groups, user-permissions and group-permissions through tables. For `"guardian"` it adds `crud_views_guardian.lib.ancestors._guardian_grant_tables(model)`: the configured generic user/group grant models and every enabled direct grant model of `model`. No content type is resolved. A refusal is an `ImproperlyConfigured` naming the ViewSet, the view key and the table.

### Task 1: ancestor gates

- `_authorize_ancestors` calls the helper for each **selected** level, right after resolving it and before `_permission_name` (the vocabulary) and the provider. The provider is that ancestor's effective provider. Levels that nearest-only mode does not select get no route check, no map read and no provider call.
- `_immediate_parent_access` (the bounded helper) does the same before its map and provider.
- This happens at the call site, so a warm `ViewSet._default_permissions` cache cannot bypass it. The cache is never invalidated.

### Task 2: local Guardian gates and nested manage

- `GuardianObjectPermissionMixin.get_object` checks after the object loads and before the map, the checker, the superuser shortcut and the local model fallback. `cv_has_access` does the same for nested view classes.
- `GuardianQuerysetMixin.get_queryset` checks before the map and `get_objects_for_user`.
- `ManageView`:
  - `has_permission` checks only right before the group-membership query, so public settings and anonymous actors do no auth work;
  - `get_context_data` checks before the permission rows;
  - `get_permission_holders` checks before its queries.
- `GuardianManageView.get_permission_holders` checks the Guardian inventory before its first query.
- `GuardianViewSet.get_objects_for_user` and top-level views are unchanged.

### Task 3: core permission checks

`CrudViewPermissionRequiredMixin` gets the check in three places:

- `_cv_ancestor_actor_response` (all-none early admission of anonymous or inactive actors), before `PermissionRequiredMixin.has_permission`;
- `has_permission`, before `permission_required` and `super()`. This is the local gate after ancestry, and it runs before the child lookup and action state;
- `cv_has_access`.

Plain nested endpoints without a permission check do no auth work.

### Auto-fixed Issues

**1. [Rule 1 - Bug] Filtered nested lists skipped the parent scoping (directed by the orchestrator)**
- **Found during:** 06.18-06, logged in `deferred-items.md` and in `.planning/WINDOWS.md` entry 40.
- **Issue:** `CrudView.get_context_data` scoped `object_list` only when it was not passed as a keyword. django-filter passes `object_list=...`, so a nested `ListViewTableFilterMixin` list whose `get_queryset` omits the parent filter rendered other parents' rows.
- **Fix:** both the keyword and `self.object_list` are scoped. When the keyword is `self.object_list`, the same scoped queryset is reused, so the table (which reads `self.object_list`) renders the same rows. Plan 06's alias check on the consumed collection is unchanged.
- **Files modified:** `src/crud_views/lib/view/base.py`, `tests/test1/test_ancestor_resolution.py`
- **Verification:** 12 RED cases are now green. The broad regression shows only H2 rows.
- **Committed in:** `620852bf` (test), `1442363c` (fix). The `deferred-items.md` entry is marked `status: resolved` and WINDOWS entry 40 is marked fixed.

**2. [Rule 3 - Blocking] The gate call site lives in `src/crud_views/lib/ancestors.py` (outside the plan's file list)**

A check inside `ViewSet` / `GuardianViewSet._ancestor_has_permission` would come after a cold vocabulary query. A check inside the cached `default_permissions` would run once per process, as the REVIEWS concern notes.
- **Fix:** the check sits at those two call sites. `viewset/__init__.py` is not modified: its permission map stays side-effect-free, as the review suggested.

## Known limits (documented, bounded)

The helper validates the finite table inventory of Django's `ModelBackend` and Guardian. Some paths are not validated:

- **Custom authentication backends:** their own SQL. The standard auth tables are still checked before any backend runs.
- **Application code:** inside `cv_action_enabled` / hooks.
- **A custom `get_object` or `has_permission` that does not call `super()`.**
- **Guardian's delete-preview label projection:** it keeps its separate route check, which hides labels.

A nested Guardian manage page reads its default-routed core permission rows before the Guardian holder check refuses a grant-table route.
