# Phase 06.18 Plan 09: Expose policy diagnostics and preserve nested redirect behavior Summary

**Manage pages now show each ViewSet's declared ancestor policy in two scopes, with declared `None` next to the effective default. The core `ManageView` owns this through a new `ancestor_policy` context entry, and Guardian's alert rows read from the same entry. Two new modules pin the rest: `test_ancestor_manage.py` covers nested manage (ancestry plus the local gate), and `test_ancestor_redirect.py` covers the built-in child redirect (Read, ancestry checked before its own lookup, destination authorized separately).**

## Accomplishments

- **Manage diagnostics (Task 1).** The new `ManageView.get_ancestor_policy_data()` returns two scopes:
  - `as_ancestor`: the declared `provider`, the `effective_provider` and `accept_global_perms`.
  - `requests`: `cascade`, `read` and `write` as `{declared, effective}` pairs, plus the exact `actions` map. It is `None` at top level.

  It evaluates nothing for the actor and loads no ancestor. A new `ancestor_policy` block in `view_manage.html` renders it as a table that names both scopes. That block shows declared `None` as "None (global setting)" or "None (ViewSet class default)" and says the table is configuration only. Guardian's `guardian_config.ancestor_policy` now reads from this entry. The local per-view fallback table and the strict-helper row are unchanged and stay separate.
- **Nested manage admission pins (Task 1).** Core and Guardian ancestors:
  - Public settings and manage-group membership never bypass a selected ancestor, and the local gate is not reached when an ancestor denies.
  - After ancestor success, the local group gate still denies a non-member, and the events show it ran after both ancestor lookups.
  - Reached missing or mismatched ancestors return 404.
  - Full cascade and nearest-only are both covered, and a farther grant never substitutes for the nearest one.
  - All-none ancestry keeps the manage gate's early anonymous rule, the group gate and relationship 404s.
  - Top-level manage is unchanged and does no ancestor work.
- **Redirect pins (Task 2).**
  - `RedirectChildView`, plain or as a renamed subclass, is Read without an action entry, and an exact entry replaces that pair.
  - When ancestry is denied (403) or a reached parent is missing (404), the redirect never looks up its child or builds its URL.
  - Following an allowed redirect is a fresh request. The destination's own pair, cascade mode and local gate can each deny it, and its events show it resolving its ancestors again.
  - A custom `ActionView` that returns a redirect, even under the key `redirect_child`, and a generic redirect view both stay unclassified (E268 and a runtime `ImproperlyConfigured`).
