# Phase 06.18 Plan 10: Prove mutation boundaries, fresh authorization and measured cost Summary

**Two new pin modules and a cost record. `test_ancestor_boundaries.py` shows that ancestry authorizes the URL path only: a shared M2M edit through A reaches B, a delete through A deletes the row, and an editable FK can move a child from A to B with no destination gate. It also shows that revoked direct, group and model grants deny the next request. `test_ancestor_costs.py` measures the 24-cell matrix against plan 01's pre-edit baseline and attributes every added query to the guard. `06.18-COSTS.md` records each cell with its explanation.**

## Accomplishments

### Mutation boundary (Task 1)

Ancestors are Guardian ViewSets. Their strict object grants make path A and path B distinguishable, which model grants could not. The tests run at one ancestor (Publisher) and three (Publisher → Book → BookNote → a test-scoped leaf), each in full cascade and nearest-only. Leaf views are core permission-required views, and their local model grants pass. Spies record which ancestors are resolved, which are gated, and which parent each child membership check uses. In every write, only path A appears in those records, and nothing of B does.

- **Shared M2M edit.** Editing a shared M2M child through A changes the shared row and leaves both memberships in place. An actor authorized for B then sees the edit through B. An editor of A alone is denied through B.
- **Ordinary delete.** Deleting through A deletes the row and B's through rows with it. Nesting does not turn the delete into unlinking.
- **Editable parent FK move.**
  - A valid form moves the child from A to B. The editor has no grant on B, and there is no destination gate or pin.
  - Afterwards, the editor is denied (403) on B and gets 404 on A.
  - A view-only actor on A is denied the move, because the write still needs A's nearest change permission.
  - An editor whose form excludes the FK is the application-owned control: the child stays under A.

### Fresh-request authorization (Task 1)

- **Revocation before the next request.** A direct or group Guardian grant revoked on the nearest ancestor, or a model grant revoked on a core ancestor, denies the next request. The child queryset is never called, and the data is unchanged.
- **Higher-grant revocation.** Revoking the outermost grant denies under full cascade. Under nearest-only the next request still succeeds, because it never evaluated that grant.
- **Caller-held caches.** A caller-held `User` instance keeps its primed permission cache. The framework neither reads nor invalidates it, and a fresh request ignores it.
- **Request-local state.**
  - Two requests get distinct views, distinct `_cv_ancestor_state`, re-resolved objects and distinct Guardian checkers.
  - No access state is kept on the ViewSets or the view classes.
  - The permission-vocabulary cache outlives requests unchanged, while the decision changes.
- **Concurrency probe (ANCE-08).** While an authorized request is inside its gate, two other requests run to completion: a grantless actor, and the same actor on path B. Both get 403, and the outer request then returns 200. On one ViewSet, interleaved actors (reader, stranger, reader, anonymous) are decided independently: 200, 403, 200, 302.

### Cost matrix (Task 2)

- **Setup.** The matrix replays plan 01's exact observation fixtures for all 24 depth/provider/operation/mode cells, cold and warm. Each request is split into the guard and the rest. The baseline totals and SHA `d5567ba2` are embedded in the module.
- **What is asserted.** These are invariants, not a budget:
  - all 48 requests return 200;
  - each ancestor is resolved exactly once, in the guard, outermost first;
  - no ancestor queryset runs, and no ancestor table is read, outside the guard;
  - full cascade evaluates one gate per ancestor, nearest-only exactly one (the nearest), and the event list for higher ancestors is empty;
  - no gate repeats within a request;
  - for plain leaves, the rest of the request equals the pre-edit total;
  - warm guards still query permission rows, so no persistent access cache hides the cost.
- **Supplementary create-button list.** Guardian's immediate-parent helper adds exactly one gate outside the guard. It applies to the guard-resolved immediate parent, needs no lookup, and the request's checker already holds that object's permissions, so the warm totals are unchanged.
- **Top-level controls.** Plain and Guardian top-level list and detail make zero guard queries, no structure walk, no gate, and only their own queryset call.
- **Recorded in `06.18-COSTS.md`.**
  - Plain chains: +2 for the actor load, +1 per ancestor, and +2 for the shared permission load. Cold requests add the pre-existing core vocabulary N+1.
  - Guardian at depth 1: equal to the baseline, because the legacy parent gate is replaced one-for-one.
  - Guardian at depth 3: nearest-only adds +2 (the higher lookups); full cascade adds +6 warm (higher lookups plus one object-permission pair per higher gate).
  - The file also lists the non-comparable legacy parts and a cold-ContentType order effect.

## Decisions Made

- **Pins only.** No production change; nine reverted mutations show that the pins detect the regressions that matter.
- **No budget.** The cost assertions cover attribution and prohibited repeated work; no fixed query count is asserted.
- **Baseline embedded.** The baseline totals are embedded in the module with their SHA, so the test does not read `.planning/` at runtime. A PR branch that drops planning commits would otherwise break it.
- **Guardian ancestors for the boundary tests.** Object grants make the two URL paths distinguishable.
- **No Guardian permission prefetch.** One object-permission pair per Guardian ancestor gate is permitted, distinct work. Prefetching across levels would conflict with interleaved gating (D-32).

## Issues Encountered

- **Order effect in cold Guardian lists.** The first cold Guardian list request in a worker process reads one extra `django_content_type` row outside the guard (cells 8 and 19 in COSTS). Swapping the mode order moves the read, and a serial replay shows it once. Guard counts are identical in every order. The cause is per-process state outside the reset scope; it is not an access decision. It is documented in COSTS and `task2-green.txt`.
