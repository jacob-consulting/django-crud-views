Failure-mode choice (justified, not a third invention): the two request gates (`get_object`, `get_queryset`)
raise `ImproperlyConfigured` — the exception the same request's ancestor gate already raises for the identical
condition on an ancestor (`crud_views/lib/ancestors.py::_permission_name`), and the exception the documented
Guardian collection-link path raises (docs/reference/guardian.md "Limits and configuration failures"). The
message carries the core request-time hint (`crud_views/lib/view/base.py::permission_required`: run
`manage.py migrate`, restart a server started before the migration). The render-time classmethod
`cv_has_access` returns False — the core precedent (`CrudViewPermissionRequiredMixin.cv_has_access`, #318,
docs/reference/inaccessible_actions.md "Missing core permission declarations"): a helper that renders a control on
someone else's page must not fail that page, the control is hidden, and opening the target raises the named
error. That is the split core already ships, so Guardian now follows one documented rule instead of two
packages disagreeing. `GuardianViewSet._resolve_permission_key` (ValueError listing valid keys) stays as is: it
validates caller-supplied API keys, not a view's own declaration. Both branches fail closed: access is never
granted on a missing key (ASVS L1, T-06.18-26).

grant through an absent vocabulary.
