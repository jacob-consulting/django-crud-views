## Method and vocabulary

- **Fixtures.** These are plan 01's observation fixtures, replayed unchanged: `test_ancestor_authorization._observation_chain` and `_deep_leaf_model`.
  - One ancestor: Publisher → Book.
  - Three ancestors: Publisher → Book → BookNote → a test-scoped leaf table.
  - Leaf views are plain (`ListView` / `DetailView` / `CreateView`, no local gate) or Guardian (`Guardian*ViewPermissionRequired`), with no list or context actions.
  - Actor: model view+change on every ancestor. Guardian cells also give object view+change on each ancestor and object view on the leaf row.
  - Requests are GET only. "create" means the form GET.
- **Cold / warm.** "Cold" clears the ViewSets' `_default_permissions`, the ContentType cache and `crud_views.lib.check._VOCAB_CACHE` before one request. "Warm" repeats the same request immediately. These caches hold *permission vocabulary*: they name permissions, they record nothing about who holds them.
- **Counting.** `CaptureQueriesContext` on `default`. Each query is categorized by the first table after `FROM` / `INTO` / `UPDATE`, so a Guardian object-permission query counts as `auth_permission`. **Guard** = the queries executed inside `crud_views.lib.ancestors._authorize_ancestors`. **Rest** = everything else in the request (session and user loading when it happens outside the guard, local gates, child lookup, rendering).
- **Modes.** Each cell is run under `full` (`AncestorPolicy(cascade=True)` on the leaf) and `nearest` (`cascade=False`). Legacy had no modes. Its single request (`legacy-no-mode`) is the comparison base for both mode cells. Plan 01 claims no mode-specific legacy behavior.
- **Order.** In each test, `full` runs before `nearest`, and list, object, create run in that order.

## Attribution

### Plain leaves (cells 1–6, 13–18)

The baseline plain nested request performed no ancestor work, no session or user load and no permission query. In every plain cell, cold and warm, the rest of the request equals the baseline total exactly (`rest == baseline` is asserted). The guard is therefore the only added work:

- **Actor load: +2 (session, user).** Protected ancestry needs the actor (anonymous or inactive admission), so the guard loads `request.user`. The legacy plain path never touched it.
- **Ancestor lookups: +1 per ancestor, in both modes.** Each ancestor is read once through its ViewSet queryset, constrained to its URL PK and to the resolved outer ancestor. Nearest-only still reads every ancestor: existence and relationship validation are not optional (D-20). This is the depth-3 nearest +2 over depth 1.
- **Model permission load: +2, shared by all levels.** `ModelBackend` loads the actor's user and group permissions once per request and caches them on that request's user instance. Full cascade at depth 3 checks three permissions with the same two queries, so warm full and warm nearest are equal (8 = 8).
- **Cold vocabulary.** The core `ViewSet.default_permissions` loop issues one ContentType lookup and one Permission query per gated ancestor (ct 1, perm 1). Full cascade at depth 3 resolves three ancestor vocabularies (ct 3). Nearest-only resolves only the nearest one (ct 1), because it never names a higher permission. Cold totals are therefore 8 (list, object) and 7 (create) at depth 1, 14 and 13 under full cascade at depth 3, and 10 and 9 under nearest-only at depth 3. The former extra ContentType read per permission row (ct 5 per ancestor, ct 15 at depth 3 full in the plan 12 record) was removed after the phase by quick task 261109-bf5 (`8b11572a`). It was vocabulary only, never access state, and runs once per ViewSet per process.

### Guardian leaves (cells 7–12, 19–24)

- **Depth 1: equal to the baseline.** Warm totals are identical in all six cells. Cold totals are identical except cell 8 (−1, explained below). The legacy immediate-parent gate (Publisher read once + two object-permission queries) is replaced one-for-one by the guard (publisher 1 + perm 2 warm). Nothing is left in the local path: the rest of the request reads no ancestor table (asserted). Since WR-01 (`76fdc7ff`) the guard loads the actor for nested Guardian views, so session 1 and user 1 are guard work: the warm guard is session 1, user 1, perm 2, publisher 1 (5). The guard's object-permission gate itself needs no model permission load.
- **Depth 3, nearest-only: +2.** These are the two higher-ancestor lookups (Publisher, Book). Legacy resolved only the immediate parent. The permission work is identical to legacy (one gate, two object-permission queries, on BookNote).
- **Depth 3, full cascade: +6 warm.** This is the two higher lookups plus two object-permission queries for each of the two higher gates. Guardian's `ObjectPermissionChecker` is one checker per request, reused across levels (`_cv_guardian_ancestor_checker` on the view). Each ancestor is a different object, though, so the checker issues its user/group object-permission pair per object. That is distinct work, not a repeated identical check. Prefetching all ancestors' permissions in one pair would require knowing every ancestor before the first gate. That conflicts with "gate each level before resolving the next" (D-32: a denied outer gate must prevent the deeper queryset), so it is deliberately not done.
- **Cold vocabulary (Guardian).** `GuardianViewSet.default_permissions` uses the single configured content type (ct 1, perm 1 per gated ancestor). Full cascade at depth 3 shows ct 3 and perm 9 (3 vocabulary + 6 object-permission queries). Nearest-only shows ct 1 and perm 3. Since quick task 261109-bf5, plain and Guardian vocabulary cost the same (ct 1 per gated ancestor).
- **Cell 8 (−1 cold) and cell 19 vs 20 (rest 4 vs 3 cold): an order effect, not mode behavior.** The first cold Guardian list request of a test reads one extra `django_content_type` row outside the guard (Guardian's local list path), and later cold requests in the same process do not. The cause is state cached once per process outside the reset scope; it is not an access decision. Swapping the mode order moves the extra read to `nearest`, and a serial replay (one process) shows it only once (`evidence/06.18-10/task2-green.txt`). Guard counts are identical in every order.

### Repeated work: permitted vs prohibited

| Work | Status | Evidence |
|---|---|---|
| Each ancestor resolved more than once per request | **Prohibited**, absent | Guard queryset events equal the ancestors outermost-first, exactly once. No ancestor queryset runs outside the guard. No ancestor table is read in the rest of the request. Mutation M2/M4 (double resolution, second parent read) fails the matrix. |
| An identical gate evaluated twice in one request | **Prohibited**, absent | The `(phase, ViewSet, permission, object)` gate events are unique per request. |
| Higher gates under nearest-only | **Prohibited**, absent | The event list of gates on higher ancestors is empty in every nearest cell, and the guard evaluates exactly one gate (the nearest). This is checked on the event list, not inferred from totals. Mutation M1 (cascade forced) fails. |
| A persistent access cache suppressing counts | **Prohibited**, absent | Every warm request still queries permission rows inside the guard (asserted). Mutation M3 (memoized decisions on the ViewSet) fails. Fresh-request revocation is proven by `test_ancestor_boundaries.py`. |
| One object-permission pair per Guardian ancestor gate | Permitted | Distinct objects; one checker per request; see above. |
| Higher-ancestor lookups under nearest-only | Permitted, required | Relationship and visibility validation (D-20). |
| Core vocabulary N+1 on a cold ViewSet | Removed after the phase (quick task 261109-bf5, `8b11572a`) | Plain cold ct equals the gated-ancestor count in every cell (1 at depth 1 and depth 3 nearest, 3 at depth 3 full). Regression test `tests/test1/test_viewset.py`. |
| Local gates after ancestry | Permitted, independent | Guardian local object/list checks keep their own queries (the object rest perm 2 warm). Ancestor success never waives them. |
| Guard entered twice by permission-required views | Permitted, free | `CrudView.dispatch` and the permission-required `dispatch` both call `_cv_ancestor_guard`. | M2M or reverse-relation child object pages | Permitted, local, outside this matrix | Plan 05 notes one membership `exists()` per `get_object()` call. Detail-style views call `get_object()` twice per request, so such pages issue two. The matrix uses forward-FK leaves, which need no membership query (the stored key is compared). |

## Render-helper work, separate from the guard

`test_render_helper_work_is_separate_from_the_guard` gives the leaf list view its `create` context button. The list op runs in both modes, cold and warm, at both depths (`*-list-with-create-button.json`).

- **Plain leaf (core create button).** No ancestor gate outside the guard. Totals equal the matrix list cells 1, 2, 13 and 14 (depth 1: 8/6 full, 8/6 nearest; depth 3: 14/8 full, 10/8 nearest).
- **Guardian leaf.** Guardian's immediate-parent helper (`_immediate_parent_access`) adds exactly one gate outside the guard. It is on the immediate parent, with the create operation's nearest permission (`change_publisher` at depth 1, `change_booknote` at depth 3), on the guard-resolved parent object. There is no ancestor lookup and no farther ancestor. The extra object-permission queries are absent because the request's checker already holds that object's permissions: the depth 1 warm total is 6, as in the matrix. Totals (depth 1: 11/6 full, 10/6 nearest; depth 3: 21/12 full, 12/8 nearest) are unchanged from the plan 12 record; only their guard/rest split moved with WR-01. Rendering never traverses higher ancestors. A visible button can still lead to a request denied higher up; that is the documented first-wave UI limitation.

## Legacy comparability

These cells, or parts of cells, have no legacy counterpart:

1. **Modes.** Legacy has no `full` / `nearest` distinction. Both mode cells compare against the single `legacy-no-mode` request.
2. **Plain cells 1–6, 13–18.** Legacy plain nested views authorized no ancestor at all: no lookup, no permission query, no session or user load. The whole guard is new protection, not a regression of existing work. The comparable part (the rest of the request) is unchanged and asserted equal.
3. **Guardian depth 3, higher ancestors (cells 19, 21, 23 and the higher lookups of 20, 22, 24).** Legacy Guardian resolved and gated only the immediate parent (BookNote), never Book or Publisher. Higher lookups and higher gates have no legacy behavior to compare. The comparable part is the BookNote gate (identical cost).
4. **Plan 01 interim observations (`f717e58d`).** These are intermediate states (legacy Guardian gate still active, model provider on Guardian ancestors). They are superseded by this file and are not a comparison base.

No fixed or universal query limit is claimed. Depth and cascade mode are cost controls, not a promise that traversal is free.
