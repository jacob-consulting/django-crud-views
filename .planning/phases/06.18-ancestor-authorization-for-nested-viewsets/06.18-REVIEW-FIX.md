## Fixed Issues

### WR-01: Guardian compositions run actor admission before static validation (D-32 / documented order)

**Status:** fixed: requires human verification
**Files modified:** `src/crud_views_guardian/lib/mixins.py`, `tests/test1/test_ancestor_actors.py`
**Commit:** 76fdc7ff
**Applied fix:**
- `GuardianParentPermissionMixin.dispatch` now has two branches:
  - **Nested views** go straight to `_cv_ancestor_guard()`. The guard runs static validation first, then
    Guardian's actor rules through the mixin's existing `_cv_ancestor_actor_response` adapter (anonymous: the
    configured `cv_guardian_anonymous_behavior`; inactive: 403), then the ancestors.
  - **Top-level views** keep the explicit anonymous/inactive checks, because the guard does nothing there.
    Top-level behavior is unchanged.
- The secondary no-object state gate after the guard is unchanged.
- Test-first:
  - `test_static_configuration_error_precedes_actor_admission` now takes four kinds: `act`, `pact`, `gobj`
    (standalone `GuardianObjectPermissionMixin`) and `gact` (shipped `GuardianActionViewPermissionRequired` on
    a `GuardianViewSet`).
  - It runs each kind for anonymous and inactive-superuser actors and asserts `ImproperlyConfigured` with no
    queryset or permission event.
  - Before the fix only `gact` failed, for both actors (302 redirect / `PermissionDenied`); afterwards all 8
    cases pass.
- Docs: unchanged. `docs/reference/nested.md` "Request order and responses" already described the fixed
  behavior. `docs/reference/guardian.md` "Inactive users" still holds (403 before any parent/object
  resolution, and static validation does no database work).

### WR-02: Leaf seams and parent reuse fail open when reached inside a request before the guard has run

**Status:** fixed: requires human verification (partial: leaf seams only)
**Files modified:** `src/crud_views/lib/ancestors.py`, `tests/test1/test_ancestor_resolution.py`,
`docs/reference/nested.md`
**Commit:** a17823d9
**Applied fix:**
- `_child_edge` now fails closed: a nested ORM view that has a bound `request` but no `_cv_ancestor_state`
  raises `ImproperlyConfigured`, naming the ViewSet and view key. `_child_edge` feeds `_validate_child_parent`
  (`CrudView.get_object`) and `_scope_child_queryset` (`CrudView.get_context_data`).
- Unchanged paths:
  - Views without a request (class-level or outside-request use) still return `None`.
  - Top-level and Resource-leaf views still return `None`.
- Test-first:
  - New fixture `pre_bridge`: Django's `UserPassesTestMixin` placed before `DetailView` / `ListView`. Its
    `test_func` calls `get_object()` or `get_context_data()` in dispatch.
  - `test_leaf_seam_before_the_guard_fails_closed[detail|list]` asserts three things: `ImproperlyConfigured`,
    `test_func` never received the object or collection, and no ancestor (Publisher) queryset was entered.
    It failed before the fix with "DID NOT RAISE".
  - `test_leaf_seam_outside_a_request_keeps_its_unscoped_behavior` pins the no-request path.
- Docs: `docs/reference/nested.md` "Ancestor querysets and the resolved parent" gained a paragraph stating the
  fail-closed rule and the remaining unsupported case.

**Not applied: the `CrudView.cv_get_parent_object` half of the suggestion.** I prototyped the same
`request is not None and state is None` guard there and ran the full suite: 32 existing tests failed, in
`test_guardian.py`, `test_cancel_permissions.py` and `test_core_nested_create_state.py`. They pin a supported
contract: rendering helpers call `cv_get_parent_object()` on views that are set up with a request but not
dispatched, so "request bound" does not mean "inside a dispatch before the guard". The affected helpers are
the parent/sibling/create buttons in `buttons.py`, `CreateView._cv_action_enabled_for_rendering`, and the
cancel availability check through `_cv_cancel_parent_object`.

Telling the two cases apart would need a new per-dispatch flag set by all four bridges. That is hidden state
and a change across the bridges, which the CLAUDE.md maintainability rule argues against for a case no shipped
composition reaches. The limit is documented in `docs/reference/nested.md` instead: `cv_get_parent_object()`
called before `super().dispatch()` does not authorize ancestry. One minor remaining limit: inside `get_object`
the child SELECT runs before the refusal, and its result is discarded without reaching the caller.

No CHANGELOG or `docs/migrating-1.0.md` change was needed: child scoping is itself new and unreleased in this
phase, so no published Breaking entry is affected.
