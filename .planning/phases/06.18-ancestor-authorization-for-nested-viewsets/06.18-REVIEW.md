## Warnings

### WR-01: Test helper restores one ViewSet's cache while its row deletion affects every ViewSet on the model

**File:** `tests/test1/test_guardian_vocabulary.py:26-44`
**Issue:** `without_permission_key` deletes the shared `Permission` row for `view_author` (line 37) and afterwards
restores only `viewset._default_permissions` (line 44). The same row backs the vocabulary of every other ViewSet on
`Author`: core `cv_author`, `cv_author_wide_card`, `cv_author_custom_detail`, `cv_author_detail_only`
(`tests/test1/app/views.py:53, 222, 252, 266`), plus `cv_guardian_author_origin` (line 1170) and the ViewSets at
lines 914 and 1081. Nonempty discovery is cached for the **process lifetime** (`src/crud_views/lib/viewset/__init__.py:484-485`,
`src/crud_views_guardian/lib/viewset.py:136-137`). If any of those ViewSets is cold and its `permissions` is read
inside the `with` block (a sibling link rendered on a hosting page, a `cv_has_access` call from a template tag, a
future test that renders instead of raising), it caches the three-key vocabulary and keeps it after the transaction
rolls the row back — for the rest of that pytest/xdist worker. Today the five requests in this module raise inside
`get_queryset`/`get_object` before any template renders, so the pollution is latent, but it is silent and
order-dependent, which is exactly the class of flake that is hard to attribute later. `tests/test1/test_workflow_execution.py:31-33`
already uses the snapshot-and-finalizer pattern for a single ViewSet; the same idea needs to cover the model, not
one ViewSet.
**Fix:** Snapshot and restore `_default_permissions` for every registered ViewSet sharing the model, using the
private registry the ViewSet module already exposes to `get_viewset`/`checks_all`:

```python
from crud_views.lib.viewset import _REGISTRY  # or expose a tiny `ViewSet.all()` for tests


@contextmanager
def without_permission_key(viewset, key):
    assert key in viewset.permissions
    siblings = [vs for vs in list(_REGISTRY.values()) if getattr(vs, "model", None) is viewset.model]
    saved = {vs: vs._default_permissions for vs in siblings}
    content_type = get_content_type(viewset.model)
    deleted, _ = Permission.objects.filter(content_type=content_type, codename=f"{key}_{content_type.model}").delete()
    assert deleted
    viewset._default_permissions = None
    try:
        assert key not in viewset.permissions
        yield
    finally:
        for vs, cache in saved.items():
            vs._default_permissions = cache
```

Alternatively, assert in `finally` that no sibling's cache changed during the block, so a future pollution fails
the test that caused it instead of a later one.

## Info

### IN-01: Three diagnostics for one failure class, with the Guardian message repeating the ViewSet name

**File:** `src/crud_views_guardian/lib/mixins.py:42-57` (compare `src/crud_views/lib/view/base.py:1159-1166`,
`src/crud_views/lib/ancestors.py:384-391`)
**Issue:** The same configuration failure (a permission key with no entry in a ViewSet's map) now surfaces three
ways: core request gate as an `AssertionError` from `assert perm, ...` (with the migrate/restart hint), the ancestor
gate as `ImproperlyConfigured` **without** the hint, and the Guardian gate as `ImproperlyConfigured` with the hint.
The Guardian text also names the ViewSet twice ("ViewSet 'guardian_author' view 'list': permission key 'view' is not
in the permission map of ViewSet 'guardian_author'") — the repetition is meaningful in the ancestor message, where
the second name is a different ViewSet, but is noise here. Separately, the parameter is named `view_or_cls` and the
docstring says "request gates only"; both call sites pass `self` (lines 121, 276) and `cv_has_access` deliberately
does not use it, so the "cls" half of the name promises a use that does not exist. None of this changes
authorization; it is a CLAUDE.md maintainability point — the developer must currently know three message shapes
and two exception types to debug one condition.
**Fix:** Introduce one core helper (e.g. in `crud_views.lib.ancestors` next to `_permission_name`) such as
`missing_permission_error(viewset, view_key, key, *, ancestor=None) -> ImproperlyConfigured` that produces a single
message with the migrate/restart hint, names the ancestor only when `ancestor is not None`, and have
`_permission_name`, `_local_permission_name` and core `permission_required` (replacing the `assert`) all raise it.
Rename `view_or_cls` to `view`. If the core `assert` is kept for now, at least align the ancestor message with the
hint so the two `ImproperlyConfigured` paths read the same.

### IN-02: Guardian list/card links stay visible on a missing key, unlike core and unlike the object views fixed here

**File:** `src/crud_views_guardian/lib/mixins.py:197-199` (compare `src/crud_views/lib/view/base.py:1217-1223`)
**Issue:** The plan made `GuardianObjectPermissionMixin.cv_has_access` return `False` on a missing key "as the core
helper does" (CHANGELOG), but `GuardianQuerysetMixin.cv_has_access` still returns `True` for every active actor
without consulting the map. So on a hosting page a list or card link to a misconfigured collection renders as usable
for ordinary users and superusers, and clicking it yields the new 500, whereas the core list view's
`cv_has_access` hides the control. This is not a grant (the request raises before any row is read) and the new
docs paragraph is carefully scoped to "`cv_has_access` on object views", so the documentation is not wrong — but
the asymmetry is undocumented and a reader of the CHANGELOG line will expect parity.
**Fix:** Either state the exception in `docs/reference/guardian.md` ("list and card links are not hidden; the list
request raises"), or mirror core by adding `if not cls.cv_viewset.permissions.get(cls.cv_permission): return False`
before the actor check. The latter costs one dict lookup per rendered link once the vocabulary is cached (one
query on a cold ViewSet), which should be weighed under the CLAUDE.md "additional queries on existing paths" rule
before adopting it.
