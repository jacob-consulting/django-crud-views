## Warnings

### WR-01: `GuardianQuerysetMixin.cv_has_access` reads the vocabulary without the nested default-database boundary the core helper applies

**File:** `src/crud_views_guardian/lib/mixins.py:198-203`
**Issue:** The IN-02 fix changed the list access helper from a pure actor check (no auth reads) into a permission-map read (`cls.cv_viewset.permissions.get(cls.cv_permission)`). Every other access helper that reads a nested ViewSet's vocabulary runs `_check_nested_auth` first — `CrudViewPermissionRequiredMixin.cv_has_access` (`src/crud_views/lib/view/base.py:1217-1224`) and `GuardianObjectPermissionMixin.cv_has_access` (`mixins.py:129-136`) — because `ancestor_db.py:23-26` documents the invariant: "before a nested request's permission check reads its vocabulary (cached or not) or takes a backend shortcut ... the actor and the tables the check queries must be on `default`." The comment on line 202 says "as the core helper does", but the core helper does the boundary check too.

Reproduced with a probe (`/tmp/claude-1000/-home-alex-projects-alex-django-crud-views/f566be73-e188-406b-8102-d32489be0589/scratchpad/test_probe_list_access.py`, run against the `adb`/`routes` fixtures of `tests/test1/test_ancestor_auth_databases.py`): with `Permission` reads routed to `shard`, `adb.CDetail.cv_has_access(user)` and `adb.GDetail.cv_has_access(user, book)` raise the documented `ImproperlyConfigured("... nested ViewSets support only the 'default' database ...")`, while `adb.GList.cv_has_access(user, None)` returns `True` both with a warm cache and with a cold cache (where the `Permission` query actually went to the shard). The commit message's "one dict lookup on the cached vocabulary" does not hold for the exact scenario the fix targets: an empty vocabulary (unapplied migration) is never cached (`crud_views_guardian/lib/viewset.py:136-137`), so every link render on a cold or empty ViewSet queries `ContentType`/`Permission` through the router with no boundary check.

Impact is bounded to link visibility — the request itself still refuses in `get_queryset()` — but it is a provable inconsistency between sibling helpers that the phase's own module docstring rules out, and `test_ancestor_auth_databases.py` has no case for the Guardian list helper, so nothing pins it.

**Fix:** Mirror the core helper (the vocabulary read touches only Django's auth/content-type tables, so the model-provider table set is sufficient; the Guardian object helper's `provider="guardian"` would also be defensible for symmetry):

```python
@classmethod
def cv_has_access(cls, user, obj=None):
    if _guardian_inactive_actor(user):
        return False
    # nested: the vocabulary read must be on default, as the core and object helpers require (06.18)
    _check_nested_auth(cls, actor=user, model=cls.cv_viewset.model)
    # a missing key hides the link, as the core helper does; the request itself raises in get_queryset()
    return bool(cls.cv_viewset.permissions.get(cls.cv_permission))
```

Add the list helper to the enumeration in `src/crud_views/lib/ancestor_db.py:31-33` ("Guardian object gates and list filters" → also "the Guardian list/card access helper"), and add a case next to `test_guardian_object_access_helper_refuses_nested_shard_auth_records` in `tests/test1/test_ancestor_auth_databases.py:621-629` asserting `adb.GList.cv_has_access(user, None)` raises `REFUSED` once `routes.read[Permission] = "shard"` (and that `adb.GTList` — top level — does not).

## Info

### IN-01: `GuardianQuerysetMixin` docstring says "every active actor" but anonymous actors also get `True`

**File:** `src/crud_views_guardian/lib/mixins.py:163-166`
**Issue:** The rewritten docstring line reads "Overrides cv_has_access() to return True for every active actor without a model permission". `_guardian_inactive_actor` (`mixins.py:15-22`) deliberately treats anonymous users as *not* inactive, so `cv_has_access(AnonymousUser(), None)` returns `True` when the key is present (unchanged pre-fix behavior, and intentional: the anonymous response is decided by `cv_guardian_anonymous_behavior` at request time). `AnonymousUser.is_active` is `False`, so "active actor" misdescribes the helper's admission rule to a reader comparing it with `_guardian_inactive_actor`.
**Fix:** Say what the code does: "Overrides cv_has_access() to return True for every actor that is not an inactive authenticated user (anonymous actors included; their configured anonymous behavior applies at request time) when the permission key is present — the list page is always accessible; queryset filtering is the sole gate."
