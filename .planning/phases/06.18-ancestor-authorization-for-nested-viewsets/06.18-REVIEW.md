## Summary

Reviewed the ancestor-authorization feature against `016d402a..HEAD`. The 20 production files under `src/` were
read in full (the three new modules `ancestors.py`, `ancestor_policy.py`, `ancestor_db.py` and
`crud_views_guardian/lib/ancestors.py`) or as full diffs with surrounding context (`view/base.py`,
`viewset/__init__.py`, Guardian mixins/views/viewset, manage, delete/create/action/mixins, workflow, polymorphic,
checks, settings, templates). The adversarial focus was authorization bypasses, work performed before the ancestor
gate, queryset scoping leaks, database-alias boundary gaps and read/write classification.

What was traced and found sound:

- **Gate order.** Every shipped composition reaches `_authorize_ancestors` at its first `dispatch`
  (`CrudView`, `CrudViewPermissionRequiredMixin`, `GuardianParentPermissionMixin`, `ManageView`); the Django
  `PermissionRequiredMixin.has_permission()` object/state load now runs after ancestry. Outermost-inward
  resolution gates each selected level before the next lookup (`ancestors.py:417-428`); denial raises before any
  deeper queryset; a filtered-out or mismatched ancestor is 404 (`_resolve_ancestor` constrains to the resolved
  outer ancestor so a `get_queryset` override cannot waive the relationship).
- **Leaf scoping.** `CrudView.get_object` validates the reached child against the resolved parent (FK by stored
  key, M2M/reverse by one `exists()`), and `get_context_data` scopes both `self.object_list` and the django-filter
  `object_list` keyword. 404 precedes the Guardian object 403 in `GuardianObjectPermissionMixin.get_object`.
- **Classification.** `CustomFormView`/`WorkflowView` inherit Django's `generic.DetailView`, not the core
  `DetailView`, so they stay unclassified and require an exact `actions` entry; `ObjectDetailView`,
  polymorphic detail/create and `GuardianManageView` inherit classified cores; `PolymorphicCreateSelectView`
  carries the `_cv_ancestor_operation = "write"` marker. An unknown marker value fails closed.
- **Providers.** Core model gate is `user.has_perm(permission)`; the Guardian gate denies inactive actors
  before any shortcut, accepts the model permission only with the ancestor's own `accept_global_perms`, and
  guardian's `ObjectPermissionChecker.has_perm` strips the `app_label.` prefix (verified in the installed
  guardian `core.py:80-82`). `provider="guardian"` on a core ViewSet and `accept_global_perms` on a non-Guardian
  provider are rejected before registry insertion.
- **Database boundary.** `queryset.db` is read without evaluation for ancestors, child objects and consumed
  collections; writes are checked after object/form-instance resolution and again at the write wrapper; the delete
  alias is re-checked on every consumption. Auth-record checks precede the vocabulary read at both gate call
  sites. No alias is rerouted anywhere.
- **Validation/registry.** Construction-decidable policy constraints run inside `register()` before
  `_REGISTRY` insertion and manage-view creation; removed Guardian parent fields are rejected from constructor
  keys and subclass declarations in a `mode="before"` validator.
- **Docs.** Every documented API name (`AncestorPolicy`, `AncestorPermissions`, re-exported from
  `crud_views.lib.viewset`), setting (`CRUD_VIEWS_ANCESTOR_PERMISSION_CASCADE/_READ_PERMISSIONS/_WRITE_PERMISSIONS`),
  check ID (`viewset.E261/E266/E267/E268`) and manage context key matches the source; all twelve cross-page
  anchors used by the new sections resolve to existing headings. The CHANGELOG Breaking entry is paired with
  the anchored `docs/migrating-1.0.md` section as CLAUDE.md requires.
- **Tests.** No test in the 40 listed modules matches an always-pass pattern (`assert True`, bare
  `pytest.raises(Exception)`, skipped/xfail, assertion-free bodies). The widened shared `user_book_*` fixtures
  (now holding Publisher `view`/`change`) were checked against their consumers; no assertion about Publisher
  access relies on those users lacking it.

## Warnings

### WR-01: Guardian compositions run actor admission before static validation (D-32 / documented order)

**File:** `src/crud_views_guardian/lib/mixins.py:353-364`
**Issue:** `GuardianParentPermissionMixin.dispatch` denies anonymous (`_guardian_deny_anonymous`) and inactive
(`PermissionDenied`) actors at lines 355-358 and only then calls `self._cv_ancestor_guard()` at line 362. The
engine's static steps — `_validate_ancestor_structure`, `_validate_action_declarations`,
`_operation_requirements` (`src/crud_views/lib/ancestors.py:403-407`) — therefore run *after* actor admission
for every shipped Guardian composition. CONTEXT D-32 and the "Request sequence" section put static validation
first, and `docs/reference/nested.md:400-412` publishes that order for "plain and `*PermissionRequired` views,
Guardian views and manage pages". Observable effect: a nested Guardian ViewSet with an unregistered `actions`
key, a missing exact entry or an unsupported relationship answers anonymous/inactive requests with a login
redirect/403/404 instead of `ImproperlyConfigured`, so the misconfiguration surfaces only to active authenticated
actors. The existing regression `tests/test1/test_ancestor_actors.py:567`
(`test_static_configuration_error_precedes_actor_admission`) parametrizes only the core `act`/`pact` kinds, so
the deviation is untested. The mixin's own `_cv_ancestor_actor_response` (line 366-368) already returns the
identical Guardian response, which is why the comment there says the dispatch checks are "kept so every bridge
sees the same answer" — the duplication is what produces the wrong order.
**Fix:** For nested views let the guard own actor admission (it calls the Guardian adapter); keep the explicit
checks only for the top-level branch, where the guard does nothing:
```python
def dispatch(self, request, *args, **kwargs):
    self._guardian_validate_child_composition()
    if self.cv_viewset.parent is not None:
        # static validation, then Guardian's actor rules via _cv_ancestor_actor_response, then ancestry
        response = self._cv_ancestor_guard()
        if response is not None:
            return response
        if not self.cv_object and not self.cv_action_enabled(request.user, _resolved_parent(self)):
            raise PermissionDenied
        return super().dispatch(request, *args, **kwargs)
    if not request.user.is_authenticated:
        return self._guardian_deny_anonymous()
    if _guardian_inactive_actor(request.user):
        raise PermissionDenied
    return super().dispatch(request, *args, **kwargs)
```
Add `"guardian"` and `"gobject"` kinds to `test_static_configuration_error_precedes_actor_admission` so the
order is pinned for Guardian compositions too.

### WR-02: Leaf seams and parent reuse fail open when reached inside a request before the guard has run

**File:** `src/crud_views/lib/ancestors.py:451-458` (also `461-482`, `485-497`) and
`src/crud_views/lib/view/base.py:1120-1132`
**Issue:** `_child_edge` returns `None` whenever `_cv_ancestor_state` is absent, and both
`_validate_child_parent` and `_scope_child_queryset` then return the object/queryset unchanged.
`cv_get_parent_object` likewise falls back to `get_object_or_404(parent_model, pk=pk)` — the unscoped model
manager, bypassing the ancestor ViewSet's `get_queryset` visibility rules. The `None` path is needed for
class-level/outside-request helpers, but it is indistinguishable from "inside a request and the guard has not
run yet". That state is reachable: any mixin placed before the four bridges whose `dispatch` loads the object
(e.g. `UserPassesTestMixin` with a `test_func` that calls `self.get_object()` or `cv_get_parent_object()`) reads
an unvalidated child or an unscoped parent before ancestry is authorized, and can turn that into a response
(403 from `test_func` vs. continue) before the guard denies. No shipped composition does this (the ordering
inventory in `tests/test1/test_ancestor_ordering.py` asserts each shipped MRO's first `dispatch`), so this is
defense in depth for the custom compositions the docs invite, but the package's own invariant ("ancestry
succeeds before child lookup", CONTEXT step 5) is currently enforced only by convention for them.
**Fix:** Fail closed when a nested ORM view that is already inside a request reaches a seam without guard
state, keeping the `None` path for class-level calls:
```python
def _child_edge(view):
    viewset = view.cv_viewset
    if viewset is None or viewset.parent is None or viewset.is_resource:
        return None
    state = getattr(view, "_cv_ancestor_state", None)
    if state is None:
        if getattr(view, "request", None) is not None:
            raise ImproperlyConfigured(
                f"ViewSet {viewset.name!r} view {view.cv_key!r}: the ancestor guard has not run for this request; "
                "a mixin placed before CrudView must not load objects in dispatch() before super().dispatch()"
            )
        return None
    return viewset.parent.get_attribute(), state.parent
```
Apply the same `request is not None and state is None` guard in `CrudView.cv_get_parent_object` before the
`get_object_or_404` fallback. Add one test with a pre-bridge mixin that calls `get_object()` in `dispatch` and
assert `ImproperlyConfigured` with no ancestor query.

### IN-01: Already-defended-elsewhere — `_check_nested_write` re-tests `_is_nested_orm` after its only caller did

**File:** `src/crud_views/lib/ancestor_db.py:105`
**Category:** necessity
**Issue:** `_check_nested_write` returns early on `not _is_nested_orm(view)`. Its only call site,
`CrudView._cv_check_nested_write` (`src/crud_views/lib/view/base.py:373-381`), already returned on the same
predicate three lines earlier; no other caller exists in `src/` or `tests/`. Info rather than Warning because the
helper is documented in the module docstring as the boundary API and may legitimately gain direct callers.
**Fix:** Either drop the inner check and document the precondition in the docstring, or drop the outer early
return and let the helper own it (it already needs `view` for the error message). One owner, not two.

### IN-02: Effective-default expressions duplicated between manage diagnostics and the engine

**File:** `src/crud_views/lib/views/manage.py:150-165`
**Issue:** `get_ancestor_policy_data` recomputes "declared `None` → global setting" for cascade, read and write
(`crud_views_settings.ancestor_permission_cascade if cascade is None else cascade`,
`policy.read or crud_views_settings.ancestor_read_permissions`, ...). The same rules live in
`src/crud_views/lib/ancestors.py:323-326` (`_operation_requirements`) and `:340-342` (`_selected_gates`). Plan 09's
summary records this as a known duplication left because `ancestors.py` was outside its file list. If either side
changes (for example a per-ViewSet default), the manage page would report a policy the engine does not apply.
**Fix:** Add `_effective_cascade(viewset)` and `_effective_pair(viewset, family)` to `ancestors.py`, use them
from `_operation_requirements`/`_selected_gates`, and have `get_ancestor_policy_data` call the same helpers.
