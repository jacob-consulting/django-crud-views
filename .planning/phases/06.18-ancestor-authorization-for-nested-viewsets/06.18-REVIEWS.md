## 06.18-01

**Summary.** The tracer is well aimed: one engine, invoked from `CrudView.dispatch`, with policy types exported from `crud_views.lib.viewset` and settings validated without importing ViewSet. The plan correctly identifies where registration side effects begin. Its main weakness is sequencing honesty: once the engine is wired into `CrudView.dispatch` for every nested ViewSet, a large part of the existing suite goes red until plans 02.3 and 03, and the plan's verify command never looks at it.

**Strengths.**
- Pre-side-effect placement is right: `_REGISTRY[self.name] = self` at `viewset/__init__.py:151` and manage creation at 154-156 are the only mutations; validating above line 146 keeps Guardian's `super().register()` path (`guardian/lib/viewset.py:68`) safe.
- `cv_get_parent_object()` is today an unfiltered `get_object_or_404(parent_model, pk=pk)` (base.py:1028-1040); reusing the resolved identity there is the correct D-51 seam, and `CreateViewParentMixin.cv_form_valid` already flows through it (`src/crud_views/lib/views/create.py:91`).
- Baseline capture before any `src` edit matches v2's "measure against current baseline" requirement, and `database_routes`/registry-restore patterns already exist (`conftest.py:136-169`, `test_guardian_parent_none.py:26-60`).

**Concerns.**
- **HIGH — interim breakage of Guardian suites.** Plan 01 gives `ViewSet._ancestor_provider` a `model` default and touches no Guardian file. `GuardianViewSet` inherits that default, so from wave 1 to wave 3 every nested Guardian request (`cv_guardian_book`, the `pn`/matrix dynamic fixtures) is gated on a **model** permission on the parent while the old object gate at `mixins.py:384-396` still runs. Those tests grant object permissions only (`tests/lib/helper/guardian.py` via `user_guardian_object_perm`). The plan's verify runs only `test_ancestor_authorization.py`, so the executor will not see this; the `<verification>` text says to re-run affected regressions, which will be red with no instruction on what is expected.
- **MEDIUM — the "denied actor never reaches child queryset" claim holds for lists only.** For object views the core permission phase loads the child at base.py:1086 before `CrudView.dispatch`, and `GuardianObjectPermissionMixin.get_object` (mixins.py:74-82) evaluates object grants there too. Plan 04 fixes this; plan 01's SUMMARY must not generalize the tracer evidence.
- **MEDIUM — settings failure stage is unspecified and conflicts with convention.** The plan says invalid global mappings make "fresh-import tests fail". Existing settings validation is deliberately non-raising: raw `Any` fields (`settings.py:53-56`) plus `check_messages` system-check errors (`settings.py:196-232`, consumed at `checks.py:26`). v2 asks for "structural validation error" without naming the stage. Pick one: a system-check Error plus `ImproperlyConfigured` at the reached gate matches the codebase; an import-time raise would break `manage.py check` itself.
- **LOW — no plain nested list exists in the shared app.** `BookListView` is `ListViewPermissionRequired` (`tests/test1/app/views.py:410`); a plain child needs a dynamic ViewSet fixture, which `files_modified` does not mention (fine if done inside the new test module, as `test_guardian_parent_none.py:26-60` does).
- **LOW — estimate.** Two tasks at 26k tokens cover: two Pydantic models, settings fields, the engine, a model provider, dispatch wiring, `cv_get_parent_object` reuse, registry/URL fixtures, three-ancestor dynamic models with `schema_editor` (precedent `test_delete_migration_docs.py:143`), and a 24-cell baseline. Confidence is already marked low; expect overrun.

**Suggestions.**
- Add a minimal Guardian provider in plan 01 (a `_ancestor_provider = "guardian"` class attribute and a `_ancestor_has_permission` that wraps `ObjectPermissionChecker`, roughly ten lines in `crud_views_guardian/lib/viewset.py`), leaving fallback, bridge replacement and field removal to plan 03. This keeps the Guardian suites green across waves 1–2.
- Alternatively, list the expected-red modules per wave in each plan's `<verification>` so an executor does not "repair" them by granting permissions (plan 02.3 explicitly forbids that, but only from wave 2 on).
- State the settings failure stage explicitly (recommend `check_messages` Error with a new ID, plus `ImproperlyConfigured` when a nested request reads an invalid pair).

**Risk.** MEDIUM. The design is right; the sequencing gap is the risk.

**Concerns.**
- **MEDIUM — Resource-parent runtime guard duplicates an existing check.** `E261` already reports a Resource parent (`viewset/__init__.py:216-225`). The new runtime `ImproperlyConfigured` is required by v2, but the plan should reuse E261 rather than mint a second ID, and the walk should not re-report it.

Dynamic fixtures in `test_guardian_policy.py`/`test_authorization_matrix.py` are where custom nested views live, and those belong to plan 08.

**Suggestions.**
- Name the check IDs now (E26x range is in use at 260/261/262; W280 exists) and record them in ACCEPTANCE rather than "unused IDs selected during execution".
- Extend Task 3's verify to the five extra consumer modules above.

**Risk.** LOW–MEDIUM. Mostly mechanical; the check-timing question is the one design decision to settle.

## 06.18-07

**Summary.** This plan extends the default-only contract to authorization records. It is the most over-engineered plan in the set: three tasks across eight files to instrument every auth consumer, for a contract whose only outcome is "raise if not default". The threat is real, but the surface can be far smaller.

**Strengths.**
- The route inventory source is correct: `default_permissions` queries ContentType/Permission (`viewset/__init__.py:458-467`; Guardian variant `guardian/lib/viewset.py:86-98`), manage queries user/group permission joins (manage.py:41-72) and `GroupObjectPermission` (guardian views.py:420-452), and `_PermittedPks` in the delete projection enumerates Guardian tables.
- "Do not import the delete preview engine" is the right boundary.
- Higher-ancestor gates in nearest-only mode must not touch vocabulary; the spy approach proves it.

**Concerns.**
- **MEDIUM — scope/maintainability.** v2 lists this as one acceptance row ("Database boundary"). Plans 06 and 07 together budget ~52k tokens and touch `base.py`, `viewset/__init__.py`, Guardian `ancestors.py`, `mixins.py`, `views.py`, `manage.py`. The project's hard constraint is developer maintainability; a route guard woven into every local Guardian consumer is the opposite. The factual check is DB-free (`router.db_for_read(Model)` plus `queryset.db`), so one request-local helper evaluated once at the first reached permission gate, for the fixed set {ContentType, Permission, User, Group, UserObjectPermission, GroupObjectPermission, the Guardian direct-FK models if configured}, satisfies the contract without instrumenting each consumer.
- **MEDIUM — cached vocabulary.** `_default_permissions` is cached for the process after first non-empty read (`viewset/__init__.py:452-470`). A nested request after a warm cache executes no vocabulary query, so "reject before cached vocabulary" can only mean "consult the router anyway". Fine, but say so; otherwise an executor may try to invalidate the cache, which Phase 6.2 deliberately avoided (#151 note at 447-450).
- **LOW — Task 2 and Task 3 overlap** (both wire `_check_nested_auth` into "early actor" and "local permission" consumers, one for Guardian/manage, one for core). Merge them.

**Suggestions.**
- Reduce to one task: a single `_check_nested_auth(view, actor)` called once by the engine at the first selected gate and once by the local permission bridge, plus the manage holders query. Keep tests for colliding IDs and no default-copy retry.

**Risk.** MEDIUM. Not a correctness risk; a complexity and blast-radius risk.

## Cross-plan assessment

**Dependency ordering.** Waves are strictly sequential through 09 and the file-ownership table is consistent with the plans. The real ordering issue is not between plans but *inside the red windows the sequence creates*:

| Window | Cause | Modules affected | Fixed by |
|---|---|---|---|
| Waves 1–2 | Engine active for all nested ViewSets; Guardian has no provider yet | all Guardian nested suites; 7 `client_user_book_*` consumers; 19 nested-URL modules | 02.3 (core), 03 (Guardian) |
| Waves 3–7 | Legacy fields removed | 9 legacy-field modules fail at fixture construction/`monkeypatch.setattr` | 08 |

Both windows are survivable because each plan's verify is narrow, but neither is written down, and the generic "re-run directly affected regressions" instruction will show failures the executor is told not to "fix" by granting permissions only from plan 02 onward. Mitigation is cheap: a ten-line Guardian provider in plan 01 and mechanical fixture rewrites in plan 03.

**Scope and over-engineering.** Plans 06+07 (five tasks, ~52k tokens, eight production files) implement one acceptance row whose only outcome is "raise on non-default". This collides with the project's hard maintainability constraint more than any other part of the phase. Recommend collapsing to one data-alias helper and one auth-route helper, each called from at most two seams.

**Security.** Threat coverage maps to v2's acceptance rows and the plans consistently demand ordered event evidence, not status codes. The one gap: plan 04's "no queries before actor admission" is not literally true for permission-required all-none paths (vocabulary lookup at `viewset/__init__.py:459-461`); phrase the acceptance as "no ancestor or child queries".

**Performance.** Baseline-before-edit and the 24-cell matrix are the right instruments. Expect the measured delta to be: +1 query per ancestor level (scoped lookup) plus the Guardian checker's own grant queries per selected gate; the plans correctly refuse to promise a budget.

**Do the plans achieve the phase goal?** Yes, if executed as written with the two sequencing fixes above. Every v2 acceptance row has a named owner in ACCEPTANCE.md and the owners' source premises are accurate. The main delivery risks are (1) the undocumented red windows, (2) the plan 07 blast radius, and (3) estimate pressure on plan 01, which carries engine, policy types, settings, fixtures, dynamic three-level chains and a 24-cell baseline in two tasks.

**Overall risk: MEDIUM.** No plan rests on a false premise about the codebase. The design-level risk is concentrated in sequencing (01→03, 03→08) and in the database-boundary plans' surface area; both are fixable before wave 1 starts.
