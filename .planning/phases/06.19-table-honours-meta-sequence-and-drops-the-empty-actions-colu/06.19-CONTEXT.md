# Phase 06.19: Table honours Meta.sequence and omits the Actions column for `cv_list_actions = None` (#337) - Context

**Gathered:** 2026-11-09
**Status:** Ready for planning

<domain>
## Phase Boundary

`crud_views.lib.table.Table` respects a subclass's `Meta.sequence` (appending `actions` last unless the sequence
names it) and omits the `actions` column when the owning list view declares `cv_list_actions = None`. Tables without a
`Meta.sequence` keep today's column order; an empty list keeps today's empty column. No per-user permission work
happens during table construction. Deliverables: the `Table` change, one test module, one `### Changed` changelog
entry, a docs subsection in `docs/reference/list_view.md`, and the Resource docs example switched to `None`.

GitHub issue: [#337](https://github.com/jacob-consulting/django-crud-views/issues/337). Origin: tabler-test finding 26.

</domain>

<decisions>
## Implementation Decisions

### Carried forward from the plan's GSD handoff (approved 2026-11-09, unchanged)
- **D-01:** `Table.__init__` stops forcing `sequence=("...", "actions")`. When no `sequence` kwarg is passed and the
  class declares a non-empty `Meta.sequence`, that sequence is used with `"actions"` appended unless it already names
  `"actions"`. A middle `"..."` is fine: `actions` still lands last.
- **D-02:** Without a `Meta.sequence` the historical default `("...", "actions")` is kept exactly, so every existing
  table renders in the same order as today (no table in `src/`, `tests/`, `docs/` declares `Meta.sequence`).
- **D-03:** A caller-supplied `sequence` kwarg wins unchanged.
- **D-04:** The actions-column decision is static (a class attribute of the view), never per user. Hiding the column
  when every configured action is inaccessible to the current user is out of scope (maintainability rule, CLAUDE.md).
  The docs state this limit explicitly.
- **D-05:** `exclude` is merged, not replaced: django-tables2 evaluates `exclude or Meta.exclude`, so the
  implementation merges `Meta.exclude`, any caller `exclude` kwarg and `"actions"` (order-preserving dedupe).
- **D-06:** `Meta.exclude = ("actions",)` stays the table-side manual opt-out. No new attribute or setting.
- **D-07:** Classification: behaviour change, not breaking. `### Changed` under `## Unreleased`; no `### Breaking`,
  `docs/migrating-1.0.md` untouched.
- **D-08:** Two small helpers on `Table`, `cv_default_sequence()` (classmethod) and `cv_exclude_actions(view)`
  (staticmethod), keep the rules independently testable. No new module, mixin or setting. `order_actions` untouched.
- **D-09:** Tests construct `Table` subclasses directly with a `SimpleNamespace` view stub plus one end-to-end test on
  `/author/` using `monkeypatch.setattr` on `AuthorListView.cv_list_actions`. No new ViewSets or views are registered
  (the registry-leak pattern that broke PR #336's CI).

### Opt-out semantics (decided in this discussion; supersedes the plan's "Empty actions column" paragraph)
- **D-10:** `cv_list_actions = None` on the owning view is the explicit opt-out: the `actions` column is excluded.
  `Table.cv_exclude_actions(view)` returns `True` only when `getattr(view, "cv_list_actions", <missing>) is None`.
  A view stub or non-crud view without the attribute keeps the column.
  — **Reversibility:** costly — once documented, `None` is a public contract for list views and the Resource docs
  example; flipping back to `[]` would be a second public change of the same name before 1.0.0.
- **D-11:** An empty list keeps the column exactly as today, whether written on a view (`cv_list_actions = []`) or
  inherited from `CRUD_VIEWS_LIST_ACTIONS = []` (copied onto `ListView.cv_list_actions` at import). A project-wide
  empty setting must not remove the column; the user rejected that as unintended. Because the setting value and a
  view-written `[]` are indistinguishable on the class, `None` carries the explicit meaning instead.
- **D-12:** Rationale recorded for downstream agents: nothing in the package resolves `None` to the setting today.
  `cv_resolved_actions` iterates `keys or []`, so on a list view `None` and `[]` both already render an empty column.
  The plan's statement that `None` "means the settings default" described an intent, not behaviour, and is retired.
- **D-13:** No system check or warning for `cv_list_actions = []` (option rejected). No change to `ListView`'s
  class-level default, to `cv_resolved_actions`, the manage view, templates or system checks.
- **D-14:** `docs/reference/resources.md` (the `PublisherFileListView` example, currently `cv_list_actions = []`)
  switches to `cv_list_actions = None` so readers see the column disappear. Test-app views that use `[]` stay as
  they are unless a test asserts on the column. Existing ancestor tests with `cv_list_actions = []` keep rendering
  an empty column and need no change.
