## Warnings

### WR-01: `Meta.sequence` without `"..."` places `actions` before the unlisted columns

**File:** `src/crud_views/lib/table/table.py:34-39`
**Issue:** `cv_default_sequence` returns `(*declared, "actions")`. When `declared` has no `"..."`, django-tables2's
`Sequence.expand` (`django_tables2/utils.py`, `elif ellipses == 0: self.append("...")`) appends the ellipsis
*after* `actions`, so every column the author did not list lands after the actions column. Verified against
django-tables2 3.0.1:

```text
Meta.sequence = ("last_name",)               -> ['last_name', 'actions', 'id', 'first_name']
Meta.sequence = ("last_name", "first_name")  -> ['last_name', 'first_name', 'actions', 'id']
```

Naming only the leading columns and letting the rest follow is the standard django-tables2 way to write
`Meta.sequence`. The changelog bullet ("appends the `actions` column after it"), the docs subsection
(`docs/reference/list_view.md:102-105`) and D-01 ("`actions` still lands last") all promise the historical
"actions last" placement for this input. The test module covers a leading, a middle and an absent ellipsis but
never a sequence with no ellipsis at all, which is why the case was not caught.
**Fix:**

```python
@classmethod
def cv_default_sequence(cls) -> tuple[str, ...]:
    declared = tuple(cls._meta.sequence or ())
    if not declared:
        return ("...", "actions")
    if "actions" in declared:
        return declared
    if "..." not in declared:
        declared = (*declared, "...")  # django-tables2 would append it after actions otherwise
    return (*declared, "actions")
```

Add a test alongside `MiddleEllipsisTable`:

```python
class NoEllipsisTable(PlainTable):
    class Meta:
        sequence = ("last_name",)


def test_meta_sequence_without_ellipsis_keeps_actions_last():
    table = NoEllipsisTable(ROWS, view=_view(["detail"]))
    assert _names(table) == ["last_name", "id", "first_name", "actions"]
    assert NoEllipsisTable.cv_default_sequence() == ("last_name", "...", "actions")
```

### WR-02: Caller `exclude=None` raises `TypeError` when the view has `cv_list_actions = None`

**File:** `src/crud_views/lib/table/table.py:52`
**Issue:** `(*self._meta.exclude, *kwargs.get("exclude", ()), "actions")` uses `kwargs.get("exclude", ())`, which
only substitutes `()` when the key is *absent*. django-tables2's `Table.__init__` signature declares
`exclude=None` as the default (`django_tables2/tables.py:259`) and treats `None` as "no exclusion"
(`exclude or self._meta.exclude`, line 282), so passing `exclude=None` explicitly is a legitimate call that worked
before this phase. It now fails:

```text
PlainTable(ROWS, view=_view(None), exclude=None)
-> TypeError: Value after * must be an iterable, not NoneType
```

The failure is conditional on the view's `cv_list_actions`, so a table that renders fine under one list view
crashes under another.
**Fix:** Mirror django-tables2's own falsy handling (this also sets up the WR-03 normalisation):

```python
if self.cv_exclude_actions(kwargs.get("view")):
    caller = kwargs.get("exclude") or ()
    if isinstance(caller, str):
        caller = (caller,)
    # django-tables2 uses `exclude or Meta.exclude`, so merge both sources instead of replacing them
    merged = (*self._meta.exclude, *caller, "actions")
    kwargs["exclude"] = tuple(dict.fromkeys(merged))
```

Add `PlainTable(ROWS, view=_view(None), exclude=None)` to `test_exclude_kwarg_is_merged_with_actions_exclusion`
and assert the names are `["id", "first_name", "last_name"]`.

### WR-03: Caller `exclude="column"` string is splatted into characters, silently dropping the exclusion

**File:** `src/crud_views/lib/table/table.py:52-53`
**Issue:** django-tables2 documents the `exclude` argument as `iterable or str` (`django_tables2/tables.py:201`)
and honours a bare string upstream because `BoundColumns` tests membership with `name not in self._table.exclude`
(`django_tables2/columns/base.py:753`), which is a substring test on a `str`. The new merge iterates the value
with `*`, so `"first_name"` becomes `('f', 'i', 'r', 's', 't', '_', 'n', 'a', 'm', 'e', 'actions')` and the
column the caller asked to hide is rendered again. Verified:

```text
PlainTable(ROWS, view=_view(["detail"]), exclude="first_name")  -> ['id', 'last_name', 'actions']   (upstream, hidden)
PlainTable(ROWS, view=_view(None),       exclude="first_name")  -> ['id', 'first_name', 'last_name'] (merged, exposed)
```

The threat register entry T-06.19-02 ("the `exclude` merge must not drop a `Meta.exclude` or caller `exclude` the
author relied on, which could re-expose a deliberately hidden column") names exactly this outcome; the pinned
tests only cover the tuple form. `Meta.exclude` is not affected: `TableOptions._check_types` rejects a `str`
there (`tables.py:164`).
**Fix:** Normalise a `str` to a one-tuple before merging (see the snippet in WR-02), and add a test:

```python
def test_exclude_kwarg_as_string_still_hides_the_column():
    table = PlainTable(ROWS, view=_view(None), exclude="first_name")
    assert _names(table) == ["id", "last_name"]
```

### IN-02: The `None` opt-out is scoped to "a list view" in the docs, but `CrudView` defaults `cv_list_actions` to `None` for every view

**File:** `src/crud_views/lib/table/table.py:42-45`; `CHANGELOG.md:381-386`; `docs/reference/list_view.md:117`
**Issue:** `cv_exclude_actions` keys off `view.cv_list_actions is None`. `ListView` overrides the attribute with the
setting (`src/crud_views/lib/views/list.py:27`), but the `CrudView` base default is `None` (`base.py:100`), so any
non-list `CrudView` (a detail or update view embedding a child `Table` with `view=self`) now drops the actions
column implicitly rather than by declaration. The behaviour is arguably right (`cv_get_list_action_group` would
render an empty cell there anyway), but the changelog and the docs describe the switch only for "a list view with
`cv_list_actions = None`" and the helper docstring says the view "declares" it. No such non-list construction site
exists in `src/`, `tests/` or `docs/` today, so this is a documentation gap, not a defect.
**Fix:** Add one sentence to the docs subsection and the docstring: "Views other than `ListView` inherit
`cv_list_actions = None` from `CrudView`, so a `Table` rendered by such a view has no actions column unless the
view sets `cv_list_actions`."
