## Summary

Review of the re-scoped phase 06.19 as it stands at HEAD relative to `e35a6b66~1` (net diff of the revert
`e35a6b66`, the failing test `e95730d0`, the one-line fix `6bf4cc35` and the docs commit `560bd2a6`). This report
replaces the earlier 06.19-REVIEW.md, which covered the reverted `cv_default_sequence` / `cv_exclude_actions`
design.

The code change is a single condition in `Table.__init__` (`src/crud_views/lib/table/table.py:31-33`): the default
`sequence=("...", "actions")` is supplied only when the caller passes no `sequence` kwarg *and* the class declares
no `Meta.sequence`. Cross-file tracing confirms the only production construction site is
`ListViewTableMixin.get_table_kwargs` returning `{"view": self}` (`src/crud_views/lib/views/mixins.py:302-303`); no
code in `src/`, `tests/test1/app` or the docs passes `sequence` or `exclude`, and no in-repo `Table` subclass
declares a `Meta.sequence`, so the change has no in-repo callers beyond the new test module. The condition is correct
against the installed django-tables2 3.0.1: `TableOptions.sequence` defaults to `()` (`tables.py:149`),
`Table.__init__` prefers a non-`None` `sequence` kwarg, then a truthy `Meta.sequence`, then `"..."`
(`tables.py:332-340`), and `BoundColumns.iteritems` filters `self._table.exclude` while walking the expanded
sequence (`columns/base.py:752-754`), which is what makes `Meta.exclude = ("actions",)` work even though the default
sequence still names `actions`.

Every docs claim was executed against django-tables2 3.0.1 (probe script, `PYTHONPATH=src`):

| Claim | Observed | Verdict |
|---|---|---|
| No `Meta.sequence` → declaration order, `actions` last | `['id', 'first_name', 'last_name', 'actions']` | true |
| `Meta.sequence = ("last_name", "...", "actions")` used as written | `['last_name', 'id', 'first_name', 'actions']` | true |
| Sequence that leaves `actions` out → `actions` first among unlisted columns | `("last_name", "...")` → `['last_name', 'actions', 'id', 'first_name']` | true (`actions` is the parent-declared column, so it leads `base_columns`) |
| Same for a sequence without `"..."` | `("last_name",)` → `['last_name', 'actions', 'id', 'first_name']` | true (django-tables2 appends `"..."`) |
| `Meta.exclude = ("actions",)` removes the column | `['id', 'first_name', 'last_name']` | true |
| `Meta.sequence` naming `actions` + `Meta.exclude = ("actions",)` in the same `Meta` (FAQ) | `['last_name', 'id', 'first_name']` | true |
| `actions = None` on the subclass "is not supported" | `KeyError: 'actions'` raised from `BoundColumns.iteritems` | true, but the failure mode is an opaque crash (WR-01) |
| `cv_list_actions = []` empties the column but keeps it | `cv_resolved_actions` iterates `keys or []` (`base.py:758`) | true |

Not covered by any docs claim but relevant for upgraders: django-tables2 does **not** inherit `Meta` — a subclass of
a sequenced table without its own `Meta` has `_meta.sequence == ()` and therefore gets the default
`("...", "actions")` back (IN-02); and the Fixed changelog entry no longer tells users whose previously ignored
`Meta.sequence` lacks `"actions"` that the Actions column will move (WR-02).

The four new tests pass (`pytest tests/test1/test_table_meta.py`, 4 passed). No necessity findings: the
`"sequence" not in kwargs` branch guards a public constructor kwarg (a documented extension point for
`get_table_kwargs` overrides), not an impossible state. The implementation respects the CLAUDE.md maintainability
rule; none of the findings below recommend re-adding the reverted convenience logic.

## Warnings

### WR-01: `actions = None` on a subclass crashes with an opaque `KeyError` from inside django-tables2

**File:** `src/crud_views/lib/table/table.py:31-33`, `docs/reference/list_view.md:121`
**Issue:** `actions = None` is django-tables2's documented idiom for removing an inherited column (the metaclass pops
it from `base_columns`, `django_tables2/tables.py:86-88`). On a `Table` subclass it still passes class creation and
construction, then the default `sequence=("...", "actions")` is expanded into `_sequence`, and the first iteration
of `table.columns` (template render) raises `KeyError: 'actions'` at `django_tables2/columns/base.py:754`
(verified). The new docs sentence "setting `actions = None` on the subclass is not supported" is accurate, but it
names neither the symptom nor the reason, so a user who hits the traceback has nothing to search for. This is
pre-existing behaviour (the pre-phase `__init__` injected the same default unconditionally), but this phase is the
one that documents the case as unsupported.
**Fix:** Minimum, in line with the "document unsupported cases explicitly" rule: name the symptom in both docs
locations, e.g. in `list_view.md`:

```markdown
Remove the column only with `Meta.exclude`: setting `actions = None` on the subclass is not supported and fails at
render time with `KeyError: 'actions'`, because the default sequence still names the column.
```

Optional, if the developer prefers the idiom to work rather than be documented away (one clause, no new helper):

```python
if "sequence" not in kwargs and not self._meta.sequence and "actions" in self.base_columns:
    kwargs["sequence"] = ("...", "actions")
```

### WR-02: Changelog "Fixed" entry drops the upgrade consequence for existing `Meta.sequence` declarations

**File:** `CHANGELOG.md:420-422`
**Issue:** Before this fix every `Meta.sequence` on a `Table` subclass was a silent no-op, so projects may carry one
that never named `"actions"` (e.g. `("last_name", "...")`). After upgrading that sequence takes effect and, as
verified above, the Actions column moves from last to the front of the unlisted columns
(`['last_name', 'actions', 'id', 'first_name']`). The reverted "Changed" entry stated "A `Meta.sequence` that was
silently ignored before now takes effect"; the replacement under "Fixed" says only "Name `"actions"` in a declared
sequence", which reads as guidance for new code, not as a heads-up that existing layouts change. `docs/migrating-1.0.md`
does not mention it either.
**Fix:** Add one sentence to the entry so the user-visible change is explicit:

```markdown
- **`Table` honours `Meta.sequence`.** A `Table` subclass's `Meta.sequence` was silently replaced by the
  default `("...", "actions")`; it is now used as written. Tables without a `Meta.sequence` keep `actions` last.
  An existing `Meta.sequence` that does not name `"actions"` now takes effect and places the Actions column first
  among the columns it does not list; add `"actions"` where you want it. Remove the column with
  `Meta.exclude = ("actions",)`. (#337)
```

If the developer judges this a layout break rather than a fix, move it to `### Changed` or `### Breaking`; the
latter also requires a `docs/migrating-1.0.md` entry per CLAUDE.md.

### WR-03: Resource example now renders an empty Actions column, contradicting the FAQ it sits next to

**File:** `docs/reference/resources.md:454-470`
**Issue:** The example was changed from `cv_list_actions = None  # no row actions: the Actions column is omitted`
to a bare `cv_list_actions = []`. With the reverted column-removal logic gone, `[]` leaves an empty "Actions"
header on every row of a read-only `PublisherFile` list — exactly the case the new FAQ entry ("To drop the Actions
column, for example on a read-only list, exclude it in the same `Meta`") tells users to avoid. `PublisherFileTable`
(`resources.md:455-456`) declares no `Meta`, and the comment explaining the intent was removed, so the example now
demonstrates the empty-column anti-pattern without saying so.
**Fix:** Apply the documented table-side opt-out in the example and keep a comment:

```python
class PublisherFileTable(Table):
    key = tables.Column()

    class Meta:
        exclude = ("actions",)  # read-only list: no Actions column


class PublisherFileListView(ResourceViewMixin, ListViewTableMixin, ListView):  # Read: Publisher view
    cv_viewset = cv_publisher_file
    table_class = PublisherFileTable
    cv_list_actions = []  # no row actions
```

## Info

### IN-01: An explicit `sequence=None` kwarg bypasses the default, unlike django-tables2's own precedence

**File:** `src/crud_views/lib/table/table.py:31`
**Issue:** django-tables2 treats `sequence=None` as "not passed" (`if sequence is not None ... elif
self._meta.sequence ... else "..."`, `tables.py:332-340`). `Table` keys on `"sequence" not in kwargs`, so a caller
(e.g. a `get_table_kwargs` override forwarding an optional value) that passes `sequence=None` skips the default and
gets `['actions', 'id', 'first_name', 'last_name']` (verified) — `actions` first, because it is the parent-declared
column. Pre-existing; no in-repo caller passes `sequence`.
**Fix:** `if kwargs.get("sequence") is None and not self._meta.sequence:` matches the library's semantics and
keeps `test_sequence_kwarg_wins_over_meta_sequence` green.

### IN-02: Docs omit that django-tables2 does not inherit `Meta`, so a subclass loses the parent's sequence

**File:** `docs/reference/list_view.md:115-119`, `docs/faq.md:423-425`
**Issue:** `TableOptions` is built from `attrs.get("Meta", None)` of each class (`tables.py:26`), so
`class ChildTable(SequencedTable): pass` has `_meta.sequence == ()` and `Table` supplies the default
`("...", "actions")` again (verified: child renders `['id', 'first_name', 'last_name', 'actions']`; a child with
`class Meta(SequencedTable.Meta): pass` keeps the parent order). The fix is consistent with the library, but a
reader of "No `Meta.sequence`: columns render in declaration order with `actions` last" may not realise an
inherited-but-not-redeclared `Meta` counts as "no `Meta.sequence`".
**Fix:** One sentence in the `Meta.sequence` bullet: "`Meta` is not inherited by django-tables2; a subclass that
should keep the order declares `class Meta(ParentTable.Meta)`."

### IN-03: Documented ordering claims without a test

**File:** `tests/test1/test_table_meta.py:35-49`
**Issue:** The module docstring and four tests cover the default, a sequence naming `actions`, the kwarg precedence
and `Meta.exclude`. The docs additionally claim (a) a `Meta.sequence` that omits `actions` puts it first among the
unlisted columns, and (b) `Meta.sequence` naming `actions` combined with `Meta.exclude = ("actions",)` in the same
`Meta` removes the column. Both hold today (verified) but depend on django-tables2 internals (`base_columns`
ordering from the parent; `iteritems` filtering `exclude` after `expand`) that the nox matrix could surface a change
in.
**Fix:** Two small cases alongside the existing ones:

```python
class SequenceWithoutActionsTable(PlainTable):
    class Meta:
        sequence = ("last_name", "...")


def test_sequence_without_actions_puts_actions_first_among_unlisted():
    assert _names(SequenceWithoutActionsTable(ROWS, view=VIEW)) == ["last_name", "actions", "id", "first_name"]


class SequencedNoActionsTable(PlainTable):
    class Meta:
        sequence = ("last_name", "...", "actions")
        exclude = ("actions",)


def test_meta_exclude_wins_over_sequence_naming_actions():
    assert _names(SequencedNoActionsTable(ROWS, view=VIEW)) == ["last_name", "id", "first_name"]
```
