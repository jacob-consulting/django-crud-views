## Warnings

### WR-01: Explicit `sequence=None` bypasses `cv_default_sequence` while `exclude=None` is now normalised

**File:** `src/crud_views/lib/table/table.py:51-52`
**Issue:** `if "sequence" not in kwargs:` tests key presence, so a caller passing django-tables2's own default
`sequence=None` (the signature default at `django_tables2/tables.py:263`) skips the `actions`-last default
entirely. Upstream then falls back to `Meta.sequence` or `("...",)` (`tables.py:332-340`), and because `actions` is
declared on the base `Table` it is first in `base_columns`, so the actions column jumps to the first position
without appending to a declared `Meta.sequence` either. Verified against 3.0.1:

```text
PlainTable(ROWS, view=v, sequence=None)      -> ['actions', 'id', 'first_name', 'last_name']
SequencedTable(ROWS, view=v, sequence=None)  -> ['last_name', 'actions', 'id', 'first_name']
```

The 06.19-02 fix for `exclude` (`table.py:54`, "None (django-tables2's default) or any falsy value adds nothing")
deliberately treats `None` as "not supplied"; `sequence` three lines above still does not, so the two kwargs the
class intercepts now follow different rules. A downstream `get_table_kwargs()` that forwards an optional attribute
(`{"view": self, "sequence": self.table_sequence}` with a `None` default) silently gets the actions column first.
The pre-phase code had the same key-presence test, so this is not a regression, but the asymmetry is new.
**Fix:**

```python
def __init__(self, *args, **kwargs):
    if kwargs.get("sequence") is None:  # absent or django-tables2's own default: supply the actions-last default
        kwargs["sequence"] = self.cv_default_sequence()
```

Add to `test_sequence_kwarg_wins_over_meta_sequence` (or a sibling):

```python
def test_sequence_none_kwarg_uses_the_default_sequence():
    table = SequencedTable(ROWS, view=_view(["detail"]), sequence=None)
    assert _names(table) == ["last_name", "id", "first_name", "actions"]
```

and update the `cv_default_sequence` docstring ("used when the caller passes none") to say `None` or omitted.

### WR-02: `cv_default_sequence` names `actions` even when the subclass has removed the column, raising `KeyError`

**File:** `src/crud_views/lib/table/table.py:37,42`
**Issue:** django-tables2 supports removing an inherited column by redeclaring it as `None` in a subclass
(`DeclarativeColumnsMetaclass`: "Remove any columns from our remainder", `tables.py:86-89`) and by passing
`extra_columns=[("actions", None)]` (`tables.py:249-250, 320-323`). In both cases `actions` is gone from
`base_columns`, but `cv_default_sequence` still returns a sequence naming it. `Sequence.expand` does not validate
names, `Table.__init__` filters the reordered `base_columns` with `if x in base_columns` (`tables.py:346`) and so
survives, but `BoundColumns.iteritems` walks the unfiltered `self._table.sequence` and does `self.columns[name]`
(`columns/base.py:752-754`), so the first `table.columns.names()` or template render raises:

```text
class Removed(PlainTable):
    actions = None
Removed(ROWS, view=_view(["detail"]))                              -> KeyError: 'actions'
PlainTable(ROWS, view=_view(["detail"]), extra_columns=[("actions", None)])  -> KeyError: 'actions'
```

The `cv_list_actions = None` path does not crash only because `actions` is then also in `exclude` and the
`name not in self._table.exclude` test short-circuits before the lookup. The docs (`list_view.md:122-123`) steer
users to `Meta.exclude = ("actions",)`, which works (`test_meta_exclude_actions_still_works_as_manual_opt_out`),
but nothing tells a django-tables2 user that the library's usual `actions = None` idiom is unsupported on this
base class, and the failure is a bare `KeyError` far from the cause. Pre-existing (the pre-phase default
`("...", "actions")` crashed the same way), not introduced by 06.19-02.
**Fix:** Either guard the class-level removal in the helper the phase introduced:

```python
@classmethod
def cv_default_sequence(cls) -> tuple[str, ...]:
    declared = tuple(cls._meta.sequence or ())
    if "actions" not in cls.base_columns:  # removed via `actions = None`: nothing to append
        return declared or ("...",)
    ...
```

with a test (`class Removed(PlainTable): actions = None` renders `["id", "first_name", "last_name"]`), and treat
`extra_columns=[("actions", None)]` the same way in `__init__` (check `kwargs.get("extra_columns")` for an
`("actions", None)` pair before deciding to append), or, per the CLAUDE.md rule to document unsupported cases
explicitly, add one sentence to `list_view.md` after line 123: "Remove the column with `Meta.exclude`, not by
redeclaring `actions = None` or via `extra_columns`; `Table` always places `actions` in its default sequence and
django-tables2 raises `KeyError` for a sequence entry that is not a column." The guard is the smaller change and
removes a crash; the docs sentence is acceptable if the maintainer prefers a single opt-out.

### IN-02: The `None` opt-out is described as a list-view declaration, but every non-list `CrudView` inherits `cv_list_actions = None` (carried over from 06.19-01, still open)

**File:** `src/crud_views/lib/table/table.py:46-47`; `docs/reference/list_view.md:120`
**Issue:** `cv_exclude_actions` keys off `view.cv_list_actions is None`. `ListView` overrides the attribute with the
setting (`list.py:27`), but the `CrudView` base default is `None` (`base.py:100`), so a non-list `CrudView` that
renders a `Table` with `view=self` drops the actions column implicitly, not by declaration. The docstring says the
view "declares" it and the docs say "A list view with `cv_list_actions = None`". No such construction site exists in
`src/`, `tests/` or `docs/` today, so this is a documentation gap. Not addressed by 06.19-02 (out of its scope).
**Fix:** Add one sentence to the docs subsection and the docstring: "Views other than `ListView` inherit
`cv_list_actions = None` from `CrudView`, so a `Table` rendered by such a view has no actions column unless the
view sets `cv_list_actions`."
