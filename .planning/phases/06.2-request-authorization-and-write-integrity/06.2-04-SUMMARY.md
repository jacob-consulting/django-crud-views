# Phase 6.2 Plan 04: Remove the inert flag and display truthful per-view policy Summary

**GuardianViewSet now rejects the removed `cv_guardian_accept_global_perms` key with a Pydantic error naming the per-view replacement. The Guardian manage page shows each view's own effective global-fallback policy (strict, global fallback, or not applicable) next to the ViewSet helper's fixed strict policy.**

## Accomplishments

- **D-04 (constructor):** the `GuardianViewSet.cv_guardian_accept_global_perms` field is removed. A `mode="before"` validator, guarded by `isinstance(data, Mapping)`, raises on that exact key. Pydantic reports it as a `ValidationError`: "GuardianViewSet no longer accepts cv_guardian_accept_global_perms … Set cv_guardian_accept_global_perms = True on each Guardian view class … GuardianViewSet.get_objects_for_user() stays strict …". The error fires before the after-validator, so nothing is registered.
- **D-05 (strict helper):** `get_objects_for_user` behaves exactly as before. It now reads `accept_global_perms` and `use_groups` from `STRICT_HELPER_POLICY`, and manage shows that same constant as `guardian_config["get_objects_for_user"]`. The manage reader of the removed field was replaced in the same commit as the field removal (A09), so manage kept rendering 200 throughout.
- **D-06 (manage):** `get_view_data` adds a `guardian_policy` section to every registered view. The manage template renders it as a "Global permission fallback" table, followed by a note that the helper is independent of these view policies and always strict.
- **A17:** a parent-only create whose parent permissions are both None reports "not applicable" even when its own fallback is True, and the enabled create still succeeds with no grants. A queryset view in that same ViewSet still reports its own strict policy.
- **A20:** the manage gate was checked across 12 cases: modes yes, debug_only and no; live DEBUG True and False; anonymous, non-group and group actors. The gate is unchanged.
