## Executable actor and response matrix (A10)

Use fresh rows per destructive cell and explicit expected statuses, never an allowed-status set. For each actor run list/card GET, detail GET, update GET/valid POST, delete GET/confirmed POST/DELETE, action POST, create GET/valid POST and fragment GET. Bind the fixture action to a measurable field update and 302 redirect. The first table determines a granted object operation; the second pins method/storage results. Include strict and global-accepting views on the same ViewSet.

| Actor, active unless stated | Core permission views | Guardian strict | Guardian global-accepting |
| --- | --- | --- | --- |
| No grants / revoked on fresh request | Denied | Denied | Denied |
| Object grant for requested permission only | Denied | Granted for that object | Granted for that object |

| Inactive ordinary/object/group/global/superuser under AllowAllUsersModelBackend | Denied by core permission gate | Dispatch 403 | Dispatch 403 |

"Granted" applies to detail/update/delete/action and update-fragment operations. Guardian list/card GET is 200 for every active authenticated actor: strict no-grant/global-only/revoked yields an empty object_list, object/group grants yield only granted rows, global-accepting global-only and active superuser yield all rows. Core list/card GET needs global view permission (otherwise 403). Top-level create requires global add permission in both families; object grants never substitute. All GETs and rejected requests leave storage/hooks unchanged.
