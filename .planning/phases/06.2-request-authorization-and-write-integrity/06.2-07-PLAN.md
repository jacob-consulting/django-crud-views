## Gap being closed

- **gap_id:** G-06.2-1 (UAT test 1, severity blocker; review CR-01).
- **Gap reason:** `_PermittedPks.__call__` (src/crud_views_guardian/lib/views.py:68-78) passes the app-qualified
  string `app_label.view_<model_name>` built from `model._meta` to `guardian.shortcuts.get_objects_for_user` for every
  model in the delete tree and in the protected list. guardian 3.5.2 resolves that string through
  `ContentType.objects.get(app_label=..., permission__codename=...)` and then requires the result to equal
  `guardian.ctypes.get_content_type(klass)`, both before its superuser short-circuit. Three raise modes share that
  step: no `view_` row (auto-created M2M through models, `Meta.default_permissions` without `view`) gives
  `ContentType.DoesNotExist`; a row on another content type (proxy roots, polymorphic children under a polymorphic
  `GUARDIAN_GET_CONTENT_TYPE`) gives `MixedContentTypeError`; a duplicate codename in the app gives
  `MultipleObjectsReturned`. The tree path pre-exists (fd25f4d); 06.2-01 (4300f3d) extended the same lookup to the
  protected list. The core path (`user.has_perm(perm)` without an object) never resolves rows and is safe.
- **Fix direction (diagnosis, confirmed by the what-if probe over 275 existing guardian/delete tests):** resolve
  against guardian's own content type — `ct = guardian.ctypes.get_content_type(model)` and the bare codename
  `view_<ct.model>` with `klass=model`. guardian then derives the content type from `klass` and skips the
  app-label resolution entirely, which removes all three raise modes at the source. Non-superusers get an empty
  set for models that carry no grantable view permission (fail closed); active superusers get guardian's superuser
  short-circuit (parity with core). The inactive-actor guard stays first.
- **Discretion settled here:** `opts.auto_created` is short-circuited before any content-type access, because
  `ContentType.objects.get_for_model` would lazily INSERT a row for a through table on the first preview (a write
  during GET; see the diagnosis evidence at 14:40). In that branch an active superuser sees the rows (parity with
  the core view, which shows through-table rows because `has_perm` is always true for superusers); everyone else
  gets an empty set. Django creates no permissions for auto-created models, so no object grant can exist for them.
- **Rejected shape:** the review's precheck on `Permission.objects.filter(content_type=get_for_model(...))` keeps
  the app-qualified string, still raises `MixedContentTypeError` under a polymorphic `GUARDIAN_GET_CONTENT_TYPE`,
  hides proxy roots that hold a valid grant, and keeps the duplicate-codename mode (diagnosis, eliminated 14:35).
