## Exception boundary and collection decision

ORCH-01 replaces the former broad catch: exception class alone cannot establish that deletion was prevented.
Tag only the default Django Model.delete collection stage when both the pre-call native-graph check and exact
code-object/collector identities specified in 08-01 pass. Both installed Django versions call arbitrary on_delete
handlers, catch ProtectedError and raise a fresh aggregate in Collector.collect; terminal traceback identity alone
cannot prove native origin. Check every possible cascade/parent branch before invoking delete, even absent rows,
and exclude custom handlers and callable-bearing SET/SET_DEFAULT wrappers. Unknown collection/model extensions and
later signal/callback failures propagate; do not bypass model.delete or introduce a transaction when cv_atomic=False.
Existing early preview protection still applies to every model.

Keep one `cv_get_related_objects()` call per context on every GET/POST so existing overrides still supply the
unfiltered blocked state. The default uses `router.db_for_write`, `NestedObjects.can_fast_delete=False`, the full
cascade graph, summary and nested tree even with previews disabled. This is an explicit accepted operational cost,
not equivalent to Django's normal fast-delete Collector; 09-01 documents it and the existing override's responsibility.
Do not introduce a second Collector path that silently bypasses cv_get_related_objects overrides.
