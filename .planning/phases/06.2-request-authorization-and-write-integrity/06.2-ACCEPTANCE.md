## Phase 7 handoff — retained contracts and unresolved qualifications

Phase 7 must wait for 6.3's verified remediation before freezing affected delete contracts. The list below records
6.2 behavior and named evidence, subject to the acceptance split above and separate older open dispositions.

1. **Method.** Package delete views answer GET and POST. HTTP `DELETE` gets 405 after the existing login, permission,
   parent and state gates (an inactive Guardian user gets 403). `DeleteView.http_method_names` has no `"delete"`.
   `_allowed_methods()` keeps `DELETE` out of `Allow` and `OPTIONS`, also when a subclass restores the name.
   `DeletionMixin.delete` is not overridden, so Django 4.2 emits no `DeleteViewCustomDeleteWarning`. The guard
   (`_DeleteMethodGuardMixin`) is private.
2. **Diagnostic.** `GuardianViewSet` rejects `cv_guardian_accept_global_perms` (`True` or `False`, keyword or mapping)
   with a Pydantic `ValidationError` naming the per-view replacement and the strict helper. Nothing is registered.
   Unrelated extra keys are still ignored, and `model_validate(existing_instance)` keeps its after-validator behavior.
   A core `ViewSet` never had the field.
3. **Safe context and blocked deletion.** Every delete GET/POST context has `has_protected_objects` from the
   unfiltered collection. Preview keys and `cv_filter_related_objects` remain behind `cv_show_related_objects`;
   `protected_objects` is a fresh, ordered list of permitted objects. Core uses model-level view permission;
   Guardian replaces that filter with object/group grants and the **delete view's** global fallback. Guardian uses
   its own content type and bare `view_<ct.model>` codename: global fallback consults `app.view_publisher` for
   `PublisherProxy` under concrete resolution, `app.view_vehicle` for `Car` under polymorphic base resolution.
   Proxy-only global grants do not authorize concrete labels; strict mode ignores global fallback. Models without a
   grantable view permission fail closed for ordinary users, retaining authenticated active-superuser core parity
   and inactive denial. Auto-created through rows need no ContentType lookup/write; their superuser PK cache covers
   the whole through table once per projection, including unrelated rows.
   The stock content template omits the whole form while blocked, including confirm, submit and form-contained
   cancel. Permitted labels keep the colon heading/items; no labels get a colon-free heading and generic sentence.
   Named native target PROTECT/RESTRICT tests record 200 / modal 422 without deletion. Their pre-call graph and
   traceback checks do not establish the full unknown-error propagation promise: CR-03 demonstrates a nested
   converter failure translated into a blocked response. DEL-03 must establish the reviewed exception boundary.
   Existing callback tests with a substituted empty preview retain their narrow evidence only.
   The current one-traversal NestedObjects implementation can execute SET/default/custom deletion callbacks even
   with previews off (CR-02); it is not accepted as safe inspection. The no-instance-hint write-router selection
   can inspect another database (CR-04). DEL-02/04 must settle inspection and routing, including override behavior;
   these implementation details must not be frozen as accepted contracts. No large-cascade benchmark is claimed.
   Filtered labels and independent notice remain preservation obligations. Unfiltered related_summary (D-13)
   remains an explicitly open IN-01 disposition, not an implied resolution. Conditional purge authority and
   custom filter responsibilities remain preservation constraints. Templates read the flag, not the label list.
4. **Manage applicability and helper.** `views[key]["guardian_policy"]` =
   `{global_fallback_applicable, cv_guardian_accept_global_perms (None if not applicable), effective_policy}`.
   Object and queryset views are always applicable. Parent-only views are applicable only with an actual parent and a
   non-`None` resolved parent key. Plain views, manage and top-level create are not applicable. Values come from the
   view class, never the ViewSet. `guardian_config["get_objects_for_user"]` = `STRICT_HELPER_POLICY`
   (`{"policy": "strict", "accept_global_perms": False, "use_groups": True}`), the same constant the helper passes to
   guardian. The manage access gate (`CRUD_VIEWS_MANAGE_VIEWS_ENABLED` yes / debug_only+DEBUG / no, plus
   `CRUD_VIEWS_MANAGE_GROUP`) is unchanged.
5. **Wrong-type access helper (H02 superseded by H03, qualified by A25).** On a nested
   `GuardianCreateViewPermissionRequired`, `cv_has_access(user, obj)` and `cv_create_has_access(user, view, parent_obj)`
   are permission-only. They accept a parent instance, or an own child of `ForeignKey` nesting, resolved through
   `ParentViewSet.get_attribute()`. `None`, unrelated models, own children whose relation is missing, and own children
   of `ManyToMany` nesting deny, superusers included. Inactive actors deny. The parent key resolves with `is None`
   fallback, exactly as dispatch does. A `None` key skips only the permission evaluation. Top-level `cv_create_has_access`
   delegates to `cv_has_access(user, None)`, the model-level add check.
6. **Normalized state arguments (Guardian evidence; core WR-01 open).** Rendered controls compute state through the private
   `_cv_action_enabled_for_context(user, page_obj)` adapter. Guardian nested create overrides it so a custom
   `cv_action_enabled` receives the actual parent, while labels and URLs keep the page object. All four
   `ContextButton` classes and both card-action branches use the adapter. The URL-bound list fallback sets
   `cv_access = cv_action_enabled = False` without calling any hook when parent resolution fails late
   (`Http404` / `KeyError`). Request-dispatch state gates still call `cv_action_enabled` with the real object.
   `cv_context_has_permission` stays permission-only.
7. **Preserved inherited policy values.** `GuardianParentPermissionMixin` declares `cv_guardian_accept_global_perms`
   and `cv_guardian_anonymous_behavior` as annotations only. They stay known to W280, and a later custom
   object/queryset mixin's `True` / `"404"` values stay inherited.
8. **Parent `None` policy.** Dispatch always resolves the URL parent (404 when missing) and runs
   `cv_action_enabled(user, parent)` for no-object child views. No child add permission is required.
9. **Inactive actors.** Authenticated users with `is_active = False` are denied at Guardian dispatch (before parent,
   method or fragment handling), in object/queryset `has_permission`, `get_queryset` (`.none()`), access helpers,
   `_PermittedPks`, and `GuardianViewSet.get_objects_for_user` (`.none()`). Anonymous handling and active superusers
   are unchanged.
10. **Fragment and UUID sentinel.** Fragment GETs set `self.object` through `get_object()` for object views (or
    `None`) before rendering. They never build the full editor context. Coordinates are validated against the
    declaration and the persisted FK ancestry before rendering, and any mismatch is 400. Indices are 1–9 ASCII
    digits. Request keys (`template`, `pk`, `num`, `formset_parent_prefix_key`) and the `{html, rows}` response are
    unchanged. An unsaved instance renders `None` in prefixes even with a populated UUID default. `formset.js` parses
    multi-digit integer keys correctly. Ordinary `ModelChoiceField` queryset filtering stays the application's
    responsibility (D-13).
