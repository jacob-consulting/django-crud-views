<decisions>
## Implementation Decisions

### HTTP DELETE
- **D-01:** Reject HTTP DELETE with HTTP 405; deletion uses the existing validated POST workflow. Do not add a
  supported DELETE lifecycle or a new opt-in switch for it in this phase.
- **D-02:** Apply the restriction to all package delete views, including core and Guardian, rather than limiting
  it to Guardian. The implementation must close the inherited direct-delete route.

### Guardian global-permission configuration
- **D-03:** Preserve the documented per-view `cv_guardian_accept_global_perms` source of truth and existing
  access behavior. Do not introduce ViewSet-to-view inheritance.
- **D-04:** Remove the ineffective `GuardianViewSet.cv_guardian_accept_global_perms` setting before 1.0, with
  migration guidance directing users to the per-view setting. Do not retain it for a warning-only grace period.
- **D-05:** `GuardianViewSet.get_objects_for_user()` remains strict: it does not accept global model permissions.
  Document this explicitly. Do not add a global-permission option to this helper in this phase. This decision
  preserves the helper's existing object/group/superuser semantics subject to the inactive-user correction;
  it does not redefine strict mode as a new requirement for explicit grants from active superusers.
- **D-06:** The manage page shows each view's effective global-permission policy, identifying which views allow
  global fallback, and states that the ViewSet helper remains strict. A generic notice directing developers to
  source code is insufficient. Keep the existing manage authorization policy.

### Protected-object previews
- **D-07:** Filter unauthorized protected-object labels before templates receive their context. Show one generic
  blocked-deletion notice, plus only protected-object labels the user may view. Do not emit one placeholder for
  each hidden object.
- **D-08:** Apply protected-object filtering to core and Guardian delete previews, each using its existing
  permission rules. The generic notice must remain visible even when every protected-object label is hidden.
  Filtering display data must never make deletion appear unblocked or weaken actual deletion protection.

### Carried-forward roadmap requirements and compatibility
- **D-09:** B2 remains in scope: authorize formset fragment requests and validate target, URL-parent and fragment
  coordinates before rendering. Cover ungranted/revoked/inactive users, disabled actions, missing targets and
  wrong-parent targets. Preserve authorized fragment request coordinates and the `{html, rows}` response contract.
- **D-10:** B4/B6 remain in scope: `None` disables the configured parent permission check, not parent resolution or
  the independent action-state check. Make create controls/access helpers and direct GET/POST agree; do not add
  a new child-add requirement to this intentional parent-permission-free policy.
- **D-11:** B5 remains in scope: inactive users must receive no unauthorized rows or object access, including
  ordinary, object/group-granted and superuser actors authenticated by a backend that allows inactive sessions.
- **D-12:** Verify allowed write paths retain validation, protection, hooks and atomic/rollback behavior. Repeat
  the source note's actor matrix with direct requests and native list/card/action/manage/alert/formset overrides.
  Server enforcement and context filtering belong in the library, not custom templates or hidden controls.
- **D-13:** Preserve intentional aggregate purge authority and already-implemented parent/global safeguards.
  The generic protected-object notice does not revoke the existing documented aggregate summary/count policy.
  Ordinary custom ModelChoiceField filtering remains the application's responsibility; the fragment fix prevents
  users denied the entire editor from receiving its choices.
- **D-14:** Document changed method, access, configuration and safe-context behavior. Pair every CHANGELOG
  Breaking entry with `docs/migrating-1.0.md`. Phase 7 must inventory the settled contracts. Preserve completed
  Phase 6/6.1 form-leaf, label-mode, escaping and cancel-link decisions.

### Agent's Discretion and Planning Notes
- No additional product choices were explicitly delegated. Internal helper placement, safe-context field names,
  test organization and precise documentation wording are implementation details within the decisions above.
- Determine a safe template-data shape that carries blocked state independently of the visible protected list;
  avoid exposing forbidden model objects through alternative context fields. Document custom-template migration.
- Choose manage presentation/context details that expose effective policy for each registered view without
  implying that the strict ViewSet helper shares a view's global fallback.
- Preserve existing denial/login behavior when applying method restrictions; D-01 does not require leaking an
  endpoint or bypassing authentication merely to return 405 before existing access checks.
- Removing the Pydantic field must not leave an apparently functional configuration knob silently ignored;
  research existing extra-field/check behavior and provide clear removal/migration diagnostics as appropriate.
- The analysis is evidence from its recorded checkout, not fresh proof that every defect still reproduces.
  Reproduce against current source and add discriminating regressions. Its supported-version corroboration and
  stated limits matter; do not treat green historical suites as coverage of the missing adversarial cases.

- `src/crud_views_guardian/lib/views.py`: `GuardianDeleteRelatedObjectsMixin`, `_PermittedPks`, create access

- `src/crud_views_guardian/lib/mixins.py`: object, queryset and parent gates already implement per-view global
  fallback. Preserve those policies while correcting early returns, inactive access and fragment composition.
- `src/crud_views_guardian/lib/viewset.py`: the ineffective flag lives alongside the deliberately strict helper;
  helper calls currently specify `accept_global_perms=False` and `use_groups=True`.

### Established Patterns
- Core preview filtering uses model-level view permissions; Guardian uses per-object permissions with the view's
  configured global fallback. Existing related summaries intentionally have a separate aggregate disclosure policy.
- `FormSetMixinBase.get()` currently serves fragments before `super().get()` and object loading. Guardian object
  authorization relies on `get_object()`; supported mixin ordering therefore matters for the shared request gate.
- `protected_objects` currently receives unfiltered protected values, and the stock leaf checks its truthiness
  to decide whether to show the blocked alert. Filtering alone would lose that notice when no labels are visible.
- Manage currently displays the ViewSet flag, which does not describe runtime view policy. Its administrative/debug
  access gate is intentional and is separate from ordinary object permissions.

### Integration Points
- `src/crud_views/lib/formsets/mixins.py`: fragment authorization and coordinate validation.
- `src/crud_views/lib/views/mixins.py`: existing write hooks and transaction lifecycle to preserve.
- `src/crud_views/templates/crud_views/snippets/delete/related_objects.html`: generic blocked notice and safe labels.
- `src/crud_views_guardian/templates/crud_views/view_guardian_manage.html`: effective-policy presentation.
- `tests/test1/test_guardian.py`, `tests/test1/test_guardian_card.py`, `tests/test1/test_guardian_delete.py`:

<specifics>
## Specific Ideas

- An authorized actor sending DELETE to a protected deletion endpoint receives 405 and cannot delete the row.
- A user allowed to delete a Publisher but unable to view a protected Contract sees the generic blocked notice,
  never the Contract title; visible protected labels remain available for partially authorized previews.
- Two views on the same GuardianViewSet may have different global-fallback policies. Manage reports both values,
  while `get_objects_for_user()` retains its independent strict behavior.
- The removed ViewSet flag is replaced in application code by configuration on the appropriate view classes.

</specifics>
