## Implementation guidance

### B1 — HTTP methods

Restrict methods in core `DeleteView`, inherited by Guardian. Preserve existing authentication/denial behavior.
Close inherited Django `DeletionMixin.delete()` rather than adding an alternate DELETE lifecycle. Preserve POST
protection, validation, `cv_form_valid_process`, hooks and transaction boundaries. Verify the core and Guardian
routes, subclass composition and protected/form-invalid POST cases, plus rollback and hook execution.

### B2 — Fragment authorization and coordinates

`FormSetMixinBase.get()` in `src/crud_views/lib/formsets/mixins.py` returns fragments before object loading;
Guardian's object mixin checks permission and action state in `get_object()`. Resolve the authorized target first
for object views; initialize create object state appropriately. Preserve cooperative MRO and polymorphic formset
declaration lookup, and exercise real supported compositions rather than testing a helper in isolation.

Before rendering, validate the declared key path, row index, root identity, parent-prefix structure and persisted
nested ancestry. **Nested query `pk` identifies the inline parent, not necessarily the endpoint object.** Preserve
unsaved `None` parents and client-added rows; do not whitelist only indices present in the initial response.
Use declaration/model PK grammar rather than splitting UUIDs on hyphens. Keep request coordinates and `{html, rows}`.
Test legitimate persisted and unsaved chains alongside wrong-root, wrong-parent and forged-coordinate requests.

### B3 — Protected preview projection

Filter protected labels in core and Guardian projection hooks. Compute an independent blocked boolean from the
original protected collection before filtering; expose only the boolean and permitted protected objects.
Preserve `RelatedObjects` tuple shape if possible. Guardian's empty-tree shortcut must not skip protected filtering.
Keep the aggregate summary/count policy. Test template context as well as HTML, with no/partial/full related grants,
protected-only collections, native alert overrides and actual POST preservation. No per-hidden-object placeholders.

### B4/B6 — Parent-None creation

Resolve the parent before the optional permission check; always evaluate the independent no-object action state
with the parent. Centralize permission-key fallback across dispatch and create helpers. `None` must not introduce
child-add requirements. Preserve the existing distinction between permission denial and action-state presentation.
Missing parents fail closed; enabled/disabled states must agree across controls, callable helpers and direct requests.

### B5 — Inactive actors

Enforce inactive denial in Guardian dispatch and callable access/queryset helpers, including the strict ViewSet
helper and preview PK cache. Preserve active-superuser semantics: `accept_global_perms=False` does not disable
superuser privileges. Exercise actual sessions under a backend allowing inactive authentication, including ordinary,
group/object-granted and superuser actors; the default backend would mask this defect.

### B7 — Effective policy and removed configuration

Remove the ViewSet field with a targeted before-validator rejection that names the per-view replacement. Broad
extra-field prohibition expands scope; checks cannot recover input already discarded by Pydantic. Keep view-level
fallback unchanged and the ViewSet helper strict. Manage reports each registered view's applicable effective policy
and separately identifies the strict helper, without changing manage authorization. Include constructor/removal
diagnostics and mixed-policy manage tests. Document migration, including copied manage/preview template context.
