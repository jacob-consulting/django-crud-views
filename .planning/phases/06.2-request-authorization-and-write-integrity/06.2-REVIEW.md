## Critical Issues

### CR-02: Mandatory collection executes deletion callbacks on GET and unconfirmed POST

**Severity:** BLOCKER

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:309-311`

**Related lines:** `delete.py:212-214,339-350`; `tests/test1/test_delete.py:789-796` (`_delete_probe` replaces the real preview).

**Issue:** `get_context_data()` now unconditionally calls `cv_get_related_objects()`, including with the default
`cv_show_related_objects=False`. Django's `NestedObjects.collect()` executes relationship handlers; it is not
a callback-free read. A normal `on_delete=SET(callable)` immediately evaluates the callable, and `SET_DEFAULT`
can likewise evaluate a callable default. Such callbacks commonly create a replacement/sentinel row.

Consequently, merely opening the confirmation page can write to the database. An invalid POST also invokes the
callback before `cv_form_is_valid()`, and those writes happen outside `cv_get_atomic()` even when `cv_atomic=True`.
A subsequent rejected or failed deletion cannot roll them back. A successful POST can execute the callback once
for the preview and again for the actual deletion. Custom handlers can have further external side effects.
The new metadata certification only runs later in `cv_form_valid()`, so its rejection of SET/default handlers
does not protect this path.

**Reproduction:** In the existing test project, create a Publisher and Book, configure the Book's publisher FK
with the equivalent of:

```python
def replacement():
    return Publisher.objects.create(name="Created by preview").pk

Book._meta.get_field("publisher").remote_field.on_delete = models.SET(replacement)
```

Use an authorized client on the registered `/publisher/<pk>/delete/` route, whose related preview is disabled.
A GET returns 200 and creates one replacement row. A subsequent POST with `{}` returns 200 and creates a second
replacement row; the target remains present and no deletion was confirmed. The probe used real in-memory tables
and runtime field configuration, without changing repository files.

Identical result on Django **6.0.9** and **4.2.30**:

```text
get 200 created rows 1 target exists True
post 200 created rows 2 target exists True
```

**Fix:** Separate protection inspection from executable deletion collection. The GET/pre-validation path must
inspect supported native CASCADE/PROTECT/RESTRICT relationships without invoking SET/default/custom handlers or
other application callbacks. Treat unsupported collection paths conservatively and leave their execution to the
validated write lifecycle. Do not rely solely on a transaction rollback: external callback effects are not
transactional. Add regressions using the real preview on GET, invalid POST, custom-protected POST, and a failing
valid POST; assert that replacement factories and custom handlers have not run before the write boundary.

### CR-03: Native-graph certification overlooks custom field read converters

**Severity:** BLOCKER

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:51-60`

**Related lines:** `delete.py:78-88,97-124,371-378`; `docs/reference/delete_view.md:311-322`.

**Issue:** `native_loader()` certifies a model using its manager/queryset classes, model construction methods and
initialization signals, but does not inspect field/database conversion callbacks. A model can meet every check
while a field supplies a custom `from_db_value()` (the standard custom-field read hook).

If that converter runs while loading a nested cascade and raises `ProtectedError`, an enclosing native
`CASCADE` call can cause Django to aggregate the error. Its final traceback then satisfies the exact
`Model.delete -> Collector.collect` checks. The code converts this unknown application failure into
`_TargetDeleteBlocked` and returns a normal protection page. This violates the documented promise that unknown
loading failures propagate, and with `cv_atomic=False` can hide already committed converter side effects behind
a response that claims a blocked deletion. The target need not have any PROTECT relationship.

**Reproduction:** Use the existing Publisher → Book → BookNote cascade, a stale empty preview (as in the existing
backstop tests), and `cv_atomic=False`. Add a no-op BookNote `pre_delete` listener to prevent fast deletion so its
row is loaded. Give BookNote's ID field a custom read converter that creates a Publisher named
`"Converter side effect"` and raises `ProtectedError("Converter failure", {note})`. The ordinary model manager,
`Model.__init__` and `Model.from_db` remain unchanged.

Both Django **6.0.9** and **4.2.30** produced:

```text
certified True
status 200 reported blocked True calls ['converter'] side effects 1 target exists True
```

The error is swallowed, the callback's write remains committed, and there was no native protected target.
This is distinct from CR-02: it occurs during the actual validated delete after the preview was deliberately
bypassed to exercise the race handler.

**Fix:** Extend the conservative eligibility check to cover the row-conversion path, including custom field
converters and configurable conversion callbacks, for every potentially loaded cascade/parent model. Reject
unknown conversion behavior before deletion rather than inferring safety from the aggregated traceback.
Add a nested custom-field regression with a real committed side effect and verify that the original protection
error propagates for both atomic settings; only the atomic setting should determine rollback.

### CR-04: The blocking precheck ignores the target instance's database

**Severity:** BLOCKER

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:309-311,344-348`

**Root cause:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:212-214`.

**Issue:** The newly authoritative `has_protected_objects` value comes from a collector using
`router.db_for_write(self.object._meta.model)` without the target instance hint. Actual Django `Model.delete()`
uses `router.db_for_write(self.__class__, instance=self)`; with no overriding router this falls back to
`self._state.db`. An explicitly routed queryset or an instance-aware shard router therefore lets the precheck
and the actual delete address different databases. An override of the documented `cv_get_db_alias()` transaction
hook does not fix the collection alias.

If the default database contains a protected row whose target PK matches an unprotected target in another
database, the view now suppresses the form and refuses to delete the unprotected target. With previews disabled,
this was not a blocking decision before the change. If the default database lacks the relevant tables, the same
new collection also causes an avoidable database error before the valid write path.

**Reproduction:** Create independent in-memory `default` and `shard` databases. In default, create Publisher
PK 999 plus a Contract protecting it. In shard, create an unrelated Publisher PK 999 with no protector.
Configure the registered Publisher delete view to use `Publisher.objects.using("shard")` and
`cv_get_db_alias() == "shard"`. POST a valid confirmation.

Both Django **6.0.9** and **4.2.30** produced:

```text
status 200 blocked True shard target survives True
direct delete (1, {'app.Publisher': 1})
```

The direct deletion uses the same shard instance and succeeds, demonstrating that the view's blocked state
came from the unrelated default-database object.

**Fix:** Resolve the protection collector's alias consistently with the real target deletion. For native model
deletion, include `instance=self.object` and use the target's class, matching `Model.delete()`; ensure any
supported explicit database override is shared by collection, transaction handling, and deletion. Add a
two-database regression with colliding PKs and protection on only one database. The existing write-router test
returns `"default"` for every call and therefore cannot detect the mismatch.
