## Summary

Scope: the 14 source files and 13 test files changed by phase 06.2 (`git diff fd25f4d..HEAD`), reviewed as a security-hardening phase. The review traced the full dispatch chains (MRO) of the core and Guardian delete views, the Guardian parent/object/queryset mixins, the formset fragment endpoint (`FormSetMixinBase.get` → `get_object()` → `_cv_validate_fragment_coordinates` → `get_template`), the rendered-control state adapter (`_cv_action_enabled_for_context`) across `base.py`, `buttons.py`, `card.py` and the Guardian create view, and the `formset.js` prefix parser against the server-side prefix grammar.

What holds up under adversarial tracing:

- **HTTP DELETE rejection.** `_DeleteMethodGuardMixin` sits after `CrudView` in the MRO of every package delete view (core, `*PermissionRequired`, polymorphic, Guardian). `PermissionRequiredMixin.dispatch` / `GuardianParentPermissionMixin.dispatch` run first, `CrudView.dispatch` still applies the modal `Vary`, and the guard fires before any handler or `get_object()`. `_allowed_methods` feeds both the 405 `Allow` header and `OPTIONS`. A subclass restoring `"delete"` in `http_method_names` is still stopped. No `delete()` override, so no Django 4.2 warning.
- **Fragment authorization.** The fragment path now resolves `self.object` through the cooperative `get_object()` (Guardian object-permission and state gates; wrong-URL-parent targets 404 because `ViewSet.get_queryset` filters by the parent chain), and `_cv_validate_fragment_coordinates` ties the root identity to the authorized object, enforces the declared child positions, and verifies every persisted ancestor with an FK-scoped `exists()`. The top-level index 0 rule matches `FormSets.init` (all top-level formsets get index 0). Unicode digits, overlong indices, empty `pk`, and unsaved-under-saved mixes are all 400. No bypass found.
- **Inactive actors.** `_guardian_inactive_actor` is applied before every permissive shortcut (None policy, accept-global, superuser) in dispatch, `get_object()`, `cv_has_access`, `get_queryset`, `_PermittedPks` and `GuardianViewSet.get_objects_for_user`. Anonymous handling is unchanged.
- **Removed ViewSet flag.** The before-validator rejects the key for mapping input only; instance input still reaches the after-validator. Nothing is registered on failure.
- **`formset.js` regex fix.** `^(?:(.*)-)?(None|pk)-(\d+)$` is correct for multi-digit INT pks and for the UUID grammar (the greedy prefix cannot split a UUID because the grammar anchors on 8 leading hex digits).

What does not hold up:

- **CR-01 (BLOCKER):** the Guardian delete preview crashes (500) whenever the cascade tree or protected set contains an object of a model that has no `view_<model>` permission row — notably Django's auto-created M2M through models. Reproduced against the test project (Publisher with a Genre). This predates the phase, but the phase rewrote `cv_filter_related_objects`, dropped the empty-tree shortcut and extended the same lookup to protected objects without fail-closing it, and the phase's own goal was a hardened delete preview.
- **WR-01:** the new state adapter contract ("a view whose state object differs from the page object overrides the adapter") is only implemented for the Guardian create view. Core nested `CreateViewPermissionRequired` still renders `cv_action_enabled(user, page_object)` while dispatch enforces `cv_action_enabled(user, parent)`.
- **WR-02:** the delete page announces "Deletion is blocked" but the confirm button still submits and the POST raises `ProtectedError` (500). Documented as a deliberate deferral in 06.2-01; recorded here so it is tracked.

Acknowledged, documented deferrals not re-raised as findings: A19 (`get_template` emits index 0 for a non-first sibling child declaration, characterized in `test_two_child_declaration_characterizes_emitted_index_and_keeps_gates`), A25 (M2M own-child create controls), and the AUTH-06 "unclassified" acceptance note.

## Critical Issues

### CR-01: Guardian delete preview raises `ContentType.DoesNotExist` (500) for cascade/protected models without a `view_` permission

**File:** `src/crud_views_guardian/lib/views.py:68-78` (`_PermittedPks.__call__`), called from `src/crud_views_guardian/lib/views.py:48-56` and reached on GET and POST via `src/crud_views/lib/views/delete.py:202-209` and `:224-227`
**Severity:** BLOCKER
**Issue:** `_PermittedPks.__call__` builds `f"{app_label}.view_{model_name}"` for every model in the cascade tree and in `related.protected` and passes it to `guardian.shortcuts.get_objects_for_user`. Guardian resolves that string with `_get_ct_cached(app_label, codename)` → `ContentType.objects.get(app_label=..., permission__codename=codename)`, which raises `ContentType.DoesNotExist` when no such `Permission` row exists. Django's `NestedObjects` collector includes auto-created M2M through rows (e.g. `Genre_publishers`), and auto-created models never get default permissions; models with a restricted `default_permissions` behave the same. Result: any `GuardianDeleteViewPermissionRequired` with `cv_show_related_objects = True` whose model participates in an M2M returns a 500 on the delete confirmation page, and on the confirming POST (`DeleteView.post` calls `get_context_data` before writing). The core filter (`user.has_perm`) does not have this problem.

Reproduced with the test project:

```
tree: [<Publisher: P>, [<Genre_publishers: Genre_publishers object (1)>]]
Publisher -> set()
Genre_publishers RAISED DoesNotExist ContentType matching query does not exist.
filter RAISED DoesNotExist ContentType matching query does not exist.
```

This is pre-existing for the tree path, but the phase rewrote this method (removed the `if not related.tree: return related` shortcut, added the protected projection through the same cache) and its AUTH-03 claim is a hardened Guardian delete preview. The phase's Guardian delete tests never delete a Publisher that has a Genre, so the suite does not see it.

**Fix:** Fail closed per model instead of letting guardian raise — a model that cannot carry a `view_` permission has nothing the user may view:

```python
def __call__(self, model) -> set:
    if _guardian_inactive_actor(self.user):
        return set()
    if model not in self._cache:
        from django.contrib.auth.models import Permission
        from django.contrib.contenttypes.models import ContentType
        from guardian.shortcuts import get_objects_for_user

        opts = model._meta
        codename = f"view_{opts.model_name}"
        ct = ContentType.objects.get_for_model(model, for_concrete_model=True)
        if opts.auto_created or not Permission.objects.filter(content_type=ct, codename=codename).exists():
            # no view permission can be granted for this model -> hide its labels (fail closed)
            self._cache[model] = set()
        else:
            qs = get_objects_for_user(
                self.user, f"{opts.app_label}.{codename}", klass=model, accept_global_perms=self.accept_global
            )
            self._cache[model] = set(qs.values_list("pk", flat=True))
    return self._cache[model]
```

Add a Guardian delete test whose root object has an M2M relation (Publisher with a Genre) for GET, modal GET and POST. Decide explicitly whether an active superuser should still see through-model rows (the core path shows them because `has_perm` is always True for superusers); if so, short-circuit on `user.is_superuser` before the permission lookup.

## Warnings

### WR-01: Core nested create still evaluates rendered state against the page object, not the parent

**File:** `src/crud_views/lib/view/base.py:368-374` (default adapter), `src/crud_views/lib/view/base.py:908-918` (dispatch enforcement via `cv_get_action_object()`), `src/crud_views/lib/views/create.py` (no override)
**Severity:** WARNING
**Issue:** The phase introduced `_cv_action_enabled_for_context` so that rendered controls and request enforcement agree on the state object, and `cv_get_action_object()` defines that object for every child create view as the parent. But only `GuardianCreateViewPermissionRequired` overrides the adapter (`crud_views_guardian/lib/views.py:162-171`). A core `CreateViewPermissionRequired` under a `ParentViewSet` with a custom `cv_action_enabled(user, obj)` (e.g. "no new books while the publisher is locked") still receives the *page* object from every rendering path — the Book instance on a book detail page, `None` on the book list page, the Publisher only on the publisher's own page — while `has_permission` calls it with the Publisher. The control can therefore render enabled for a request that dispatch will 403, or disabled for one it would allow. The adapter docstring says "a view whose state object differs from the page object overrides this"; core nested create is exactly such a view and does not.

**Fix:** Move the parent-resolution adapter into core `CreateView` and let the Guardian view reuse it:

```python
# crud_views/lib/views/create.py
class CreateView(CrudViewProcessFormMixin, CrudView, generic.CreateView):
    ...
    @classmethod
    def _cv_create_parent(cls, obj):
        parent = cls.cv_viewset.parent
        if obj is None or parent is None:
            return None
        parent_model = parent.viewset.model
        if isinstance(obj, parent_model):
            return obj
        if not isinstance(obj, cls.cv_viewset.model) or parent.many_to_many_through_attribute:
            return None
        try:
            candidate = getattr(obj, parent.get_attribute())
        except ObjectDoesNotExist:
            return None
        return candidate if isinstance(candidate, parent_model) else None

    @classmethod
    def _cv_action_enabled_for_context(cls, user, obj=None):
        if cls.cv_viewset.parent is None:
            return cls.cv_action_enabled(user, obj)
        parent_obj = cls._cv_create_parent(obj)
        return parent_obj is not None and cls.cv_action_enabled(user, parent_obj)
```

Then `GuardianCreateViewPermissionRequired._cv_guardian_create_parent` becomes an alias of `_cv_create_parent`, and the core child-page agreement rows in `test_authorization_matrix.py` (`test_child_page_create_control_matches_direct_route`) can be extended to the core family with a state-dependent `cv_action_enabled`. Note this is a behavior change for core nested create pages (a page whose object is unrelated to the parent renders the create control disabled) and belongs under the same `### Breaking` entry as the Guardian helper change.

### WR-02: Blocked delete page still submits, and the confirmed POST raises `ProtectedError` (500)

**File:** `src/crud_views/lib/views/delete.py:224-247`, `src/crud_views/templates/crud_views/snippets/delete/related_objects.html:4-6`
**Severity:** WARNING
**Issue:** `get_context_data` computes `has_protected_objects` from the unfiltered `collector.protected`, and the template shows "Deletion is blocked by protected relationships". Nothing uses that flag on the write path: `post()` only consults `cv_check_delete_protection()` (default `[]`), so a user who clicks the still-rendered confirm button gets `self.object.delete()` → `django.db.models.ProtectedError` → 500. `test_database_protect_post_raises_and_keeps_storage` and its Guardian twin pin this as the current contract, and 06.2-01 records the deferral explicitly. It is still an incorrect response for a state the page itself detected one call earlier, and it is reachable by every delete-permitted user on any PROTECT relation.

**Fix:** Treat database protection like custom protection in `post()`:

```python
def post(self, request, *args, **kwargs):
    self.object = self.get_object()
    context = self.get_context_data(**kwargs)
    self.cv_post_hook(context)
    if self.cv_form_is_valid(context):
        errors = list(context.get("delete_protection_errors", []))
        if context.get("has_protected_objects"):
            errors.append(_("Deletion is blocked by protected relationships."))
        if errors:
            ...  # existing add_error / render / 422 path
```

`has_protected_objects` is only computed when `cv_show_related_objects` is True; if the block should apply regardless, compute `bool(NestedObjects(...).protected)` separately in `post()` (or catch `ProtectedError` around `cv_form_valid_process` and re-render with a form error). Either way, record the change in CHANGELOG/migrating-1.0.md since the current 500 is documented.

## Info

### IN-01: `related_summary` is not permission-filtered

**File:** `src/crud_views/lib/views/delete.py:206-208`, `src/crud_views_guardian/lib/views.py:52-56`
**Severity:** INFO
**Issue:** Labels and protected objects are filtered by view permission, but `summary` (verbose model name → count) is passed through unchanged in both the core and Guardian projections, so a user without view permission on Contract still sees "contract: 3". The phase states this is deliberate ("summaries stay unchanged"). Counts of rows that the cascade will delete are arguably necessary for the decision, so this is noted as a residual disclosure, not a defect.
**Fix:** If the aggregate should match the labels, zero or drop summary entries for models with no permitted pk, and document the choice either way in `docs/reference/delete_view.md`.

### IN-02: `STRICT_HELPER_POLICY` is a mutable module dict read at call time

**File:** `src/crud_views_guardian/lib/viewset.py:11`, `:106-107`
**Severity:** INFO
**Issue:** `get_objects_for_user` reads `accept_global_perms` / `use_groups` from the dict on every call. A downstream `STRICT_HELPER_POLICY["accept_global_perms"] = True` silently turns the "strict, non-configurable" helper permissive; the manage page would faithfully display the mutated value, so the "cannot drift" property holds but the strictness guarantee does not.
**Fix:** `STRICT_HELPER_POLICY = MappingProxyType({...})` (and `dict(STRICT_HELPER_POLICY)` in the manage context keeps working), or pass literal `False`/`True` to guardian and derive the display from the same constants.

### IN-03: Unknown permission key crashes with `AttributeError` instead of a clear error

**File:** `src/crud_views_guardian/lib/mixins.py:66-67`, `:78`, `:278-286`
**Severity:** INFO
**Issue:** `cv_viewset.permissions.get(key)` returns `None` for a key that is not in the ViewSet's permission map (e.g. `cv_guardian_parent_create_permission = "approve"` or a custom `cv_permission`), and the next line calls `perm.split(".")` / `user.has_perm(None)` → 500 rather than a system check or a deny. Pre-existing; surfaced because `_guardian_user_has_parent_perm` is now the single shared resolver.
**Fix:** Add a system check on `GuardianViewSet` that both parent keys resolve in `parent.viewset.permissions`, and make the resolver deny (`return False`) when the lookup is `None`.

### IN-04: Formset fragments on slug-pk roots are now a hard 400

**File:** `src/crud_views/lib/formsets/formsets.py:49-51`, `:452-453`
**Severity:** INFO
**Issue:** `FormSet.PK` offers only `INT` and `UUID` grammars, while ViewSets support slug primary keys. `_cv_validate_fragment_coordinates` rejects any root `pk` that does not match the declared grammar, so a slug-keyed root can never request a fragment. Before the phase this already failed client-side (`formset.js` parses the prefix with the same grammar), so this is not a regression, but the server now enforces the limitation explicitly without a system check naming it.
**Fix:** Either add a `SLUG` grammar to `FormSet.PK` (and mirror it in `formset.js`) or add a system check that rejects `FormSetMixin` on a slug-pk ViewSet.

### IN-05: `GuardianParentPermissionMixin.has_permission` returns True for any child composition

**File:** `src/crud_views_guardian/lib/mixins.py:227-230`
**Severity:** INFO
**Issue:** With a parent ViewSet, `has_permission()` is unconditionally True, which bypasses `CrudViewPermissionRequiredMixin.has_permission` (model permission and the `cv_action_enabled` state gate). The package's own view classes always pair it with `GuardianObjectPermissionMixin` (gates in `get_object()`) or `GuardianQuerysetMixin` (gates in `get_queryset()`), but a downstream composition `class X(GuardianParentPermissionMixin, UpdateViewPermissionRequired)` has no object permission, no model permission and no state gate at all — a fail-open by composition. Pre-existing and described in the docstring, noted because this phase audited exactly these gates.
**Fix:** A system check: a `GuardianParentPermissionMixin` view with `cv_object = True` must also subclass `GuardianObjectPermissionMixin`; a list view must subclass `GuardianQuerysetMixin`.
