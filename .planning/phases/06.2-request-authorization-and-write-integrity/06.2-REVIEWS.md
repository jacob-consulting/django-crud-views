## ORCH-01 — HIGH: plan 08 catches lifecycle errors after deletion may already have committed

Plan `.planning/phases/06.2-request-authorization-and-write-integrity/06.2-08-PLAN.md:135` specifies catching `ProtectedError` and `RestrictedError` around the whole `cv_form_valid_process(context)` call, then returning a blocked response. Its justification says both exceptions come from the collector before delete SQL and that `transaction.on_commit` was never scheduled.

That is true for an exception raised by the target object's initial collector, but not for every exception crossing this boundary. `src/crud_views/lib/views/mixins.py:54` runs the delete, `cv_form_valid_hook`, and callback registration in the same method; leaving its outer atomic block can execute `cv_on_commit` before the method returns. `src/crud_views/lib/view/base.py:244` also supports `cv_atomic=False`. A user callback can attempt deletion of an unrelated protected object and raise either exception after the original target's deletion has committed. Existing real-commit semantics are independently pinned by `tests/test1/test_transactions.py:619`.

The temporary probe below used the unchanged `PublisherDeleteView.cv_form_valid_process` and in-memory test database. It disabled only the normal success-message hook (a direct view instance has no request), raised each exception from `cv_on_commit`, and placed the proposed catch around the call. All four cases reached that catch with the Publisher already absent, on both cached environments:

- Django 6.0: **4 passed in 0.36s**.
- Django 4.2: **4 passed in 0.40s**.

These passes demonstrate the counterexample, not successful implementation of plan 08. The current production `post()` was not changed; the probe verifies the exception boundary rather than asserting a future rendered HTTP response. An initial probe failed because the direct view had no request for its success-message hook; that setup error was corrected before these results.

**Required plan improvement:** scope or tag protection failures from the target deletion before treating them as blocked responses. Preserve propagation of failures from lifecycle hooks and commit callbacks. Add real-commit regressions for both exception types, with atomic writes on and off, proving that a completed deletion is never reported as prevented. Preserve the existing pre-write PROTECT/RESTRICT response and rollback tests. The final design must not assume every exception of these two classes came from the target collector.

This is an orchestrator-confirmed finding, not a third external-reviewer vote. Fable and Gemini affirm the broad backstop for collector-origin errors but do not examine this callback-origin counterexample.

## Reproduction

Run from the repository root with the probe saved as a temporary Python file:

```bash
PYTHONPATH="$PWD/src:$PWD" .nox/crispy_floor-3-12-django-6-0/bin/python -m pytest -p tests.test1.conftest /path/to/test_review_backstop.py -q -p no:cacheprovider
```

```python
import pytest
from django.db.models import ProtectedError, RestrictedError
from tests.test1.app.models import Publisher
from tests.test1.app.views import PublisherDeleteView

@pytest.mark.django_db(transaction=True)
@pytest.mark.parametrize('error_type', [ProtectedError, RestrictedError])
@pytest.mark.parametrize('atomic', [True, False])
def test_proposed_catch_can_run_after_delete_commit(monkeypatch, error_type, atomic):
    publisher = Publisher.objects.create(name='Review callback probe')
    original_pk = publisher.pk
    view = PublisherDeleteView()
    view.object = publisher
    view.cv_atomic = atomic
    monkeypatch.setattr(view, 'cv_form_valid_hook', lambda context: None)
    def callback(context):
        raise error_type('Callback encountered unrelated protected relationship', set())
    monkeypatch.setattr(view, 'cv_on_commit', callback)
    caught_as_blocked = False
    try:
        view.cv_form_valid_process({})
    except (ProtectedError, RestrictedError):
        caught_as_blocked = True
    assert caught_as_blocked
    assert not Publisher.objects.filter(pk=original_pk).exists()
```

**Disposition: revise plan 08 before execution.** All three external reviewers rate the pending closure work MEDIUM risk and agree that the Guardian lookup fix and the 07 → 08 → 09 dependency order are sound. Independent verification adds one HIGH correctness finding, ORCH-01: the proposed exception boundary can classify an error from a commit callback as a prevented deletion after the target has already been deleted. This supplements, rather than represents agreement among, the external reviewers.

### Agreed Strengths

- **The Guardian lookup fix addresses the actual cause.** All reviewers trace the app-qualified permission lookup in `src/crud_views_guardian/lib/views.py:74` to guardian's content-type resolution before its superuser branch. The bare-codename lookup and early auto-created-model branch address the pending gap while preserving the inactive-user check at `src/crud_views_guardian/lib/views.py:69`.
- **The closure sequence is coherent.** All reviewers agree that plan 07 supplies the Royalty RESTRICT fixture needed by 08, and 09 updates documentation and records both-version regression evidence after the code changes. Their file overlap is sequential.

Plan 08 addresses all three, with migration work in 09.

### Agreed Concerns

1. **MEDIUM — Account for the cost of collecting every delete graph (plan 08).** Fable and Gemini flag the full cascade walk even with previews disabled; Grok additionally notes that it hits the write database. The source uses `router.db_for_write` and `NestedObjects` at `src/crud_views/lib/views/delete.py:104`, then builds a summary and tree whether or not the new caller needs them. Correct T-06.2-17's claim that this is the same collector cost as ordinary deletion. 2. **MEDIUM — Make plan 07's intermediate verification boundary explicit.** Fable questions the narrow module selection after adding shared test-app models; Grok points out that the direct proxy/polymorphic modes are not run on Django 4.2 until plan 09. Both identify deferred evidence, not a missing final gate: 09 already runs both complete suites. Either add focused 4.2 coverage and relevant registry/model collateral checks to 07, or explicitly state which claims remain provisional until 09.

### Divergent Views

- **Backstop safety:** all three external reviewers approve the broad `cv_form_valid_process` catch for collector-origin exceptions. Their reasoning does not cover callbacks that raise the same exception classes. ORCH-01 demonstrates that counterexample using the existing lifecycle; the source and reproduced result take precedence over the reviewers' general safety claims. This finding is not counted as cross-reviewer consensus.
- **Grok's atomic-placement warning is already addressed by the plan.** Plan 08 explicitly puts the catch around `self.cv_form_valid_process(context)` in `post()` (`06.2-08-PLAN.md:135`), outside the method's `with self.cv_get_atomic()` (`src/crud_views/lib/views/mixins.py:54`). At catch time that block has unwound. Do not treat Grok's warning about placing the catch inside the block as an additional defect in the written plan. Its blanket assertion that a collector exception necessarily leaves the connection broken is also too broad. The distinct callback-origin issue above remains actionable.
- **Older migration text:** Gemini asks to reconcile adjacent sections; Grok asks to preserve the earlier filtering entry's meaning. Both can be satisfied by retaining that guidance and anchor, clarifying which context keys depend on preview configuration, and cross-linking the new blocked-deletion section. A historical entry does not need to be rewritten as if it originally described the later change.
- **Performance severity:** Fable calls the collector cost MEDIUM, Gemini LOW, and Grok adds a MEDIUM write-alias concern. The full materialization is source-confirmed; no large-cascade benchmark was run in this review. The final choice should retain the locked product behavior and accurately record the operational cost.
