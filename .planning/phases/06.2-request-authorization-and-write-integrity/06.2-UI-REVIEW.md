## Top 3 Priority Fixes

1. **WARNING — Empty blocked notice ends in a dangling colon and explains nothing** — A user who may delete a
   Publisher but may not view its Contracts sees a red box reading `Deletion is blocked by protected
   relationships:` followed by whitespace (`delete-hidden-desktop.png`; markup: `<strong>…relationships:</strong>`
   then `</div>`, no `<ul>`, because `alert_data()` picks `TEXT_BODY` with empty `text` when `items == []`). It
   looks like a truncated message. — In `src/crud_views/templates/crud_views/snippets/delete/related_objects.html:5`
   branch on `protected_objects`: with labels keep the current heading; without labels pass a colon-free heading plus
   a `text=` such as `_("This object is referenced by protected objects you are not allowed to view.")`. D-07
   forbids per-object placeholders, not a single generic explanation. Alternatively drop the trailing colon from the
   heading unconditionally.
2. **WARNING — Per-view policy is rendered twice with two vocabularies** — `GuardianManageView.get_view_data()`
   (`src/crud_views_guardian/lib/views.py:329`) adds `guardian_policy` as a *section* of each view's data, and the
   base `view_manage.html:117-131` loops over every section, so each per-view table at the bottom of the page shows
   `global_fallback_applicable: True`, `cv_guardian_accept_global_perms: None`, `effective_policy: strict`, while
   the designed table above says `—` / `strict: object and group grants only` for the same view (5 raw sections in
   `guardian-manage.html`). A developer comparing the two will wonder which one is authoritative. — Either
   keep the structured data out of the generic loop (store it under a private key the template skips, or have the
   Guardian template override the `Views` block), or make the raw section the only rendering and drop the table.
   If both stay, use the same strings (`effective_policy` should read exactly what the table shows) and render
   `None` as `—`.
3. **WARNING — The manage policy table loses its payload column on narrow viewports** — At 375 px the third column
   ("Effective policy") is completely outside the viewport and the page has no horizontal scroll affordance for
   the table (`guardian-manage-mobile.png`; the config table inside the alert is cut at
   `GuardianViewSet.get_objects_for_` too). — Wrap the new table (and, while there, the config table) in
   `<div class="table-responsive">`, and shorten the header to `accept_global_perms` with the full attribute in a
   `title`/`abbr`, which also fixes the balloon rows.

Further findings (not in the top 3):

4. **WARNING (pre-existing, made more prominent)** — Blocked state does not disable the write path: `Confirm
   deletion` checkbox and `btn btn-primary` **Delete** are enabled under the red notice
   (`delete-hidden-desktop.png`); a POST reaches `DeletionMixin` and 06.2-01-SUMMARY records that database
   PROTECT still raises `ProtectedError` (500). At minimum render the submit disabled when
   `has_protected_objects` (the phase introduced exactly the flag needed for that), or route the POST to the
   existing `delete_protection_errors` branch.
5. **Copy** — `config_table.html:20` puts `GuardianViewSet.get_objects_for_user()` under the column header
   "Setting"; it is a method, not a setting. Rename the header to "Item"/"Policy" or move the row to its own
   caption line.
6. **Copy (pre-existing)** — `None` is printed raw for `cv_guardian_parent_create_permission` and
   `parent_viewset` in the same table while the new table uses `—` for "no value"; pick one.
7. **Copy** — The strict wording appears in three variants on one page: `strict: object and group grants only;
   global model permissions are not accepted` (config row), `strict: object and group grants only` (table),
   `strict` (raw section). Collapse to one translatable string.
8. **Observation (pre-existing, outside phase)** — the delete page still nests a `<form>` inside `<form
   class="cv-form">` (crispy helper renders its own form tag); unchanged by this phase, noted in 06.1 as well.
9. **Observation** — `related_objects_tree.html` shows `(restricted)` placeholders for cascaded objects the user
   may not view (`delete-mixed-*`). This is the documented aggregate policy (D-13) and is not scored, but it sits
   next to the new notice-without-placeholders policy for protected objects, so the two disclosure styles differ
   on the same page.

## Detailed Findings

### Pillar 1: Copywriting (2/4)

Evidence:

- `delete-hidden`: context `has_protected_objects=True, protected_objects=[], related_summary={}` renders exactly
  one `alert-danger` whose entire content is the heading `Deletion is blocked by protected relationships:`
  (`related_objects.html:5`, heading literal unchanged from before the phase; the phase only changed the guard
  from `protected_objects` to `has_protected_objects`). A colon promises a list that never comes. No sentence
  tells the user that items exist but are hidden, so the page reads as broken rather than as a policy.
- `delete-visible`: with labels the copy works (`Secret Contract`, `Second Contract` as `<li>`), and labels are
  escaped through `alert_data()`.
- `config_table.html:4` header "Setting" vs row `GuardianViewSet.get_objects_for_user()` (finding 5).
- `view_guardian_manage.html:12` header is the raw attribute name `cv_guardian_accept_global_perms` (fine for a
  developer page, but the third column header "Effective policy" is translated while this one is not; consistent
  with the config table convention, so not penalised).
- Three spellings of "strict" on one page (finding 7); `None` vs `—` (finding 6).
- Good: `view_guardian_manage.html:23` states the helper's independence in one plain sentence, satisfying D-06's
  "not a generic notice" requirement; `not applicable` rows are explicit instead of blank.

### Pillar 2: Visuals (2/4)

Evidence:

- Duplicate rendering: `grep -c guardian_policy guardian-manage.html` = 5 — one raw `<th colspan=2>guardian_policy`
  section per view (`manage`, `list`, `detail`, `update`, `create`) below the designed table. Source:
  `views.py:329` writes `view_data["guardian_policy"] = OrderedDict(...)`; `view_manage.html:117-131` renders
  every section generically. The tests only assert the designed table, so this went unnoticed.
- Mobile (`guardian-manage-mobile.png`): the `Global permission fallback` table's first two columns occupy the
  viewport and the third is out of frame; the Guardian Configuration alert is clipped at its right edge. Desktop
  (`guardian-manage-desktop.png`) is clean: the table sits between the config alert and the Permissions table with
  the same `h4` rhythm.
- Empty red alert (`delete-hidden-desktop.png`): icon + bold heading in an otherwise empty box; visually
  indistinguishable from a rendering failure.
- Icon-only buttons in the header (trash, gear) are pre-existing and carry `title`s (not changed here).
- Good: `delete-mixed-mobile.png` shows the three alerts stack cleanly with consistent `mb-3`, bullets indent
  correctly, and the danger/warning distinction is clear.

### Pillar 3: Color (3/4)

Evidence:

- Blocked notice uses level `error` → `alert alert-danger` (`cv_button_class "alert" "error"`), the only red on the
  page; cascade summary/tree use `alert-warning`. Correct hierarchy: blocking > consequential.
- Config table is rendered via `{% cv_alert "warning" body_template=… %}` (`view_guardian_manage.html:6`,
  pre-existing). The phase added the strict-helper row inside it, so a purely informational policy statement is
  framed in yellow with a triangle icon while the new, equally informational policy table below it is unframed.
  Inconsistent signalling on one screen.
- No hardcoded colours added (`git diff 2bd9d8d..HEAD` on the five files contains no `#…`/`rgb(`).
- No new `text-primary`/`bg-primary` usage; the primary accent remains on the single **Delete** CTA.

### Pillar 4: Typography (4/4)

Evidence:

- Diff adds `<h4>`, `<table class="table table-striped">`, `<th scope="col">`, `<p>` only; no `fs-*`, `fw-*`,
  `small` or `lead` classes. Heading level matches the surrounding `h4`s in `view_manage.html`.
- Minor: identifiers are set in the same font as prose (the test theme uses a monospace body, so it is invisible
  here; in the Bootstrap example theme they would be proportional). A `<code>` wrapper would be more precise but
  would differ from the existing config rows, so not penalised.

### Pillar 5: Spacing (3/4)

Evidence:

- The config table keeps `mb-0` inside the alert; the new table relies on Bootstrap's default `.table` margin and
  the explanatory `<p>` follows with its default margin — rhythm matches the Permissions section on desktop.
- No `table-responsive` wrapper on the new table (`view_guardian_manage.html:9`), consistent with the siblings but
  the new table is the widest on the page (three columns with a 30-character header and a 45-character cell), so
  it is the first to break: at 375 px rows `list`/`detail` are ~90 px tall with the visible cells top-aligned over
  empty space.
- `related_objects.html` unchanged structurally: `cv-related-objects mb-3` and alert `mb-0 mt-2` lists; the
  mobile stack is even.

### Pillar 6: Experience Design (2/4)

Evidence (code-derived; no interaction captures):

- Blocked delete: `view_delete.content.html:12-18` always renders the confirm form; nothing reads
  `has_protected_objects` to disable the submit. `delete.py` `post()` keeps the write path (06.2-01-SUMMARY:
  "A database-PROTECT POST still raises `ProtectedError` (500)"). From the user's seat: a red box says "blocked",
  the blue button says "Delete", ticking the box and clicking yields a server error page. The phase deliberately
  deferred response handling, but it also shipped the flag that makes a disabled state a one-line template change.
- Loading/empty/error states on the manage page: `Permission Holders` has an empty state ("No permission holders
  found."); the new policy table has none, but a ViewSet always has at least the `manage` view, so an empty table
  is unreachable — acceptable.
- Information scent: the two renderings of the same policy (Pillar 2) give a developer contradictory-looking
  data (`None` vs `—`, `strict` vs the longer sentence) while verifying exactly the thing D-06 wanted to make
  clear.
- formset.js: regex change `^(?:(.*)-)?(None|pk)-(\d+)$` (`formset.js:154-156`), covered by
  `tests/js/formset.test.js` ("parses multi-digit and UUID parent pks"), vitest 234 passed per 06.2-03-SUMMARY.
  No DOM/visual change; nothing to capture.
- Not observed in a browser: alert `role="alert"` on page load for the blocked notice (screen readers will announce
  it; fine) — code-derived.
