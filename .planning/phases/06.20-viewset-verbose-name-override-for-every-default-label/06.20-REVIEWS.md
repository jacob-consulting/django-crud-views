### Agreed Concerns

No HIGH concern. Non-HIGH concerns raised by two or more reviewers, or confirmed by source grounding:

1. **The `PHASE_BASE` variable is overloaded in plan 02 (and the terminology in plans 01/03 drifts)** (astra MEDIUM,
   gemini LOW, grok LOW). Confirmed against the plan text. Plan 02's "Phase baseline" section tells the executor to
   set `PHASE_BASE=$(git rev-parse HEAD)` before plan 02's first commit. That HEAD already contains plans 01 and 03.
   The section's last sentence then says to use plan 01's earlier base for the phase-wide checks, but the verification
   commands (`06.20-02-PLAN.md:315-319`) read the same `${PHASE_BASE}` variable. With plan 02's own base,
   `git diff --stat "$PHASE_BASE" -- src` prints nothing, so "lists only `src/crud_views/lib/viewset/__init__.py`"
   fails, and the `docs/migrating-1.0.md` invariant is checked only against wave 2. grok also notes that the
   `:-$(git merge-base HEAD main)` fallback is still vacuous on `main` if the export is skipped. Plan 03 calls its own
   per-plan HEAD "the phase-start commit" (`06.20-03-PLAN.md:207,254`). **MEDIUM, actionable.** Fix: use two
   variables, an immutable `PHASE_BASE` (read from `06.20-01-SUMMARY.md`, taken before either wave-1 plan) and a
   per-plan `PLAN_BASE`. Use `PLAN_BASE` for the plan-scope gates. A missing `PHASE_BASE` should fail the gate on
   `main`, not fall back.
2. **D-02 "stored as given" is pinned only on the classmethod, not on a constructed instance** (astra LOW, grok LOW).
   `ViewSet.check_verbose_name(" volume ") == " volume "` does not go through construction. **LOW, actionable.** Fix:
   add one constructor assertion `ViewSet(..., verbose_name=" volume ").verbose_name == " volume "` to the existing
   lazy-probe `try`/`finally`, or to a second probe that pops its own name.
3. **The icon-mode rationale names the wrong configuration owner** (astra LOW, grok LOW; grok traced it). The ledger
   entry and `<interfaces>` cite `cv_book.context_actions_label_mode={"parent": "label"}` (`views.py:404`). For a
   button that `PublisherDetailView` renders, the mode comes from `cv_get_action_label_mode("context", ...)` on the
   rendering view, with `target_default` from `BookListView` (`base.py:460-470,615`), and then the `"icon"` floor
   (`label_mode.py:23-24`). The assertion still holds. Plan 02 already defers this concern explicitly in its ledger,
   so it is **not counted**. Correcting the one-line rationale is still recommended, so that an executor never "fixes"
   a failure by patching `cv_book`'s map.
