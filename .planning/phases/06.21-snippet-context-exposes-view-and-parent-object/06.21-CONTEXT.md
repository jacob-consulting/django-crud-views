# Phase 06.21: Snippet context exposes `view` and `parent_object` (#339) - Context

**Gathered:** 2026-11-09
**Status:** Ready for planning

<domain>
## Phase Boundary

The snippets a view renders for its own page (header, paragraph, the list/card filter header, and the success and
error messages) gain two context keys: `view`, which is the view instance, and on a child ViewSet a lazy
`parent_object`. Both are added in `CrudView.cv_get_meta()` only. As a result, texts such as
`"New book for {{ parent_object }}"` and `"Created {{ view.duplicate }} from {{ object }}"` render their values
instead of coming out empty. Default snippets render byte for byte as today.

Issue [#339](https://github.com/jacob-consulting/django-crud-views/issues/339) is the canonical specification. Its
"Proposed behaviour", "Decisions (do not reopen in planning)" and "Acceptance criteria" sections are authoritative.

</domain>

<decisions>
## Implementation Decisions

### Locked by issue #339 (carried forward, not reopened)
- **D-01:** Only instance-rendered snippets change. These are `cv_header_template[_code]`, `cv_paragraph_template[_code]`,
  `cv_message_template[_code]`, `cv_message_template_error[_code]` and `cv_filter_header_template[_code]` (list and
  card). All of them reach `cv_get_meta()` today (`base.py` `cv_get_message`, `cv_header`, `cv_paragraph`;
  `views/list.py:47`; `views/card.py:138`).
- **D-02:** The class-level label snippets keep their context unchanged. These are `cv_action_label_template[_code]`,
  `cv_action_short_label_template[_code]`, `cv_breadcrumb_label_template[_code]`, card actions, context buttons, row
  buttons and `LinkChildColumn`. They render through `cls.cv_viewset.get_meta(context)` or
  `ContextButton.render_label`, and there `context.view` is the hosting page's view, not the labelled one. This limit
  is documented; the code does not change.
- **D-03:** `ViewContext.to_dict()` stays `{"object": ...}`. `ViewSet.get_meta()` is untouched. The two keys are added
  in `cv_get_meta()` only.
- **D-04:** `view` is `self`. `parent_object` is a `django.utils.functional.SimpleLazyObject`, added only when
  `self.cv_viewset.has_parent`. On a top-level ViewSet the key is absent, so `{{ parent_object }}` renders empty
  rather than raising.
- **D-05:** The parent is resolved one level up only. There is no `ancestors` list and there are no `request` or
  `user` keys, since both are reachable as `view.request`.
- **D-06:** The change is not breaking. The changelog gets a `### Added` entry in `CHANGELOG.md`, and
  `docs/migrating-1.0.md` stays untouched.

### Unguarded fallback
- **D-07:** The lazy wrapper calls `self.cv_get_parent_object()` as it is, with no new resolution path. While the
  ancestor guard's state is present, the parent costs no query, because it comes from `_resolved_parent()`. Without
  that state (a direct `cv_get_meta()` call in a test, or a mixin rendering before dispatch), it falls back to the
  existing single `get_object_or_404` and lets `Http404` propagate, the same as any other `cv_get_parent_object()`
  caller. The wrapper must not catch errors or turn a missing parent into an empty string.

### Docs layout
- **D-08:** `docs/reference/templates.md` gets one new section with the canonical table of snippet variables
  (`object`, `view`, `parent_object`, `verbose_name`, `verbose_name_plural`, `verbose_name_translate`,
  `verbose_name_plural_translate`, `viewset`/`cv`). The same section states that action, short-action and breadcrumb
  labels (and buttons, and `LinkChildColumn`) do not get `view` or `parent_object`, and why. Today `templates.md`
  covers the base template only, so this is a new section, not an edit of an existing snippet description.
  `docs/reference/messages.md` gets a one-line summary that links to the table. `docs/reference/nested.md` shows the
  `cv_header_template_code = "New ... for {{ parent_object }}"` example and links to the table. Keeping one table
  means only one place to maintain.

### Claude's Discretion
- **E2E test vehicle (AC3):** The planner picks the smallest existing view that can carry it, without registering new
  ViewSets. A likely candidate is `AuthorPingView` (`tests/test1/app/views.py:133`, an `ActionViewPermissionRequired`
  whose `action()` can set an attribute). Another option is a book create view under the `Publisher` parent for the
  `{{ parent_object }}` header. Per-test patching of `cv_message_template_code` / `cv_header_template_code` is
  acceptable, but it must not leak between xdist workers or tests. Use `monkeypatch` or a restoring fixture.
- The exact placement of the new section inside `templates.md`, and whether `breadcrumb.md:74` (which already lists
  the label context) gets a one-line note that it has no `view`/`parent_object`.
- Test layout: a new test file versus extending existing snippet and message tests.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `cv_get_parent_object()` already does the guard-state reuse and the fallback. Wrap it in `SimpleLazyObject` and add
  no new logic.
- Test fixtures follow the `cv_<model>`, `user_<model>_<perm>` and `client_user_<model>_<perm>` conventions.
  `Book` is the child of `Publisher` (int PK), and `Author` is top-level (UUID PK).
- `AuthorPingView` (`tests/test1/app/views.py:133`) is an existing action view with `cv_message_template_code` and an
  `action()` hook.

### Established Patterns
- `render_snippet` builds a `django.template.Context` from the dict for `template_code`, or calls `render_to_string`
  for `template`. A `SimpleLazyObject` value resolves on first attribute or `str` access in either path.
- `cv_get_meta()` runs once per snippet, so laziness plus guard reuse gives zero additional parent queries for header,
  paragraph and message together (AC2).
- Phase 06.18 ancestor guard: `_cv_ancestor_state` is set in dispatch before any snippet renders on a guarded request.

### Integration Points
- `cv_get_meta()` is the only edit point in `src/`. The workflow, polymorphic, guardian and Resource views inherit it
  without overriding it (grep confirmed no other `cv_get_meta` or `cv_get_parent_object` overrides in `src/`).
- Phase 06.20 (ViewSet `verbose_name` override, running in parallel) edits `ViewSet.get_meta()`, not `cv_get_meta()`.
  A merge conflict is unlikely, but rebase onto whichever phase lands first.

</code_context>
