- **D-03:** `ViewContext.to_dict()` stays `{"object": ...}`. `ViewSet.get_meta()` is untouched. The two keys are added

- **D-04:** `view` is `self`. `parent_object` is a `django.utils.functional.SimpleLazyObject`, added only when

  rather than raising.
- **D-05:** The parent is resolved one level up only. There is no `ancestors` list and there are no `request` or
  `user` keys, since both are reachable as `view.request`.
- **D-06:** The change is not breaking. The changelog gets a `### Added` entry in `CHANGELOG.md`, and
  `docs/migrating-1.0.md` stays untouched.

#### Unguarded fallback
- **D-07:** The lazy wrapper calls `self.cv_get_parent_object()` as it is, with no new resolution path. While the
  ancestor guard's state is present, the parent costs no query, because it comes from `_resolved_parent()`. Without
  that state (a direct `cv_get_meta()` call in a test, or a mixin rendering before dispatch), it falls back to the
  existing single `get_object_or_404` and lets `Http404` propagate, the same as any other `cv_get_parent_object()`
  caller. The wrapper must not catch errors or turn a missing parent into an empty string.

#### Docs layout
- **D-08:** `docs/reference/templates.md` gets one new section with the canonical table of snippet variables

## Summary

This phase is a one-method additive change in `src/crud_views/lib/view/base.py` (`CrudView.cv_get_meta()`, lines
1096-1107) plus tests and docs. The method today returns `self.cv_viewset.get_meta(context)` and adds `object` when the
view has one. It will also add `view = self` and, when `self.cv_viewset.has_parent`, `parent_object =
SimpleLazyObject(self.cv_get_parent_object)`. Everything the issue asks for falls out of two existing mechanisms:
Django's `SimpleLazyObject` defers the callable until first proxied access (so an unreferencing snippet never pays),
and `cv_get_parent_object()` already reuses the ancestor guard's request-local `_cv_ancestor_state` (so the common case
costs no query). No new library, no new resolution path, no change to `ViewContext.to_dict()` or `ViewSet.get_meta()`.

I verified the design against the real test project with a monkeypatched `cv_get_meta()` (nothing in `src/` touched):
a Book create GET with header and paragraph both referencing `{{ parent_object }}` ran 1 Publisher query and 5 total
queries, identical to the unpatched page; `{{ view.duplicate }}` set in `AuthorPingView.action()` rendered in the
success message; a top-level Author view had no `parent_object` key and `[{{ parent_object }}]` rendered `[]`; a class
label `"x{{ view }}y"` still rendered `"xy"`; and a missing parent raised `Http404` from the render, as D-07 requires.
All 55 default snippet templates (core and Guardian) and the workflow app's literal `_template_code` defaults contain no
`view` or `parent_object` reference, so default output stays byte for byte.

Two things the planner must design around. First, running pytest from this worktree with the main checkout's venv
imports the **main checkout's** `src/crud_views` unless `PYTHONPATH=src` is set or a worktree venv is created with
`task dev`; a test run that "passes" could be exercising the wrong tree. Second, `cv_get_parent_object()` is already
called twice on a nested create GET by existing callers (the parent context button and the create-control state
helper), so the AC2 "never called" proof must spy on the *delta* introduced by the wrapper or test at the unit level,
not assert zero calls on a full request.

**Primary recommendation:** Add the two keys in `cv_get_meta()` exactly as D-04/D-07 specify (four lines), prove it
with one new test module `tests/test1/test_snippet_context.py` using the existing `BookCreateView` and
`AuthorPingView` plus `monkeypatch.setattr` on class attributes, and write the one canonical variable table in
`docs/reference/templates.md` with links from `messages.md` and `nested.md`.

### Pattern 1: The change in `cv_get_meta()`

**What:** Add `view` and a lazy `parent_object` after the existing `object` handling.
**When to use:** This is the whole implementation.

Current code, quoted verbatim `[VERIFIED: src/crud_views/lib/view/base.py:1096-1107]`:

```python
    def cv_get_meta(self) -> dict:
        """
        Metadata from ViewSet plus ViewContext
        """
        context = self.cv_get_view_context()
        data = self.cv_viewset.get_meta(context=context)

        # add view specific data
        if hasattr(self, "object"):
            data["object"] = self.object

        return data
```

Proposed (the exact shape the probe verified; `SimpleLazyObject` is not yet imported in `base.py` — the import block at
lines 16-29 has no `django.utils.functional` import `[VERIFIED: src/crud_views/lib/view/base.py:16-29]`):

```python
from django.utils.functional import SimpleLazyObject
...
        # add view specific data
        if hasattr(self, "object"):
            data["object"] = self.object
        data["view"] = self
        if self.cv_viewset.has_parent:
            # lazy: a snippet that never mentions it never resolves the parent; one that does reuses the
            # ancestor guard's resolved parent (no query) or falls back to cv_get_parent_object()'s 404
            data["parent_object"] = SimpleLazyObject(self.cv_get_parent_object)
        return data
```

Why the pieces hold:

- `ViewSet.get_meta()` returns exactly `viewset`, `cv`, `verbose_name`, `verbose_name_plural`,
  `verbose_name_translate`, `verbose_name_plural_translate` plus `context.to_dict()`
  `[VERIFIED: src/crud_views/lib/viewset/__init__.py:498-516]`, and `ViewContext.to_dict()` is
  `return {"object": self.object}` `[VERIFIED: src/crud_views/lib/view/context.py:44-45]`. Neither changes (D-03).
- `has_parent` is `return self.parent is not None` `[VERIFIED: src/crud_views/lib/viewset/__init__.py:287-288]`.
- `cv_get_parent_object()` first does `resolved = _resolved_parent(self); if resolved is not None: return resolved`,
  then `get_object_or_404(parent_model, pk=pk)` `[VERIFIED: src/crud_views/lib/view/base.py:1112-1131]`;
  `_resolved_parent` reads `getattr(view, "_cv_ancestor_state", None)` and returns `state.parent`
  `[VERIFIED: src/crud_views/lib/ancestors.py:443-446]`.
- `SimpleLazyObject.__init__` stores `self.__dict__["_setupfunc"] = func`; `_setup()` does
  `self._wrapped = self._setupfunc()` once, on first proxied access
  `[VERIFIED: .venv/lib/python3.12/site-packages/django/utils/functional.py:383-399]`. `callable(lazy)` is `False`,
  so Django's template engine does not try to call it `[VERIFIED: local render probe, Django 6.1.2]`.
- A Django page template already has `view`: `ContextMixin.get_context_data` does `kwargs.setdefault("view", self)`
  `[VERIFIED: .venv/lib/python3.12/site-packages/django/views/generic/base.py:31]` — the snippet key mirrors it.

### Anti-Patterns to Avoid
- **Catching `Http404` in the lazy wrapper** or returning `""` for a missing parent — violates D-07 and would hide a
  broken URL. Pass `self.cv_get_parent_object` to `SimpleLazyObject` directly; do not wrap it in a lambda that swallows.
- **Adding `view` in `ViewContext.to_dict()` or `ViewSet.get_meta()`** — leaks into every class-level label and
  `LinkChildColumn` (D-02/D-03).
- **Resolving the parent eagerly** (`data["parent_object"] = self.cv_get_parent_object()`) — turns every unguarded
  snippet render into a query or 404 even when the text never mentions the parent (fails AC2).
- **Adding `request`/`user` keys or an `ancestors` list** — D-05.
- **Asserting `cv_get_parent_object` is called zero times on a full nested request** — it is already called twice by
  existing code (Pitfall 2); the test will fail for the wrong reason.
- **Registering a new ViewSet or view in `tests/test1/app/views.py` for the E2E test** — excluded by AC3; also
  changes registration-inventory tests (STATE notes a prior fixture-expectation failure from exactly that).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Deferred parent resolution | A custom `__str__`/`__getattr__` proxy class or a `lambda` with caching | `django.utils.functional.SimpleLazyObject` | Proxies `__str__`, `__getattr__`, `__getitem__`, `__bool__`, `__eq__`, `__hash__`, `__iter__`, `__len__`, `__contains__`, `__class__`, `__repr__`; evaluates once; `copy`-safe; locked by D-04 |
| Parent lookup | A new `kwargs`-based lookup in `cv_get_meta()` | `self.cv_get_parent_object()` as is | Already reuses `_resolved_parent()` and falls back to `get_object_or_404` (D-07) |
| Query counting | Manual `connection.queries` diffing | `CaptureQueriesContext(connection)`; filter `captured_queries` by table name | Existing idiom in 10+ modules; attributes queries to `"app_publisher"` instead of asserting a brittle total |
| Reading flash messages | Parsing the redirected page | `get_messages(response.wsgi_request)` | Existing `_messages()` helper idiom |
| Per-test class-attribute override | `try/finally` restore blocks | pytest `monkeypatch.setattr(ViewClass, "cv_header_template_code", ...)` | Auto-restored per test; xdist workers are separate processes, so no cross-worker leak |
| Docs fence verification | A new docs parser | The `recipe(path, section, language)` helper pattern in `tests/test1/test_heading_docs.py:30-36` | Already asserts unique headings and exactly one fence per section |

**Key insight:** every piece of the behaviour already exists; the phase composes them in four lines. Any added
abstraction is cost without a demonstrated need under the project's Developer Maintainability rule.

### Pitfall 3: `Http404` propagates out of the render; `DoesNotExist` would not
**What goes wrong:** Expecting a missing parent to render empty. With no guard state and an unknown `publisher_pk`,

that on a nested view the key resolves "as `cv_get_parent_object()` does" (404 on a bad URL).

### Pitfall 4: `view` exposes zero-argument methods to the template engine
**What goes wrong:** `{{ view.get_object }}` runs a query; `{{ view.cv_get_parent_object }}` resolves the parent;
these are developer-authored texts, not user input, but reviewers may flag it.
**Why it happens:** Django calls any callable variable part that has no required arguments; methods needing
arguments render as `string_if_invalid`, and `alters_data`/`do_not_call_in_templates` suppress calls
`[CITED: docs.djangoproject.com/en/5.2/ref/templates/api/#variables-and-lookups]`.
**How to avoid:** Document that `view` in a snippet is the same object a page template already has under `view`
(Django's `ContextMixin`), so the exposure is not new. No code mitigation needed; `template_code` values are class
attributes set by the developer.
**Warning signs:** None in this phase; note it in the Security Domain.

### Pitfall 5: A project-level `string_if_invalid` changes the "renders empty" claim
