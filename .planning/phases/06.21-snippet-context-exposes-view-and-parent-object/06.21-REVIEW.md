## Warnings

### WR-01: `templates.md` misstates the context of button label templates and of `LinkChildColumn`

**Classification:** WARNING
**File:** `docs/reference/templates.md:187-190`
**Issue:** The paragraph says action labels, breadcrumb labels, "context, row and card buttons and `LinkChildColumn`
... get the same variables **except** `view` and `parent_object`". That is true for the target view's action and
short labels and for breadcrumb labels, which render through `cls.cv_viewset.get_meta(context)`
(`base.py:579-592`, `breadcrumb.py:122`). It is false in two of the listed cases:

1. A `ContextButton` with its own `label_template[_code]` does not get the snippet variables at all.
   `ContextButton.render_label()` (`view/buttons.py:63-67`) renders with `data = cls.cv_get_dict(...)`, the button
   dict of `cv_*` keys. Probe, `label_template_code="[VN:{{ verbose_name }}][VS:{{ viewset }}][O:{{ object }}][K:{{ cv_key }}][V:{{ view }}]"`
   on a `ContextButton(key_target="list")`: rendered `[VN:][VS:][O:][K:list][V:]`. So `verbose_name`, `viewset` and
   `object` are all absent there, not only `view` and `parent_object`. `context_buttons.md:122` already describes
   this context correctly ("receive the resolved `cv_label_mode`").
2. A `LinkChildColumn` template does see `view`. `LinkChildColumn.render()` (`table/columns.py:39-44`) adds the child
   ViewSet's meta to `extra_context`, and django-tables2 renders the column on top of the page context that
   `{% render_table table %}` (`view_list_table.content.html:3`) attaches to the table. Probe, a
   `LinkChildColumn(name="book", template_code="[V:{{ view.cv_key }}][P:{{ parent_object }}][O:{{ object }}][VN:{{ verbose_name_plural }}]")`
   on the Publisher list: rendered `[V:list][P:][O:None][VN:Books]`. `view` is the hosting list view, not empty.

Runtime behaviour is unchanged by this phase, and the changelog wording ("are unchanged") is correct. The defect is
that the canonical reference now tells a developer `{{ verbose_name }}` works in a button label template and
`{{ view }}` is empty in a child-link column. `test_snippet_variables_section_states_the_class_label_exclusion`
(`tests/test1/test_snippet_docs.py:44-49`) checks only that the needles `LinkChildColumn` and `except` are present,
so it pins the wording and not the behaviour; `test_label_class_level_action_label_does_not_see_view` covers
`cv_get_action_label` only.
**Fix:** Narrow the paragraph to what the code does, for example:

```markdown
Action labels (`cv_action_label_template[_code]`, `cv_action_short_label_template[_code]`) and breadcrumb labels
(`cv_breadcrumb_label_template[_code]`) are rendered *for* a target view *from* another page, also where they appear
on context, row and card buttons. They get the same variables **except** `view` and `parent_object`, because there
the hosting page's view is not the labelled view.

Two neighbours have their own context: a context button's own `label_template[_code]` gets the button data (the
`cv_*` keys, see [Context buttons](context_buttons.md)), and a `LinkChildColumn` template gets the child ViewSet's
variables on top of the list page's context, so `view` there is the hosting list view. Neither gets `parent_object`.
```

Then either drop `LinkChildColumn` from the needle list in `test_snippet_docs.py:46` or replace the needle check
with the two behaviour probes above.

### WR-02: The docs guard pins the variable table to a test constant, not to `cv_get_meta()`

**Classification:** WARNING
**File:** `tests/test1/test_snippet_docs.py:15-24`, `tests/test1/test_snippet_docs.py:33-36`
**Issue:** The module docstring calls the table "the one canonical list", but
`test_snippet_variables_table_lists_exactly_the_eight_names` compares the docs rows with the hard-coded `VARIABLES`
tuple. Nothing compares either of them with the keys the code produces. `tests/test1/test_snippet_context.py` has no
exact key-set assertion either: it checks `view`, `parent_object` and the absence of `request` / `user` /
`ancestors` (lines 64-65, 76-80). `cv_get_meta()` currently returns nine keys (`cv`, `object`, `parent_object`,
`verbose_name`, `verbose_name_plural`, `verbose_name_plural_translate`, `verbose_name_translate`, `view`,
`viewset`), which matches the table plus the `cv` alias today. A key added to or removed from `ViewSet.get_meta()`
or `cv_get_meta()` leaves both test files green and the table wrong. The risk is concrete: `06.21-CONTEXT.md`
records that Phase 06.20 edits `ViewSet.get_meta()` in parallel.
**Fix:** Tie the constant to the code in `test_snippet_context.py`, reusing the tuple:

```python
from tests.test1.test_snippet_docs import VARIABLES


@pytest.mark.django_db
def test_meta_keys_match_the_documented_table(publisher_penguin):
    child = _make_view(BookCreateView, publisher_pk=publisher_penguin.pk)
    assert set(child.cv_get_meta()) == {*VARIABLES, "cv"}
    top = _make_view(AuthorCreateView)
    assert set(top.cv_get_meta()) == {*VARIABLES, "cv"} - {"parent_object"}
```

### IN-01: "a bad URL raises 404" does not hold inside `{% if %}` operator expressions

**Classification:** INFO
**File:** `docs/reference/templates.md:180-182`
**Issue:** The section states that without guard state "a bad URL raises 404 rather than rendering an empty string".
Probed on `BookCreateView` with `publisher_pk=999999` and no guard state:

| Snippet | Result |
|---|---|
| `{{ parent_object }}`, `{{ parent_object.name }}`, `{{ parent_object\|default:'x' }}`, `{% firstof parent_object 'x' %}`, `{% if parent_object %}` | `Http404` |
| `{% if not parent_object %}EMPTY{% else %}SET{% endif %}` | renders `SET` |
| `{% if parent_object == 1 %}EQ{% else %}NE{% endif %}` | renders `NE` |

Django's smartif operators catch every exception and evaluate to `False`, so a missing parent takes the `else`
branch silently; `{% if not parent_object %}` reports a nonexistent parent as set. The wrapper itself does not
swallow anything (decision D-07 is met), and the case needs the unguarded path, which a dispatched request does not
take because the guard has already resolved the parent or answered 404. Hence Info.
**Fix:** Qualify the sentence, e.g. "... and a bad URL raises 404 when the snippet outputs or tests the variable
directly; Django's `{% if %}` operators (`not`, `==`, `in`, ...) swallow the error and evaluate to false".
