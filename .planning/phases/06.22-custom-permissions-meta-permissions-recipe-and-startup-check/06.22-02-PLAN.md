<objective>
Add the second half of `viewset.E269`: for every nested core ViewSet, the permission-map keys of its effective Read and
Write pairs (explicit or inherited from the global default) and of every `actions` pair must exist in the declared
permission set of the ancestor they apply to — `nearest` against the nearest protected ancestor, `higher` against every
farther protected ancestor — mirroring the request-time resolution of `_authorize_ancestors` but reading
`_declared_permission_keys(ancestor.model)` instead of `ancestor.permissions`. Emitted from `check_ancestor_declarations`
behind the `completed` barrier next to plan 01's half (D-09). GitHub issue #341 is the canonical specification;
CONTEXT.md D-11, D-12, D-15 and D-16 bind this plan.

Purpose: `nearest="approve"` on a Book ViewSet whose Publisher has no `approve_publisher` permission starts fine today
and fails with `ImproperlyConfigured` from `_permission_name` on the first nested request. After this plan the same
mistake is a startup error naming the key, where it came from (`actions['approve'].nearest`, `ancestor_policy.read`,
`global CRUD_VIEWS_ANCESTOR_READ_PERMISSIONS`), the ViewSet and the ancestor model. The mechanism is one small
`_requirement_source` sibling of `_operation_requirements` (so engine and check share one code path) and one loop over
the data the engine already produces; the request path keeps its authorization semantics — `_operation_requirements`
now delegates to `_requirement_source`, which additionally builds the D-11 source label, and the pair it returns is
pinned by the 06.18 engine tests.

Output: `src/crud_views/lib/ancestors.py` with `_requirement_source` and the delegating `_operation_requirements`;
`src/crud_views/checks.py` with `_ancestor_pair_messages` wired into `check_ancestor_declarations`; ten tests appended
to `tests/test1/test_permission_declarations.py` (24 functions after this plan) covering ROADMAP success criteria 3,
the pair part of 4 and the zero-DB assertion of 5; the D-16 test in `tests/test1/test_missing_permission_access.py`.

Plan 01's tracer proved the slot end to end; this plan's Task 1 is the tracer of the pair half (one `actions` key
missing on one ancestor, proven through `run_checks`), Task 2 expands it with the skips, D-16 and D-15.

## Flagged assumptions from spec-less probe

Carried from plan 01 (visible skip recorded there: no requirement IDs, no SPEC). Decisions specific to this plan:

- **D-12 de-duplication key** is `(key, ancestor.name)` within one checked ViewSet, literally as D-12 states; the
  message keeps the first source encountered in registration order (RESEARCH.md A2 noted the alternative of including
  the source in the key — rejected: the fix is on the model, one message per missing codename per ancestor is enough).
- **Which ancestors are checked:** exactly the entries of `_selected_gates(viewset, chain)` (so `"none"` ancestors
  and, without cascade, the farther ancestors are never visited — the engine's own selection) filtered by
  `_has_model_vocabulary(ancestor)` (skips Guardian-class ancestors, including those declaring `provider="model"`,
  Pitfall 3, and Resources, which cannot be parents anyway — E261).
- **Why iterate registered views instead of "always check read, write and actions" (decision of record for review
  A5):** the Write pair applies only if a Write-family view is registered; a read-only child under an ancestor without
  `change` must not get a false error. The Read pair is always exercised because `register()` auto-creates the `manage`
  view (Read family) for every non-Resource ViewSet. The same rule is kept for an *explicitly* declared
  `ancestor_policy.read` / `ancestor_policy.write` when no registered view of that family exists (gemini's suggestion to
  check explicit pairs regardless of registered views is rejected): the check's correctness is defined as mirroring
  `_authorize_ancestors`; a pair that no registered view applies can never fail at request time, so flagging it would
  break startup for a configuration #341 promises is not breaking ("a project whose existing configuration fails the
  new check was already failing at request time"); the moment a view of that family is registered, the same check
  fires at startup, so no request-time failure escapes. Smallest mechanism per CLAUDE.md's maintainability rule;
  pinned both ways by `test_pairs_are_checked_only_through_registered_views` (Task 2) and recorded as T-06.22-08.
- `_requirement_source` raises the same `ImproperlyConfigured` as `_operation_requirements` did (E268's case); the
  message builder catches it and continues.
