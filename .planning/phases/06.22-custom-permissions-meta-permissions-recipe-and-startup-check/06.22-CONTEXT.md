# Phase 06.22: Custom permissions: `Meta.permissions` recipe and startup check for `cv_permission` and ancestor pair keys (#341) - Context

**Gathered:** 2026-11-09
**Status:** Ready for planning

<domain>
## Phase Boundary

A view that is not a CRUD operation ("Run subscriptions", "Duplicate order", "Approve") can be given a permission of
its own by a documented recipe, and an undeclared or misspelled permission key fails at startup instead of on the first
request. Two deliverables:

1. **Docs.** `docs/reference/custom_form_view.md` gains a section with the recipe: `cv_permission` is a key of the
   ViewSet's permission map, the keys are the model's permission codenames with the `_<model>` suffix stripped (the same
   `removesuffix` keying as `ViewSet.default_permissions`), so a non-CRUD endpoint declares a `Meta.permissions` entry
   and names the stripped key. `docs/reference/action_view.md` points to the section. `docs/reference/guardian.md` states
   that Guardian ViewSets are not covered by the new check. `docs/reference/nested.md` lists the check in its
   "Configuration errors" table. `CHANGELOG.md` gains a `### Added` entry.
2. **Check.** A new static, database-free system check `viewset.E269` on core `ViewSet`s: (a) every registered view that
   subclasses `CrudViewPermissionRequiredMixin` has a `cv_permission` that is a key of the model's *declared* permission
   set (`Meta.default_permissions` plus `Meta.permissions`, keyed like `default_permissions`); (b) every nested core
   ViewSet's effective Read and Write pairs and every `actions` pair resolve on the ancestor they apply to (`nearest`
   on the nearest protected ancestor, `higher` on every farther protected ancestor). Skipped for `GuardianViewSet`
   (as checked ViewSet or as ancestor), Resource ViewSets (`E260`) and ancestors with provider `"none"`. `E202` and the
   request-time `assert` / `ImproperlyConfigured` stay as backstops.

Issue [#341](https://github.com/jacob-consulting/django-crud-views/issues/341) is the canonical specification. Its
"Proposed behaviour", "Decisions (do not reopen in planning)", "Acceptance criteria" and "Out of scope" sections are
authoritative. Criterion 1 was corrected in the issue body during this discussion (D-01). The ROADMAP.md Phase 06.22
entry repeats the scope and success criteria.

Locked by #341 (not re-discussed):
- Docs and check in one phase. Core `ViewSet` only; Guardian documented as unsupported because its permission map is
  discovered on whatever type `GUARDIAN_GET_CONTENT_TYPE` resolves. Static derivation from `Meta`, never from
  `Permission` rows. Error, not warning. Ancestor pair values covered. `E202` unchanged. No new API (no `cv_permission`
  auto-derivation, no helper, no change to `default_permissions` keying). Not breaking: `### Added` entry,
  `docs/migrating-1.0.md` untouched.

Carried forward from Phase 06.18: structural checks query no model, ContentType, Permission or grant tables;
completion-dependent checks run only after `_url_configuration_loaded()` is true. From 06.19/06.20: keep the change
minimal under the maintainability rule; tests never leak ViewSets into the registry.

</domain>

<decisions>
## Implementation Decisions

### Proxy and inherited models
- **D-01:** The declared permission set of a ViewSet is read from `model._meta.concrete_model._meta`, not from a proxy's
  own `Meta`. — **Reversibility:** reversible — a one-line attribute choice, but changing it later silently changes
  which projects get errors.
  - Why: `ViewSet.default_permissions` calls `ContentType.objects.get_for_model(model)` with the default
    `for_concrete_model=True`, so a `PublisherProxy` ViewSet resolves `view` to `app.view_publisher` at request time.
    The check mirrors the runtime map. Issue #341 criterion 1 originally said "proxy ... use their own Meta"; the issue
    body was edited to this decision.
- **D-02:** Multi-table-inheritance children use their own `Meta` only. `get_for_model(child)` returns the child's
  content type, so the runtime map holds only the child's permissions; no union with parent models.
- **D-03:** A model whose `default_permissions` omits an action (e.g. `("add", "change", "delete")` like the test-project
  `Royalty`) and a `*PermissionRequired` view that still names it (`view`) is an ordinary E269 error with the standard
  message. No special-cased hint.
- **D-04:** The correction to criterion 1 is recorded in the #341 issue body (criterion 1 rewritten, one Decisions
  bullet added), so the issue stays the single canonical spec the planner reads.

### Docs example and shape
- **D-05:** The recipe section in `docs/reference/custom_form_view.md` extends the page's own `AuthorContactView`
  example: `Author` gains `Meta.permissions = [("contact_author", "Can contact an author")]` and the view sets
  `cv_permission = "contact"`. The no-object `SiteFeedbackView` gets a one-line note that the same applies. The demo's
  `CustomerSubscription` / "run" case is mentioned only as motivation, if at all; no second model vocabulary on the page.
- **D-06:** The nested case is one sentence plus a link: a nested custom endpoint additionally needs an
  `ancestor_policy.actions` pair whose keys resolve on the *ancestor* model, see `docs/reference/nested.md`
  "Example: permissions for a nested Book ViewSet". No second code block in the recipe section.
- **D-07:** The Guardian note is appended to the existing "Configured content-type defaults" section of
  `docs/reference/guardian.md` (one or two sentences): E269 skips `GuardianViewSet`s because their map is discovered on
  the resolver's type; the request-time assert stays.
- **D-08:** The recipe code block is an executed fence, following `tests/test1/test_ancestor_docs.py` (`INVENTORY`,
  `_section` / `FENCE`, exec against `myapp.*` backed by test-app models). The test asserts E269 is silent for the
  published recipe and fires when the key is misspelled. — **Reversibility:** reversible.
  - Constraint for the planner: the fence shows a model `Meta`; a test cannot exec a model class definition as a live
    model. The fence's view half execs against the real test-app `Author`, which therefore declares `contact_author`
    (D-14). The fence may show the `Meta` as a separate, non-executed snippet or the executable fence may import
    `Author` from `myapp.models` as the page already does — planner's call, as long as the published source is what runs.

### Check messages and timing
- **D-09:** Both halves of E269 are emitted from `check_ancestor_declarations` in `src/crud_views/checks.py`, behind the
  existing `_url_configuration_loaded()` barrier, like E267/E268. One place, one timing rule; views that the URLconf
  does not import are not checked, as today. — **Reversibility:** reversible.
- **D-10:** Hint for an undeclared `cv_permission` spells out the entry to add, with the codename derived as
  `<key>_<model_name>`: e.g. `add ("run_customersubscription", "...") to CustomerSubscription.Meta.permissions, or use
  the non-PermissionRequired view variant`. Mirrors the E260 hint.
- **D-11:** A pair message names the key, where it came from, the ViewSet and the ancestor model: e.g.
  `ancestor permission key 'approve' (actions['approve'].nearest) of ViewSet 'book' is not declared on model
  app.Publisher`. Inherited pairs name their source: `ancestor_policy.read.nearest` or
  `global CRUD_VIEWS_ANCESTOR_READ_PERMISSIONS.nearest` (and `write` likewise).
- **D-12:** One `Error` per unresolved (key, ancestor) pair. Three protected ancestors missing the same `higher` key
  produce one message each.

### Test strategy
- **D-13:** E269 tests build throwaway models inside `isolate_apps("tests.test1.app")` with `app_label = "app"`,
  following `tests/test1/test_ancestor_authorization.py`: custom `Meta.permissions`, trimmed `default_permissions`, a
  proxy of an existing model. No table is created; the check is static. Uniquely named ViewSets, registry and
  `_VOCAB_CACHE` restored (pattern: `tests/test1/test_ancestor_structure.py` `registry` fixture).
- **D-14:** `tests/test1/app/models.py` `Author` declares `("contact_author", "Can contact an author")` in
  `Meta.permissions`. The test app has no migrations directory, so no migration file is needed. This is the only
  shared-model change.
- **D-15:** Zero database access is asserted with `django_assert_num_queries(0)` around `check_ancestor_declarations()`
  (or the two message builders) on a populated registry.
- **D-16:** `tests/test1/test_missing_permission_access.py` keeps its deliberate `cv_permission = "undeclared_action"`
  fixture (its tests never run the system checks). One test is added there asserting the fixture yields exactly one
  E269 from `check_ancestor_declarations()`, tying the request-time and startup diagnostics together.

### Claude's Discretion
- How "Guardian" is detected without importing the guardian app into core. Suggested: skip when
  `type(viewset)._ancestor_provider != "model"` (core is `"model"`, Guardian `"guardian"`), and skip ancestors whose
  `_effective_provider(...)` is not `"model"` (covers `"none"` and Guardian in one rule). Any equivalent that keeps core
  importable without Guardian is fine.
- Name and location of the declared-set helper (a small function next to `_action_declaration_problems` in
  `src/crud_views/lib/ancestors.py`, or in `checks.py`). It must reuse the `removesuffix(f"_{model_name}")` keying of
  `default_permissions` verbatim; consider extracting that one expression so both read the same code.
- Exact message wording beyond D-10/D-11, test module names (one new `tests/test1/test_permission_declarations.py`
  or split), the `### Added` changelog sentence, the `nested.md` configuration-errors row text and the
  `action_view.md` pointer sentence.
- Whether the docs fence shows the `Meta` snippet separately from the executable view fence (see D-08 constraint).

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `check_ancestor_declarations` + `_url_configuration_loaded()`: the completion-gated check slot E269 joins.
- `_walk_ancestors`, `_effective_provider`, `_effective_cascade`, `_effective_pair`, `_selected_gates`: already compute,
  statically, which ancestors are protected and which half of a pair applies to each. The pair half of E269 is a loop
  over `_selected_gates(viewset, chain)` plus `_operation_requirements(view_class)` for every registered view, resolving
  each key against the ancestor's declared set instead of its runtime map.
- `_action_declaration_problems` / `_ancestor_action_messages`: message-list shape and hint convention to copy.
- `isolate_apps` throwaway-model pattern and the `registry` fixture for isolation.

### Established Patterns
- `cv_permission` is declared only on `*PermissionRequired` classes; plain views' `cv_has_access` returns `True`. So
  "views that subclass `CrudViewPermissionRequiredMixin`" is exactly the set that consumes the key.
- Runtime permission map: `Permission.objects.filter(content_type=get_for_model(model))` keyed by
  `codename.removesuffix(f"_{content_type.model}")`. The declared set must produce the same keys from
  `concrete_model._meta.default_permissions` (`f"{action}_{model_name}"` → `action`) and `concrete_model._meta.permissions`
  (codename → `removesuffix`), where `model_name` is `concrete_model._meta.model_name`.
- `W280` (`crud_views/lib/check.py`) is about unknown `cv_*` attribute names and does not overlap with E269.
- Check ids in use end at `viewset.E268`; `E269` is free.

### Integration Points
- `src/crud_views/checks.py` `check_ancestor_declarations`: add the two message builders behind `completed`.
- `src/crud_views/lib/ancestors.py` (or `checks.py`): one declared-set helper.
- Docs: four pages plus CHANGELOG. Tests: one new module, one added test in `test_missing_permission_access.py`, one
  `Meta.permissions` line on the test-app `Author`, one docs-fence inventory entry.
