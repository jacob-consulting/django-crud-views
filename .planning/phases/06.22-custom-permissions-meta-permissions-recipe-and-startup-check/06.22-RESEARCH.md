### Locked Decisions

#### Proxy and inherited models
- **D-01:** The declared permission set of a ViewSet is read from `model._meta.concrete_model._meta`, not from a proxy's
  own `Meta`. — **Reversibility:** reversible — a one-line attribute choice, but changing it later silently changes
  which projects get errors.
  - Why: `ViewSet.default_permissions` calls `ContentType.objects.get_for_model(model)` with the default
    `for_concrete_model=True`, so a `PublisherProxy` ViewSet resolves `view` to `app.view_publisher` at request time.
    The check mirrors the runtime map. Issue #341 criterion 1 originally said "proxy ... use their own Meta"; the issue
    body was edited to this decision.
- **D-02:** Multi-table-inheritance children use their own `Meta` only. `get_for_model(child)` returns the child's
  content type, so the runtime map holds only the child's permissions; no union with parent models.
- **D-03:** A model whose `default_permissions` omits an action (e.g. `("add", "change", "delete")` like the test-project
  `Royalty`) and a `*PermissionRequired` view that still names it (`view`) is an ordinary E269 error with the standard
  message. No special-cased hint.
- **D-04:** The correction to criterion 1 is recorded in the #341 issue body (criterion 1 rewritten, one Decisions
  bullet added), so the issue stays the single canonical spec the planner reads.

  `cv_permission = "contact"`. The no-object `SiteFeedbackView` gets a one-line note that the same applies. The demo's

## Summary

The phase adds one static system check (`viewset.E269`) with two halves plus a documented recipe. Everything the check
needs already exists as static, database-free helpers from Phase 06.18: `_walk_ancestors`, `_selected_gates`,
`_operation_requirements`, `_effective_pair`, `_effective_provider`, the completed-registry barrier
`_url_configuration_loaded()` and the `check_ancestor_declarations` slot. The only new primitive is a declared-set
helper that mirrors `ViewSet.default_permissions` without the database: codenames from
`concrete_model._meta.default_permissions` (via Django's public `get_permission_codename(action, opts)`) plus
`concrete_model._meta.permissions`, each keyed by `codename.removesuffix(f"_{opts.model_name}")`. This is provably the
same keying as the runtime map because `ContentType.objects.get_for_model(model)` resolves `opts = model._meta.concrete_model._meta`
and stores `model=opts.model_name`, so `content_type.model == concrete_model._meta.model_name` for every model
`[VERIFIED: django/contrib/contenttypes/models.py:26-61 in .venv]`.

A dry run of exactly this rule over the shared test registry (33 ViewSets, URLconf imported) found **zero** would-be
E269 errors, and both `check_ancestor_declarations()` and `check_viewsets()` already run with a DB blocker installed
without touching the database — so criterion 5 ("passes unchanged", "no database query") is achievable with no
test-fixture surgery beyond the planned `Author.Meta.permissions` line. Two environment facts matter for execution: this
worktree had **no `.venv`** at research start (created during research with `task dev`), and `task dev` installs the
package **non-editable**, so tests would have exercised a stale site-packages snapshot; research switched it to an
editable install (`uv pip install --python .venv/bin/python -e . --no-deps`), which the planner must keep as a Wave 0
precondition for any fresh worktree.

**Primary recommendation:** Put one pure helper `_declared_permission_keys(model)` (and the shared one-liner
`_permission_key(codename, model_name)`) in `src/crud_views/lib/ancestors.py`; build the pair messages there next to
`_action_declaration_problems`; build the `cv_permission` messages in `src/crud_views/checks.py` (where
`CrudViewPermissionRequiredMixin` can be imported without a cycle); emit both from `check_ancestor_declarations` behind
`completed`; skip by **class** provider (`type(vs)._ancestor_provider != "model"`) for both the checked ViewSet and
ancestors, plus `_effective_provider(ancestor) == "none"` and `is_resource`.

`[VERIFIED: django/db/models/options.py:173-174]` `label = "%s.%s" % (self.app_label, self.object_name)` (gives `app.Publisher`, the D-11 format).
`[VERIFIED: django/contrib/auth/__init__.py:363-367]` `get_permission_codename(action, opts)` → `"%s_%s" % (action, opts.model_name)`.
`[VERIFIED: django/contrib/auth/management/__init__.py:18-34, 80-103]` `create_permissions` creates `[*_get_builtin_permissions(opts), *opts.permissions]` for each model, with the content type from `get_for_models(*models, for_concrete_models=False)`.

Consequences (all follow from the quoted code; probe-confirmed):
1. Runtime map for a core ViewSet on model `M` = permission rows of CT `(concrete(M)._meta.app_label, concrete(M)._meta.model_name)`, keyed `codename.removesuffix(f"_{concrete(M)._meta.model_name}")`.
2. Rows that exist after `migrate` for that CT are exactly `get_permission_codename(a, opts) for a in opts.default_permissions` + `[c for c, _ in opts.permissions]` with `opts = concrete(M)._meta` — so the static set is: `{_permission_key(c, opts.model_name) for c in those codenames}`.
3. **Proxy:** rows for the proxy's own `Meta` are created under the proxy's own CT (`for_concrete_models=False`), which the core runtime map never reads. D-01 (read `concrete_model._meta`) is correct, and a `Meta.permissions` entry placed on the proxy class would **not** fix an E269 — the hint must name the concrete model (`opts.object_name`), see Pitfall 2.
4. **MTI child:** `Car._meta.concrete_model is Car` (probe) → its own `Meta` (D-02) with no extra code.
5. Default actions: `removesuffix` on `f"{action}_{model_name}"` always returns `action` (suffix is literally appended), so using one expression for both lists is safe and is the "same code" CONTEXT asks for.

### Helper — `src/crud_views/lib/ancestors.py`, next to `_action_declaration_problems`
```python
# Source: mirrors ViewSet.default_permissions (src/crud_views/lib/viewset/__init__.py:475-483) statically
from django.contrib.auth import get_permission_codename

def _permission_key(codename: str, model_name: str) -> str:
    """The permission-map key of a codename: Django codenames are '<action>_<model>'; strip only the exact
    terminal suffix (a custom 'change_book_status' on Book keeps its full codename)."""
    return codename.removesuffix(f"_{model_name}")

def _declared_permission_keys(model: type[Model]) -> set[str]:
    """Static mirror of the runtime permission map's keys: the model's declared permissions
    (``Meta.default_permissions`` plus ``Meta.permissions``) of the *concrete* model, because
    ``ContentType.objects.get_for_model(model)`` resolves proxies to their concrete model. No database."""
    opts = model._meta.concrete_model._meta
    codenames = [get_permission_codename(action, opts) for action in opts.default_permissions]
    codenames += [codename for codename, _name in opts.permissions]
    return {_permission_key(codename, opts.model_name) for codename in codenames}
```

```python
def _permission_key_messages(viewsets) -> list:
    """viewset.E269 (half 1): a *PermissionRequired view whose cv_permission is not a declared permission of the
    ViewSet's (concrete) model. Core ViewSets only; Resource ViewSets are E260's; None is E202's."""
    messages = []
    for viewset in viewsets:
        if viewset.is_resource or type(viewset)._ancestor_provider != "model":
            continue
        declared = _declared_permission_keys(viewset.model)
        opts = viewset.model._meta.concrete_model._meta
        for key, view_class in viewset.get_all_views().items():
            if not issubclass(view_class, CrudViewPermissionRequiredMixin):
                continue
            permission = view_class.cv_permission
            if permission is None or permission in declared:
                continue
            messages.append(Error(
                f"cv_permission {permission!r} of view {key!r} is not declared on model {opts.label}",
                hint=(f"add ({permission}_{opts.model_name!r}, \"...\") to {opts.object_name}.Meta.permissions, "
                      f"or use the non-PermissionRequired view variant"),
                obj=viewset, id="viewset.E269"))
    return messages
```

```python
def _ancestor_pair_problems(viewset: ViewSet) -> list[str]:
    if viewset.parent is None or viewset.is_resource or type(viewset)._ancestor_provider != "model":
        return []
    try:
        chain = _walk_ancestors(viewset)          # E266 reports structure problems; nothing to resolve here
    except _AncestryError:
        return []
    selected = _selected_gates(viewset, chain)    # index -> "nearest" | "higher"
    seen, problems = set(), []
    for view_class in viewset.get_all_views().values():
        try:
            source, pair = _requirement_source(view_class)   # see below
        except ImproperlyConfigured:
            continue                                # E268 reports the missing actions entry
        for index, side in selected.items():
            ancestor = chain[index][1]
            if ancestor.is_resource or type(ancestor)._ancestor_provider != "model" or _effective_provider(ancestor) != "model":
                continue                            # Guardian / "none" / Resource ancestors are not checked
            key = getattr(pair, side)
            item = (f"{source}.{side}", key, ancestor.name)
            if item in seen:
                continue
            seen.add(item)
            if key not in _declared_permission_keys(ancestor.model):
                problems.append(f"ancestor permission key {key!r} ({item[0]}) of ViewSet {viewset.name!r} is not "
                                f"declared on model {ancestor.model._meta.concrete_model._meta.label}")
    return problems
```
`_requirement_source(view_class) -> tuple[str, AncestorPermissions]` is a small sibling of `_operation_requirements`
that returns the D-11 label with the pair: `f"actions[{key!r}]"` when `key in policy.actions`; else for family
read/write: `f"ancestor_policy.{family}"` when `getattr(policy, family) is not None`, else
`f"global CRUD_VIEWS_ANCESTOR_{family.upper()}_PERMISSIONS"`; else raise the same `ImproperlyConfigured` as
`_operation_requirements`. Either refactor `_operation_requirements` to `return _requirement_source(view_class)[1]`
(one code path) or keep both — maintainability favors the refactor since the branch logic is 6 lines.

Why iterate registered views instead of "always check read, write and actions": the Write pair applies only if a
Write-family view is registered; a read-only nested child under an ancestor without `change` would otherwise get a
false error. The Read pair is always exercised because `manage` is auto-registered for every non-Resource ViewSet
(`[VERIFIED: viewset/__init__.py:192-195]`), which matches "passes with the default pairs for Book under Publisher".

De-duplication: `(source.side, key, ancestor)` gives one `Error` per unresolved key per ancestor per source — D-12's
"three protected ancestors missing the same `higher` key produce one message each" holds; two views sharing the Read
pair produce one message. (If the planner prefers D-12 literally as `(key, ancestor)`, drop `source` from `item`
and keep the first source in the message.)

### Pattern 1: Completion-gated registry check (copy of E267/E268)
**What:** Build `Error(...)` lists from pure functions over `list(_REGISTRY.values())`, emitted only when
`_url_configuration_loaded()` is true. **When to use:** anything that depends on views registered by late-imported
modules. **Example:** `_ancestor_action_messages` above `[VERIFIED: checks.py:64-75]`.

### Pattern 2: Static selection reuse
**What:** Use `_walk_ancestors` + `_selected_gates` + the pair resolver exactly as `_authorize_ancestors` does at
request time (`[VERIFIED: ancestors.py:404-439]`: `chain = _validate_ancestor_structure(viewset)`, `pair =
_operation_requirements(type(view))`, `selected = _selected_gates(viewset, chain)`, `key = pair.nearest if
selected[index] == "nearest" else pair.higher`, `permission = _permission_name(viewset, ancestor, key, view.cv_key)`).
The check mirrors this loop with `_declared_permission_keys(ancestor.model)` in place of `ancestor.permissions`.

### Anti-Patterns to Avoid
- **Reading `Permission`/`ContentType` rows in a check** — forbidden by 06.18 decisions and #341; use `_meta` only.
- **Using the proxy's own `Meta`** — diverges from the runtime map (D-01).
- **Skipping Guardian by `isinstance(viewset, GuardianViewSet)`** — imports the optional app into core; use the
  class attribute `_ancestor_provider`.
- **Checking the Write pair for ViewSets without Write views** — false positives on read-only children.
- **Importing `crud_views.lib.view` at module level in `ancestors.py`** — `viewset/__init__.py:17` imports
  `ancestors`; keep ancestors free of view/viewset runtime imports.
- **Changing `E202`, `permission_required`'s assert or `_permission_name`** — locked as backstops.

## Common Pitfalls

### Pitfall 1: Adding `class Meta:` to `Author` drops its ordering
**What goes wrong:** `Author(OrderedModel)` has no `Meta` today and inherits the abstract `OrderedModel.Meta`
(`ordering = ("order",)`). Declaring `class Meta: permissions = [...]` replaces it and Author lists become unordered,
which can break goldens/ordering assertions across the suite.
**How to avoid:** `class Meta(OrderedModel.Meta): permissions = [("contact_author", "Can contact an author")]` — the
pattern `FolderTask.Meta(OrderedModel.Meta)` already uses `[VERIFIED: tests/test1/app/models.py:331; ordered_model/models.py:432-434; probe Author._meta.ordering == ('order',)]`.
**Warning signs:** `Author._meta.ordering != ('order',)` after the edit.

### Pitfall 2: The hint must name the concrete model for proxies
**What goes wrong:** For a ViewSet on `PublisherProxy`, telling the user to add the entry to
`PublisherProxy.Meta.permissions` would create the row under the proxy's own content type (Django creates permissions
with `for_concrete_models=False`), which the core runtime map (`get_for_model(model)` → concrete) never reads.
**How to avoid:** derive `opts = model._meta.concrete_model._meta` once and use `opts.object_name`, `opts.model_name`,
`opts.label` in messages and hints `[VERIFIED: django auth/management/__init__.py:80-82; contenttypes/models.py:26-29]`.

### Pitfall 3: Guardian ancestor with `provider="model"`
**What goes wrong:** `_effective_provider(ancestor) == "model"` for a `GuardianViewSet(ancestor_policy=AncestorPolicy(provider="model"))`,
but `_permission_name` still reads `ancestor.permissions` → Guardian's resolver-based map. Checking it against
`concrete_model._meta` could be wrong in both directions (the locked rationale for skipping Guardian).
**How to avoid:** skip ancestors by class (`type(ancestor)._ancestor_provider != "model"`) **and** by effective
provider `"none"`.

### Pitfall 4: `_operation_requirements` raises for unclassified endpoints
**What goes wrong:** a nested `ActionView` without its `actions` entry raises `ImproperlyConfigured` from
`_operation_requirements` `[VERIFIED: ancestors.py:325]`; an uncaught raise would crash the whole check run.
**How to avoid:** `except ImproperlyConfigured: continue` — E268 already reports that case.

### Pitfall 5: Resource models have no `_meta`
**What goes wrong:** `viewset.model._meta` on a Resource ViewSet raises `AttributeError`.
**How to avoid:** test `viewset.is_resource` / `ancestor.is_resource` first (E260 and E261 own those cases).

### Pitfall 6: Only one `python` fence per executed docs section; heading unique on the page
**What goes wrong:** `_fence` asserts exactly one fence and `_section` exactly one heading occurrence; a second fence
(the `Meta` snippet) in the same section fails `test_inventory_heading_and_fence_occur_once`.
**How to avoid:** split into `###` subsections; put only the executable one in `INVENTORY`.

### Pitfall 7: The worktree venv is non-editable after `task dev`
**What goes wrong:** `task dev` runs `uv pip install --upgrade .[all,dev,test,examples] ...` (non-editable
`[VERIFIED: taskfile.yaml dev-install]`), so `import crud_views` resolved to `site-packages` and tests would have
exercised a snapshot, not `src/` edits. The main checkout's venv is editable (resolves to `src/`).
**How to avoid:** after `task dev`, run `uv pip install --python .venv/bin/python -e . --no-deps` and verify
`.venv/bin/python -c "import crud_views; print(crud_views.__file__)"` prints `.../src/crud_views/__init__.py`
(done in this worktree during research `[VERIFIED: direct_url.json "editable":true]`).

### Pitfall 8: Double reporting with E202 / E260
**How to avoid:** skip `cv_permission is None` (E202) and Resource ViewSets (E260) in half 1.

### Pitfall 9: `CRUD_VIEWS_STRICT=True` in tests
**What goes wrong:** registering throwaway views with default `cv_context_actions`/`cv_list_actions` that name
unregistered keys fails at class creation under strict mode.
**How to avoid:** the `_view` helper's empty lists, or `override_settings(CRUD_VIEWS_STRICT=False)` as the docs harness
does `[VERIFIED: test_ancestor_docs.py:156]`.
