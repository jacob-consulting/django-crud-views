  - *Why it matters:* While skipping the *inherited* global `CRUD_VIEWS_ANCESTOR_WRITE_PERMISSIONS` on a read-only child avoids false positives when an ancestor omits `change` from `default_permissions`, an **explicitly declared** `policy.read` or `policy.write` (`policy.read is not None` / `policy.write is not None`) on a nested `ViewSet` is an explicit configuration on that `ViewSet` (and is displayed by `ManageView.get_ancestor_policy_data()` in `src/crud_views/lib/views/manage.py:153-154`), and ROADMAP SC-3 / CONTEXT.md Domain 2(b) state that `E269` fires for a nested `ViewSet` whose `actions`, Read or Write pair names a key the ancestor model does not declare.
- **LOW — Deduplication by `(key, ancestor.name)` hides secondary misconfigured sources on the same `ViewSet` when the mistake is a typo in `AncestorPolicy` (`06.22-02-PLAN.md` Task 1):**
  - *Mechanism:* Task 1 deduplicates `seen` by `(key, ancestor.name)` within each `ViewSet`, rationale being "the fix is on the model, one message per missing codename per ancestor is enough." However, when the mistake is a typo in `AncestorPolicy` (which the hint explicitly recognizes: `or change the pair on ViewSet {viewset.name!r}`), e.g., both `ancestor_policy.read` (exercised first by `_AutoManageView`) and `actions['stamp']` contain the typo `"vieww"`, deduplicating by `(key, ancestor.name)` reports only `(ancestor_policy.read.higher)` on the first `manage.py check` run and hides `(actions['stamp'].higher)` until the first is fixed. This matches D-12 ("One `Error` per unresolved (key, ancestor) pair") and is tested by `test_one_error_per_unresolved_key_and_ancestor`, so it is acceptable as designed.

### 4. Suggestions
- Consider also checking explicitly declared `policy.read` (when `policy.read is not None`) and `policy.write` (when `policy.write is not None`) in `_ancestor_pair_messages` even if no registered view falls through to that family, while continuing to check the *inherited* global `CRUD_VIEWS_ANCESTOR_{READ,WRITE}_PERMISSIONS` only when a registered view actually uses that family. Because `seen` deduplicates by `(key, ancestor.name)` per `ViewSet`, adding `(f"ancestor_policy.{family}", explicit)` when `explicit is not None` will not add duplicate messages when a view of that family is also registered.
