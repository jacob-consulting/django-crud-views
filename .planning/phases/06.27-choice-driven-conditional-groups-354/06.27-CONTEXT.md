# Phase 06.27: Choice-driven conditional groups (#354) - Context

**Gathered:** 2026-11-12

**Source:** Maintainer discussion in this session and issue #354's approved D-01–D-10 and `gsd-handover`.

<domain>
## Phase Boundary

Allow an existing single-choice field to activate conditional field groups through a standard dropdown or radio
group. Each group matches one or more explicit values; several groups may be active together. Preserve existing
conditional required-field and inactive-group clearing behavior, extend bounded automatic clearing to standard
choice fields, and retain authoritative explicit `empty_values` overrides.

Deliver updated documentation and a complex runnable upstream example with three options, multiple groups, and
at least one group shared by two options. Documentation and the example must link to each other using the existing
project conventions. Preserve existing checkbox usage.

Issue #354 already contains the reviewed handover and acceptance criteria. The preceding conversation settled
the material behavior decisions; this invocation captures them for GSD rather than reopening them. No phase
SPEC.md or implementation plans exist. Finish these contracts before Phase 7's public theme-surface freeze.
</domain>

<decisions>
## Implementation Decisions

### Approved maintainer decisions carried forward from issue #354

- **D-01 — Choice-driven groups:** several groups may follow the same choice field. Each group activates when
  the selected value matches one or more explicitly configured values. Support a group shared by two of three
  options; this was explicitly selected over a single-value-only API.
- **D-02 — Existing inactive behavior:** active groups enforce their configured required fields; inactive groups
  clear editable fields on save just as checkbox groups do. Browser hiding/disabling preserves unsaved entries
  when switching away and back before submission. A shared group remains active and keeps its data when switching
  between two matching options. Fields outside all groups are unaffected.
- **D-03 — Bounded conditions:** one controlling field per group, explicit matching values, no expressions or
  combinations of multiple controllers. Multiple groups may activate together, but their controlled fields must
  be distinct so an inactive group cannot clear a field belonging to an active group.
- **D-04 — Reuse the descriptor:** use the demonstrated `ValueToggle("kind", values=[...])` configuration shape.
  Reuse the same descriptor in `ConditionalGroup(toggle=...)` and `ToggleGroup(descriptor, ...)` so browser and
  server conditions are declared once. Preserve existing string-based checkbox `ToggleGroup` configuration.
- **D-05 — Automatic clearing with explicit overrides:** include bounded automatic clearing for standard choice
  fields. Explicit `empty_values` is a first-class API and takes precedence for editable fields, including falsy
  values. Nullable choices clear automatically to `None`; unsupported or ambiguous automatic cases require an
  explicit value. Preserve the precedence of server-side disabled fields over any clearing instruction.
- **D-06 — Both controls:** support ordinary single-select dropdowns and radio buttons as controllers.
- **D-07 — Documentation is required:** explain configuration, both controls, multiple/shared groups, active
  required fields, clearing, explicit overrides, compatibility and unsupported cases.
- **D-08 — Complex runnable example is required:** the upstream example app must have three options, multiple
  groups and a group shared by two options. Show automatic clearing, explicit overrides and persisted save/reopen
  behavior. Retain the existing checkbox examples. A browser test fixture alone does not satisfy this requirement.
- **D-09 — Reciprocal links:** docs link to the runnable example, and the example links back to the relevant docs,
  using the existing conventions. Verify real destinations and anchors.
- **D-10 — Handover and subsequent scheduling:** issue #354 is the canonical discussion handover. Its original
  statement that filing did not create a phase is historical: the maintainer subsequently explicitly scheduled
  this work as Phase 06.27 and invoked this GSD discussion. Context capture does not implement the feature.

### Clearing details established in the discussion

Precedence is server-disabled field, explicit dictionary entry, then bounded automatic inference:

1. `Field.disabled=True` keeps Django's trusted initial value and validation behavior, including when an explicit
   `empty_values` entry exists. Temporary browser disabling is not this server policy.
2. For editable fields, dictionary membership wins. Preserve `None`, `""`, `False`, `0`, and other configured
   native-compatible values exactly; never replace a falsy entry through truthiness-based fallback.
3. Without an explicit entry, infer only a supported empty value. Unsupported or ambiguous shapes produce a
   descriptive configuration error, not a guessed default.

| Standard model field with choices | Automatic inactive value |
| --- | --- |
| Nullable text, including `blank=True` | `None` |
| Nonnullable text with `blank=True` | `""` |
| Nullable integer | `None` |
| Nonnullable integer | Explicit `empty_values` required |
| Nonnullable text with `blank=False` | Explicit `empty_values` required |

A model default is not a clearing instruction. For example, a nullable choice defaulting to `"A"` clears to
`None`. An explicit override may select a valid application sentinel or choose `""` instead of an inferred `None`.
Existing model validation and database constraints remain authoritative. Do not weaken inherited validation.

On submission, discard inactive editable fields' submitted values and apply their clearing values even without
JavaScript or with tampered input. Only a successful save persists changes. After saving and reopening, previously
cleared values have no history to restore. `required=[]` means optional while active; it does not mean retain
values while inactive.

### Delivery and preservation constraints from the handover

- Preserve existing checkbox groups, checkbox-driven formset skip/purge behavior, the non-choice clearing matrix,
  trusted disabled values, defaulted/omitted persistence, and inherited form/model validation.
- Preserve exact bound names and owning-form identity, safe template metadata, repeat-safe initialization,
  reset/cancellation, modal lifecycle, independent disabled state and keyboard focus handling.
- Keep Python authoritative. Invalid controller values must retain validation errors and cannot become a
  successful save through raw submitted-data fallback. Numeric choices and HTML string values must agree
  between browser and server.
- New value-based groups must not rely on declaration order to resolve overlapping controlled fields or allow
  their controller to be cleared by the groups it governs. Detect unsupported declarations clearly; do not add
  unrelated breaking restrictions to existing checkbox-only configurations.
- Follow the existing legend hooks from Phase 06.25.1 and preserve fieldset/legend semantics. Supporting radio
  controllers here does not expand stock radio admission in compact formset columns.
- Cover initial create/edit, changes, reset, invalid redisplay, JS-off/tampered requests, disabled fields, shared
  groups and persistence with meaningful Python, rendered-template and JavaScript/browser evidence.
- Demonstrate both controller widgets in the example without duplicating business logic unnecessarily. Include
  a visible way to understand the saved record and confirm clearing through the actual example app.
- Update `docs/reference/conditional.md`, changed JavaScript/template contracts and the changelog. Expected release
  treatment is additive. Any actual Breaking entry also requires `docs/migrating-1.0.md` under repository policy.
- Keep the addition understandable and opt-in. Preserve proven paths and avoid broad refactoring, new framework
  abstractions or speculative custom-widget support. Use multicore pytest for broad verification.

### Researcher / planner discretion

These are bounded engineering choices, not separately selected maintainer decisions:

- Private descriptor representation, safe metadata serialization and comparison normalization; static/runtime
  check identifiers and exact supported standard field/model pairs.
- Start with ordinary scalar `ChoiceField` / `TypedChoiceField` and native Select/RadioSelect widgets with string
  and integer values. Keep unusual coercion, relation selectors and multiselect controllers outside the guaranteed
  contract. Define and document edge cases such as empty/invalid choices without inventing a condition language.
- For plain forms, preserve existing clearing behavior unless a small explicit standard-choice rule is justified;
  do not infer database nullability where there is no model.
- Extend the existing toggle/clearing/layout paths. Reuse existing test fixtures and conditional lifecycle machinery;
  exact helper structure, test arrangement and internal implementation are planning work.
- Choose the example domain, model/field names, routes, migrations and seeds to fit the existing Bootstrap example.
  The consumer/wholesale/distributor matrix below is illustrative; the three-option and shared-group behavior is
  mandatory. Retain readable page navigation and existing example documentation-link machinery.
- New value-driven activation of entire `ConditionalFormSet` instances is outside this issue. The shared descriptor
  must not silently behave like a checkbox in that unsupported path; document and reject unsupported usage clearly.

No meaningful unresolved maintainer decision was found in the source scout. Do not reopen the agreed API,
multi-value matching, explicit overrides, dual widgets or example/docs requirements without concrete conflicting
evidence. Technical details above are for research/planning.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `ToggleSource` already supplies `field_name()` and `is_on(form)`; `ModelFieldToggle` and `UIFieldToggle` differ in
  whether a boolean field is injected. Its current evaluation is checkbox-specific, so a choice descriptor must
  not inherit truthiness as its matching semantics.
- `ConditionalGroup` delegates activation to its descriptor. `ConditionalGroupFormMixin` handles conditional
  required fields, discarded inactive data, trusted disabled fields and persistence. Extend these seams rather
  than introducing a second validation system.
- `resolve_conditional_empty_value()` already honors explicit dictionary membership before inference and uses
  bounded standard field/model pairs. Standard model choices currently fall outside that automatic matrix.
- `ToggleGroup.render()` already computes the bound field name with `form.add_prefix()`. It currently accepts a
  string; descriptor support needs to project matching metadata while preserving the existing string path.

### Established Patterns

- `toggle.js` discovers exact-name checkbox controls through `form.elements` and owning-form identity, maintains
  independent disabled baselines and supports repeat-safe resets/modal/row initialization. Preserve this behavior
  while allowing one radio group to comprise several same-name inputs.
- Current config checks inspect registered form classes without constructing arbitrary request-dependent forms;
  the mixin also checks runtime fields. Preserve that static/runtime split.
- The template already uses `conditional:legend` from the existing class registry. The feature does not need a
  new styling registry or layout system.

### Integration Points

- The existing conditional app has persisted Registration and Event examples, ViewSets, seed data and tests.
  Add the complex example coherently rather than replacing checkbox demonstrations.
- `Feature` entries in `examples/bootstrap5/project/features.py` point to `reference/conditional.md` using `DocRef`
  and anchors; the docs' live-example block points back to runnable routes. Reuse this two-way convention.
- Codebase maps and direct source reads support this context; no browser behavior or implementation feasibility
  is claimed as verified by this discussion-only phase.
</code_context>

| Group | Consumer | Wholesale | Distributor |

| Consumer preferences | Active | Inactive | Inactive |
| Business details | Inactive | Active | Active |
| Wholesale terms | Inactive | Active | Inactive |
| Distribution details | Inactive | Inactive | Active |

The user specifically requested a complex upstream example, not merely a two-group snippet, and emphasized
that explicit `empty_values` is important. Show a meaningful explicit override alongside automatic inference.
