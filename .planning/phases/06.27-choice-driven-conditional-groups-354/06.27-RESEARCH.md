## Implementation Decisions

### Approved maintainer decisions carried forward from issue #354

- **D-01 — Choice-driven groups:** several groups may follow the same choice field. Each group activates when
  the selected value matches one or more explicitly configured values. Support a group shared by two of three
  options; this was explicitly selected over a single-value-only API.
- **D-02 — Existing inactive behavior:** active groups enforce their configured required fields; inactive groups
  clear editable fields on save just as checkbox groups do. Browser hiding/disabling preserves unsaved entries
  when switching away and back before submission. A shared group remains active and keeps its data when switching
  between two matching options. Fields outside all groups are unaffected.
- **D-03 — Bounded conditions:** one controlling field per group, explicit matching values, no expressions or
  combinations of multiple controllers. Multiple groups may activate together, but their controlled fields must
  be distinct so an inactive group cannot clear a field belonging to an active group.
- **D-04 — Reuse the descriptor:** use the demonstrated `ValueToggle("kind", values=[...])` configuration shape.
  Reuse the same descriptor in `ConditionalGroup(toggle=...)` and `ToggleGroup(descriptor, ...)` so browser and
  server conditions are declared once. Preserve existing string-based checkbox `ToggleGroup` configuration.
- **D-05 — Automatic clearing with explicit overrides:** include bounded automatic clearing for standard choice
  fields. Explicit `empty_values` is a first-class API and takes precedence for editable fields, including falsy
  values. Nullable choices clear automatically to `None`; unsupported or ambiguous automatic cases require an
  explicit value. Preserve the precedence of server-side disabled fields over any clearing instruction.
- **D-06 — Both controls:** support ordinary single-select dropdowns and radio buttons as controllers.
- **D-07 — Documentation is required:** explain configuration, both controls, multiple/shared groups, active
  required fields, clearing, explicit overrides, compatibility and unsupported cases.
- **D-08 — Complex runnable example is required:** the upstream example app must have three options, multiple
  groups and a group shared by two options. Show automatic clearing, explicit overrides and persisted save/reopen
  behavior. Retain the existing checkbox examples. A browser test fixture alone does not satisfy this requirement.
- **D-09 — Reciprocal links:** docs link to the runnable example, and the example links back to the relevant docs,
  using the existing conventions. Verify real destinations and anchors.
- **D-10 — Handover and subsequent scheduling:** issue #354 is the canonical discussion handover. Its original
  statement that filing did not create a phase is historical: the maintainer subsequently explicitly scheduled
  this work as Phase 06.27 and invoked this GSD discussion. Context capture does not implement the feature.

### Clearing details established in the discussion

Precedence is server-disabled field, explicit dictionary entry, then bounded automatic inference:

1. `Field.disabled=True` keeps Django's trusted initial value and validation behavior, including when an explicit
   `empty_values` entry exists. Temporary browser disabling is not this server policy.
2. For editable fields, dictionary membership wins. Preserve `None`, `""`, `False`, `0`, and other configured
   native-compatible values exactly; never replace a falsy entry through truthiness-based fallback.
3. Without an explicit entry, infer only a supported empty value. Unsupported or ambiguous shapes produce a
   descriptive configuration error, not a guessed default.

| Standard model field with choices | Automatic inactive value |
| --- | --- |
| Nullable text, including `blank=True` | `None` |
| Nonnullable text with `blank=True` | `""` |
| Nullable integer | `None` |
| Nonnullable integer | Explicit `empty_values` required |
| Nonnullable text with `blank=False` | Explicit `empty_values` required |

A model default is not a clearing instruction. For example, a nullable choice defaulting to `"A"` clears to
`None`. An explicit override may select a valid application sentinel or choose `""` instead of an inferred `None`.
Existing model validation and database constraints remain authoritative. Do not weaken inherited validation.

On submission, discard inactive editable fields' submitted values and apply their clearing values even without
JavaScript or with tampered input. Only a successful save persists changes. After saving and reopening, previously
cleared values have no history to restore. `required=[]` means optional while active; it does not mean retain
values while inactive.

### Pattern 1: one descriptor, bounded string-token comparison

**Recommendation within planning discretion:** store a defensive, immutable copy of configured matches; expose the existing field-name/activation contract and a small private serialization seam. Normalize ordinary string/integer values into the same string tokens emitted by native choice widgets. Preserve exact spelling and whitespace; do not borrow checkbox falsey parsing. Reject unsupported scalar types and ambiguous representations. [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]

Django ChoiceField validates against declared choices and normalizes to strings. TypedChoiceField validates before coercion, and its empty value is not coerced. Django's generated model-choice form field uses the model's conversion function, so support must include the native text/integer model-generated case rather than whitelist only the built-in int/str functions. [CITED: https://docs.djangoproject.com/en/5.2/ref/forms/fields/#typedchoicefield] [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/db/models/fields/__init__.py]

**Bound contract to plan and test:**

- Support ordinary ChoiceField/TypedChoiceField with exact stock Select/RadioSelect, ordinary string/integer keys and grouped choices if Django's native choice validation handles them. Reject relation/multiselect controllers and custom widgets/coercions outside the documented boundary.
- Use the actual cleaned controller value during group cleaning. If field cleaning failed or a parent clean removed that key, the group is inactive and the original controller error survives. Never activate from raw POST once cleaning is underway.
- For initial/display-only evaluation, use bound-field value semantics so disabled controllers retain trusted initial values. Do not call whole-form cleaning recursively from descriptor evaluation.
- Keep zero a real choice. Recommend no match for missing selection or Django empty values; reject empty match collections and blank/None match tokens with an actionable error. This is a proposed bounded edge contract, not a previously locked detail.
- Test coercion parity explicitly. A noncanonical string key transformed by int coercion, or custom coercion collapsing distinct options, cannot safely use naive string conversion of cleaned data. Reject such unsupported declarations rather than invent a reverse-mapping engine.
- Do not use isinstance(ChoiceField) alone: multiselect forms inherit choice behavior and need an explicit exclusion or exact standard-class check.

These are implementation prescriptions derived from the native API and the issue's limits. [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/fields.py] [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/widgets.py] [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]

### Pattern 2: validate declarations before mutating group state

The existing runtime clean first verifies all editable controlled fields can clear, then invokes inherited cleaning and processes groups in order. Static checks inspect base_fields without constructing forms. [VERIFIED: src/crud_views/lib/conditional/group.py:134-148; src/crud_views/checks.py:329-362]

**Recommendation:** add a small shared validator over declared groups plus available field metadata. Run structural checks before any group's clearing/enforcement, and run field-dependent checks at runtime where request-added fields are available. Startup checks may inspect class fields; do not instantiate forms, issue queries, or evaluate arbitrary request-dependent configuration merely to improve diagnostics.

Check conflicts involving a value-driven group against **all** groups, including checkbox groups. Reject overlapping controlled fields; reject any group clearing a value controller, including cross-group cases. Conversely, reject a value group clearing another group's controller. Do not add unrelated restrictions to checkbox-only forms. Keep this a set-intersection check, not a dependency graph. [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]

Existing missing-controller and clearing diagnostics are exactly “crud_views.E311” and “crud_views.E312”. Preserve their meanings, and choose unused identifiers for new declaration errors after inspecting the current check inventory. Do not preassign an ID merely because it looks adjacent. [VERIFIED: src/crud_views/checks.py:252-270]

Reject unsupported whole-formset ValueToggle configuration at its shared consumer boundary, ideally during ConditionalFormSet construction plus any required defensive runtime check. Its declared type accepts ToggleSource, and its consumer calls the descriptor directly; without a guard it would silently execute unsupported behavior. The existing state values are exactly “on_off: Literal["skip", "purge"] = "skip"”. [VERIFIED: src/crud_views/lib/conditional/formset.py:10-19; src/crud_views/lib/formsets/formsets.py:349-359,387-399]

### Pattern 3: extend empty inference without changing precedence

**Recommended standard automatic-choice matrix:** use exact stock ChoiceField/TypedChoiceField paired with the resolver's standard text model family and integer model family, with model choices present and native persistence hooks intact. Keep unusual model/form subclasses, conversion hooks and nonstandard choice scalar types explicit-only. Plain-form controlled choice fields should continue requiring explicit empty_values; no model nullability exists to infer there. This is the smallest extension permitted by the context. [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]

| Model-backed controlled choice | Automatic inactive value | Important evidence |
|---|---|---|
| Nullable text, blank or nonblank | None | Nullability wins over blankability and model default. |
| Nonnullable blankable text | Empty string | Retain native model validation. |
| Nullable integer | None | Numeric Select values must still match string HTML tokens. |
| Nonnullable integer | Explicit required | A default or zero is not automatically a clearing instruction. |
| Nonnullable nonblank text | Explicit required | A sentinel must be configured by the application. |

This matrix is locked, not inferred from metadata absence. [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]

Preserve the sequence: skip server-disabled fields; check dictionary membership; infer from the bounded pair. The current exact-class/native-hook guards and pre-model-clean assignment already implement the non-choice contract. Do not replace them with a generic “field.empty_value” shortcut or broad nullable-field rule. [VERIFIED: src/crud_views/lib/conditional/group.py:19-76,138-141,163-184,193-201]

Django deliberately leaves defaults alone when a defaulted field is omitted and its cleaned value is empty. Thus a nullable choice with a nonempty default must pass through the existing forced native assignment before model construction. Test both omitted and maliciously supplied inactive values, then refresh from the database; a cleaned_data assertion alone cannot prove this. [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/models.py] [VERIFIED: src/crud_views/lib/conditional/group.py:163-184]

### Pattern 4: extend binding shape, preserve lifecycle ownership

## Don't Hand-Roll

| Problem | Do not build | Use instead |
|---|---|---|
| Valid controller data | A second raw-POST validation path | Django field cleaning, preserving errors |
| Inactive persistence | A new save override or manually saved model subset | Existing conditional native assignment and Django ModelForm save |
| Browser state | A new controller framework/observer system | Existing group bindings, owned states and disabled baselines |
| Safe match metadata | Hand-escaped delimiters or executable inline code | JSON serialization plus Django template escaping |

## Common Pitfalls

1. **Reusing checkbox truthiness.** Current ToggleSource reads boolean cleaned data or falsey-filtered raw POST. A nonempty choice is not necessarily a matching choice. Override activation in ValueToggle and keep legacy behavior unchanged. Existing falsey tokens are exactly “{"", "false", "0", "off", "none"}”. [VERIFIED: src/crud_views/lib/conditional/toggle.py:5,24-33]
2. **Controller error becomes a valid save.** Clearing a controller through another group can remove its field error; raw fallback can reactivate invalid data. Reject conflicts and only use cleaned values during server policy. [VERIFIED: src/crud_views/lib/conditional/group.py:193-201] [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]
3. **Numeric coercion mismatch.** HTML tokens and Python integers differ in type; transforming coercion can differ even after string conversion. Test native integer models and zero, and explicitly refuse exotic cases. [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/fields.py] [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/widgets.py]
4. **Only replacing checkbox discovery.** State sync, focus recovery and both cleanup paths also assume a single checkbox. Extend all those sites together and verify rebinding/unload. [VERIFIED: src/crud_views/static/crud_views/js/toggle.js:68-88,138-165,206-210]
5. **Treating hidden inputs as cleared database values.** Browser disabling omits fields; Django defaults may survive without the existing pre-construction assignment. Assert database values after refresh and reopen. [CITED: https://raw.githubusercontent.com/django/django/stable/5.2.x/django/forms/models.py] [VERIFIED: src/crud_views/lib/conditional/group.py:163-184]
6. **Static checks instantiate application forms.** Keep startup inspection on class declarations; runtime validates request-added fields. Report unsupported shapes clearly without introducing startup request/query effects. [VERIFIED: src/crud_views/checks.py:329-362; src/crud_views/lib/conditional/group.py:134-141]
7. **Fixture mistaken for the required example.** Browser fixtures cannot substitute for the upstream persisted example with navigation, visible saved state, both widgets and reciprocal links. [CITED: https://github.com/jacob-consulting/django-crud-views/issues/354]
8. **Tests import a stale installed package.** An initial run in an old nox environment produced seven old legend-template failures. Setting source PYTHONPATH made all 155 focused tests pass. Diagnose import provenance before treating such failures as current-code defects. [VERIFIED: session baseline commands below]
