## Top 3 Priority Fixes

1. **WARNING — Explain conditional required fields before submission.** Company, Price tier and Distribution region look optional beside visibly starred Name/Customer kind. Add concise, translated help text in the example identifying which fields are required while their group is shown. Keep the existing server-side enforcement; do not restore unconditional `required=True` on hidden fields.
2. **WARNING — Reduce duplicated teaching copy above the controls.** Retain a short choice/clearing explanation beside the form and move the detailed default/sentinel explanation into the existing teaching area or documentation link. Preserve the warning that saving clears inactive groups. This is a readability recommendation requiring human judgment, not failed behavior.
3. **WARNING — Make the alternative editor easier to discover.** Use the existing inline context-action facility for the relevant Dropdown/Radio alternative, or explicitly tell readers to open the actions menu. Keep navigation semantics and permission filtering. This is a discoverability recommendation requiring human judgment, not an inaccessible route.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

**C1 — WARNING; needs_human_review: true.** `examples/bootstrap5/conditional/views.py:278` supplies the same long paragraph to list, detail, create, update and delete views. The feature-level explanation at `examples/bootstrap5/project/features.py:375` repeats the shared-group/clearing lesson while beginning with the older checkbox demonstrations. In both screenshots, the feature explanation occupies roughly y=80–329 and the Customer heading/paragraph y=393–611; the first form label appears around y=632. Readers must scan two substantial explanations before interacting. Shorten the form paragraph and keep the expanded developer teaching in the existing supporting panels. Technical terms such as None and unset are appropriate to this developer example and are not themselves defects.

Positive findings: the four legends describe their domains; action labels distinguish Create/Edit Dropdown and Radio (`views.py:404`, `:415`, `:427`, `:438`); saved-value formatting deliberately distinguishes None from blank (`views.py:376`). Existing Save/Cancel labels are understandable in this CRUD context and do not justify a generic-label penalty. The clearing warning explicitly distinguishes unsaved switching from persistence.

### Pillar 2: Visuals (3/4)

**V1 — WARNING; needs_human_review: true.** The instruction “Compare the Dropdown and Radio editors” has no adjacent visible alternative-editor control in either screenshot. Create/update variants declare the alternatives but set `cv_context_actions_inline = []` (`examples/bootstrap5/conditional/views.py:401`, `:412`); the visible card action is an ellipsis. The routes work according to checked evidence, but finding the comparison action requires discovering the overflow menu. Expose the relevant alternative through the existing action presentation, or add a short menu-location cue. No new navigation component is needed.

Positive findings: Customer is the clear page heading, group legends are visually distinct and implemented as real fieldset/legend pairs (`src/crud_views/templates/crud_views/conditional/toggle_group.html:6`). Native controls have visible text labels. The teaching-panel icon is decorative and marked `aria-hidden` (`examples/bootstrap5/project/templates/project/example_about.html:4`). The screenshot alone does not establish the accessible name of every inherited shell action; no comprehensive shell accessibility pass is claimed.

### Pillar 3: Color (4/4)

**Passing finding:** Both desktop captures use predominantly white/light-neutral surfaces, dark text and a dark navigation bar. Blue is limited to actionable links, Save, overflow and the selected radio. Color is not the only indication of a selected radio or a form group. No accent-filled conditional sections or conflicting feature palettes were found.

The new group template has **zero hardcoded color literals and zero explicit primary-color classes**; it delegates classes through `cv_toggle_css` and the existing legend hook (`toggle_group.html:6–11`). The Customer layout introduces no color classes (`views.py:317`). Bootstrap is loaded by the existing base (`examples/bootstrap5/project/templates/project/base.html:16`). Neutral surfaces dominate in a manner consistent with the 60/30/10 heuristic, but exact pixel proportions and contrast ratios were not measured. No requirement for literal 60/30/10 area percentages was imposed on this inherited shell.

### Pillar 4: Typography (4/4)

**Passing finding:** The captures consistently distinguish the main Customer heading, conditional legends, body/field labels, and smaller footer text. Dropdown and Radio use the same hierarchy. The new template introduces **zero font-size declarations and zero font-weight declarations**; the legend uses the existing configurable hook, whose stock value is empty (`src/crud_views/lib/button_classes.py:80`). The layout adds no arbitrary text-size overrides.

The existing supporting-panel heading uses `h5` styling (`examples/bootstrap5/project/templates/project/snippet_panels.html:4`, `:24`). The visible monospace appearance is consistent across the inherited shell and feature; there is no phase-specific font mismatch. Paragraph density is classified once under C1, not treated as a new font-system defect. Actual computed font-size/weight distribution was not measured in a live target DOM; no fabricated Tailwind token counts are used for Django/crispy templates.

### Pillar 5: Spacing (4/4)

**Passing finding:** `CustomerForm.get_layout_fields()` uses **seven Column6 and one Column8 instances** within the existing Row abstraction (`examples/bootstrap5/conditional/views.py:319–328`). Both captures show aligned input edges, consistent two-column gutters, and clear separation between group legends and controls. Radio options increase the first row's height without overlap or clipping in the inspected desktop view.

The new conditional wrapper has **zero arbitrary px/rem spacing values**; the Customer layout has no new padding/margin overrides. The supporting panels retain established `mt-4`/`mt-3` utilities (`snippet_panels.html:3`, `:24`). Extra height above the form comes from the teaching content identified in C1, not inconsistent grid spacing. Mobile stacking/overflow and tablet appearance remain visually unverified; passing 390px behavioral assertions are not substituted for those observations.

### Pillar 6: Experience Design (3/4)

**E1 — WARNING; needs_human_review: false (defect existence).** Company and Price tier are required for both business kinds, Wholesale terms for Wholesale, and Distribution region for Distributor (`examples/bootstrap5/conditional/views.py:297–301`). Yet the visible distributor screenshots show no required marker on Company, Price tier or Distribution region, while Name and Customer kind carry stars. The shared conditional mixin intentionally disarms field-level required flags before its authoritative clean (`src/crud_views/lib/conditional/group.py:208–211`, `:286–291`); the JS controls visibility/disabled ownership, not required-state presentation (`src/crud_views/static/crud_views/js/toggle.js:95–134`). This is an inherited presentation limitation now exposed by the example, not a newly broken validation path. Add example-level explanatory help text as a bounded improvement. Broader dynamic accessible required-state support should be a separately scoped change if desired.

Positive findings: exact owning-form lookup supports native Select and radio sets (`toggle.js:31`); active-state membership is shared across groups (`:38`); hidden controls preserve values and independent disabled reasons (`:95`); focus recovery prefers a usable checked radio (`:82`); reset defers until native default behavior and respects cancellation (`:142`); unload removes listeners (`:223`). The checked actual-example record covers navigation, create, unsaved return, shared retention, save-time clearing, None versus model default, explicit unset, saved detail, reopened values, invalid zero-write behavior, native reset, docs links and keyboard focus across four cells.

These state changes are synchronous; an additional loading spinner or empty-state component would not improve the bounded group interaction. Existing server CRUD error/confirmation behavior is reused. The intentional inactive-value clearing is explained and required by D-02; this audit does not recommend an extra confirmation for every kind change. Error-state styling, screen-reader announcements, keyboard comfort and visual focus-ring quality require further human review; functional assertions alone do not establish those qualities.
