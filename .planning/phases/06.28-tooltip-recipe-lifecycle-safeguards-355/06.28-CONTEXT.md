<decisions>
## Implementation Decisions

### Approved decisions carried forward from issue #355

- **D-01 — Bounded fix:** Documentation and focused executable regression tests only. Preserve production
  JavaScript behavior and the current adapter API.
- **D-02 — Delegate initialization:** Document the downstream wrapper approach: apply the placement default
  before calling the original factory `tooltip.init`. Do not initialize directly through
  `Tooltip.getOrCreateInstance`. Retaining `hide` and `dispose` alone does not retain the initialization-time
  transition guard.
- **D-03 — Placement and ordering:** Context-toolbar triggers default to `bottom` only when they lack an explicit
  `data-bs-placement`; explicit placement wins. Other locations retain the library default. Install the wrapper
  after factory wiring and before tooltip initialization. Reconfiguring existing instances is outside this recipe.
- **D-04 — Preserve intentional replacements:** Keep the native-tooltip opt-out
  `cv.adapters.tooltip = {init() {}}` and the custom non-Bootstrap adapter examples. Those deliberately replace
  the implementation and are not the defect being corrected.
- **D-05 — No new hook:** The wrapper meets the demonstrated downstream need. Do not add a configuration hook,
  options API, lifecycle redesign, or downstream theme migration.
- **D-06 — Execute the published recipe:** Extract and execute the actual documentation snippet. Do not maintain
  a separate test-only copy that could diverge from the documentation.

### Acceptance and verification carried forward

- Explain wrapper installation order, placement precedence, and why calling the original initializer preserves
  its safeguards as well as the existing `hide`/`dispose` methods.
- Verify that the context default is set before instance creation, explicit placement is preserved, and other
  locations receive no placement override.
- Verify working `hide` and `dispose` through the documented adapter.
- Through the documented wrapper, a live queued transition callback runs; stale callbacks after disposal or
  instance replacement do not run.
- Missing Tooltip remains harmless. Repeated initialization does not duplicate instances or guard wrapping.
- Keep the native-tooltip opt-out documented and unchanged.
- Run focused Vitest coverage and applicable repository JavaScript checks. Report actual evidence; source
  inspection and mocked transition tests are not a new browser reproduction.

### Researcher / planner discretion

- Exact documentation wording, extraction marker, fixture arrangement, and whether tests extend
  `tests/js/adapters.test.js` or use a focused neighboring file remain implementation choices, as recorded in
  the issue handover. Reuse existing helpers and keep the result easy for the developer to maintain.
- Use the existing transition-guard test pattern rather than introduce another test framework. The published
  snippet should exercise the production adapter, not a substitute implementation of its guard.
- Specific verification commands and test grouping are planning details. Existing JS CI runs `npm test`.
- If documentation and tests cannot satisfy the agreed acceptance criteria, present concrete evidence before
  expanding scope. Do not modify production code merely to simplify a test.
</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets

- `publishedAdapterRecipe(marker)` already extracts a uniquely marked JavaScript fence from the reference
  documentation. Existing tests execute those snippets against the factory adapters.
- `loadScript("adapters")` loads the shipped script in the Vitest DOM environment. Existing fixture and cleanup
  conventions avoid retaining namespace/global state between tests.
- Existing transition tests model queued callbacks and active instance identity, covering live execution,
  disposal, and replacement on the same trigger.

### Established Patterns

- Factory `tooltip.init` resolves the namespace at call time, obtains the instance, and installs the transition
  guard once using a WeakSet. The guard checks current instance identity before running queued work.
- `hide` and `dispose` use `getInstance` and do not create an instance during cleanup.
- The current documentation directly calls `globalThis.tabler.Tooltip.getOrCreateInstance`, bypassing the guard
  and the factory's missing-component no-op. The production initializer already provides the needed behavior.
- The downstream wrapper sets `data-bs-placement` only when absent and delegates to the captured initializer.

### Integration Points

Expected changes are the existing reference page and focused JavaScript tests. No templates, Python views,
runtime assets, dependencies, or downstream source changes are required by the agreed scope.
</code_context>

<specifics>
## Specific Ideas

The motivating theme puts toolbar tooltips below buttons so they do not cover the page heading. Use the existing
Tabler namespace factory wiring and wrapper from issue #355. The example's other locations keep their library
default rather than receive a forced `top` option.

Preserve the distinction between customizing the factory implementation and intentionally replacing it with
native tooltips or another library. No new behavior decisions or extra capabilities were requested during this
GSD context capture.
</specifics>
