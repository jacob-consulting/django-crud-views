## Accomplishments

- Corrected the native PK precondition: use `Model._is_pk_set` where the installed version provides it.
  A partial composite key previously reached collection and raised TypeError instead of native ValueError.
  Django 4.2 retains its scalar-PK check; this does not add composite ViewSet URL support.
- Added module-owned isolated graph fixtures, with an actual field converter, nullable/ignored relations,
  nested protection and a cascade/restriction diamond. Test metadata and signal registration are scoped and restored.
- Explicit named controls establish immediate native PROTECT before handler/SET/SET_DEFAULT/private collection,
  original ProtectedError after a returned custom callback, recursive sticky provenance, deferred outer RESTRICT
  reconciliation, and non-sticky native SET_NULL/DO_NOTHING behavior.
- A real provider timing seam inserts nested PROTECT or RESTRICT only after inspecting the actual diamond graph.
  Fresh confirmed collection catches it, retains all rows, and produces 200/full or 422/modal in both atomic modes.
  No empty-preview replacement or preview-as-deletion-instructions is used.
- The adapter retains the installed `Collector.delete` by identity. Native tests observe fast-delete membership,
  scheduled SET_NULL updates, signal origin/alias, returned count maps, root PK clearing, parent deletion order
  and keep_parents retention. No SQL engine or global on_delete mutation was introduced.
- Actual custom model methods run once through keyword-only `using` or forwarding `**kwargs` signatures.
  Missing/positional-only signatures raise configuration errors before any method event.
- Actual transaction requests prove callback SET/default/custom writes roll back only with cv_atomic=True;
  independent Python events remain visible. Callbacks that return before a later native blocker retain this
  distinction and propagate ordinary protection, rather than claiming a harmless blocked response.
- Model, private collector, nested converter, signal, success hook and commit failures retain original identity
  and cause. Django's signal SQL transaction rolls back signal writes even with cv_atomic=False. Success-hook
  writes/deletion persist only without the package boundary. Post-commit failures leave deletion committed.
- A handler's on_commit runs immediately before SQL in non-atomic mode, and after actual deletion/commit in
  atomic mode. Tests observe both durable row outcomes directly; no captured-callback simulation supplies evidence.
- Native and actual custom successful request controls retain mutation → success hook → commit order, full/modal
  status/redirect behavior, and no callback replay on a repeated confirmed POST (404).
