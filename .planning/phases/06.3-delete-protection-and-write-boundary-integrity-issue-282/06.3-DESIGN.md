# Phase 06.3 integrated deletion design

Status: **PROPOSED — no maintainer implementation approval recorded.** This is the concrete review package for
DEL-01/D-16. External plan convergence reviews this proposal; it cannot satisfy the maintainer gate. Plan 01 must
record the maintainer's decision on the final reviewed content before any production or test implementation.

## Outcome and evidence boundary

GET, invalid confirmation and a custom-protected POST inspect supported relationships without calling deletion
handlers. A permitted confirmed POST runs deletion once, on one resolved alias, with the existing hook order and
configured atomic boundary. Known protection blocks independently of displayed labels and inspection completeness.
Unknown effects produce honest partial previews; unexpected errors propagate (D-01–D-04, D-12–D-15).

Research reproduces CR-02/03/04 and IN-02/03 on cached Django 4.2.30 and 6.0.9. It does not provide 5.2 evidence.
The former native-graph/traceback classifier is disproven. Ordinary ORM loading may run converters, managers,
initializers and read signals; callback-free here specifically excludes deletion handlers, SET/default factories,
private collection hooks, model deletion and delete signals. It is not a proof that arbitrary application Python
or database reads have no effects. Providers and display filters remain trusted application extension code.

## Source-grounded seams

Existing `src/crud_views/lib/views/delete.py` owns `RelatedObjects`, `cv_get_related_objects`, display filtering,
context, protection response, POST and `cv_form_valid`. `CrudViewProcessFormMixin.cv_form_valid_process` orders

hints. `GuardianDeleteRelatedObjectsMixin` replaces core filtering; `_PermittedPks` currently caches by model only.
`GuardianViewSet` reads a mutable policy mapping and indexes permissions after an inactive shortcut.

Installed Django 4.2/6.0 `Model.delete` constructs `Collector` directly: there is no collector-factory hook.
`Collector.collect` catches and aggregates ProtectedError around on_delete, losing provenance. The native
`Collector.delete` owns SQL ordering, signals, origin, field updates and PK clearing and will remain in use.
Installed `PolymorphicModel.delete` is an override with parent-retention behavior and is treated as custom below.
Installed source paths are read-only comparison evidence, never modification targets. All existing paths named in
the plans were checked against tracked repository paths; new paths are explicitly identified below.

## Inspection algorithm and completeness

`inspect_deletion(target, *, using) -> DeleteInspection` creates a request-local inspector. It does not construct
NestedObjects or call Collector.collect. It reads candidate reverse relations via Django's metadata utility and
queries `_base_manager.using(using)`; it never uses a cached relation loaded on another alias. Handler comparisons
use identity, never application-defined equality/deconstruct. Exact ForeignKey/OneToOne metadata is supported;
other relation-field classes and private fields exposing collection behavior become identified unknown boundaries.

| Effect | Read behavior |
|---|---|
| Native CASCADE | Read children, record parent/child edge, recurse with visited identities; no handler invocation |
| Native PROTECT | Read blockers directly, retain unfiltered instances privately |
| Native RESTRICT | Read candidates, reconcile only after the supported cascade closure; a candidate also in that closure is not a blocker |
| Native SET_NULL / DO_NOTHING | No deletion traversal and no handler invocation |
| Any SET closure, SET_DEFAULT, unknown handler | Record boundary even for an empty relationship; never call handler, lazy_sub_objs, deconstruct or default factory |
| Concrete multi-table parents | Use the link's actual local/remote join fields; query the parent target field from the raw child-link value on `using`, never child.pk or a cached descriptor; recurse with collect_related=False |
| Auto-created through models | Traverse their ordinary native relations; preserve protected data and existing summary semantics |
| Generic/private bulk relation | Record boundary without invoking bulk_related_objects; safe provider may describe it |
| Root Model.delete override, including OrderedModel/PolymorphicModel | Record model-delete boundary; still inspect known metadata; do not call the method. Ordinary Author/Car previews are partial unless expressly described by a safe provider |

For reverse relations obtain each remote tuple with field.get_foreign_related_value(source), match the actual
related_fields local/remote pairs, and query the local field.attname against the corresponding remote target value.
ForeignKey(to_field=...) is not a PK join. For parent links use field.get_local_related_value(child) and the actual
remote target field. A distinct child PK/parent-link key and non-PK reverse target are mandatory discriminators.
Track traversal mode separately from row identity: discovering a parent with collect_related=False must not suppress
a later required related traversal. Candidate reverse relations follow Django's opts.get_fields behavior.

Cycles, diamonds, repeated edges and self-relations terminate. Deduplicate by `(using, model, pk)` without coercing
UUID/int/string identities. Preserve deterministic discovery order; no numeric/string sorting promise is added.
The compatible tree is root-inclusive and alternates objects with optional child lists, for example
[root, [child, [grandchild], sibling]]. Permission redaction preserves None positions and child structure. A repeated
cycle edge does not recursively expand again. Provider-deleted rows attach as deduplicated direct root children.
Summary counts come from distinct discovered deletion rows, excluding the root model as today; concrete parent rows
are counted (Car root includes Vehicle parent rows). SET-affected rows are not counted as deleted. related_summary
remains dict[str,int]; partial qualification belongs in the alert heading, not numeric values. The inspector loads
full display rows rather than introducing .only/defer-driven per-row queries; large cascades still materialize and
no bounded-cost guarantee is made. Unknown paths never clear native blockers or establish that a RESTRICT candidate will
be deleted. A known RESTRICT candidate outside the supported closure remains blocking even if a provider describes
its deletion. This conservative rule is explicit: custom behavior is allowed only after known protection gates.

No broad exception handler turns a failed ORM read, converter, provider or renderer into incompleteness. Unknown
metadata produces incompleteness by explicit branch, while unexpected failures leave the request as errors.

`DeleteInspection` carries `related: RelatedObjects`, `boundaries: tuple[DeletePreviewBoundary, ...]` and derived
`complete: bool`. Raw blockers and unresolved boundaries are local and never included in template context.
Display filtering cannot mutate completeness or native blocked state.

## Supported safe-preview provider

`cv_get_delete_preview(self, boundaries, *, using) -> Iterable[DeletePreviewContribution]` defaults to an empty
tuple and is called once per context after native inspection, including previews disabled. The application must
perform read-only description; the package cannot sandbox application code. Exceptions propagate unchanged.

`DeletePreviewBoundary` is frozen and contains `kind` (`on_delete`, `private_relation`, `model_delete`), `model`,
`field_name` (None for model_delete), `using`, and `source_pks` (tuple). The package creates these descriptors. A
contribution must reference an equal descriptor from this call; ordered source_pks remains part of equality.
Normalize each descriptor once and index its complete immutable identity rather than rebuilding its source tuple
for every contribution. A cross-alias, stale, duplicate or unknown boundaries
raise ValueError before rendering or deletion. There is no whole-result completeness override.

`DeletePreviewContribution` is frozen with `boundary`, `deleted: tuple[Model, ...] = ()`,
`protected: tuple[Model, ...] = ()`, and `complete: bool = False`. Validate saved model instances and matching
`_state.db == using`; reject strings/HTML/dicts as model records. Merge unique deleted rows as direct-root child branches
and compute counts, merge protected rows additively, then perform the existing core/Guardian permission projection.
Neither provider nor display redaction removes native protection. `complete=True` attests coverage of that one
boundary only; every other boundary remains incomplete. Known native RESTRICT closure is not expanded by asserted
provider rows. A provider can explicitly describe a no-effect boundary with empty tuples and complete=True.

The raw related tuple remains exactly `(tree, summary, protected)`. Its old import path remains valid. Display
filters retain their signatures and may narrow permitted data. Unsupported collection overrides migrate immediately:
detect any effective override of `cv_get_related_objects` by method identity before invoking it, emit a new unused
viewset Error check and raise ImproperlyConfigured at runtime with the new provider/filter replacements. The base
method may remain a read-only compatibility accessor for callers, but the lifecycle uses private inspection and
does not dispatch through legacy overrides. No grace period or sample invocation of unknown overrides (D-05–D-08).

## Explicit native write provenance

`execute_deletion(target, *, using)` examines the bound delete method without invoking it. If its `__func__` is
exactly Django Model.delete, reproduce native Model.delete validation and sequence with
`_DeleteCollector(using=using, origin=target)`, `collect([target])`, then inherited `Collector.delete()`.
Validate PK/non-null state like native deletion. Preserve the returned count map, signal origin and PK clearing.
For every other method (including standard ordered-model and polymorphic), call the actual bound
`delete(using=using)` once. Preserve Author sibling reordering and Car/Vehicle parent semantics; do not bypass an
override through an identity allowlist. Every exception from that call propagates, including stale native protection.
Ordered sibling queries are custom-method side effects and must follow the same-alias trusted router; tests observe
this explicitly. Ordinary Author/Car pages therefore show the independent incomplete warning while form-control
golden bytes stay unchanged. Known pre-inspection protection blocks before either real method runs. Do not monkeypatch Django or global model metadata.

`_DeleteCollector` adapts the collection algorithm from supported Django versions, preserving parent traversal,
nullable-CASCADE field updates, batching, keep_parents, fast-deletes, field deferral, dependencies and outer RESTRICT
reconciliation. It retains Django's data structures and SQL executor. Maintain upstream attribution and a source-
comparison table in the implementation evidence. Differences between 4.2/5.2/6.0 must have explicit parity tests.

The critical differences from native collect are exact handler-identity dispatch and no broad ProtectedError catch:

1. Native CASCADE recurses directly with fail_on_restricted=False. A nonempty native PROTECT immediately stops
   collection: emit the private marker before any custom callback, or ordinary ProtectedError if the sticky flag
   is already set. Do not run later custom handlers after observing that blocker. RESTRICT is deferred to outer
   closure and uses the native dependency/candidate reconciliation semantics. Query evaluation is
   outside any translation catch. Nested converter/manager/model-initialization errors propagate unchanged.
2. SET_NULL schedules the native update; DO_NOTHING skips; neither sets the custom-callback flag. SET closures, SET_DEFAULT, arbitrary handlers and private
   bulk collectors run only here, after valid confirmation and inside the selected write boundary. Before calling
   any such executable extension set a collector-wide sticky `custom_callback_entered` flag. Recursive custom
   calls cannot reset it. Failures propagate without aggregation, including unrelated deletion inside a callback.
3. On a native blocker with no custom callback entered, raise private `_NativeDeleteBlocked` without serializing
   raw objects to context. The view catches only this marker after the atomic context unwinds. A native blocker
   following a returned custom callback raises the ordinary native protection exception and propagates: external
   effects may already have happened. Never claim that outcome was a harmless blocked request.
4. No catch encloses inherited Collector.delete, custom model deletion, `cv_form_valid_hook` or `on_commit`.
   Delete-signal and post-commit failures therefore retain ordinary error and commit semantics. Successful custom
   callbacks that mutate a database participate only in the configured transaction on that alias.
5. Write collection is fresh. A real stale-preview test inserts protection after inspection, before execution;
   it must demonstrate the native marker/backstop without substituting an empty preview. There is no locking or
   race-free preview promise. IntegrityError or a race after the collector check propagates.

Model.delete overrides that cannot accept `using` fail a signature-binding diagnostic before execution. Do not call
a method and catch TypeError to infer compatibility. An opaque callable whose signature cannot be inspected raises
an actionable configuration error requiring an inspectable adapter. Cooperative startup checks allocate unused
viewset.E... IDs for effective legacy collection overrides and inspectable incompatible delete signatures. A
keyword-only using parameter or **kwargs forwarding adapter is supported; positional-only using/no-using methods
fail without being called. Opaque signatures require runtime diagnostics. Add allocated IDs to migration tables. Application overrides of view mutation hooks
remain trusted lifecycle extensions; docs prohibit bypassing super where package deletion semantics are expected.

## One alias for inspection, writes, atomic and on_commit

Keep changes delete-scoped: do not alter create/update/resource lifecycle. Add `cv_get_delete_db_alias()` as the
public pinned accessor. On its first call after authorized object resolution it invokes `self.cv_get_db_alias()`
once, validates the alias against connections, and caches the nonempty string for that view instance/request.
DeleteView's default `cv_get_db_alias` uses `router.db_for_write(type(self.object), instance=self.object)`; router
choice has precedence over `_state.db`, exactly as native Model.delete. Application overrides remain the selection
hook and run once. Request parameters never select a database.

The default delete-specific `cv_get_atomic` uses the pinned accessor and cv_atomic; a delete-specific
`cv_form_valid_process` preserves the existing sequence and registers on_commit with the same cached alias.
It continues calling self.cv_get_atomic so cooperative overrides calling super remain valid. The accessor raises
ImproperlyConfigured before a saved self.object is resolved. Direct cv_form_valid_process with a supplied saved
self.object pins unconditionally at entry before any write, even when non-atomic; its caller owns prior authorization
and confirmation. No bare-view/default-model fallback is promised. A custom atomic
boundary must use `cv_get_delete_db_alias`; document the immediate migration from repeated selector calls. No
general claim can certify an arbitrary custom context manager's database behavior. Side-effect hooks must route
their own ORM writes explicitly; the package cannot create cross-database transactions or undo external I/O.

Inspect on the selected write alias even when the target was read elsewhere. Explicit selection authorizes the
same model/PK deletion on that alias according to native Django using semantics; document this intentional behavior
and test it with asymmetric records. Use same-alias fresh relationships/parent rows, never read-instance caches.
The original authorized target remains the origin; application router/selector policy is trusted configuration.

Guardian projection keys its request-local cache by (model, using), deriving using from candidate._state.db and
binding the candidate queryset. Before any ordinary, superuser, global or through-row label path, a runtime topology
predicate requires the persisted actor's _state.db and all actual auth/permission query routes to equal using:
User, Group, Permission, ContentType, user-group/user-permission/group-permission joins and the configured Guardian
user/group object-permission models. Check related manager query routes such as user.groups.all().db, not only model
defaults. Never substitute another actor with the same PK. Configured anonymous-object access resolves Guardian's
actual anonymous actor under this same predicate; unsupported resolution yields no labels.

Only after route validation, resolve Guardian's configured content type and require its _state.db == using;
through rows still skip content-type lookup entirely. Do this before Guardian's global/superuser early returns.
Cross-alias global display requires recognized auth backend query paths obeying these routes; unrecognized custom
backend topology is not certified there. Use fresh permission-cache state on an identity-verified same-alias actor
for cross-alias projection, without replacing request.user or trusting unknown cache provenance. Normal supported
single-alias behavior and the existing per-view/global/object/group/superuser policy are retained.

Any topology mismatch yields an empty permitted-PK set, including fast paths, while keeping native block state,
completeness and disclosed aggregates intact. This is a defined unsupported-topology result, not permission denial
from a newly invented policy. Positive same-alias object/group/global/superuser display is mandatory; always-empty
output does not satisfy DEL-05. Negative tests independently misroute actor, auth/global joins, content types and
user/group grant tables with colliding actor/object PKs. No general central-auth multi-database support is claimed.

The test router context must begin before authentication/session middleware; use contextvars and function-scoped
restoration, transaction=True and databases=[default, shard], independent databases per worker and interleaved
requests. Restore routers, actors/caches, signals and metadata at teardown. ContentType caches are already alias-
keyed; clearing them is fixture hygiene and does not replace the runtime predicate.

## Bounded Guardian helper corrections

Wrap STRICT_HELPER_POLICY in MappingProxyType over a private literal mapping. Manage continues to expose dict(...),
so mutating displayed data cannot alter authority. This protects accidental mutation, not arbitrary monkeypatching.
`_resolve_permission_key(perm)` first rejects non-str inputs (including list/dict/None/int) with the same descriptive
ValueError, before a hash lookup; it then validates exact configured keys before inactive shortcuts, queryset access or
Guardian assign/remove calls. Invalid keys raise ValueError naming repr(perm) and sorted configured keys; valid
inactive queries remain empty. Custom configured keys work; no whitespace, casefolding or Unicode normalization.
Both assignment helpers validate before any permission change. D-09–D-13 retain object/group/active-superuser,
inactive denial, per-view global fallback and manage applicability/access without adding policy options.

Bounded residual review records scenarios for removed constructor/model_validate key; inherited/mixed per-view
flags; strict helper independence; actors; manage applicability; copied display mutation; and the prior proxy/base
content-type concern. Reproduce a concrete new defect or explain why no additional predicate follows from the
unclassified detector. A substantial redesign returns a scope decision; it cannot be silently included or closed.
