## CR-01

### Current defect and independent expected state

The connection is pinned, but `execute_deletion()` feeds the original authorized read instance directly to
`_DeleteCollector`. Its stale non-PK values can select an unrelated write-side object's children. Parent collection
also dereferences parent descriptors, allowing cached or read-side parent values into the selected graph.

The discriminating fixture has `Root(pk=1, code="original")` on the read alias. The selected write alias has
`Root(pk=1, code="selected")`, `Root(pk=2, code="original")`, and `Child.target` referencing the latter through
`to_field="code"`. Current inspection reports no child, but native execution deletes write-side root 1 **and the
unrelated child**. The reproduced count is 2. Required state, independently constructed from those fixture rows:
delete only write-side root 1, return native deleted count 1, and preserve root 2, its child and every read-side row.
Use both alias directions, both atomic settings and page/modal requests. Counts/expected survivors must not come
from the inspector being tested.

### Proposed target and lifecycle contract

| Stage | Identity and behavior |
|---|---|
| Resolve/authorize | Existing URL, authentication, parent, object and state gates resolve the original object. A missing URL object remains 404. No second object replaces that authorized instance. |
| Select | `cv_get_delete_db_alias()` calls the trusted selector once with the original instance available. The default remains instance-aware `router.db_for_write(type(self.object), instance=self.object)`. Request data does not select an alias. |
| Inspect | Keep read-only inspection and same selected-alias relationship reads. A cross-alias inspection reloads the same model/PK on that alias. Preview data is descriptive and never reused as write instructions. |
| Confirm/protect | Existing confirmation and business/native/provider protection gates run before executable deletion. GET, invalid confirmation, denied and known-protected requests preserve rows and record zero deletion callback events. |
| Enter write boundary | Preserve `cv_form_valid_process`, cooperative `cv_get_atomic()` and the pinned alias. The selected native reload described below happens immediately before native collection, inside the existing write lifecycle. |
| Native execute | Only exact bound Django `Model.delete` uses `_selected_native_target(target, *, using)`: validate the original PK, then read the same model/PK through `_base_manager.using(using).get(...)`. Collect this fresh object with `_DeleteCollector(using=using, origin=target)`, retaining inherited `Collector.delete()` SQL/signal execution and its return value. |
| Parent collection | `_native_parent_rows(objects, field, *, using)` queries actual parent-link values on the pinned alias, as specified below. |
| Original-instance state | Keep the original values, relation caches and `_state.db` intact. After successful native deletion returns, clear its PK using its PK attname, before the success hook. Do not clear it when collection/deletion raises. Native signal `origin` remains identical to this original instance. |
| Custom execute | Every non-native bound method, including actual ordered Author and polymorphic Car deletion, still runs exactly once on the original object with `delete(using=using)`. Preserve inspectable-signature validation, its real implementation and its return/errors. |
| Hook/commit | Preserve deletion → success hook → commit callback ordering. Transaction entry and `on_commit` use the one pinned alias. Hooks keep the original object. Their failures propagate with the existing atomic/non-atomic durable-state semantics. |

For native parents, derive each join tuple from `field.get_local_related_value(child)`, pair it with
`field.related_fields` and query remote field attnames through the parent's `_base_manager` on `using`. Use
`non_polymorphic()` when available to retain the concrete parent row. Never substitute `child.pk`, dereference a
cached parent descriptor or copy selected values onto the authorized object. Preserve `source_attr`,
`collect_related=False`, `reverse_dependency=True`, `keep_parents` and RESTRICT closure semantics.

A multi-table fixture must separate the child's PK from a parent link targeting a unique non-PK parent code,
vary selected/read parent values and poison the cached descriptor. Only actual selected parents participate;
unrelated and read-side parents survive. The CR-03 absent-null-join rule also applies to supported native joins.

If the selected native root no longer exists, raise its model's `DoesNotExist` before deletion callbacks,
success hooks or commit registration. Keep the original PK. This is distinct from a missing URL object's 404;
there is no friendly protection translation or silent success for a missing selected native row. Query/converter
failures retain their exception identity. A fresh read provides current selected values at that point; it adds no
lock, cross-database transaction or guarantee against arbitrary concurrent updates after the read.

### Compatibility and bounded scope

Same-model/PK selection on the trusted alias is retained; the repair makes its native graph use that alias's
current values. Original authorization, selector hints and signal origin are retained. Applications must observe
the original PK cleared before a successful native hook, as with native deletion. A later success-hook failure
does not promise restoration of in-memory PK state even when database writes roll back.

Custom methods continue to own their relation routing and external side effects. Passing `using` does not certify
every query they make. No custom-method rewrite, new routing option, create/update lifecycle change or general
central-auth topology support is proposed. Friendly translation remains limited to the private native blocker
before custom callback entry; failed reads, custom methods, signals, hooks and commit callbacks propagate.

Plan 11 owns `_selected_native_target`, `_native_parent_rows` and `tests/test1/test_delete_join_identity.py`:
`test_native_selected_join_request`, `test_native_selected_parent_links`, `test_native_selected_missing_row` and
`test_native_selected_custom_dispatch`. Tests retain direct external event lists and real commit/rollback evidence
in both atomic modes, including success-hook failures and spy wrappers that forward real Author/Car methods.

## CR-02

### Current defect and independent expected state

Boundary grouping currently uses `(kind, source model, field name)` and source PK batching, losing the declaring
field owner. Two custom reverse relations `First.target` and `Second.target` from the same root collapse into one
descriptor. One provider attestation then incorrectly yields `complete=True`. The observed two custom relations
produce only one boundary. Required state: **two boundaries** whose owners are independently asserted as First
and Second; attesting either leaves exactly the other unresolved, and attesting both exact descriptors completes
them. Adding the second relationship to an existing First-only provider must leave it incomplete, including when
that unknown relationship currently has no rows.

### Proposed descriptor and provider contract

Append frozen `DeletePreviewBoundary.field_model: type[Model] | None = None`. It is a separate identity component
from the source `model` and ordered `source_pks`; include it in grouping, equality, hashing and merge validation.
Appending the default supports compatible construction for model-delete descriptors; it does not make old copied
field descriptors valid.

| Boundary | `model` / `source_pks` describe | `field_model` describes |
|---|---|---|
| Reverse `on_delete` | Source/root rows whose relations are inspected | `relation.field.model`, e.g. First for First.target, even though the source model is Root |
| Unsupported parent field | Child/source rows carrying the parent link | The declaring parent-link `field.model` |
| `private_relation` | Source rows owning the private relationship | The declaring private `field.model` |
| `model_delete` | Original custom-model deletion source | `None`; it has no relationship field owner or field name |

Keep `kind`, `model`, `field_name`, `using` and ordered `source_pks` intact. Source batching may join multiple source
PKs for one owner; it must not merge owners. Reverse discovery order cannot change the unresolved owner set,
blocked state or callback count. Equality requires all six fields, including the owner and the exact source batch.

A provider selects an exact descriptor supplied in the current call. In the published custom-effects example,
selection checks source `model`, `field_name` and **`field_model is Attachment`**. Passing only a source/name match
could attest an unrelated newly added relationship and must be migrated. Reconstructed descriptors must still equal
the supplied descriptor in every field. Reject ownerless field descriptors, wrong owners, stale source batches,
cross-alias, unknown and duplicate contributions descriptively before rendering/confirmation proceeds. Preserve
`model_delete` with `field_model=None`, existing saved-instance/alias/type validation, additive native/provider
blockers and merge-before-permission-projection order.

Attesting one boundary cannot remove another from incompleteness, clear protection, widen native RESTRICT closure
or bypass core/Guardian filtering. No raw descriptors, alias names or forbidden objects enter template context.
Providers remain trusted application description code; exceptions propagate and no universal purity guarantee is
added.

### Compatibility and bounded scope

This is an immediate provider-descriptor migration under D-05–D-08, with no legacy grace period. Compatible code
using supplied descriptors and explicit owner selection remains supported. Old copied ownerless field descriptors
fail rather than silently attest effects. The `RelatedObjects(tree, summary, protected)` display shape and
compatible filtering hooks remain intact.

Incomplete status still allows the existing single confirmation when no known gate blocks. The incomplete notice
and partial-count heading remain visible across page/modal/details-disabled cases; known/hidden protection remains
independently blocking and permission-filtered. There is no second acknowledgement or new presentation contract.
GET, invalid and known-protected POST record zero deletion callbacks.

Plan 13 owns `test_boundary_field_owner_request`, `test_boundary_field_owner_validation`,
`test_boundary_field_owner_batching` and `test_documented_provider_added_same_name_relation`. Its second task
updates the boundary table, the actual owner-qualified provider fence, its executable doc tests, `CHANGELOG.md`
and `docs/migrating-1.0.md` in the same commit. The independently defined second relation must remain unresolved
when that actual fence runs; existing model-delete and copied-notice recipes remain executable.

## CR-03

### Current defect and independent expected state

For a nullable unique alternate key `Root.code=None`, an unlinked nullable `Ref.target_id=None` is currently
queried as `IS NULL`. Native PROTECT inspection reports one false blocker, although native deletion removes only
the root and preserves Ref. The CASCADE variant falsely reports `{"ref": 1}` even though Ref survives. Current
request gates faithfully render those incorrect inputs and can prevent a legitimate confirmed deletion.

Required state: the raw blocker count is zero, the related summary excludes unlinked Ref, and confirmed deletion
removes only the selected root (native count 1). Another null-key root, all unlinked refs and unrelated non-null
targets survive. Expectations are exact fixture PK sets/counts, independent of inspection output. Cover zero, one
and many unlinked refs, multiple null-key roots, page/modal and both atomic modes.

### Proposed native join rule

Before building equality filters in supported native reverse/parent inspection, inspect the actual related-value
tuple. **Any `None` component means no relationship** for these supported native joins; traversal yields no rows
and must not turn it into `IS NULL`. Use reverse foreign-related values and parent local-related values without
PK substitution or coercion. This is an explicit no-match branch, not an exception fallback.

Detect unsupported metadata and unknown handlers **before** native value traversal. An unknown `on_delete` on a
null-valued relation still creates its owner-qualified incomplete boundary and never executes during inspection.
Native SET_NULL/DO_NOTHING handling and the Django-based write collector remain intact. Do not catch read/database
or converter errors into empty results.

### Compatibility and bounded scope

Known non-null PROTECT and RESTRICT still block; CASCADE still counts/deletes actual matching children. Preserve
RESTRICT closure, cycles, callback provenance, exact key types and independent known protection. Adding/reordering
unlinked rows cannot alter actual blockers/counts. Partial custom effects retain their notice and ordinary
confirmation rules, with a positive callback control only after permitted confirmation.

The correction changes false blockers/counts to native no-relationship semantics. It does not introduce a new
public API or promise unsupported composite/custom field behavior. A valid supported nullable parent-link case
uses the same rule where model construction permits it; errors are never suppressed to simulate such support.

Plan 14 owns `test_nullable_join_protect_request`, `test_nullable_join_restrict_cascade_request`,
`test_nullable_join_nonnull_controls` and `test_nullable_join_unknown_boundary` in the plan-11 module. Direct
executor controls assert native total counts and durable rows; registered requests separately assert raw
inspection, rendered notices and confirmation outcomes. Run all three native handlers and non-null positives
on Django 4.2, 5.2 and 6.0, with no added skips/xfails.

## CT-01

### Current defect and independent expected state

With Guardian's `GET_CONTENT_TYPE` set to
`polymorphic.contrib.guardian.get_polymorphic_base_content_type`, a registered Car ViewSet infers
`view -> app.view_car` while Guardian resolves Vehicle. A real `view_vehicle` object grant still produces
`MixedContentTypeError` in the strict helper and list queryset. The two existing expected-error characterization
cases reproduce this failure; their passing status does not prove authorized access.

Required state: a fresh registered Car ViewSet infers **`view -> app.view_vehicle`** and both the helper and a real
registered list response return exactly the granted Car, excluding an ungranted sibling. The caller's queryset
remains Car, on its original alias and restricted/empty scope; it is not replaced by Vehicle or preauthorized rows.
Normal Publisher and default PublisherProxy concrete-permission behavior remain unchanged.

### Proposed Guardian-only discovery contract

Override `GuardianViewSet.default_permissions` only. Obtain the content type from
`guardian.ctypes.get_content_type(self.model)` and query real `Permission` rows belonging to that selected type.
Mirror existing OrderedDict construction: strip only the exact terminal `_<content_type.model>` suffix from each
codename to derive the short key, and preserve the qualified value
`<content_type.app_label>.<permission.codename>`. For Vehicle, `view_vehicle` yields `view`, `réviser_vehicle` yields
`réviser`, and a nonterminal name such as `inspect_vehicle_status` stays `inspect_vehicle_status`.

Discover all custom Permission rows on the selected content type, not a hardcoded CRUD set. When it is Vehicle,
do not union Car permissions or guess child/base equivalents. A child-only custom permission is therefore no
longer inferred into default keys under that resolver. This compatibility effect requires explicit maintainer
review and the worked migration in plan 15; it is not presented as an unchanged default.

Explicit application `permissions` overrides remain authoritative. Retain inherited `permissions` dispatch;
do not normalize or rewrite an explicit key or qualified permission string, including custom Unicode/codenames.
An explicit mapping incompatible with the configured content type continues to raise Guardian's original error;
there is no silent empty/all result or fallback. An application's explicit mapping does not itself promise that
Guardian accepts a mismatched child content type.

Preserve `_default_permissions` process-lifetime semantics: cache a nonempty discovery, do not cache an empty
result. Configured content type is startup configuration. A resolver/permission change after nonempty discovery
requires a fresh ViewSet or process restart; no runtime setting hot-reload/cache-invalidation policy is introduced.
Core `ViewSet.default_permissions` is unchanged.

### Permission flow and retained actor policy

| Stage | Required behavior |
|---|---|
| Resolve defaults | Selected Guardian content type → only its Permission rows → exact terminal suffix keys → qualified values → existing nonempty cache. |
| Select configured mapping | Explicit application `permissions` override takes precedence over inferred defaults without rewriting its data. |
| Validate helper key | `_resolve_permission_key` retains exact string matching; reject invalid/non-string keys with the existing descriptive ValueError and sorted actual keys before queryset access, inactive shortcuts or assignment/removal effects. |
| Strict helper | Existing `get_objects_for_user` receives the exact resolved value and caller's Car queryset. Global-only authority stays excluded; group/object grants and active-superuser scoped access remain; valid inactive queries remain empty. |
| List requests | Existing `GuardianQuerysetMixin` consumes the same mapping. Per-view `cv_guardian_accept_global_perms` remains independent; only accepting views admit global-only `view_vehicle` authority. |
| Object/action checks | Existing object-permission consumers use the same qualified mapping through their existing Guardian checker path. Inactive requests remain denied, without bypassing parent/state gates. |
| Assign/remove | The helpers validate first and forward the selected value unchanged to Guardian. An inferred base key assigns, queries and removes an actual object permission row; invalid keys change no rows. |
| Manage | Effective per-view policy and the detached immutable strict-helper display retain their existing applicability and administrative access rules. |

Retain D-09–D-13, existing anonymous behavior, exact integer/UUID/key types and supplied queryset scope. Do not
broaden strict-helper global policy, introduce policy flags, change group/superuser semantics or claim universal
custom-PK/cast/collation correctness. Delete-preview permission topology is a distinct existing path; its green
tests do not establish this helper/list fix.
