## Public exception contract and plan 08 handoff

For `assign_perm`, `remove_perm` and `get_objects_for_user`, an unsupported key raises **ValueError**:

```python
alternatives = ", ".join(repr(key) for key in sorted(self.permissions))
f"Invalid permission key {perm!r}. Valid keys: {alternatives}."
```

For example, actual keys inserted as `zebra`, `réviser`, `alpha` are reported as
`Invalid permission key 'view'. Valid keys: 'alpha', 'réviser', 'zebra'.` Non-strings include `None`, integers,
bytes, lists and dicts. The non-string check precedes dictionary membership; no unhashable `TypeError` leaks.
Configured string keys match exactly, without casefolding, whitespace trimming or Unicode normalization.
The selected configured permission string is forwarded unchanged. Validation precedes the inactive shortcut,
default/supplied queryset access, and Guardian assignment/removal. Existing permission rows remain unchanged
on invalid operations. The shared resolver does not add a policy option or alter valid assignment semantics.

The public **KeyError → ValueError** change is **Breaking**, including newly diagnosed inactive queries.
Plan 08 must pair its CHANGELOG entry with `docs/migrating-1.0.md` and update `docs/reference/guardian.md`;
applications catching KeyError must catch ValueError. This review hands off that exact type/message/order
contract; it does not claim the documentation is already shipped. The strict-helper immutability correction
preserves the existing documented policy, rather than creating configurable global access.

## Historical plan-06 CT-01 reproduction and scope handoff

This section records the pre-repair observation. The approved plan-12 repair and current positive evidence follow.

The initial positive probe selected the registered proxy control and two Car paths on Django 6.0.9:
**2 failed, 1 passed in 1.52s**. Both failures were the same real exception:

```text
guardian.exceptions.MixedContentTypeError: Content type for given perms and klass differs
```

The fixture sets `guardian_settings.GET_CONTENT_TYPE` to
`polymorphic.contrib.guardian.get_polymorphic_base_content_type`, saves a Car, registers a fresh GuardianViewSet
and Guardian list, and assigns `view_vehicle` on that Car. `GuardianViewSet.permissions['view']` is
`app.view_car`; Guardian compares its permission-derived Car content type against configured Vehicle before
filtering the supplied Car queryset. It fails in `guardian.shortcuts._compute_queryset` for both
`GuardianViewSet.get_objects_for_user` and `GuardianQuerysetMixin.get_queryset`.

The historical 6.2 acceptance entry already identified this risk but explicitly had no registered-ViewSet
reproduction. This is fresh reproduction, not a regression caused by key validation or policy freezing.
No unauthorized access was demonstrated; the observable result is an application error/failed list query.
At plan-06 closeout, two characterization tests required the exact error. Plan 12 converted them to positive
access assertions before implementation; neither now requires an exception for a valid configured base grant.

The precise possible fix scope is coordinated content-type/permission identity selection across
`GuardianViewSet` and `GuardianQuerysetMixin`, with explicit custom-permission and polymorphic/proxy semantics
and object/group/global/superuser tests. Silently replacing the app-qualified permission with a bare codename
would change the configured permission contract and requires separate review. The orchestrator was informed;
no such redesign was made in plan 06. Plan 10 subsequently obtained approval of the bounded discovery contract;
plan 12 implements it. The unrelated unidentified AUTH-06 predicate remains visible for acceptance disposition.

its prior green tests cannot close this failure.
