## Narrative Findings (AI reviewer)

### CR-01: [BLOCKER] Cross-alias native deletion collects relations from the wrong row values

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/deletion.py:384-386`

**Related locations:** `deletion.py:143-146` reloads the selected row for inspection;
`deletion.py:280-289` dereferences parent objects during native write collection;
`src/crud_views/lib/views/delete.py:328-329` forwards the original resolved object;
`docs/reference/delete_view.md:388-390` promises fresh relationships/parents on the selected alias.

**Issue:** Inspection reloads the target on `using` when its loaded alias differs, but native execution feeds the
original read-alias instance into the collector. Django's relationship query uses the instance's target-field
values, not exclusively its PK. Consequently a `ForeignKey(to_field="code")` can cause a completely different
object's children to be deleted on the selected database, despite an empty complete preview. Passing the right
connection is insufficient when the collected instance has another database's join values. Cached or router-loaded
multi-table parent instances present the analogous boundary.

**Reproduction:** On `default`, create `Root(pk=1, code="original")`. On `shard`, create
`Root(pk=1, code="selected")`, `Root(pk=2, code="original")`, and a child of the latter through
`ForeignKey(Root, to_field="code", on_delete=CASCADE)`. Inspect and execute the default-loaded pk=1 with
`using="shard"`. Inspection reports complete with no related rows. Execution returns two deletions:
the selected root and **the unrelated pk=2 root's child**. The unrelated parent survives; its child does not.
No custom handler, model override, malicious router or race is needed; a trusted explicit alias selector suffices.

**Impact:** Unpreviewed unrelated data loss under the newly documented cross-alias selection contract.
This is a defect in the phase implementation/guarantee; native Django also using the supplied instance's values
does not make the package's different inspection and execution targets consistent.

**Fix:** For exact native `Model.delete`, resolve the same model/PK on the pinned write alias before collection
and use that row's current join values. Keep the original authorized instance as collector `origin`, preserve
original-instance PK clearing and hook semantics, and explicitly load concrete parents on `using` from their
actual link fields rather than read-alias caches/descriptors. Retain the actual custom-method dispatch contract;
do not bypass OrderedModel/PolymorphicModel methods. Clarify any custom-method routing limits without claiming
that the package refreshes arbitrary application logic. Add real request regressions with different non-PK join
values on the two aliases, an unrelated target sharing the old value, both atomic modes and parent-link coverage.
The unrelated child must survive and the deleted graph must match the selected target.

### CR-02: [BLOCKER] Different custom relationships collapse into one preview boundary

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/deletion.py:79-82`

**Related locations:** `deletion.py:123-124` records only the reverse field's name;
`deletion.py:163-166` constructs descriptors; `deletion.py:231-232` clears their completeness;
`docs/migrating-1.0.md:535-538` selects custom effects by the same ambiguous identity.

**Issue:** The boundary key is `(kind, source._meta.model, field_name)`. Reverse foreign-key names are local to
their owning child model, so two ordinary child models can both have `target` pointing at the same root.
If both handlers are unknown, their boundaries are silently merged. The provider receives no field-owning/related
model identity with which to distinguish them. A valid contribution describing only one relationship clears the
sole boundary and suppresses the incomplete warning for the other relationship too.

**Reproduction:** `First.target -> Root` uses `SET_DEFAULT`; `Second.target -> Root` uses
`SET(lambda: None)`. Both nullable relations are empty, which still requires distinct unknown boundaries.
Inspecting a Root returns **one** descriptor `("on_delete", Root, "target", "default", (root.pk,))` for the two
relations. Returning one complete contribution makes `merged.complete` true. Adding the second relation to an
existing application can therefore invalidate a previously correct provider without any diagnostic.

**Impact:** The per-boundary completeness contract is false, and a partial preview is presented as complete.
This is not a demand that trusted providers be sandboxed: the package has discarded the identity needed for a
provider to attest precisely.

**Fix:** Include unambiguous relationship identity in both internal grouping and public descriptors, retaining
the source model/PK batch separately. For example, carry the field-owning model plus field name, with a distinct
identity for private and parent relationships. Update provider examples/validation accordingly. If identity cannot
be extended immediately, detect ambiguous collisions and retain unresolved boundaries or raise an actionable
configuration error instead of accepting one attestation for both. Add two-child-model collision tests, an
existing-provider/new-relation regression, and assertions that covering either boundary leaves the other incomplete.

### CR-03: [BLOCKER] Nullable alternate-key joins manufacture blockers from unlinked rows

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/deletion.py:126-132`

**Issue:** Reverse inspection converts each foreign target value directly into an equality filter.
When a nullable unique `to_field` is `None`, Django turns that filter into `IS NULL`. Rows with a null foreign key
are unlinked; they do not reference this root. The inspector nevertheless treats all such rows as its children or
blockers. With PROTECT or RESTRICT the view refuses a legitimate deletion; with CASCADE the preview falsely claims
unrelated rows will be deleted. Native collection does not make this association.

**Reproduction:** Define `Root.code = CharField(unique=True, null=True)` and
`Ref.target = ForeignKey(Root, to_field="code", null=True, on_delete=PROTECT)`. Create a root with `code=None`
and a ref with `target=None`. Inspection returns that ref as protected. Calling the native execution adapter
successfully deletes only the root, retaining the unlinked ref. Through the ordinary view, the earlier
`has_protected_objects` gate prevents this valid operation.

**Impact:** Incorrect blocking and preview contents for supported ordinary ForeignKey metadata. This is newly
introduced by manual inspection; the prior Django collection semantics do not consider null foreign keys linked.

**Fix:** Treat a relation with a null remote join component as having no related rows, or use an equivalent
Django relation lookup that preserves native null semantics. Apply the rule consistently to the supported
join paths. Add nullable non-PK `to_field` cases for PROTECT, RESTRICT and CASCADE, including multiple null-key roots
and unlinked rows, and verify valid confirmed requests delete only the target.
