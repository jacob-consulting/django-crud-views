## Narrative Findings (AI reviewer)

### CR-04: [BLOCKER] Modal replacement and dismissal lose keyboard focus (UI-F01)

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/static/crud_views/js/modal.js:42-47`

**Related locations:** `modal.js:91-101` processes the real 422 replacement;
`modal.js:115-128` opens/dismisses without retaining a return-focus element;
`/home/alex/projects/alex/django-crud-views/src/crud_views/static/crud_views/js/adapters.js:16-17`
uses programmatic Bootstrap show/hide.

**Issue:** Replacing `#cv-modal-content.innerHTML` removes the currently focused submit button.
No code assigns focus to a surviving modal element afterward. The visible modal therefore has
focus on `BODY`, outside the dialog, with no visible focus indicator. Dismissal also leaves
focus on `BODY`: this programmatic opening path never records/restores the original trigger.
This breaks the keyboard focus lifecycle after validation/protection feedback and on return to
the page. The fact that a subsequent Tab recovers to Close does not preserve the user's current
focus or return location.

**Independent reproduction:** Against the unchanged production JavaScript served by the
disposable host at `http://127.0.0.1:8143`, sign in at `/signin/`; select the English
`partial` case from `/cases/`; open
`/harness/?target=<URL-encoded case URL>`. Focus `#launch`, press Enter, then focus Delete
and press Enter with confirmation unchecked. The real server returns 422. The rendered form's
existing `novalidate` is used; no preview, response or JavaScript is substituted. Inspect
`document.activeElement`, then press Tab and activate Close with Enter.

The reviewer independently repeated that sequence in cached Chromium on the current source:

| Observation | tag / id | Inside modal | `:focus-visible` |
|---|---|---|---|
| Enter opens dialog | DIV / cv-modal | true | true |
| Unchecked POST returns 422 and replaces content | BODY / empty | false | false |
| Next Tab | BUTTON / empty (Close) | true | true |
| Enter on Close dismisses dialog | BODY / empty | false | false |

The target still existed after the invalid request. This replay did not submit a confirmed delete.
The existing durable `17-evidence/browser-results.json` additionally records the equivalent
BODY result after the real stale-protection 422; its harness/source were inspected. Only the
unchecked-422 and dismissal paths were freshly replayed in this re-review.

**Scope/baseline:** Both `modal.js` and `adapters.js` are byte-identical to `74c7f63`.
This is an independently confirmed existing defect exposed by the phase's required browser
review, not a regression attributed to plans 11–15. A baseline browser replay was not performed.
The finding is a BLOCKER because focus behavior is concretely incorrect in the reviewed
keyboard workflow, not because human visual acceptance is merely pending. It does not reopen
the four backend repair findings.

**Fix:** On replacement in an already visible dialog, move focus after injection to a meaningful
surviving target, such as the first invalid control/error summary or the focusable dialog shell
when the blocked response removes the form. Preserve adapter independence and avoid stealing
focus during initial injection before the dialog is shown. Capture the opener on modal open and
restore focus to that connected, usable element after the adapter's completed hide lifecycle,
with a defined fallback if the opener no longer exists. Cover unchecked 422, blocked 422 without
a form, Close/Escape dismissal and a removed opener with actual browser assertions on
`activeElement`; a mocked `show()/hide()` test alone cannot establish this behavior.
