### Resolved finding — CR-01: Failed seed left a public developer credential with conflicting write access

**Resolution:** CLOSED by `125e13a1`, independently verified 2026-11-13T11:06:14Z. The following finding text and reproduction output describe the pre-fix source at `39722796`, not the current behavior.

**Classification:** BLOCKER  
**Category:** security  
**File:** `/home/alex/projects/workspaces/cv-phase-06-31/django-crud-views/examples/bootstrap5/project/management/commands/seed.py:12-17`  
**Related files:** `/home/alex/projects/workspaces/cv-phase-06-31/django-crud-views/examples/bootstrap5/project/seeding.py:25-29`, `/home/alex/projects/workspaces/cv-phase-06-31/django-crud-views/examples/bootstrap5/project/seeding.py:83-104`, `/home/alex/projects/workspaces/cv-phase-06-31/django-crud-views/examples/bootstrap5/guardian_demo/seed.py:40-42`

**Original issue:** The full seed command commits authentication changes before all privilege-conflict checks have succeeded. `ensure_demo_users()` resets the developer password immediately after checking only account flags. Model/group conflicts are checked later by `ensure_developer_read_access()`; that helper then joins the configured group before the per-feature seeds inspect Guardian object grants. A later `CommandError` does not undo these earlier changes.

Two independent reproductions against freshly migrated in-memory databases demonstrate the consequence:

1. Create an active, nonstaff, nonsuperuser `developer` with a private password and direct `library.change_author`. Calling the full `seed` command raises its expected conflict error, but afterwards `authenticate(username="developer", password="developer")` succeeds, the private password no longer works, and `has_perm("library.change_author")` remains true.
2. Start without any developer account. Give the configured manage group `guardian_demo.change_document` on the concrete seeded `Roadmap 2027` document, then run `seed`. It creates the developer account and adds its group membership before the object check raises. After the failed command, public-password authentication succeeds and the new account has the group's effective `change_document` permission.

The second case creates a new write-capable public account despite rejecting provisioning; it does not merely retain an operator's pre-existing grant. The documented acceptance of partial earlier seed work does not make exposing an incompatible identity through a public credential safe. This violates the D-10 read-only boundary on the very conflict paths intended to protect it.

**Evidence:** Actual isolated reproduction output:

```text
before public login False
seed error developer developer has conflicting permission library.change_author; leaving the grant unchanged.
after public login True
private password preserved False
write grant preserved True

developer exists before False
seed error developer developer on guardian_demo.Document pk=1 has conflicting object permission change_document; leaving the grant unchanged.
public login after failed seed True
configured membership True
effective object write True
```

Both reproductions selected `project.settings`, changed `DATABASES["default"]["NAME"]` to `:memory:` before `django.setup()`, migrated that database, and called `call_command("seed")`. Neither touched the example's persistent database or modified source files.

**Recommended fix (now implemented):** Keep credential creation/reset and new group membership from committing unless all existing privilege checks succeed. The simplest bounded option for this single-database example is to make the whole seed handler atomic, allowing the existing `CommandError` to propagate outside the transaction:

```python
from django.db import transaction

class Command(BaseCommand):
    @transaction.atomic
    def handle(self, *args, **options):
        users = ensure_demo_users()
        ensure_developer_read_access(users["developer"])
        self.stdout.write("users: alice/alice, bob/bob, developer/developer")
        for feature in FEATURES:
            import_module(f"{feature.app}.seed").seed()
            self.stdout.write(f"seeded {feature.app}")
        self.stdout.write(self.style.SUCCESS("Done."))
```

Update the seed-conflict documentation to describe rollback if this approach is selected. Add full-command regressions for both scenarios above: after rejection, preserve the old password and memberships for an existing identity, and leave no newly created public identity or inherited write access for a new one. Retain the offending operator grants unchanged. Direct helper tests alone do not cover this ordering defect.
