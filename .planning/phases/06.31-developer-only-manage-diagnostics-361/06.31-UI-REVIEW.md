## Top 3 Priority Fixes

1. **Contain wide diagnostic tables** — long configuration values can require page-wide scrolling on narrow displays. Add Bootstrap `table-responsive` wrappers around core and Guardian diagnostic tables, then verify long values at 375, 768, and 1440 pixels. This is explicitly deferred by CONTEXT, not a phase completion requirement.
2. **Correct property-table header associations** — assistive technology receives column headers for row labels. Change the six property labels to `scope="row"`; retain `scope="col"` for actual column-heading rows. Verify associations with an accessibility tree/screen reader.
3. **Make diagnostic identity explicit in the permissions section** — “Access” does not say whose model permissions are shown. Label the section as the signed-in account's model permissions and identify that account; explain that this is not impersonation or a complete endpoint/ancestor decision. Keep the existing independent authorization logic.

## Detailed Findings

### Pillar 1: Copywriting (3/4)

- **WARNING C1 — accepted translation deferral, phase-added copy.** `examples/bootstrap5/project/templates/registration/login.html:17`, `project/home.html:45`, and `project/base.html:53` append the same clear read-plus-diagnostics sentence, including `developer/developer`. Plan 05 explicitly allows English fallback; `examples/bootstrap5/test_i18n.py:200` expects English in both locales. Existing German chrome is preserved, but the German experience remains mixed-language. A later localization change should translate/compile this separate msgid and update the locale-specific assertions without replacing the preserved old msgids.
- **WARNING C2 — inherited diagnostic ambiguity.** `src/crud_views/templates/crud_views/view_manage.html:131` labels the table “Permissions” and its result “Access” at line 137. `src/crud_views/lib/views/manage.py:111` derives those rows from `self.request.user.has_perm(long)`. The page does not explain this account-specific scope beside the results. D-06's diagnostic workflow makes that distinction consequential. Add concise signed-in-account/model-permission wording; do not imply all endpoint or Guardian object checks are represented.
- Account credentials, role, and setup are concrete rather than generic submit/OK copy. The pre-existing invitation success text `Invited “”` is separately documented in this phase's `deferred-items.md` and Plan 04 summary; `examples/bootstrap5/custom_form/views.py:99` still references form context. That known adjacent defect was not reproduced here and is not counted again in this scoped audit.

### Pillar 2: Visuals (3/4)

- **WARNING V1 — inherited repetition amplified by the appended guidance.** In demo mode `project/base.html:49` renders the global account banner, while `registration/login.html:14` or `project/home.html:41` renders another account notice. The developer-role sentence therefore appears twice on those pages. Consolidate common role guidance into one notice per page while retaining the global reset warning and login-specific seed instruction. This is a minor hierarchy recommendation, not a claim of observed clipping.
- The home hero (`project/home.html:7`), feature headings/cards (lines 20–32), and login card (`registration/login.html:10`) provide a clear source-level hierarchy. The manage link remains a real link with a hidden full caption and decorative icon, not an unnamed icon button: `src/crud_views/templates/crud_views/tags/button/action.html:7` and `tests/test1/test_template_a11y.py:25`.

### Pillar 4: Typography (3/4)

- **WARNING T1 — inherited semantic heading skips.** Login starts with `h4` at `registration/login.html:11`. Diagnostic content begins with `h4` at `src/crud_views/templates/crud_views/view_manage.html:9` beneath the example's level-1 heading (`project/crud_views.html:18`), then switches to an `h3` “Views” section at line 180. Use `h1 class="h4"` for the standalone login title, and ordered `h2`/`h3` diagnostic section levels with Bootstrap size classes to preserve appearance.
- Changed notices add no font size/weight declarations. In the three notice templates, explicit type treatments are `h1`, `h4`, `h5`, `lead`, and `code`; no explicit `fw-*` overrides appear. These are Bootstrap roles, not Tailwind classes; the semantic heading defect is more concrete than imposing an unrelated Tailwind token limit. Font metrics and translated line wrapping remain unmeasured.

### Pillar 5: Spacing (2/4)

- **WARNING S1 — inherited, explicitly deferred responsive containment gap.** Core diagnostic tables at `view_manage.html:11`, `:65`, `:133`, `:157`, and `:188`, and Guardian tables at `src/crud_views_guardian/templates/crud_views/view_guardian_manage.html:9` and `:29`, have no local responsive wrappers. Long identifiers such as `cv_guardian_accept_global_perms` and arbitrary configuration values can exceed narrow content widths. Add bounded horizontal table scrolling and verify it with long real values. This is a source-derived risk, not a measured overflow claim. CONTEXT explicitly defers responsive manage-table wrappers.
- **WARNING S2 — inherited spacing outside the utility scale.** `view_manage.html:178`, `:182`, and `:204` use `<br>` sequences around section boundaries. Replace these with deliberate Bootstrap margin utilities on headings, separators, or section containers so gaps follow a consistent scale.
- Notice spacing itself follows Bootstrap utilities: login `mb-0 mt-3`, banner `mt-3`, home `mt-4`; home layout uses `p-4 mb-4`, `mt-4 mb-3`, and `g-3`. There are no arbitrary pixel/rem spacing values in these three templates. The login `col-md-5` and home `row-cols-md-3` need tablet-width visual checks once a target server exists.

### Pillar 6: Experience Design (3/4)

- **WARNING E1 — inherited table semantics.** Core Properties rows (`view_manage.html:14`, `:22`, `:30`, `:38`, `:46`, `:54`) mark their labels `scope="col"` even though each describes the adjacent value in the same row. Change these six to `scope="row"`. This degrades assistive navigation but does not establish that the diagnostic task is impossible.
- The phase's important interaction change is correctly represented in source: `_cv_manage_allowed` checks active authentication, mode, and group membership (`manage.py:40`); denied manage actions always hide (`:67`). Accessibility tests explicitly prove one authorized manage link and zero nonmember manage links, including its destination, hidden name, tooltip, and decorative icon attributes (`test_template_a11y.py:25` and `:54`). Ordinary disabled-action behavior is preserved by the phase's authorization and golden coverage.
- These are synchronous Django pages, so a new asynchronous loading spinner is not warranted. Diagnostic empty states exist (`view_manage.html:174`; Guardian template `:48`). Existing example tests cover invalid reminder/invitation input, missing composer text, unknown level, and denied write GET/POST (`examples/bootstrap5/custom_form/tests.py:43`, `:69`, `:109`, `:120`; `flash_messages/tests.py:68`, `:73`, `:108`). This audit inspected those assertions; it did not rerun the full write-action suites. The phase adds no new destructive UI requiring a new confirmation flow.
