## 06.32-01

### Summary

The plan is tightly scoped to the approved low-complexity design and its source anchors are accurate: `_workflow_configure()` already joins offered choices to `steps[name].custom` (`src/crud_views_workflow/lib/forms.py:118-139`), `get_context()` already copies each action before decorating it (`src/crud_views_workflow/lib/widgets.py:38-48`), `get_button_class()` selects by key presence and returns `""` for an intentionally empty value (`src/crud_views/lib/button_classes.py:212-223`), and `icon_host_keys()` returns `("", True)` for non-host icons and `(host_class, False)` for host icons (`src/crud_views/lib/view/button_data.py:99-107`). No existing consumer reads `custom["variant"]` or `custom["icon"]` (only `label`, `comment`, `help_text` at `forms.py:135`, `mixins.py:102-103,123`, `execution.py:82`), so the new fields collide with nothing. The main defect is an incomplete inventory of files that hard-code the current ten workflow keys: an executed-docs test will fail as soon as Task 1 adds eight defaults, and the plan neither lists the affected doc/test nor runs that test before the final gate.

### Strengths

- **Fallback contract is traced correctly.** Keeping `get_button_class("form", "submit", "label")` for unsupported variants matches the live template (`transitions.html:8`) and the plan's "select the key before lookup, keep empty results" instruction matches the registry's presence-not-truthiness rule (`button_classes.py:213-223`). Research pitfall 2 (a conflicting `form:submit:both` must lose) is a real regression target because `_action_key_parts` recognises `form:submit:<mode>` keys (`button_classes.py:320-321`).
- **New keys are automatically valid for W362.** Declaring them in `crud_views_button_class_defaults` (`apps.py:11-22`) makes `key in defaults` true at `button_classes.py:392`, so no check code changes are needed, and the `_action_key_parts` grammar is untouched as D-07 requires.
- **Metadata survives refresh for free.** The late-refusal path calls `form._workflow_refresh()` on the same bound form (`views.py:96-103`), which reruns `_workflow_configure()` (`forms.py:156-160`); adding fields inside that loop is the right insertion point. Task 2's "mutate metadata before refresh" case is the right test for it and there is an existing late-refusal fixture to extend (`tests/test1/test_workflow_buttons.py:566-653`).
- **Correct test-selector warning.** `test_comment_markers_and_guidance` counts `[aria-hidden="true"]` (`test_workflow_buttons.py:373`) and the font renderer emits exactly that attribute (`icons.py:236`). The plan tells Task 2 to assert on the asterisk span and suffix instead, which prevents a false "comment marker" match once an icon is present.
- **Registry count updates are located.** `test_button_classes.py:140-143` (10/112), `:241` and `:258` (subprocess 112) are all named, and the core-only 102 (`:119,140,254`, and the `buttons.md` sentence parsed at `:272-274`) is correctly left unchanged.
- **Reversibility ratings are honest.** The eight keys and the three widget context fields become part of the frozen theme surface (`docs/reference/theme.md:457-459`), and the plan marks Tasks 1 and 3 "costly" for exactly that reason.

### Concerns

- **HIGH — Two files that pin the current ten keys are missing from the plan.** `docs/reference/buttons.md:203-218` publishes the "Optional workflow defaults" table with the sentence "adds these ten app-owned defaults, for 112 effective default keys" (`:204-205`). `tests/test1/test_theme_adoption_docs.py:277-283` parses that table and asserts `documented == CrudViewsWorkflowConfig.crud_views_button_class_defaults`, `len(bc._get_default_button_classes()) == 112`, and the literal phrase `"112 effective default keys"`.
