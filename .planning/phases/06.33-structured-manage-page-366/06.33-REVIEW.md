## Critical Issues

### CR-01: Guardian's delegating parent wrapper hides an inherited custom gate

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views_guardian/lib/mixins.py:342-352`
**Related:** `src/crud_views/lib/view/base.py:95-104,1176-1181`
**Issue:** At the top level, GuardianParentPermissionMixin.has_permission() delegates to the next gate. Its description similarly delegates, but _cv_requirement_is_custom() always compares the first gate and description owners in the complete MRO. Both first owners are the Guardian parent wrapper, so a custom has_permission implementation between that wrapper and the core permission mixin is missed. The resulting badge claims a standard permission while the endpoint enforces the custom gate. This is within D-27's has_permission detection boundary; it does not require inspecting dispatch, queries or object-loading hooks.

**Reproduction:** Configure Django with tests.test1.conftest.pytest_configure(), create a top-level GuardianViewSet(model=Author, name="review_gate"), and define:

```python
class CustomCreate(CreateViewPermissionRequired):
    def has_permission(self):
        return False

class WrappedCustomCreate(GuardianParentPermissionMixin, CustomCreate):
    cv_viewset = viewset
```

Observed: CustomCreate.cv_get_requirement() is custom, but WrappedCustomCreate.cv_get_requirement() is permission/add while WrappedCustomCreate().has_permission() is False. The wrapper's top-level gate reaches the project override; the displayed standard requirement is therefore false.

**Fix:** Make the known Guardian top-level delegation inspect the ownership of the gate it actually delegates to. A custom intervening has_permission owner without its own description must produce custom; explicitly described project gates remain authoritative. Keep the nested parent-only bypass behavior. Add a regression for this valid MRO and pair it with the native denied request. Do not broaden inference to arbitrary dispatch/get_object/get_queryset methods.

### CR-02: Empty template declarations are shown as effective templates

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/manage.py:615-621`
**Related:** `src/crud_views/lib/view/base.py:406-411`
**Issue:** The Views configuration projection falls back only on None. The runtime cv_get_extends_template() falls back on falsey strings at both the view and ViewSet layers. Valid empty declarations consequently show a blank effective template with the wrong source, contradicting D-11 and the Presentation card's correct resolution.

**Reproduction:** In an isolated configured process, construct ViewSet(model=Author, name="review_empty_extends", extends="") and register a normal ListView. Its extends_template row is `value="''", source="from ViewSet"`, while the native resolver returns `app/crud_views.html`. Then set viewset.extends to `project/base.html` and the view's cv_extends_template to `""`: the row remains `"''"` with source set, but the native resolver returns `project/base.html`.

**Fix:** Resolve this specific field using the existing template resolver's truthiness semantics, recording the selected source separately from declaration provenance. Preserve explicit empty input as an optional declared value, as the Presentation builder already does. Keep None-only semantics for icons and inline lists, where empty values have a different meaning. Test both empty layers against the native resolver.

### CR-03: Manage's fixed hide policy is reported as the global disable policy

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/manage.py:602-614`
**Related:** `src/crud_views/lib/views/manage.py:91-93`
**Issue:** inaccessible_actions is resolved through the generic None-layer helper. The shipped ManageView.cv_get_inaccessible_actions() deliberately always returns hide. With a valid global or ViewSet disable policy, the manage view's expanded configuration incorrectly says disable. This matters when a developer uses diagnostics to understand why the manage action disappears instead of becoming disabled.

**Reproduction:** Set crud_views_settings.inaccessible_actions = "disable", create a normal model ViewSet and inspect its registered AutoManageView. _manage_view_sections() returns `inaccessible_actions.value="'disable'", source="global setting"`; the same class's cv_get_inaccessible_actions() returns `"hide"`.

**Fix:** Account for the known request-independent ManageView policy when preparing this field, retaining the actual override/source instead of applying generic layering. Use the appropriate native resolver for ordinary views. Add the disable-setting and disable-ViewSet cases for core and Guardian manage classes; avoid executing arbitrary project hooks during static inspection.

### CR-04: Guardian manage-class provenance names the wrong setting

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/manage.py:467-474`

Use CRUD_VIEWS_GUARDIAN_MANAGE_VIEW_CLASS when that setting supplies the class; retain constructor-set/default distinctions. Test the two settings independently and together.

### WR-04: State-only UI mappings overstate surface-specific browser coverage

**Classification:** WARNING
**File:** `/home/alex/projects/alex/django-crud-views/tests/browser/manage-presentation.cjs:126-137`
**Related:** `tests/browser/manage-presentation.cjs:106-118,291-292,396-437`
**Issue:** uiMappings() discards the surface portion of each criterion ID and attaches every surface to the same state-level case list. For example, views.zero-one-many, facts.zero-one-many and checks.zero-one-many are marked proved by holder-count scenarios and core-zero-defaults. Those scenarios change users/superusers/default visibility, not the number of registered views, children or checks, and their recorded counts contain only defaults/hidden/users/overflow. validateEvidence() checks that mapped cases passed, without requiring assertions for the criterion. The release report actually reports these mappings as passed. Its 52 mappings therefore do not establish 52 independently verified UI truths. Similarly, long-text geometry accepts local table scrolling without verifying the holder wrapping required by WR-01.

**Fix:** Map each surface/state criterion to cases that assert that criterion, recording the relevant measured facts. Add bounded zero/one/many view/child/check scenarios or explicitly mark those browser criteria unverified where existing non-browser tests are the only evidence. Preserve the existing source/hash/CSP/cleanup gates, and add a negative harness test that rejects a criterion mapped only to unrelated holder-count cases. Do not count populated facts or screenshots alone as semantic coverage.
