## Detailed Findings

### Pillar 1: Copywriting (3/4)

- **WARNING C1:** `src/crud_views/templates/crud_views/view_manage.html:169` renders “permission: own gate … custom: project access requirement”. It does not provide the blue/magenta/green key required by CONTEXT D-23 and UI-SPEC's Views legend, and does not explain Guardian policy in the footer. This is visible in the English desktop and German Guardian captures. Restore the approved legend without making color the sole carrier of meaning.
- The neutral requirement at `view_manage.html:124` says “none” rather than UI-SPEC's “no permission required”; its title and hidden explanation correctly say no **own** permission, and the footer explains it. This is minor copy drift within C1, not an authorization defect. Reconcile the visible wording with the contract while preserving the own/ancestor distinction.
- Empty-vocabulary actor identity and actionable empty text are present (`view_manage.html:78`); the no-views message is present at line 166. Configuration errors use the specified heading/actionable text in `snippets/alert/manage_checks.html:2`. Counts use plural-aware rendering. The empty and error screenshots substantiate these states.

### Pillar 2: Visuals (3/4)

- **WARNING V1:** `manage.css:14` applies `overflow-wrap:anywhere` to summary, td, code and list items, but not permission-holder th elements. Actor/group/user names are rendered in th at `view_manage.html:38`, `:46`, `:61` and `:71`. Long unbroken names therefore dominate intrinsic table width. In both `core-normal-390.png` and `core-layout-en-1280.png`, the visible Permissions area shows holder text with the grant columns offscreen. Local scrolling keeps the task possible, so this is a quality warning rather than a blocker. Unlike the 192px configuration keys, holder names are covered by the contract's long-name wrapping requirement.
- Passing evidence: clear card headings, Permissions first, Views/Presentation disclosures, side-card order, visible focus outlines and labeled help controls. Error alert precedes the matrix. German header actions reflow. The unusually long all-open stress capture is not itself a defect: production disclosures begin closed and SHOW_USERS remains opt-in.

### Pillar 3: Color (3/4)

- **WARNING K1:** `manage.css:55` sets code size but leaves its inherited Bootstrap color. New diagnostic code at `view_manage.html:111`, `:112`, `:143`, `:201`, `:280` and `:328` consequently appears pink across summaries, routes and class paths. The approved palette reserves the magenta semantic accent for group badges. This is a scoped visual hierarchy recommendation, not a claim of failed contrast or a request to override host-wide colors.
- Class audit: two permission-badge template call sites (own/parent), one group-badge call site and one conditional Guardian-policy call site. Runtime counts depend on registered views. Registry defaults at `src/crud_views/lib/button_classes.py:136`–144 provide neutral model/object badges, blue permission, magenta group and green Guardian policies. The only explicit semantic color pair in manage.css is group `#a61e6a` / white at line 123; other literals are Bootstrap-compatible variable fallbacks.
- White bodies and secondary headers dominate inspected captures. The contract defines 60/30/10 as a visual target, not a pixel quota; no invented numerical distribution is asserted. Release measurements show minimum visible new-content text contrast **4.500693575059644:1**. There is no whole-row opacity dimming.

### Pillar 4: Typography (4/4)

- **PASS T1:** `manage.css:1`, `:43`, `:50`, `:59`, `:69` establish 16px body, 14px diagnostics/badges, 400 regular and 600 headings/keys, with 1.5 body and 1.2 heading line heights. Code inherits role size at line 55. Browser measurements independently record exactly 14/16px and 400/600 in new content.
- The host's responsive h4 page heading is explicitly inherited; its narrow-screen size is not scored as a new-content violation. Font rendering in the isolated environment and final visual readability still require maintainer judgment, not speculative font replacement.

### Pillar 5: Spacing (4/4)

- **PASS S1:** `view_manage.html:9` and `:222` implement the prescribed row g-3 and 8/4 large-screen columns. Repeated mb-3 gives consistent card separation. `manage.css:21` provides 44px summary minimums and 8px padding; lines 74–88 provide wrapping headers, 8px gaps and 32px help targets. The 56px Presentation inset at line 105 reserves its 32px sibling help plus breathing room; it is control accommodation rather than an arbitrary new spacing scale.
- Configuration keys deliberately reserve 192px and values 160px (`manage.css:33`); their resulting local scrolling at mobile and in the desktop sidebar is an approved tradeoff, not missing responsive layout. Browser evidence confirms labeled, focusable local wrappers and no document overflow at 390/1280px. V1 addresses only names, not these keys.

### Pillar 6: Experience Design (4/4)

- **PASS E1:** `manage.js:34` binds change handling before hiding defaults; lines 41–43 initialize unchecked and reveal the control only after enhancement. Native details start closed (`view_manage.html:108`, `:174`). No asynchronous diagnostic load requires a spinner. Server errors retain existing host behavior. Hidden-default counts, zero defaults, JS missing/off, keyboard activation, local keyboard scrolling, user folding at 20/21, strict CSP and documentation failure are represented in the reviewed release evidence.
- Help links have labels/new-tab descriptions; summaries contain no nested controls and expose requirement descriptions (`view_manage.html:135`). Default rows use hidden, removing them from the accessibility tree. This is a read-only page with no destructive confirmation requirement.
- **Unverified compatibility limitation:** keeping Presentation help visible while closed uses `::details-content` (`manage.css:115`). Plan 07 explicitly records that older engines lacking it show that help only when expanded. The supplied browser evidence covers Chromium 149, not Firefox/WebKit or older engines. This is not a reproduced failure in the audited runtime; validate any additional supported browser target before claiming cross-browser parity.
