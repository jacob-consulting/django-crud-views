## Critical Issues

### CR-01: Recording evaluates a different permission source from the actual gate

**Severity:** BLOCKER  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/base.py:1285`  
**Also affected:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/base.py:1264`

**Issue:** Django's `PermissionRequiredMixin.has_permission()` obtains its requirements through `self.get_permission_required()`. After that call completes, the new observations read `self.permission_required` independently. A project can override the normal Django requirement hook, so this property need not have been read at all and need not describe the checked permissions. Recording therefore introduces new behavior into the authorization path and can turn a working request into an exception. With a populated default map, an override requesting a different permission also produces misleading requirement attribution.

**Reproduction:** Register a `ListViewPermissionRequired` subclass with `get_permission_required(self): return ()`, `cv_permission = "custom"`, and an ordinary GET response. The normal anonymous request returns **200**. The identical request inside `recording(AccessRecorder())` raises **AssertionError: permission custom not found**. `trace_access` reports `error`. The project hook intentionally supplies the actual requirement without consulting that map; Django does not require the unused property. This was executed against current checkout sources and cached Django 5.2.19. The equivalent extra property access exists in all-none ancestor admission.

**Fix:** Preserve the single existing requirement-hook invocation and permission check. Record only the requirement values actually obtained by that invocation, or describe overridden requirement hooks as opaque without evaluating the unused property. Do not call `get_permission_required()` a second time for reporting. Add regressions for overridden requirements, unused/raising permission properties, and dynamically computed requirements, comparing recorder-off/on outcomes and hook/query counts in both local and all-none ancestor paths. Keep the stock gate's exact permission reporting.

### CR-02: URI-encoded URLs are resolved without Django's request-path decoding

**Severity:** BLOCKER  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/access_trace_runner.py:163-165`  
**Also affected:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/access_trace_runner.py:402`

**Issue:** `urlsplit(...).path` preserves percent escapes, but `resolve()` expects the decoded path that Django receives as `request.path_info`. URLs copied from a browser or returned by Django's `reverse()` can therefore produce `no_such_route`, wrong lookup coordinates, or a different target from the actual request. This affects both front ends and also the ViewSet mode, which passes `reverse()` output directly to the shared trace.

**Reproduction:** Register a plain CRUD list callback at `path("café/", view.as_view(), name="unicode")`. On current source / Django 5.2.19:

```text
reverse("unicode")                    -> /caf%C3%A9/
Client().get(reverse("unicode")).status_code -> 200
trace_access(reverse("unicode"), None).outcome -> no_such_route
```

The fixture uses an isolated in-memory database and a real Django URLconf. No host fetch or real traced handler is needed.

**Fix:** Decode the extracted URI path once at the shared normalization boundary, using request-compatible percent/UTF-8 handling, before resolving it or constructing the synthetic request. Do not decode the entire URL before splitting it: encoded question marks and hashes belong to the path. Preserve literal plus characters and avoid double decoding. Add real-request-versus-trace regressions for Unicode/static routes, encoded PK/path coordinates, literal percent signs, and full URLs, including reverse-generated per-ViewSet paths.

### CR-03: Username conversion errors bypass primary-key fallback and escape both front ends

**Severity:** BLOCKER  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/access_trace_runner.py:177-180`  
**Callers:** `/home/alex/projects/alex/django-crud-views/src/crud_views/management/commands/cv_access.py:200`; `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/manage.py:811`

**Issue:** Username-first lookup catches only `DoesNotExist`. A custom user model's `USERNAME_FIELD` can be a UUID or another typed field. For an input valid as that user's primary key but invalid as its username type, Django raises `ValidationError`/`ValueError` during query preparation. The code never attempts the PK lookup. Invalid unknown input also escapes the documented `None` result. Both callers resolve the selector outside the shared trace error boundary, so the CLI gets an uncaught exception and the manage form can return HTTP 500 instead of feedback.

**Reproduction:** Using a real ORM model with `login = UUIDField(unique=True)`, `USERNAME_FIELD = "login"`, and an integer primary key, create one row at PK 1. Substitute only that model at the runner's `get_user_model` seam; retain the actual ORM manager and field conversion. Results on cached Django 5.2.19:

```text
resolve_trace_user(str(actor.login)) -> actor with pk 1
resolve_trace_user("1")              -> ValidationError: “1” is not a valid UUID.
resolve_trace_user("unknown")        -> ValidationError: “unknown” is not a valid UUID.
```

**Fix:** Treat username-field input-conversion failures as a nonmatching username and continue with the existing PK conversion/lookup. Catch only the appropriate conversion exceptions alongside `DoesNotExist`; do not swallow database or configuration failures. Preserve username precedence whenever that lookup is valid and matches. Add custom-user-field tests proving valid username selection, PK fallback, unknown input returning `None`, and the CLI/form's normal error handling.
