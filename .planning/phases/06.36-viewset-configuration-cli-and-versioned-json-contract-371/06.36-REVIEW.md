### Critical Issues

### CR-01: Known translation proxies can execute instance-supplied cast hooks

**Classification:** BLOCKER
**Current disposition:** Fixed; independently verified in `06.36-REVIEW-RECHECK.md`.

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/manage_report.py:123-130`

**Issue:** Exact proxy type and plain-string argument checks do not make `str(item)` safe. Django's proxy string conversion calls a helper through the instance; an exact `gettext_lazy` or `pgettext_lazy` object can shadow `_proxy____cast` in its instance dictionary. The validated argument tuple/dictionary can remain entirely benign while the subsequent string conversion invokes a different callable. This violates D-06/A-04 and the published guarantee that normalization does not execute arbitrary callables. It can also replace the exported value with unrelated data. The outer command exception handler cannot undo a hook's side effects.

**Proof:** With Django 5.2.19 and the current checkout, both exact wrapper families execute the supplied hook:

```python
calls = []
value = gettext_lazy("safe")
value._proxy____cast = lambda: calls.append("hook") or "changed"
record = normalize_value(value)
assert calls == ["hook"]
assert record.kind == "native" and record.value == "changed"
```

Replacing the factory with `pgettext_lazy("ctx", "safe")` produces the same result. No proxy subclass, arbitrary `lazy()` factory, hostile argument or global monkeypatch is needed. This is a configuration-to-normalizer execution boundary defect, not a claim of unauthenticated remote exploitation; configured application code is still outside the command's sandbox guarantee.

**Fix:** Resolve the already validated arguments through the trusted eager `gettext`/`pgettext` function selected by the exact known wrapper type, or create and evaluate a fresh trusted wrapper using those validated arguments. Do not dispatch string conversion on the supplied instance. Retain positional/keyword support and the existing Django 4.2 storage-layout handling. Add both wrapper families and their version-specific instance-helper overrides to the normalization and real-builder regression cases; assert the supplied hook is never called.

**Security disposition:** Reopen **T-06.36-03 (Normalization)**. The existing `06.36-SECURITY.md` assertion of 18 closed threats/zero open threats is contradicted by this proof and cannot serve as current sign-off until this defect is fixed and independently rechecked.

### CR-02: Mutated typed metadata bypasses validation and yields invalid complete reports

**Classification:** BLOCKER
**Current disposition:** Fixed; independently verified in `06.36-REVIEW-RECHECK.md`.

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/manage_report.py:19-21`

**Related locations:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/manage_report.py:449-455`; `/home/alex/projects/alex/django-crud-views/src/crud_views/management/commands/cv_manage_view.py:270-282`

**Issue:** `WireModel` is mutable and does not request instance revalidation. Shipped builders return actual `ValueRecord`/`SourceRecord` objects inside `_export`, and supported `super()` overrides receive those same objects. A builder can accidentally change a typed field or mutate a contained list/map after construction. `ConfigEntry.model_validate()` accepts the existing nested instance without checking its fields, and the final `Report.validate_python(report)` likewise receives an existing model graph. Consequently invalid known fields survive both purported validation boundaries. This breaks D-05/D-08: malformed builder output must produce an `output_validation_failed` section and exit 2, not a successful invalid document.

**Proof:** A fresh process configured the existing test Django project, migrated its in-memory database, registered a normal Publisher ViewSet with empty context buttons, and patched only the facts builder to emulate a super-preserving override:

```python
original = ManageView.get_manage_facts

def mutated_facts(self, viewset, user):
    rows = original(self, viewset, user)
    rows[0]["_export"]["value"].kind = "invalid_kind"
    return rows
```

Actual `call_command(Command(), "review_mutated", "--as-json")` returned normally (**exit 0**). Parsed output had `status="complete"`, `errors=[]` and the first fact's `value.kind="invalid_kind"`. Running `Report.validate_python(json.loads(stdout))` then raised a literal validation error at `inspection.data.facts.data.entries.0.value.kind`. Thus the command emits a document rejected by its own consumer contract. Existing tests corrupt ordinary dictionary fields, so they do not expose this typed-instance path.

**Fix:** Require recursive instance revalidation on the shared wire-model base, e.g. `ConfigDict(strict=True, allow_inf_nan=False, revalidate_instances="always")`, and verify this works on the declared Pydantic floor and supported runtime. Keep rejection at section adaptation so independent good sections survive. Add regressions for mutated `ValueRecord` and `SourceRecord` fields plus an in-place mutation of a nested container. Assignment validation or freezing alone is insufficient for in-place container changes; avoid adding a separate hand-maintained validation layer.

**Security disposition:** Reevaluate **T-06.36-09 (Failure/result semantics)** and **T-06.36-12 (Wire schema)** using this actual emitted-document case.

### CR-03: Export overwrites Guardian manage-class provenance with the core setting

**Classification:** BLOCKER
**Current disposition:** Fixed; independently verified in `06.36-REVIEW-RECHECK.md`.

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/manage.py:577-582`

**Related locations:** `/home/alex/projects/alex/django-crud-views/src/crud_views_guardian/lib/views.py:388-394`; `/home/alex/projects/alex/django-crud-views/src/crud_views_guardian/lib/viewset.py:93-101`

**Issue:** `get_manage_presentation()` obtains the source through the polymorphic `_manage_class_source(viewset)` hook, then discards that result in export mode whenever the ViewSet has no explicit manage-class override. The replacement reads only `crud_views_settings.manage_view_class`. Guardian chooses its class from `guardian_manage_view_class`, so JSON/text inspection reports the wrong setting or falsely reports a default. The inverse also occurs: a core setting can be credited even when Guardian ignores it. This is incorrect diagnostic behavior for a supported configuration, violating D-05/D-06 provenance preservation; ordinary page output remains correct.

**Proof:** With `guardian_manage_view_class="crud_views_guardian.lib.views.GuardianManageView"`, `manage_view_class=None`, and a GuardianViewSet without a per-ViewSet override, its registered collector produces:

```text
ordinary presentation source: CRUD_VIEWS_GUARDIAN_MANAGE_VIEW_CLASS
export source: {"code": "default", "setting": null, "declaring_class": null}
```

The effective exported class is still GuardianManageView, so the source record contradicts the actual resolution owner. Setting the unrelated core manage class changes the export source despite not changing Guardian's selected class.

**Fix:** Preserve source selection in the existing core/Guardian `_manage_class_source` owners. Have that owner supply the machine source in export mode, or translate its setting token without replacing it with a second core-only resolver. Retain the distinction between declaration/default state and effective source, including explicit `None`. Add core/Guardian cases with independently configured global settings, both settings together, and a per-ViewSet override; compare page provenance with exported source records.

**Security disposition:** Reevaluate **T-06.36-05 (Provenance)** against the Guardian-specific setting path.

### CR-04: Resource aliases still prevent real PK inheritance at the dependency floor

**Classification:** BLOCKER
**Current disposition:** Fixed in `0876d769ae47ad23d72e28dd34ece4c309650403`; independently rechecked against those repaired source bytes.

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/resource.py:55-76`

**Related location:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/resource.py:99-103`; `/home/alex/projects/alex/django-crud-views/tests/test1/test_resource.py:109-139`.

**Issue:** Replacing private field metadata with `model_fields` lets ordinary Resources initialize on Pydantic 2.2.1, but the inherited `_PkShim` remains visible through class-level `hasattr`. That version rejects a descendant's real `pk` field as shadowing an ancestor attribute before `__pydantic_init_subclass__` can neutralize the property. The existing `test_intermediate_base_pk_shim_does_not_shadow_subclass_pk_field` therefore still fails on the declared floor. Hiding only the property is insufficient: a further descendant encounters the class-visible `_PkShimNeutralized` marker and fails by the same mechanism. This is a pre-existing incompatibility exposed by the gap repair, not a claim that the one-line `model_fields` change introduced the shadowing algorithm. It blocks the claimed floor-compatible PK inheritance behavior.

**Proof:** At `1558c737`, the focused 21-case selection returned 21 passed on Pydantic 2.14.3 and 1 failed/20 passed on 2.2.1. The failure is `NameError: Field name "pk" shadows an attribute in parent ...IntermediateBase` at `class Concrete(IntermediateBase)`. The receipt independently replays the exact frozen Resource source from Git in an isolated process and retains the failure output. An intermediate read-only probe hiding only `_PkShim` still failed at `class Grandchild(Concrete)`.

**Fix:** Preserve the existing PK-selection algorithm and marker classes. Make `_PkShim.__get__` raise `AttributeError` for class access and delegate to the property for row instances. Make `_PkShimNeutralized` a non-data descriptor whose `__get__` raises `AttributeError`, so real instance fields win through `__dict__` while later subclasses do not see a class default. Extend the existing regression with a grandchild and an explicit default. The executor implemented exactly this bounded correction; no metaclass replacement, global patch or dependency-floor increase was introduced.

**Independent recheck:** The actual repaired checkout passed all 21 targeted tests on both Pydantic 2.14.3 (1.37s) and 2.2.1 (1.58s), with two workers and Python 3.12.3 / Django 5.2.19. The Resource file SHA-256 was `6c921ed896b570472e604b2518a26a319173b3ce46c59eb74c48765a94bc8260`. Additional standalone checks preserved subclass FormSet fields and cloned parent identity, and proved hostile raw-input `repr`/`str` hooks were not invoked by error projection.
