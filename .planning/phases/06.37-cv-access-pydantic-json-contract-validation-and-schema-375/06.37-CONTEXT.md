# Phase 06.37: cv_access Pydantic JSON contract validation and schema (#375) - Context

**Gathered:** 2026-11-16
**Status:** Ready for planning

<domain>
## Phase Boundary

Formalize the existing version-1 `cv_access` trace export with explicit Pydantic output models, validate the export
before `cv_access` renders it, and add `cv_access --schema`, which emits JSON Schema generated from those same models.

The scope is pinned by issue #375 (`gh issue view 375`): preserve the public `AccessTrace`/`AccessStep` dataclasses and
`to_dict()`, the trace runner, authorization gates, UI trace semantics, JSON version 1, field meanings, null handling,
step ordering, outcomes, exit codes, trace-JSON color behavior under color options, and ordinary-command-error handling
for invalid arguments/users. No second trace engine, generic diagnostics framework, dataclass replacement, new
outcomes, future skill implementation, or unrelated CLI cleanup.

</domain>

<decisions>
## Implementation Decisions

### Validation-failure reporting
- **D-01 — Failure channel:** If the export fails model validation, `cv_access` writes no stdout trace document. It
  writes a translated "output validation failed" diagnostic to stderr (exception class plus Pydantic error
  location(s); untrusted values escaped with the existing `_text` approach) and exits `2`. The failure is never
  represented as a trace `outcome` (not `error`, not a synthetic step) and adds no new JSON document shape to v1.
  This matches the existing "unknown user / wrong invocation → stderr, exit 2, no trace document" convention in
  `docs/reference/manage.md`.
- **D-02 — Surfaces:** Both `cv_access` modes (text and `--as-json`) validate the same `trace.to_dict()` before
  rendering, so text and JSON cannot diverge on malformed facts. The manage-page Access check
  (`src/crud_views/lib/views/manage.py:936,956`) keeps its current `trace_access(...).to_dict()` path unchanged;
  UI parity is asserted by tests only.
- **D-03 — Validation input:** Validate `trace.to_dict()` output (`Model.model_validate(trace.to_dict())`).
  Dataclasses remain untouched; conversion stays mechanical.

### Model strictness
- **D-04 — Closed enums:** `outcome`, step/plan `kind`, step/plan `result`, and `provider` are closed `Literal` sets
  inventoried from the runner/recorders and the `cv_access` label maps (`_result_label`, `_kind_label`). Unknown
  values fail validation. `source`, `message`, `how`, `key`, `permission`, `group`, `viewset`, `route`, `view`,
  `path` stay open strings (`source` carries project class paths such as `<module>.<View>.cv_get_requirement`).
  — **Reversibility:** costly — adding a value later is a contract change under D-12, so the inventory must be complete.
- **D-05 — Typed sub-models:** No unrestricted dicts. `TraceUser` (`pk`, `username`, `active`, `anonymous`, each
  nullable/optional) must also accept `user == {}` (trace failed before actor resolution, e.g. path
  normalization). `ObjectIdentity {model: str, pk: str | None}`. `TraceException {class, message}` via a field
  alias for `class`. `Counts {visible: int, total: int | None}`.
- **D-06 — Separate plan model:** `PlanRow` models the keys plan dicts actually carry (`kind`, `viewset`, `object`,
  `key`, `group`, `permission`, `provider`, `source`, optional `result="unavailable"` and `exception`); plan rows
  have no `n`. `Step` models all 14 `AccessStep` fields. The schema distinguishes the two lists.
- **D-07 — Emit path:** Validation is a gate only. On success, JSON is still
  `json.dumps(trace.to_dict(), ensure_ascii=True, indent=2)` and the existing `_color_json` path is unchanged, so
  bytes stay identical. A drift test asserts `model_dump(mode="json", by_alias=True, exclude_unset=True) == trace.to_dict()`
  across fixtures.
  *Amended 2026-11-16 (maintainer decision, research Pitfall 2):* originally without `exclude_unset=True`. Plain
  `model_dump()` fills omitted optional keys with `None`, so it can never equal `to_dict()` for plan rows (D-06) or
  `user == {}` (D-05). Keys present in the input count as set even when `None`, so steps and root keys still
  round-trip exactly; key completeness is enforced by required fields, `extra="forbid"` (D-08) and schema `required`
  assertions.
- **D-08 — Extra keys forbidden:** Trace models use `extra="forbid"` on top of the 06.36 strict conventions
  (`strict=True`, `allow_inf_nan=False`, `revalidate_instances="always"`). A dataclass field added without a model
  update fails validation (stderr, exit 2) and fails the drift test; the schema therefore emits
  `additionalProperties: false`. Documentation still tells consumers to tolerate additive fields (D-12).

### `--schema` CLI rules
- **D-09 — Exclusive mode:** `path` becomes `nargs="?"`. `--schema` combined with a path, user, or `--anonymous` is a
  usage error (`CommandError`, returncode 2), mirroring 06.36 A-01. Without `--schema`, a missing path is likewise
  exit 2. Schema mode runs no trace runner, resolves no user, and performs no diagnostic object/permission reads
  (normal Django startup excluded).
- **D-10 — `--as-json` with `--schema`:** Allowed and redundant (schema output is always JSON). Schema output is
  always plain, never colored, even with `--force-color` (same as `cv_manage_view --schema`'s identity `style_func`).
- **D-11 — Schema root:** A single root model (working name `AccessTraceExport`) with `version: Literal[1]`. All
  trace shapes (allowed, denied, login_redirect, not_found, no_such_route, error) are this model with different
  outcome values and nullable fields. No discriminator or per-outcome union (adding `kind` would change v1).
  Generated with `json_schema(mode="validation")` and dumped like 06.36 (`ensure_ascii=True, allow_nan=False, indent=2`).
  *Amended 2026-11-16 (maintainer decision, research A1):* originally `mode="serialization"`; at the supported floor
  Pydantic 2.2.1 that mode marks every field required and rejects real exports (`user == {}`, plan rows omitting
  keys). `mode="validation"` is correct on 2.2.1 and identical to serialization output on 2.14.3.
  No static `cv_access.schema.json` is published; `cv_access --schema` is the single source (maintainer decision).

### Compatibility docs
- **D-12 — Versioning rule (mirrors 06.36):** Within version 1, new optional fields are additive and consumers must
  tolerate them. A new closed-enum value, a removed/renamed field, or a changed meaning requires a version bump or an
  explicit maintainer decision. The generated schema is authoritative.
- **D-13 — Docs home:** Extend the existing `## cv_access` section of `docs/reference/manage.md` with schema access,
  the versioning/compatibility rule, and validation-failure behavior (stderr, exit 2, not an outcome), plus the
  `--schema` row(s) in the streams/exit documentation. No new shared contracts page.
- **D-14 — Not public Python API:** The Pydantic trace models live in an internal module (e.g.
  `src/crud_views/lib/access_trace_export.py`; exact placement is the planner's call). JSON and the generated schema are
  the machine contract. `AccessTrace`/`AccessStep` plus `to_dict()` remain the public Python interface.

### Claude's Discretion
- Module/class names, whether to reuse or subclass `WireModel` from `manage_report.py` (only if it does not couple
  the two contracts awkwardly), the exact stderr wording, and test file layout.
- The way the closed `Literal` inventories are derived and guarded, e.g. a test checking label-map keys against `Literal` args.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `manage_report.WireModel` / `TypeAdapter.json_schema(mode="serialization")`: the proven 06.36 pattern for strict
  wire models and schema generation.
- `cv_manage_view --schema` branch: a template for plain JSON schema output and mode-exclusivity checks.
- `cv_access._text`: escapes untrusted values for the stderr validation diagnostic.
- Existing cv_access command/trace tests and fixtures (model, Guardian, Resource, nested, login redirect, missing
  route/object, error traces) supply the drift/validation corpus.

### Established Patterns
- Pydantic floor is `pydantic>=2.2.1` (`pyproject.toml`); 06.36 already worked around 2.2 limits (`TypeAliasType`,
  `Generic` syntax). Field aliasing for `class` and `extra="forbid"` must work at that floor.
- Runner messages use `gettext` (plain `str`, not lazy proxies), so strict `str` validation of `to_dict()` is viable.
  The researcher should still confirm that no lazy or non-str values (e.g. UUID pks) reach any field.
- Invalid invocation/unknown user already go to stderr with exit 2 and no trace document, so D-01 extends an existing convention.

### Integration Points
- `cv_access.Command.handle`: insert validation after `trace_access()` and before either formatter; add the `--schema`
  branch before user resolution.
- The new internal module is importable before Django configuration, like `access_trace.py`, if feasible.

</code_context>

<specifics>
## Specific Ideas

- The drift test should run across every existing trace fixture shape: allowed, denied, login_redirect, not_found,
  no_such_route, error, `user == {}`, `unavailable` plan rows, counts with `total=None`, Guardian provider, Resource,
  and nested ancestor gates.
- Add a test that corrupts a known field (e.g. `counts.visible="3"`, unknown `result`, extra key) and asserts stderr
  plus exit 2 with no stdout, instead of coercion.
- Add a schema-mode test proving the runner and user resolution are never invoked (patch/spy), with no path/actor supplied.

</specifics>

<deferred>
## Deferred Ideas

- Structured JSON error documents for invalid arguments or validation failures, and always-plain trace JSON. Both
  are explicit compatibility decisions excluded by #375.
- Validating the trace on the manage page / UI error panel.
- Public Python export of the trace models.

</deferred>
