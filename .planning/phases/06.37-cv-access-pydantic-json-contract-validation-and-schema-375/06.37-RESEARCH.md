# Phase 06.37: cv_access Pydantic JSON contract validation and schema (#375) - Research

**Researched:** 2026-11-16
**Domain:** Pydantic v2 output models and JSON Schema for an existing dataclass export; Django management command modes
**Confidence:** HIGH (code paths read this session; Pydantic behavior probed at 2.2.1 and 2.14.3; draft models validated against 1,839 real traces from the existing suite)

## Summary

The phase adds no dependency and changes neither the trace runner nor the UI. It adds one small internal module of
strict Pydantic models that mirror `AccessTrace.to_dict()`. `cv_access` validates that dictionary before either
formatter and gains an exclusive `--schema` mode. Every value the models need was inventoried from the recorder call
sites, the `cv_access` label maps, the docs and the tests. A draft of the recommended models (in "Code Examples") was
injected into the existing suite as a probe: it wrapped `access_trace_runner._run_trace` across all 33 test modules that
produce traces. **All 1,839 real traces validated, with zero drift** for `model_dump(mode="json", by_alias=True,
exclude_unset=True) == to_dict()`, and 2,361 tests passed. The closed `Literal` inventories (D-04) are therefore
complete for every shape the suite exercises.

Two findings bear on locked decisions and need to reach the planner:

1. **D-11 `mode="serialization"` produces a wrong schema at the supported Pydantic floor (2.2.1).** At 2.2.1,
   `GenerateJsonSchema.field_is_required` marks *every* field required in serialization mode. The schema would then
   require `pk/username/active/anonymous` in `user` and `object/key/.../exception` in plan rows, which rejects real
   output (`user == {}`, and plan rows that omit keys). At 2.14.3 the same call omits defaulted fields from
   `required`. `mode="validation"` produces the correct `required` lists on **both** versions. At 2.14.3 it is
   byte-identical to serialization mode for these models, because they have no serializers. Recommendation: generate
   with `mode="validation"` and record this as a research-surfaced deviation from D-11's wording that keeps D-11's
   intent. Issue #375 requires surfacing exactly this kind of incompatibility.
2. **D-07's drift assertion needs `exclude_unset=True`.** `to_dict()` omits keys in plan rows (four distinct key sets
   were observed) and emits `user == {}` before actor resolution. `model_dump(mode="json", by_alias=True)` alone
   fills those gaps with `None` and does not equal `to_dict()`. Adding `exclude_unset=True` makes the equality exact
   (verified on 2.2.1, on 2.14.3 and on the full real corpus).

**Primary recommendation:** Create `src/crud_views/lib/access_trace_export.py` with a private base model
(`strict=True, allow_inf_nan=False, revalidate_instances="always", extra="forbid"`; do not subclass `WireModel`),
the models in "Code Examples", a `validate_export(data)` function and an `export_schema()` function using
`model_json_schema(mode="validation")`. In `cv_access.handle`, check mode exclusivity first. Schema mode writes plain
JSON and returns. Otherwise the command traces, validates `trace.to_dict()` (raising `CommandError(..., returncode=2)`
with class and locations only on failure), then renders through the unchanged formatters.

## User Constraints (from CONTEXT.md)

### Locked Decisions

### Validation-failure reporting
- **D-01 — Failure channel:** If the export fails model validation, `cv_access` writes no stdout trace document. It
  writes a translated "output validation failed" diagnostic to stderr (exception class plus Pydantic error
  location(s); untrusted values escaped with the existing `_text` approach) and exits `2`. The failure is never
  represented as a trace `outcome` (not `error`, not a synthetic step) and adds no new JSON document shape to v1.
  This matches the existing "unknown user / wrong invocation → stderr, exit 2, no trace document" convention in
  `docs/reference/manage.md`.
- **D-02 — Surfaces:** Both `cv_access` modes (text and `--as-json`) validate the same `trace.to_dict()` before
  rendering, so text and JSON cannot diverge on malformed facts. The manage-page Access check
  (`src/crud_views/lib/views/manage.py:936,956`) keeps its current `trace_access(...).to_dict()` path unchanged;
  UI parity is asserted by tests only.
- **D-03 — Validation input:** Validate `trace.to_dict()` output (`Model.model_validate(trace.to_dict())`).
  Dataclasses remain untouched; conversion stays mechanical.

### Model strictness
- **D-04 — Closed enums:** `outcome`, step/plan `kind`, step/plan `result`, and `provider` are closed `Literal` sets
  inventoried from the runner/recorders and the `cv_access` label maps (`_result_label`, `_kind_label`). Unknown
  values fail validation. `source`, `message`, `how`, `key`, `permission`, `group`, `viewset`, `route`, `view`,
  `path` stay open strings (`source` carries project class paths such as `<module>.<View>.cv_get_requirement`).
  — **Reversibility:** costly — adding a value later is a contract change under D-12, so the inventory must be complete.
- **D-05 — Typed sub-models:** No unrestricted dicts. `TraceUser` (`pk`, `username`, `active`, `anonymous`, each
  nullable/optional) must also accept `user == {}` (trace failed before actor resolution, e.g. path
  normalization). `ObjectIdentity {model: str, pk: str | None}`. `TraceException {class, message}` via a field
  alias for `class`. `Counts {visible: int, total: int | None}`.
- **D-06 — Separate plan model:** `PlanRow` models the keys plan dicts actually carry (`kind`, `viewset`, `object`,
  `key`, `group`, `permission`, `provider`, `source`, optional `result="unavailable"` and `exception`); plan rows
  have no `n`. `Step` models all 14 `AccessStep` fields. The schema distinguishes the two lists.
- **D-07 — Emit path:** Validation is a gate only. On success, JSON is still
  `json.dumps(trace.to_dict(), ensure_ascii=True, indent=2)` and the existing `_color_json` path is unchanged, so
  bytes stay identical. A drift test asserts `model_dump(mode="json", by_alias=True) == trace.to_dict()` across fixtures.
- **D-08 — Extra keys forbidden:** Trace models use `extra="forbid"` on top of the 06.36 strict conventions
  (`strict=True`, `allow_inf_nan=False`, `revalidate_instances="always"`). A dataclass field added without a model
  update fails validation (stderr, exit 2) and fails the drift test; the schema therefore emits
  `additionalProperties: false`. Documentation still tells consumers to tolerate additive fields (D-12).

### `--schema` CLI rules
- **D-09 — Exclusive mode:** `path` becomes `nargs="?"`. `--schema` combined with a path, user, or `--anonymous` is a
  usage error (`CommandError`, returncode 2), mirroring 06.36 A-01. Without `--schema`, a missing path is likewise
  exit 2. Schema mode runs no trace runner, resolves no user, and performs no diagnostic object/permission reads
  (normal Django startup excluded).
- **D-10 — `--as-json` with `--schema`:** Allowed and redundant (schema output is always JSON). Schema output is
  always plain, never colored, even with `--force-color` (same as `cv_manage_view --schema`'s identity `style_func`).
- **D-11 — Schema root:** A single root model (working name `AccessTraceExport`) with `version: Literal[1]`. All
  trace shapes (allowed, denied, login_redirect, not_found, no_such_route, error) are this model with different
  outcome values and nullable fields. No discriminator or per-outcome union (adding `kind` would change v1).
  Generated with `json_schema(mode="serialization")` and dumped like 06.36 (`ensure_ascii=True, allow_nan=False, indent=2`).

### Compatibility docs
- **D-12 — Versioning rule (mirrors 06.36):** Within version 1, new optional fields are additive and consumers must
  tolerate them. A new closed-enum value, a removed/renamed field, or a changed meaning requires a version bump or an
  explicit maintainer decision. The generated schema is authoritative.
- **D-13 — Docs home:** Extend the existing `## cv_access` section of `docs/reference/manage.md` with schema access,
  the versioning/compatibility rule, and validation-failure behavior (stderr, exit 2, not an outcome), plus the
  `--schema` row(s) in the streams/exit documentation. No new shared contracts page.
- **D-14 — Not public Python API:** The Pydantic trace models live in an internal module (e.g.
  `src/crud_views/lib/access_trace_export.py`; exact placement is the planner's call). JSON and the generated schema are
  the machine contract. `AccessTrace`/`AccessStep` plus `to_dict()` remain the public Python interface.

### Claude's Discretion
- Module/class names, whether to reuse or subclass `WireModel` from `manage_report.py` (only if it does not couple
  the two contracts awkwardly), the exact stderr wording, and test file layout.
- The way the closed `Literal` inventories are derived and guarded, e.g. a test checking label-map keys against `Literal` args.

### Deferred Ideas (OUT OF SCOPE)
- Structured JSON error documents for invalid arguments or validation failures, and always-plain trace JSON. Both
  are explicit compatibility decisions excluded by #375.
- Validating the trace on the manage page / UI error panel.
- Public Python export of the trace models.

### Pattern 1: Gate-only validation (D-03/D-07)
**What:** `validate_export(trace.to_dict())` runs and its result is discarded. The formatters keep calling
`trace.to_dict()` and `json.dumps(...)` exactly as today [VERIFIED: cv_access.py:176-178
`serialized = json.dumps(trace.to_dict(), ensure_ascii=True, indent=2)` / `return _color_json(serialized) if color else serialized`].
**When:** Insert it in `handle()` after `trace = trace_access(path, actor)` and before the `no_such_route` stderr branch,
so that a malformed no-route trace does not emit its stderr line either.
**Why not pass validated data into formatters:** the formatter signatures and bytes stay identical, and the diff stays at a few lines.

### Pattern 2: Exclusive schema mode before any lookup (D-09/D-10)
Mirror `cv_manage_view` [VERIFIED: cv_manage_view.py:228-233 `elif schema:` / `self.stdout.write(` /
`json.dumps(report_schema(), ensure_ascii=True, allow_nan=False, indent=2),` / `style_func=lambda value: value,` / `)` /
`return`], but use `CommandError(..., returncode=2)` for usage errors (D-09), as the existing check does
[VERIFIED: cv_access.py:198-199 `if anonymous == (user is not None):` /
`raise CommandError(_("Supply either a user or --anonymous, but not both."), returncode=2)`].

### Pattern 3: Own strict base, do not subclass `WireModel`
`WireModel` is [VERIFIED: manage_report.py:19-21 `class WireModel(BaseModel):` /
`# Consumers tolerate additive fields. Known fields never accept coercion.` /
`model_config = ConfigDict(strict=True, allow_inf_nan=False, revalidate_instances="always")`]. Its comment documents
*ignore-extras* semantics. Subclassing it with `extra="forbid"` would contradict that comment, and importing
`manage_report` would pull in the 06.36 contract. Define a 4-line private base in the new module instead. This choice
falls under Claude's Discretion.

### Anti-Patterns to Avoid
- **Emitting `model.model_dump()` instead of `to_dict()`.** It breaks byte identity and the omitted-key semantics (D-07).
- **Using `str(ValidationError)` in the diagnostic.** It embeds `input_value=` (possibly project exception messages with
  terminal controls) and documentation URLs. Use only `type(exc).__name__` and `error["loc"]`, escaped with `_text`.
- **Representing validation failure as `outcome="error"` or a synthetic step** (D-01).
- **Lazy `gettext_lazy` or `_()` in the export module.** Keep all translatable text in `cv_access.py`, which is already in the
  locale coverage `SOURCES`.
- **A golden schema file compared byte-for-byte.** The schema differs cosmetically between 2.2.1 and 2.14.3
  (`"type": "integer"`/`"string"` beside `const`, verified). Assert structure instead.

## Common Pitfalls

### Pitfall 1: Serialization-mode schema is wrong at Pydantic 2.2.1 (affects D-11)
**What goes wrong:** At 2.2.1, `json_schema(mode="serialization")` lists every field as required
(`return not field.get('serialization_exclude')` in 2.2.1's `field_is_required`, verified by printing the source).
`PlanRow.required` became `['kind','viewset','object','result','exception']` and `TraceUser.required` became all four
keys. At 2.14.3 the same call gives `['kind','viewset']` and no required keys for the user. The floor schema would
reject real `user == {}` output and every plan row.
**How to avoid:** Use `mode="validation"`. On both versions it gives `PlanRow.required == ['kind','viewset']`, no
`TraceUser.required`, and all 14 Step keys required. At 2.14.3 the validation-mode schema equals the serialization-mode
schema for these models (verified). Add a test asserting those `required` lists so a regression at either version fails.
**Decision status:** RESOLVED. This deviated from D-11's original wording and was surfaced for a maintainer decision
(issue #375: "surface it for a maintainer decision"). The maintainer accepted validation mode, and CONTEXT D-11 was
amended on 2026-11-16.
**Warning signs:** Any test that runs only on 2.14.3 will never catch this. See Pitfall 6.

### Pitfall 2: Drift test without `exclude_unset=True` (affects D-07)
**What goes wrong:** Optional-with-default fields (plan rows, `TraceUser`) are dumped as `None`, so the comparison
`model_dump(...) != to_dict()` fails for every plan row and for `user == {}`.
**How to avoid:** Use `model_dump(mode="json", by_alias=True, exclude_unset=True)`. Fields present in the input count as
"set" even when their value is `None`, so steps and root keys round-trip exactly. Verified on both versions and on 1,839 real traces.

### Pitfall 3: Strict-mode differences between 2.2.1 and 2.14.3
**What goes wrong:** At 2.14.3, strict `Literal[1]` **accepts `True`** for `version`; 2.2.1 rejects it. At 2.2.1,
strict `list[...]` **accepts a tuple**; 2.14.3 rejects it (both verified). Neither occurs in `to_dict()` output, but a
malformed-input test built on these values would be version-dependent.
**How to avoid:** Build malformed fixtures from cases that behave the same on both versions (all verified):
`counts.visible="3"` → `int_type`, `counts.visible=True` → `int_type`, unknown `result` → `literal_error`, extra key →
`extra_forbidden`, `{"class_": …}` → `missing`+`extra_forbidden`, removed step key → `missing`, `version=2` →
`literal_error`, non-str `path` (object with `__str__`) → `string_type`. `str` subclasses are accepted (harmless).

### Pitfall 4: Docs tests parse `manage.md` structurally
**What goes wrong:** Several parsers would misread new docs content
[VERIFIED: tests/test1/test_access_trace_docs.py:34-35, 48-60, 69-72].
- `section(title)` splits on `### {title}\n` up to the next `\n### `.
- The regex `^\| \`(\w+)\` \| \`(\d)\` \|` in "Outcomes and streams" must yield exactly the six outcomes. A row such as
  `` | `schema` | `0` | `` breaks it.
- The tables in "Version 1 document" and "Step fields" must equal the dataclass fields.
- The **first** `` ```json `` block in the whole file is parsed as the no-route sample. Any new `` ```json `` block placed
  before it (including one in `## cv_manage_view`) breaks the test.
**How to avoid:** Document `--schema` and validation failure in prose or in a new `### Schema and compatibility`
subsection placed **after** the existing JSON sample. Use `` ```bash `` for examples. Do not add backticked word/digit rows
to the outcomes table; mention schema exit 0 and validation exit 2 in a sentence. Anchors: new `###` headings are not in
`ANCHORS` (that set covers `##` headings only), so they are safe.

### Pitfall 5: Locale coverage enforcement
**What goes wrong:** `test_manage_german_catalog_covers_sources` fails on any new msgid in `cv_access.py` that lacks a
non-fuzzy German entry. `test_manage_compiled_catalog_matches_po_semantics` fails if `.mo` is stale or if `%(name)s`
placeholders differ [VERIFIED: tests/test1/test_manage_locales.py:17-24 (SOURCES incl.
`"management/commands/cv_access.py"`), 215-266]. Dynamic or f-string messages are rejected by the extractor.
**How to avoid:** Use literal msgids with named placeholders. Add them to
`src/crud_views/locale/de/LC_MESSAGES/django.po` and recompile with polib. New msgids (≈4): `--schema` help, validation
failure, `--schema` exclusivity error, missing path error.

### Pitfall 6: The floor is not exercised by default CI
**What goes wrong:** The Pydantic-2.2.1 session `manage_report_floor` is `default=False` and runs only `MANAGE_REPORT_TESTS`
[VERIFIED: noxfile.py:65-72, 81 `assert found["pydantic"] == pydantic.__version__ == "2.2.1", found`, 87-105].
`test_manage_command_ci.py:67` asserts that list by set equality.
**How to avoid:** Add `tests/test1/test_access_trace_contract.py` to `MANAGE_REPORT_TESTS` and to `EXPECTED_TESTS` in
`test_manage_command_ci.py` (a 2-line change). Run the session once as phase evidence. The session requires an empty
`CV_MANAGE_SCHEMA_EXPORT_DIR`. Alternative if the planner rejects touching the session: run the contract file once in a
throwaway `uv` venv pinned to `pydantic==2.2.1` and record the output.

### Pitfall 7: Usage-error surface for a missing path changes slightly
With `nargs="?"`, a missing path is no longer an argparse "the following arguments are required" error. It becomes our
`CommandError`. Exit 2, empty stdout, non-empty stderr and no traceback are all preserved, so the existing tests
`test_wrong_invocation_produces_no_trace([])` and `test_real_process_invocation_errors([], 2)`
[VERIFIED: test_access_trace_command.py:119-124, 305-323] still pass. Only the stderr wording changes (it gains a
`CommandError:` prefix).

### Pitfall 8: Project hooks returning non-str values now fail closed
`cv_get_requirement()` is public [CITED: docs/reference/theme.md:1049-1062]. A project returning a lazy proxy or a
non-str `value` used to produce text output (and a JSON `TypeError` for lazy proxies). It will now produce exit 2 with a
validation diagnostic in both modes. This is intended (D-02/D-08). Mention it in the docs validation-failure paragraph.

```python
# src/crud_views/lib/access_trace_export.py
"""Internal wire models for the cv_access version-1 trace. Importable before Django configuration."""

from typing import Literal

from pydantic import BaseModel, ConfigDict, Field

Outcome = Literal["allowed", "denied", "not_found", "login_redirect", "no_such_route", "error"]
Kind = Literal[
    "route", "validation", "actor_admission", "ancestor_lookup", "ancestor_gate", "own_permission",
    "object_lookup", "object_grant", "list_filter", "action_state", "manage_gate", "custom_gate",
    "login_middleware", "limitation",
]
StepResult = Literal[
    "passed", "denied", "not_found", "login_redirect", "error", "skipped", "not_reached", "not_evaluated", "unavailable"
]
Provider = Literal["core", "guardian", "model", "none"]


class _TraceModel(BaseModel):
    # Unknown keys and coercion are rejected; documentation still asks consumers to tolerate additive fields.
    model_config = ConfigDict(strict=True, allow_inf_nan=False, revalidate_instances="always", extra="forbid")


class TraceUser(_TraceModel):  # all keys absent before actor resolution
    pk: str | None = None
    username: str | None = None
    active: bool | None = None
    anonymous: bool | None = None


class ObjectIdentity(_TraceModel):
    model: str
    pk: str | None


class TraceException(_TraceModel):
    class_: str = Field(alias="class")
    message: str


class Counts(_TraceModel):
    visible: int
    total: int | None


class PlanRow(_TraceModel):  # keys other than kind/viewset may be absent
    kind: Kind
    viewset: str | None
    object: ObjectIdentity | None = None
    key: str | None = None
    group: str | None = None
    permission: str | None = None
    provider: Provider | None = None
    source: str | None = None
    result: Literal["unavailable"] | None = None
    exception: TraceException | None = None


class Step(_TraceModel):  # every AccessStep key is always present
    n: int
    kind: Kind
    viewset: str | None
    object: ObjectIdentity | None
    key: str | None
    permission: str | None
    group: str | None
    provider: Provider | None
    source: str | None
    result: StepResult | None
    how: str | None
    message: str | None
    exception: TraceException | None
    counts: Counts | None


class AccessTraceExport(_TraceModel):
    path: str
    route: str | None
    view: str | None
    user: TraceUser
    outcome: Outcome
    decided_by: int | None
    plan: list[PlanRow]
    steps: list[Step]
    untraced: list[str]
    version: Literal[1]


def validate_export(data):
    return AccessTraceExport.model_validate(data)


def export_schema():
    # Validation mode: Pydantic 2.2.1 marks defaulted fields required in serialization mode (see RESEARCH Pitfall 1).
    return AccessTraceExport.model_json_schema(mode="validation")
```
