## Warnings

### WR-01: Text output reports an unresolved actor as "None (pk None, inactive)"

**File:** `src/crud_views/management/commands/cv_access.py:108-116`
**Issue:** When a trace fails before actor resolution, `trace.user` stays `{}` (`access_trace_runner.py:397` runs
`_normalize_path` before `_fresh_actor` at line 400). `_format_text` has no branch for the empty mapping, so
`actor.get("anonymous")` is falsy and the non-anonymous branch formats three missing keys. Reproduced with an
existing active user `sam`:

```text
$ cv_access 'http://[bad/x/' sam --no-color      (exit 2)
Path: http://[bad/x/
Route: None
View: None
User: None (pk None, inactive)
```

The command states that the user is inactive, which is false, and `--anonymous` gives the same line instead of
"Anonymous user". These lines predate this phase and the diff does not touch them. The phase is what makes the
state official: `TraceUser` accepts `{}` (D-05), `docs/reference/manage.md:478` documents it, and the gate now
passes it to the formatter as a valid shape. JSON output is correct (`"user": {}`); only text mode misreports.
**Fix:** Add an explicit branch. This changes text bytes for the `user == {}` shape only, so it needs a
maintainer decision against the "valid output bytes unchanged" boundary of #375, plus a German `msgstr` and a
recompiled `django.mo`.

```python
actor = data["user"]
if not actor:
    user = _("not resolved (the trace failed before actor resolution)")
elif actor.get("anonymous"):
    user = _("Anonymous user")
else:
    ...
```

### WR-02: `TraceUser` accepts partial and null-valued actors, so gate and schema are weaker than the documented contract

**File:** `src/crud_views/lib/access_trace_export.py:39-43`
**Issue:** All four keys are independently optional and nullable. The runner emits exactly two shapes: `{}` or
all four keys with real booleans (`access_trace_runner.py:401-406`), and the reference page promises "boolean
`active` and `anonymous`" (`docs/reference/manage.md:478`). The model admits everything in between. Both of these
pass `validate_export` on Pydantic 2.14.1 and 2.2.1:

```python
{"pk": "1"}                                                        # three keys missing
{"pk": "1", "username": "sam", "active": None, "anonymous": None}  # null booleans
```

Consequences: a runner regression that drops or nulls one actor key passes the gate silently (text mode then
prints the misleading line from WR-01), the drift assertion cannot see it because `exclude_unset=True` round-trips
any subset, and the published schema types `active`/`anonymous` as `boolean | null` and optional, which
contradicts the prose a consumer reads. `test_access_trace_contract.py:474` pins the loose shape
(`"required" not in definitions["TraceUser"]`).
**Fix:** The smallest change keeps the fields and adds one validator. Checked on Pydantic 2.14.1 and 2.2.1: `{}`
and both complete shapes pass and round-trip, the two shapes above fail with `value_error` at `user`.

```python
class TraceUser(_TraceModel):  # empty before actor resolution, otherwise complete
    pk: str | None = None
    username: str | None = None
    active: bool | None = None
    anonymous: bool | None = None

    @model_validator(mode="after")
    def _empty_or_complete(self):
        if self.model_fields_set and (
            self.model_fields_set != set(type(self).model_fields) or self.active is None or self.anonymous is None
        ):
            raise ValueError("user must be empty or carry pk, username, active and anonymous")
        return self
```

This tightens the gate but not the generated schema. If the schema should express it too, `user` has to become a
union of a complete model and an empty model (`anyOf`), which rewords D-05 ("each nullable/optional") and is a
maintainer decision.

### WR-03: Contract tests leak an emptied ViewSet registry through `isolated_routes` (root cause of the open deferred item)

**File:** `tests/test1/test_access_trace_contract.py:529` (also lines 575, 596, 612, 628, 642, 707, 735); root
cause in `tests/test1/test_ancestor_authorization.py:51-52,68-70`, which is outside this phase's file list
**Issue:** `isolated_routes` snapshots `_REGISTRY` before it builds the temporary URLconf. If
`tests.test1.app.views` has not been imported yet in that process, the snapshot is empty, the project's ViewSets
register inside the block (through `include("tests.test1.project.urls")`), and the `finally` clause restores the
empty snapshot. The module stays in `sys.modules`, so the registrations never run again and the project's
ViewSets are gone for the rest of that process or xdist worker. A scratch probe around one `isolated_routes`
block printed:

```text
before: views imported = False registry size = 0
inside: views imported = True  registry size = 34
after:  views imported = True  registry size = 0   author registered = False
```

Deterministic reproduction (run in one process because test order is the variable):

```text
pytest "tests/test1/test_access_trace_contract.py::test_real_outcome_traces_validate_and_match_the_cli" \
       "tests/test1/test_manage_command_docs.py::test_published_command_examples" -p no:randomly
-> 1 failed, 6 passed   (data.entries: [])
```

This is the failure recorded as open in `deferred-items.md` with "Likely cause (unverified)". None of the seven
`MANAGE_REPORT_TESTS` modules imports the project views at collection, and before this phase none of them used
`isolated_routes`; the contract file added at `noxfile.py:73` is the first. The floor session is not failing
today: the full selection with the contract file ordered first passed in one process (487 passed), because the
earlier contract tests resolve a URL outside an `isolated_routes` block and so import the views first. Under
xdist that protection depends on which tests a worker happens to run first.
**Fix:** Register the project's ViewSets before taking the snapshot. With this import in place the probe ends with
`registry size = 33`, `author registered = True`.

```python
def isolated_routes(build):
    import_module("tests.test1.project.urls")  # the project's ViewSets must be in the snapshot
    sfx = uuid.uuid4().hex[:8]
    ...
    with _REGISTRY_LOCK:
        registry_snapshot = dict(_REGISTRY)
```

## Info

### IN-01: Cargo-culted pattern — `allow_inf_nan=False` on models without float fields

**File:** `src/crud_views/lib/access_trace_export.py:36`
**Category:** necessity
**Issue:** The guarded state (an `inf`/`nan` value reaching a float field) cannot occur: no field in this module is
`float` or `Decimal` (lines 39-101 are `str`, `bool`, `int`, `Literal` and nested models), and strict `int`
already rejects every float (`decided_by=1.0` fails with `int_type`). The option was copied from `WireModel`
(`manage_report.py:21`) under D-08. Classified Info, not Warning, because keeping the two contracts' configs
identical is a deliberate, locked choice.
**Fix:** Keep it for parity with `WireModel` or drop it; if kept, the comment on line 35 could say that the option
is inert here.

### IN-02: Generality without instantiation — three `StepResult` values are never emitted on a step

**File:** `src/crud_views/lib/access_trace_export.py:28-30,84`
**Category:** necessity
**Issue:** `Step.result` closes over nine values, but no recorder produces `skipped`, `login_redirect` or
`unavailable` on a step. `skipped` has no emitter anywhere in `src/`. A login redirect is recorded as `denied`
(`access_trace_runner.py:342-343`; `login_redirect` is only an outcome). `unavailable` rows are excluded before
they can become steps (`access_trace_runner.py:112-113`) and are already modelled by `PlanRow.result`. The values
are in the set because D-04 derived it from the shared `_result_label` map. The schema and
`docs/reference/manage.md:513-514` therefore advertise step results a consumer can never receive. Info because
reserving values is defensible under D-12, where adding one later is a contract change.
**Fix:** Either narrow `Step.result` to the six emitted values (narrowing does not break consumers) or mark the
three as reserved in the reference page.

### IN-03: "One-based" and count integers are unconstrained in the models and the schema

**File:** `src/crud_views/lib/access_trace_export.py:57-58,75,97`
**Issue:** `n` and `decided_by` are documented as one-based and `counts` as row counts, but `n=-3`,
`decided_by=0`, `decided_by=99` with two steps, and `counts={"visible": -1, "total": -5}` all validate, and the
schema carries no `minimum`. The gate checks shape only. This matches the phase goal; it is listed so the limit
of "validated" is on record.
**Fix:** Optional: `Field(ge=1)` on `n`/`decided_by` and `Field(ge=0)` on the counts. That adds `minimum` to the
generated schema, so decide it together with WR-02.

### IN-04: The documented validation-failure line omits the real prefix and is locale-dependent

**File:** `docs/reference/manage.md:438,544`
**Issue:** The reference quotes "one stderr line `Output validation failed (ValidationError): ...`". The real
command line is `CommandError: Output validation failed (ValidationError): ...`, which
`tests/test1/test_access_trace_contract.py:367` asserts, and under a German `LANGUAGE_CODE` it is
`CommandError: Ausgabevalidierung fehlgeschlagen (ValidationError): ...` (`django.po:1318-1319`). The neighbouring
no-route line is documented byte-exact, so a reader may match on the start of this one as well.
**Fix:** Show the real line and add that the text is translated; scripts should detect the case by exit `2` with
empty stdout.

### IN-05: Schema text and gate strictness vary with the installed Pydantic, and the floor session is not in CI

**File:** `noxfile.py:64-65,88`; `docs/reference/manage.md:536-537`
**Issue:** `cv_access --schema` is described as the single authoritative source, but its bytes depend on the
installed Pydantic: 2.2.1 emits `"version": {"const": 1, "title": "Version"}`, 2.14.1 adds `"type": "integer"`
(the two dumps hash differently). The gate differs as well: at 2.2.1 strict `list[...]` accepts a tuple for
`steps`, `plan` and `untraced`, and at 2.14.1 it rejects it. That one is harmless on the wire, because
`json.dumps` writes an array either way. The comment at `noxfile.py:64-65` says the list "proves the cv_access
trace contract (#375) at the Pydantic floor", but `manage_report_floor` is `default=False` and
`.github/workflows/tests.yml:25` runs only the `tests-*` sessions, so the proof exists only when someone runs the
session by hand. That arrangement predates this phase (06.36).
**Fix:** In the docs, extend "regenerate it after upgrading" to cover Pydantic upgrades and warn against comparing
schema bytes. Consider running `manage_report_floor` in CI or stating in the nox comment that it is a manual gate.
