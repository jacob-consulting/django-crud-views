### WR-04: `isolated_routes` imports the project views at call time, under the calling test's patched settings (WR-03 fix is incomplete)

**File:** `tests/test1/test_ancestor_authorization.py:50-52`
**Issue:** The fix moved the first import of `tests.test1.app.views` to the start of `isolated_routes`, but that
is still inside a test. `ViewSet.register_view_class` reads `crud_views_settings.manage_views_enabled` when each
view class is defined (`src/crud_views/lib/viewset/__init__.py:359-362`). If the first `isolated_routes` call in a
process comes from a test that has patched the setting to `"no"`, every project view is registered without the
`manage` context action, and its `cv_context_actions` stays the shared settings list. The module is then cached
in `sys.modules`, so this state lasts for the rest of the process or xdist worker. One such caller is
`tests/test1/test_access_trace_manage.py:26` (`mode="no"`). Ten more modules use `isolated_routes` and also patch
this setting; they were not checked one by one.

Probe in a fresh process, around `test_manage_trace_actual_branch[anonymous-False-no]`:

```text
before: views imported=False registry=0
after:  views imported=True  registry=33  author list/detail/create/update/delete carry 'manage': False
(same probe with the [anonymous-False-yes] case first: True)
```

Deterministic reproduction at HEAD (one process, because test order is the variable):

```text
pytest "tests/test1/test_access_trace_manage.py::test_manage_trace_actual_branch[anonymous-False-no]" \
       tests/test1/test_context_actions_isolation.py -p no:randomly
-> 10 failed, 6 passed
   AssertionError: assert 'manage' in ['home', 'detail', 'update', 'delete']   (AuthorDetailView.cv_context_actions)

control with [anonymous-False-yes] first -> 16 passed
```

It also fails without any hand-picked order. The selection `test_access_trace_manage.py
test_context_actions_isolation.py test_manage.py test_guardian.py` under xdist failed in 5 of 21 runs at HEAD
(`-n auto` and `-n 4`, 1 failed and 159 passed each time, always
`test_registered_view_class_gets_manage_action`).

Compared with the prior commit, the same order over seven manage and Guardian test files gives 54 failed at
`9b6c1fa6` and 12 failed at HEAD. The fix removed the registry loss, and these 12 are what remains.

Who is affected: only partial selections. 71 of the 271 test modules import the project views at collection
(for example `tests/test1/test_ancestor_structure.py:32`), and every xdist worker collects the whole selection, so
the full suite and CI are not exposed (15759 passed). The floor selection (`MANAGE_REPORT_TESTS`) and the
selection named in `deferred-items.md` still passed with the `"no"` case run first (519 and 658 passed), because
none of their tests depends on the `manage` action of a project view. The `deferred-items.md` entry for the
catalogue flake is therefore correctly marked resolved; this is a different symptom of the same root cause.
**Fix:** Import the project URLconf at module level, as `test_ancestor_structure.py:32` already does, and remove
the call-time import and `from importlib import import_module`. Collection finishes before any test patches a
setting, so every module that imports `isolated_routes` (43 modules) gets the views in their default state.

```python
import tests.test1.project.urls  # noqa: F401 - registers the project ViewSets at collection, before any test runs
from crud_views.lib import check as check_module
from crud_views.lib.viewset import _REGISTRY, _REGISTRY_LOCK, ParentViewSet, ViewSet
```

Verified in a scratch copy of HEAD with exactly this change (no repository file was modified): the reproduction
above gives 16 passed, the seven-file order gives 215 passed, the xdist selection passed 8 of 8 runs, the prior
WR-03 reproduction still gives 7 passed, the `deferred-items.md` selection gives 658 passed and the floor
selection plus `test_ancestor_authorization.py` gives 506 passed. A selection that contains no such module and
imports the views lazily under a patched setting is still possible; importing the URLconf once in
`tests/test1/conftest.py` after `django.setup()` would cover that too, but this variant was not tested.

### IN-06: The gate now enforces a `user` rule that `--schema` does not publish (open half of WR-02)

**File:** `src/crud_views/lib/access_trace_export.py:45-52`; `docs/reference/manage.md:534-541`;
`tests/test1/test_access_trace_contract.py:491`
**Issue:** A model validator does not change the generated JSON Schema. `$defs.TraceUser` still has no `required`
list and still types `active` and `anonymous` as `boolean | null`. So `{"pk": "1"}` and a user with null flags
are valid under the published schema, and the gate rejects both. Before `da9e018f` the schema and the gate agreed
on this object. The reference page says the schema "is generated from the same internal models that validate
every trace" and "The generated schema is authoritative"; for `user` the schema is now a superset of what the
command can emit. Consumers that validate against the schema are not harmed. A consumer that generates types from
it gets optional, nullable flags, while the field table at `docs/reference/manage.md:478` promises booleans.
`06.37-REVIEW-FIX.md` states this limit and leaves it to the maintainer, but `06.37-REVIEW-DISPOSITION.md` records
WR-02 as `fixed` without it. `test_access_trace_contract.py:491` pins the loose schema shape.
**Fix:** Decide and record one of two options. The small one is a sentence in `docs/reference/manage.md` near line
534: the schema cannot express that `user` is either empty or complete, and the command enforces it. The larger
one makes `user` a union of an empty model and a complete model, which puts `anyOf` into the schema and rewords
D-05.
