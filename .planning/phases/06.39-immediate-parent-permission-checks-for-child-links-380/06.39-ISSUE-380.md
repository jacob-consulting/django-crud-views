# Issue #380: Child links of plain ViewSets can show a destination that answers 403 (no parent gate on the link check)

Source: https://github.com/jacob-consulting/django-crud-views/issues/380
Captured: 2026-11-18

The following issue body is preserved as the approved source for phase 06.39.
Its historical scheduling status is superseded by `.planning/ROADMAP.md`.

---

**Status:** Option 2 selected for implementation before #381. The phase is unscheduled. See the GSD handover below.

## Finding

For a child of a plain `ViewSet`, the check that decides whether a child link is shown can say yes while the request it points to answers 403.

- The link check, `CrudView._cv_child_link_has_access(user, parent_obj)` (`src/crud_views/lib/view/base.py`), is `cls.cv_has_access(user, parent_obj)`. For a core permission view that asks only for the child's own model permission.
- The request additionally runs the ancestor guard (PR #336), which by default requires `view` on the parent for a read.
- Only Guardian compositions add the parent gate to links: `crud_views_guardian/lib/mixins.py` overrides `_cv_child_link_has_access` and calls `ancestors._immediate_parent_access`. `docs/reference/context_buttons.md` describes the parent check on child links as applying to shipped Guardian destinations.

## Reproduction

Run once on `70071301` (branch `gsd/phase-06.38-bulk-actions-378`) as a throwaway test in `tests/test1`, with the existing `cv_book` / `cv_publisher` plain ViewSets (Book is a child of Publisher):

- user holds `view` on Book and `change` on Publisher, but not `view` on Publisher;
- `BookListView._cv_child_link_has_access(user, publisher)` returns `True`;
- `_immediate_parent_access(BookListView, user, publisher)` returns `False`;
- `GET` on the Book list under that publisher returns `403`.

So a `ChildContextButton` to Books on a Publisher page that this user can open (for example its update page) is shown as accessible and leads to a 403. Issue #363 observed the same class of mismatch downstream with `SiblingContextButton`.

## Why it is recorded now

The original object navbar design (#381) decided that the navbar applies the parent gate itself for its child items and leaves context buttons unchanged. On a page that has both, the bar can then hide an item that a `ChildContextButton` still shows. The navbar does not depend on this issue.

## What a change would involve

The change itself would be small: the core `_cv_child_link_has_access` applying the same bounded parent gate Guardian's override applies. Its effect is wide, which is why it is not folded into the navbar work:

- **Every nested project with plain ViewSets is affected.** Child links that are shown today and answer 403 would be hidden or disabled. This changes existing pages, so before 1.0 it likely needs a `### Breaking` changelog entry and `docs/migrating-1.0.md`.
- **A new failure mode while rendering.** `_immediate_parent_access` raises `ImproperlyConfigured` for the misconfigurations its docstring lists; an existing page could start failing at render time.
- **Cost on an existing path.** One more permission check per child link.
- **`SiblingContextButton` is a separate path.** It calls `cv_has_access(user, None)` and has no parent object in hand; it would need its own treatment.
- **The current bound looks deliberate.** The documentation scopes the parent check to Guardian destinations and the Guardian code calls the remainder a bounded migration. A change reopens that decision.
- **Immediate parent only.** The helper never evaluates farther ancestors, so a shown link could still be denied higher up, as it can for Guardian links today.

The two production renderers using this hook are `ChildContextButton` and child card actions.

## Options

1. Leave as is and document that, for plain ViewSets, a shown child link can answer 403 when the user lacks the parent permission.
2. Give the core child-link check the bounded parent gate, with the consequences above.
3. As 2, and also treat sibling links.

The maintainer selected option 2 on 2026-11-18.

## gsd-handover

**Decision (2026-11-18).** Implement option 2 as a standalone fix before the object navbar in #381. A child link that already has the parent object should use the destination’s own access check and the permission required on that immediate parent. This fixes an existing UI bug and gives the navbar one method to call.

### Scope and implementation

- Keep the decision in the existing destination hook, `_cv_child_link_has_access(user, parent_obj)`. Honor the child’s own access result first. If it passes, apply the existing `_immediate_parent_access` policy using the supplied parent. The destination determines the required permission for the operation. Preserve configured parent policies, including the `none` provider.
- Both `ChildContextButton.get_context()` and `cv_get_card_action_data()` (the child-action branch in `src/crud_views/lib/views/card.py`) already call this hook. Let each renderer continue to apply its configured hide-or-disable presentation.
- Check the Guardian overrides before moving the gate. Shipped Guardian collection views and Guardian create already have paths that check the parent. Apply that check once per allowed link and preserve actor checks, custom denials and the tested behavior of standalone Guardian queryset compositions.
- The bound is the immediate parent supplied to a child link. Request authorization remains authoritative for the full ancestor chain. Sibling links, higher-ancestor rendering checks and changes to `cv_action_enabled` are separate decisions.

### Acceptance criteria

1. Reproduce the original case on `main` with a permanent regression test. Give the user Book view and Publisher change permissions, withhold Publisher view, and open an accessible Publisher page. Verify the Books child link is hidden or disabled according to configuration and the Books list GET returns 403. Exercise both the context button and the child card action.
2. Grant the required Publisher permission and verify that both renderers produce a working link for the same Publisher and that its GET succeeds. Include an accessible empty Books collection. An own-access denial should short-circuit the parent check.
3. Check the Guardian collection and create paths for duplicate parent checks. Measure the allowed plain-link cost for both renderers and record the result. The existing cost test in `tests/test1/test_guardian_child_link_visibility.py` asserts the former plain-child behavior. Update that expectation while retaining coverage of ordinary row actions and Guardian compositions.
4. Update the context-button and nested-view documentation. Explain which links now disappear or become disabled, the per-link permission cost, and when the parent policy can raise `ImproperlyConfigured` during rendering. Call out the existing-page behavior change in the release notes. A `### Breaking` entry before 1.0 also requires an update to `docs/migrating-1.0.md`.

### Follow-up for #381

After #380 lands, revise D-09 and A-03 in the navbar spec so a child item calls `target._cv_child_link_has_access(user, owner)` once. The navbar still chooses its owner and active section. Its action-state decision stays open in #381.
