# Phase 06.39 review correction

CR-01 is corrected: a backend's model-permission grant no longer enables a plain child link when its
immediate protected parent rejects the actor. This is rendering/request parity, not a request authorization
bypass. Phase completion remains the orchestrator's responsibility.

## Independent reproduction and locked scope

Read the complete original REVIEW, CONTEXT, both plans, COST and ACCEPTANCE, then traced the existing
core hook, `_immediate_parent_access`, `_effective_provider` and `_protected_actor_response`.
The original review reproduction was rerun in a fresh Django 5.2 source process at prerepair checkout
`da280e67`: repository `AnonymousBookReaderBackend`, saved Book parent, plain BookNote list, real renderer
and Client GET. Context and card both returned `cv_access=True`, `cv_disabled=False` and a usable URL;
following it returned 302 to `/accounts/login/?next=...`.

Plan 01 explicitly requires protected model/Guardian parents to deny anonymous/inactive actors while
provider `none` defers to own access. The defect is in the new immediate-parent hook, inside the approved
scope. D-01/D-02/D-04/D-05/D-06 require own access first, existing policy, one supplied parent only,
once-only composition behavior and a bounded maintainable solution. No architectural conflict was found.

Root cause: the hook treated the helper's permission-provider result as complete admission. Model providers
call `user.has_perm`, and supported custom backends can grant that permission to actors the independent
request guard rejects. The previous default-backend actor matrix masked this distinction.

## RED, correction and GREEN

Permanent test `test_plain_child_link_backend_grant_cannot_waive_actor_rule` was added before any runtime edit.
It uses the existing anonymous backend plus a test-local `InactiveBookReaderBackend` that retains inactive
sessions and grants Book read. It tests inactive ordinary users and inactive authenticated superusers as
well as anonymous users, both renderers, both visibility modes and protected/none parent providers.


On the unchanged runtime this produced **12 failures / 12 passes in 1.92s**. All failures were the intended
visibility assertion (`data is None` or `cv_access is False`); JUnit inspection confirmed no collection or
setup errors. Before those assertions, real protected GETs had already returned 302 for anonymous actors
and 403 for inactive actors. All twelve provider-none controls returned 200 and enabled same-parent URLs.
The regression was committed as `16ad5f02` before the fix.

`3e699221` changes only `CrudView._cv_child_link_has_access` in `src/crud_views/lib/view/base.py`:

1. Preserve own denial and top-level return behavior.
2. Call the existing immediate-parent helper exactly once; preserve its false result and exceptions.
3. After helper success, admit authenticated active actors, or retain the effective provider-none bypass.

The existing private `_effective_provider` function resolves the parent's explicit/inherited policy. The
two actor attributes match the request adapter's predicate; invoking that HTTP-response adapter would
require manufacturing a request/view and unnecessary side effects. No new abstraction or public API is
needed. The actor predicate is after the helper deliberately: missing-parent denial, error propagation and
provider-none ordering remain unchanged. Permission evaluation is not repeated. The normal active-actor
path short-circuits the extra registry lookup. No database or farther-ancestor lookup is added.

The original helper, request engine, both renderers and Guardian adapters are unchanged by this repair.
The new regression proves one helper call on the exact supplied actor/parent, no application-row reads,
and own-denial short circuit with zero helper calls and zero SQL. Provider-none controls remain public;
inactive superusers receive no protected-parent exception.
