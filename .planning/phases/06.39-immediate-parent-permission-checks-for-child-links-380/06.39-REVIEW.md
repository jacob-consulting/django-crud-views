### CR-01: Protected model parents admit anonymous child links when a backend grants their permission

**Classification:** BLOCKER — incorrect rendering behavior; open.
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/base.py:530-535`
**Related evidence:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/ancestors.py:421-437`,
`/home/alex/projects/alex/django-crud-views/src/crud_views/lib/ancestors.py:680-686`,
`/home/alex/projects/alex/django-crud-views/src/crud_views/lib/viewset/__init__.py:507-509`,
`/home/alex/projects/alex/django-crud-views/tests/test1/test_ancestor_actors.py:46-50`,
`/home/alex/projects/alex/django-crud-views/tests/test1/test_guardian_child_link_visibility.py:304-329`.

**Issue:** After own access passes, the new core hook treats the immediate parent's permission-provider result
as its entire admission decision. For a model provider, that ends at `user.has_perm(permission)`. A supported
custom backend can grant that permission to an anonymous user. However, actual nested requests apply
`_protected_actor_response` first: protected ancestry rejects anonymous users independently of permission
backend results. Thus a plain no-own-permission child list below a protected model parent can produce
`cv_access=True`, `cv_disabled=False` and a usable URL for an anonymous actor, while following that exact
URL redirects to login. No farther ancestor or missing object is involved.

This is reachable using the repository's existing `AnonymousBookReaderBackend`, without inventing a backend
contract: use a model-provider Book parent, a plain BookNote child list, and `AnonymousUser`. The backend grants
`app.view_book`. The current actor matrix exercises default backends, whose permission denial masks the missing
actor rule. The analogous inactive-user case also needs regression coverage with a backend that grants inactive
users permissions; the executable evidence below specifically establishes the anonymous case.

**Decision basis:** Plan 01's must-have and Task 2 behavior explicitly require protected model/Guardian parents
to deny anonymous/inactive actors, while provider `none` continues to defer to own access. The existing request
test `test_protected_ancestry_denies_anonymous_even_when_a_backend_admits_them` also establishes that backend
grants cannot waive protected ancestry's actor rule. This is an immediate-parent mismatch, not the accepted
farther-ancestor rendering limit or standalone Guardian queryset exception.

**Reproduction:** Fresh Python 3.12 / Django 5.2 source process, with the test project's in-memory database,
saved Publisher/Book rows, real discovered permissions, existing backend, both production renderers and actual
Django Client GETs. No permission helper was mocked. Run the following Python through
`PYTHONPATH=src:. .nox/tests-3-12-django-5-2/bin/python`:

**Fix:** In the bounded core child-link admission path, preserve own-access-first and top-level behavior, then
enforce the request's authenticated/active actor prerequisite when the supplied immediate parent's effective
provider is protected. Do not impose that prerequisite on provider `none`, recurse through farther ancestors,
or add a second permission evaluation. Keep missing-parent denial, existing configuration-error semantics,
Guardian composition exceptions and once-only create behavior intact. Add both-renderer hide/disable regressions
using actual anonymous/inactive-granting backends, together with provider-none and own-denial controls.
A blanket actor guard on every core child link would violate the approved provider-none behavior.
