## Critical Issues

### CR-01: Recleaning a formset erases mandatory policy errors permanently

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/formsets/render_tree.py:216-218`
**Related:** `XFormSet.is_valid` at lines 203-208; `FormSets.all_valid` in `formsets.py`; the normal changed-form save traversal.

**Issue:** `_cv_row_policy_checked` caches that policy ran, independently of Django's error-cache lifetime. A subsequent public `BaseFormSet.full_clean()` replaces `_non_form_errors`, removing `cv_additions_not_allowed`/`cv_invalid_row`, while this flag remains true. The next aggregate validity check skips the mandatory policy and returns true. Because the render tree saves individual forms rather than calling Django's edit-only formset save, a forbidden extra can then actually be inserted. This requires application/custom cleaning to reclean an already evaluated formset; it is not claimed to be an unaided bypass of the ordinary first POST validation.

**Reproduction:** A targeted Django 6.0 probe created isolated in-memory Parent/Child tables, a direct native BaseInlineFormSet adapter accepted by `FormSet`, and an `edit_only=True` declaration. With `TOTAL_FORMS=1`, `INITIAL_FORMS=0`, and a nonempty extra title, the actual results were:

```text
tree.all_valid()                         -> False, ['cv_additions_not_allowed']
tree.x_formsets[0].instance.full_clean()
tree.all_valid()                         -> True, []
main.save(); tree.save()
Child.objects.values_list('title', flat=True)
                                        -> ['forbidden extra']
```

**Fix:** Reapply policy after each native cleaning generation, or remove the lifetime-wide boolean and use the existing error-code deduplication on every aggregate pass. Policy rejection must survive `full_clean()` followed by `all_valid()`, including sibling/child custom cleaning. Add a regression that performs this sequence and proves no forbidden insert or save hook occurs.

### CR-02: The default JS suite now requires a local Python environment absent from JS CI

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/tests/js/formset.test.js:99-108`
**Related:** `/home/alex/projects/alex/django-crud-views/.github/workflows/js.yml:12-19`, `package.json` test script.

**Issue:** The new unconditional Vitest test invokes `.nox/crispy_floor-3-12-django-6-0/bin/python`. The actual JS CI workflow only checks out the repository, sets up Node, runs `npm ci --ignore-scripts`, and runs `npm test`. It neither creates that ignored nox environment nor installs the Django test dependencies. Therefore a clean JS CI job fails with `spawnSync ... ENOENT` at `expect(result.error).toBeUndefined()`. The 309 local passes depend on the preexisting review machine's nox cache and do not exercise this clean-checkout path.

**Fix:** Give the integration test an explicit, reproducible runtime contract. Either provision the required Python environment in the job and resolve its interpreter through configuration, or put this real Django bridge in an explicit integration lane while retaining the ordinary Node suite's established dependency boundary. Do not silently skip a required integration acceptance case when its selected runtime is unavailable. Verify the ordinary JS job from an environment without `.nox` and separately verify the configured integration route.

### CR-03: Requiring DELETE during row construction disables Add on legitimate extra rows

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/static/crud_views/js/formset.js:313`
**Related:** `XBase.exact`/`assert_sel`, the delegated action handler at lines 503-514, and `XFormset.reorder`'s DELETE requirement at line 251.

**Issue:** Django deliberately omits the DELETE field on extra forms when `can_delete=True, can_delete_extra=False`. The new `this.exact(...)` assertion throws for those valid rows before the action handler can inspect the requested action or capabilities. Thus even Add on a nonorderable extra row performs no request. On a create form made entirely of extras, every Add control is broken. The JS fixture masks this by always emitting DELETE whenever `canDelete` is true and hardcoding `can_delete_extra: true`. Ordered collections also need the reorder path to tolerate these deliberately absent DELETE fields.

**Reproduction:** Native Django factory inspection confirmed `"DELETE" in extra_form.fields` is false for this configuration. A jsdom probe used the existing fixture with `INITIAL_FORMS=0`, `can_delete_extra=false`, `can_order=false`, and the omitted DELETE input; loading the shipped script and clicking Add produced zero AJAX calls. Constructing the same row directly reported:

```text
book-None-0-0-DELETE not found
```

**Fix:** Treat DELETE as optional where the stable form index identifies an extra and `can_delete_extra` is false. Resolve/require it only for rows where Django provides it; absence on a nondeletable extra must not prevent Add/Move or submission. Render or disable the corresponding Delete control consistently. Extend the fixture and tests with actual Django markup for this capability combination, including ordered submission.

### CR-04: Delete eligibility changes when rows move in the DOM

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/static/crud_views/js/formset.js:509-510`
**Related:** `XForm.row_index` at line 305; row insertion and Move handlers.

**Issue:** `row.row_index` is the current visual position, but Django's initial/extra classification is the immutable form index in its bound prefix. With `can_delete_extra=False`, moving an existing row below an extra makes its Delete action return early. Insertion between existing rows can produce the same misclassification without moving them. Conversely, an extra with a Delete control supplied by an override can become eligible simply by moving above the initial-row count. Reordering must not change row capabilities.

**Reproduction:** With initial row `book-None-0-0`, extra row `book-None-0-1`, and `INITIAL_FORMS=1`, a focused shipped-script probe moved row 0 down and clicked its Delete button. DOM order became `[book-None-0-1, book-None-0-0]`, but row 0's DELETE stayed `0`. This independent guard defect remains after fixing CR-03; the probe retained the extra DELETE input to isolate it.

**Fix:** Compare `INITIAL_FORMS` against the numeric form index parsed from the stable row prefix (or an equivalent explicit server projection), not `rows.index(...)`. Retain visual position solely for movement. Test existing-row deletion after inserting/moving extras before it and extra-row rejection after moving it upward.

### CR-05: Reinitializing an ambiguous former binding enables controls in a hidden group

**Classification:** BLOCKER
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/static/crud_views/js/toggle.js:147-155`
**Related:** disabled-state recomputation at lines 94-103; CONTEXT D-02 and UI-SPEC's unchanged-state rule.

**Issue:** When a previously successful binding becomes ambiguous, initialization removes it but retains `display:none`. The following `sync()` releases its conditional disabled contribution, restoring enabled controls inside that still-hidden group. This violates the promised local unchanged-state behavior and can make a form impossible to submit: native required validation now applies to an invisible enabled input. The existing ambiguity regression only tests ambiguity on first initialization.

**Reproduction:** Initialize an unchecked `enabled` checkbox with a group containing `<input name="detail" required>`, then insert a second checkbox with the same name and call `cv.initConditional()` again. The actual jsdom output was:

```text
before: display=none, disabled=true, form.checkValidity()=true
warning: crud_views: ambiguous conditional toggle enabled
after:  display=none, disabled=false, form.checkValidity()=false
```

**Fix:** Keep an unresolved group's last owned presentation/disabled state frozen without continuing to follow an arbitrarily selected checkbox. Compose that frozen state with independent and ancestor owners, and release/recompute it when unique binding succeeds. Add transitions from bound-off to ambiguous and back, with native validity and ancestor-ownership assertions.

### WR-01: The evidence checker accepts a partial JS suite as the complete JS gate

**Classification:** WARNING
**File:** `/home/alex/projects/alex/django-crud-views/.planning/phases/06.4-conditional-and-formset-correctness-lifecycle/10-evidence/run.py:383-385`
**Related:** quality command construction at lines 344-353 and complete-JS acceptance in plan 10.

**Issue:** JS validation only requires a positive `passed == collected` aggregate. It does not check the recorded command is the required unfiltered Vitest run, require the complete file/case set, or reconcile counts with captured output. A one-test filtered invocation satisfies the same gate as all eight files. The analogous `strict-docs` branch only checks exit zero and does not require `mkdocs build --strict`. This leaves the advertised command-contract validation incomplete. The supplied current record does contain the full JS run; this finding concerns what the checker can accept or reuse, not a claim that those recorded passes are fabricated.

**Reproduction:** Copying the current JavaScript gate in memory, changing its command to a filtered `vitest run tests/js/toggle.test.js -t renders`, and setting counts to `{passed: 1, collected: 1}` was accepted by `validate_gate` with the unchanged source manifest (`PARTIAL_JS_GATE_ACCEPTED`). No evidence file was modified.

**Fix:** Validate exact expected command/selection contracts for every quality gate, and capture structured Vitest file/case outcomes rather than trusting aggregate counts alone. Add corrupted-copy controls for partial JS selection, wrong quality executable, and omitted `--strict`.

### WR-02: Capture resumption ignores newly requested runtime overrides

**Classification:** WARNING
**File:** `/home/alex/projects/alex/django-crud-views/.planning/phases/06.4-conditional-and-formset-correctness-lifecycle/10-evidence/run.py:745-753`
**Related:** browser runtime validation at lines 566-569 and top-level override update in `run()`.

**Issue:** Reuse checks a record against its own saved `runtime_overrides`, rather than the overrides requested for the current capture. For example, setting a different `CV_FOCUS_PYTHON` or Chromium path can still reuse the old browser capture; `run()` meanwhile writes the new override into top-level metadata. An invalid explicitly selected Python can therefore escape the promised fail-fast behavior whenever completed gates are reused. Historical evidence checking may appropriately use recorded overrides, but deciding whether a new requested capture is reusable needs a separate comparison.

**Reproduction:** Loading the actual conditional-browser gate, setting `CV_FOCUS_PYTHON=/nonexistent/review-python` in the probe process, and calling the exact `validate_gate` used by `reusable()` succeeded (`BROWSER_GATE_REUSABLE_WITH_DIFFERENT_REQUESTED_PYTHON`). No browser or broad test suite was rerun and no evidence was overwritten.

**Fix:** Derive the effective current command/environment selection per gate and compare it to the capture before reuse. Validate changed explicit paths before any success/reuse claim. Keep historical `--check` separate from new-run reuse semantics. Add a targeted control where a changed invalid override must fail without starting unrelated gates.
