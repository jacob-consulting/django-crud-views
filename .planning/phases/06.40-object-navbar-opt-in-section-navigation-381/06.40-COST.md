# Phase 06.40 — Navbar cost and preservation receipt

Measured 2026-11-18 on Python 3.12.3, Django 5.2.19, django-guardian 3.5.2 and SQLite in-memory test databases. Product source is unchanged from plan 02 (2a0a2bb0); plan 03 adds tests only. The new permission/cost tests also run on Django 4.2.30 and 6.0.10. No result here asserts the full Python/Django matrix.

The 78-case new cost module includes six complete-response/laziness/coexistence controls.

## Fixture and measurement boundary

Every cell uses isolated, uniquely named ViewSets and routes from the plan 01 harness. Project URLs are imported before registry snapshots. A Publisher owner has one protected Details item and one nested Book list item. A BookNote detail two levels below the owner exercises resolved-ancestor reuse; the intermediate Book views do not carry the navbar mixin. Publisher/Book/BookNote PKs are 101/202/303. All actor grants and objects are real database rows.

| Composition | Owner Details/provider | Child collection |
|---|---|---|
| plain | Core permission-required detail; model Publisher view/change grants | Core permission-required list; Book view/add model grants |
| guardian | Guardian detail; Publisher object view/change grants | Shipped Guardian parent-aware list; Book object view grant for the deep request |
| mixed | Guardian detail; Publisher object view/change grants | Core permission-required list; Book model view/add grants |

The ordinary owner/deep GET completes with a base that omits the navbar. Assert the builder has not run. Then reset the specified caches and measure only subsequent `get_context_data` plus template consumption. Request authentication, ancestor/object loading, normal header/context-button work and breadcrumbs are outside this interval. This avoids charging ordinary page work to the navbar. The same already-loaded owner instance must reach both admission hooks and both permitted rendering-state hooks.

For each composition, the cross-product covers owner/deep page, tag/split/repeated placement, cold/warm vocabulary and cold/warm actor caches: **24 cells**, **72 total**. Repeated placement renders a copied template Context, both partials and another `get_context_data` result from the same view. These are repeated consumers of the same request, not separate requests.

## Cache definitions

- **Cold vocabulary:** clear `check_module._VOCAB_CACHE`; set each participating ViewSet's `_default_permissions` to `None`; call Django `ContentType.objects.clear_cache()` **and Guardian `guardian.shortcuts.clear_ct_cache()`**. The latter is a separate cache and is explicitly reset, addressing R19. Parent/child/grandchild caches are included.
- **Warm vocabulary:** start with the same reset, then resolve `_registry_vocabulary()`, each participating ViewSet's permissions, Django ContentTypes and Guardian's per-permission content-type lookup outside measurement. No admission or state hook is run for prewarming.
- **Cold actor:** remove `_perm_cache`, `_user_perm_cache` and `_group_perm_cache` on the actual actor behind `request.user`. Use forwarded `delattr`, because editing a `SimpleLazyObject` proxy's dictionary would leave its wrapped actor warm after a deep request.
- **Warm actor:** apply that same reset, then call `get_all_permissions()` before measurement. This warms only Django model permissions. These class-level destination hooks create fresh Guardian checkers; no rendering-view checker/object-permission cache is reused or claimed warm.
- Snapshot each pre-existing ViewSet cache value and the check vocabulary; restore them in `finally`, including on assertion failure. Clear both content-type caches on exit. Registry/URL cleanup remains the existing isolated harness's responsibility.

## Preservation and zero-work controls

- The no-mixin and mixin-with-`cv_navbar=None` controls compare **entire `response.content` bytes and complete ordered SQL strings**, before/after placing the tag in the owned base. Both match exactly and perform zero navbar builds/admission/state hooks. An empty declaration also preserves bytes/SQL; it legitimately builds its empty result once and has no item hooks.
- CSRF generation is fixed identically in both requests. No navbar/header/response normalization is used. The tag is inserted without extra whitespace; later shared-template placement must likewise put the Django block delimiters on the existing line to preserve unconfigured pages.
- Omitted-consumer and actual modal-response controls assert zero builder/admission/state hooks; repeated context creation and guarded modal consumers execute zero incremental SQL. The custom modal includes both shipped partials; only its deliberately supplied page-content sentinel remains.
- A coexistence page has Children then Details context buttons. Compare original response-byte slices of the complete card header, including heading/actions, before/after adding the navbar. They match exactly, preserve order and retain their existing destination attributes. Navbar costs are measured separately, never by counting the context buttons' additional admission calls as navbar work.
- The affected regression command includes untouched form-button, form-frame, table and card golden suites plus navbar, breadcrumb, permission/state and context-button tests: **776 passed**. No existing source, golden or regression file is modified by this plan.

## Limits

These measurements exclude normal request queries by design. They do not establish a universal whole-page query budget, browser wrapping/focus/zoom behavior, custom backend costs or the full supported runtime matrix. Plan 08 owns final matrix/browser acceptance. No dependency, permission policy, router, context-button or navbar production change was required.
