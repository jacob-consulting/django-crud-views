<objective>
A developer opts a table view into current-page selection and offers one registered action form view; a user
selects rows, reviews them on a full page, confirms, and lands back on the list with a success message (D-01,
D-12, D-13, D-29). Selection mistakes return to the source with a warning (D-02) and a plain GET redirects
silently (D-27).

Purpose: prove the whole architecture end to end on one path before anything is built out: native `formaction`
submission from the source through the unchanged form leaf, real destination dispatch, scoped resolution of the
submitted IDs, review, execution inside the configured transaction and return through the existing origin
mechanism.

`tests/test1/test_bulk_flow.py`.

Out-of-range IDs and other backends (maintainer decision during plan revision 1): research measured
`OverflowError` for an oversized integer ID on SQLite with Django 4.2, 5.2 and 6.1 and assumed, without a
PostgreSQL to test on, that another backend may raise a database error instead (assumption A3). The
maintainer decided to mitigate that case and not to carry it as an accepted residual: task 02 catches
`django.db.DataError` beside `OverflowError` where the scoped queryset is evaluated, so a database-rejected ID
answers 400 instead of a server error.

NUL character (maintainer decision during plan revision 2): research assumed that a NUL character in a
string-key ID raises on PostgreSQL (assumption A4). The maintainer decided to reject it before any query: task
02 makes `_read_ids` raise the same `BadRequest` for any submitted ID that contains a NUL character, in
`cv_bulk_ids` and in `cv_bulk_blocked_ids`, for every key type. The condition sits in `_read_ids`, which `post`
calls after the count check and before any record is loaded, so the order task 01 fixed (stage, count, parse,
resolve) stays as it is; an oversized selection that also holds a NUL character still gets the D-02 warning.

What is measured and what is not. Measured: `OverflowError` on SQLite (research spike); `django.db.DataError`
imports from `django.db` on the cached Django 4.2.30, 5.2.19 and 6.0.10 environments (plan revision 1); and, in
plan revision 2 on Django 5.2.19 with SQLite: a NUL character survives Django's parsing of a multipart and of a
URL-encoded POST body; `to_python` of `AutoField`, `BigAutoField` and `UUIDField` rejects a value that contains
one, while `CharField.to_python` returns it unchanged and SQLite accepts it as a query parameter that matches
nothing. So the explicit condition changes the outcome only for a string key, and with it the NUL case no
longer depends on what a backend or driver raises. Not measured: anything a real PostgreSQL does. Only SQLite
is available, so whether PostgreSQL raises `DataError` for an out-of-range integer in a `pk__in` lookup is
unknown. The `DataError` branch is therefore proven by a test that simulates the database error; an ID that a
backend or driver rejects with another exception type is not covered by this catch.

Where the NUL tests live: the test project of this plan has only an integer key, for which `to_python` rejects
the value anyway, so a request against it cannot fail for a missing condition. Task 02 therefore decides the
condition with two direct calls of `_read_ids` that use a string primary-key field, and adds two requests
against the integer-key destination only to pin the HTTP outcome. The requests that decide it over HTTP use the
string-key ViewSet and belong to plan 05 task 01, which creates that ViewSet.

Placement of the catch relative to `cv_get_atomic()`: on the execute path the scoped queryset is evaluated inside
the atomic block. Catching a database error there is safe only because the handler re-raises at once: the
`except` clause raises `BadRequest` and runs no query, the exception leaves the atomic block, and Django rolls
the block back. It must never be changed into a handler that continues inside the block, because PostgreSQL
refuses further queries in a transaction after a failed statement. The `try` block encloses the evaluation of
the scoped queryset only, so an error raised by an item hook or by `cv_form_valid` is not converted. One
accepted side effect: a `DataError` caused by the application's own queryset expressions during that one
evaluation is reported as the same 400; the original error stays chained as the cause, and Django logs a
`BadRequest` response through the `django.request` logger with the exception attached.

The focused commands for the two simulated tests and for the four NUL tests run without xdist workers on
purpose: for a handful of tests, starting workers costs more than the run (CLAUDE.md allows a serial run for a
tiny selection).
