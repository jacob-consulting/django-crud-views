  The two sequences differ for a legitimate reason. Read at HEAD in `src/crud_views/lib/views/mixins.py`: the
  stock `post` calls the guard, then `cv_post_hook` and `cv_form_is_valid`, and `cv_form_valid_process` calls

- The hook-order test carries `django_db(transaction=True)`. Under the default fixture the test's own
  transaction never commits, so `cv_on_commit` would not appear in the recording at all. With a real
  transaction the callback runs when the view's atomic block commits, before `cv_form_valid_redirect`, which is
  the production order. `django_capture_on_commit_callbacks(execute=True)` is not used for this test: it runs
  the callbacks only when its own block ends, after the response, and would record a different order.
- `cv_atomic = False`: `cv_get_atomic()` then returns a no-op context manager and `transaction.on_commit` runs
  its callback at once, because the connection is in autocommit mode. That is the existing behavior of every
  form view of the package and not an error; nothing in this phase turns it into a raise. Task 02 asserts it.
- Threat `T-06.41-06` said that an excluded record stays excluded. Without a stored review the server can only
  honor an exclusion that the request still carries. The threat row, the D-05 truth and one behavior bullet of
  task 01 now name the three cases: still ineligible, still submitted as excluded, and now eligible and
  submitted as a candidate.
- Row-locking recipe (finding on plan 10): the issue's recipe filters by the selected keys and checks only the
  rows it gets back, so a record deleted between the check and the locked read is left out without a word,
  while the success message still counts `cv_bulk_objects`. The recipe now compares the number of locked rows
  with the number selected. It lives here as application code in the test project, beside the delete recipe,
