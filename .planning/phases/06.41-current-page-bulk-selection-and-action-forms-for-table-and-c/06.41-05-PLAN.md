Destination behavior already implemented by plans 01 and 02 (read the module first):

- `_read_ids(post, field)` normalizes each submitted value through the primary-key field's `to_python`, keeps
  string transport, deduplicates in order and raises `BadRequest` for malformed or overlapping IDs. It raises
  the same `BadRequest` for any value that contains a NUL character, in both lists and before `to_python`
  (plan 01 task 02).
- `_selection_queryset()` raises `ImproperlyConfigured` when the ViewSet queryset or `get_queryset()` is not an
  unsliced `QuerySet` of the ViewSet model on the default database, applies `_scope_child_queryset` and returns
  the intersection.
- `_review_selection(candidates, excluded)` raises `ImproperlyConfigured` when `cv_get_db_alias()` is not the
  default alias or an object's state database or write route is not the default; it lists every submitted ID as
  eligible or blocked. It converts `OverflowError` and `django.db.DataError`, raised while the scoped queryset is
  evaluated, into `BadRequest` and re-raises at once (plan 01 task 02).

Discovery level 0. No new dependency. Schema-push gate not applicable (the test app has no migrations; no ORM
schema file of the gate's list is touched). Calibration factor 1, confidence low.

This plan is mostly tests. `src/crud_views/lib/bulk/__init__.py` is listed because a failing boundary test is
fixed here, in the private helpers, without a new public name. If a boundary can only be closed with machinery
D-11 rules out, stop and report instead of building it.

Research assumptions A3 and A4 (PostgreSQL raises `DataError` for an out-of-range integer; a NUL character in a
string key raises on PostgreSQL) cannot be tested against a real backend here: only SQLite is available. By
maintainer decision both are handled, not left as assumptions, each in its own place (threat T-06.41-04):

- A3 (plan revision 1): plan 01 task 02 catches `django.db.DataError` beside `OverflowError` where
  `_review_selection` evaluates the scoped queryset, converts both into `BadRequest` and proves the `DataError`
  branch with a simulated error.
- A4 (plan revision 2): plan 01 task 02 makes `_read_ids` reject any submitted ID that contains a NUL character,
  in both lists and for every key type, before any query. The case no longer depends on what a backend or
  driver raises. Measured on Django 5.2.19 with SQLite: `to_python` of `AutoField`, `BigAutoField` and
  `UUIDField` rejects such a value by itself, while `CharField.to_python` returns it unchanged and SQLite accepts
  it as a query parameter that matches nothing. Only a string key can therefore show the condition over HTTP,
  and task 01 of this plan adds those requests against the string-key ViewSet it creates.

Real PostgreSQL behavior stays unmeasured for what remains: whether it reports an out-of-range integer as
`DataError` is unknown, and an ID that a backend or driver rejects with another exception type is not covered
by the catch. This plan adds no further handling of its own for A3 and A4 and must keep both as plan 01 placed
them: the NUL condition in `_read_ids`, and the catch around the evaluation only, re-raising at once. When a
key-type test of this plan shows a server error on SQLite for a forged ID, that is a defect of this phase and
is fixed here.

The focused command for the three NUL tests, and the one for the four narrower-destination and source-filter
tests of task 02, run without xdist workers on purpose: for three or four tests, starting workers costs more
than the run (CLAUDE.md allows a serial run for a tiny selection).

Review cycle 1 (plan revision 5). Cross-AI review `5a420bbb` led to these changes; the ledger at the end of this
plan lists every finding with its disposition.

- Both halves of the intersection. Every scope test used a destination queryset broader than the ViewSet scope.
  Those tests prove the ViewSet bound and would still pass if the destination half of the intersection were
  removed, because the default `get_queryset()` delegates to the ViewSet. Task 02 adds a destination whose
  `get_queryset()` is narrower than the ViewSet queryset and tests it on review, on execute and on a skipped
  confirmation.
- Source-only filter. "A source filter is no gate" was tested with a record on page 2, which is pagination.
  Task 02 keeps that case and adds a real one: the tenant ViewSet's source view hides records through its own
  `get_queryset()`, and such a record is still accepted on a direct review POST.
- Test list views get explicit minimal action lists (an empty `cv_list_actions`, `cv_context_actions` of
  `["home"]`). Read at HEAD in `src/crud_views/lib/view/base.py`: an action key whose view is not registered
  is skipped while rendering, so the package defaults would not fail; the explicit lists keep the test pages
  free of lookups for views these ViewSets do not have.
- Two findings on this plan ask for sentences in the guide (a router that sends a loaded row to another alias
