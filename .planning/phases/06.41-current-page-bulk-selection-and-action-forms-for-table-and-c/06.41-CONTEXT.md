# Phase 06.41: Current-page bulk selection and action forms for table and card views (#387) - Context

**Gathered:** 2026-11-19
**Status:** Ready for planning

<domain>
## Phase Boundary

A developer opts a table or card view into current-page selection and lists the registered action views it
offers in the same ViewSet. Each destination is an ordinary action form view that owns admission, scoped
resolution of the submitted IDs, eligibility, confirmation and execution.

Scope: `crud_views` core, one `crud_views_guardian` system check, a Bootstrap example app and the reference
guide. The work starts from the list, card and custom-form views on `main`. The phase 06.38 implementation
(#378) stays off `main` and is not ported.

Out of scope, fixed by the approved issue: cross-page selection, "select all matching", drafts, signing,
receipts, modal review, automatic deletion previews, automatic adaptation of single-record actions, row
locking in the library, composite keys, non-ORM Resources and other database aliases.

</domain>

<decisions>
## Implementation Decisions

### Approved issue decisions (locked before this discussion)

D-01 to D-10 and the acceptance list in section 11 of `06.41-ISSUE-387.md` are the maintainer's decisions.
Read their full prose there; the lines below only index them and do not narrow them.

- **D-01:** Start from `main` with an opt-in selection mixin; destinations are ordinary action form views.
- **D-02:** Current-page selection; explicit `cv_bulk_max` (default 100) counted before loading records;
  oversized or empty selection gives a warning, a return to the source and no writes; a system check warns
  when a source's page size exceeds an offered action's limit.
- **D-03:** The toolbar shows every configured action with zero bulk-permission queries and no page scan.
  Admission first on submission; resolve only submitted IDs within ViewSet, parent and destination scope.
- **D-04:** Destination-owned `cv_bulk_confirm` (default `True`); full-page review only, no `cv_modal`;
  the skip, mixed-selection, input-form and all-blocked outcomes of the D-04 table.
- **D-05:** Blocked rows are informational; lost eligibility means no changes and a new confirmation; no
  stored or signed review record.
- **D-06:** One eligibility check per request, inside the configured transaction for any request that can write.
- **D-07:** Missing, out-of-scope and permission-denied records show one identical message without a label;
  a business-blocked record shows its name and the specific reason.
- **D-08:** Django ORM models on the default database with a single scalar primary key.
- **D-09:** Bulk delete is application code built on the new form view.
- **D-10:** Reference guide plus a dedicated Bootstrap example app (delete, archive, assign owner) over the
  same seeded documents, linked in both directions.

The issue's revision note also records five changes approved on 2026-11-19: explicit `cv_bulk_max`, no modal
review, warning-and-return for selection mistakes, a default success message, and reuse of the existing
origin mechanism for return. The API is listed as **stable** in `docs/development/stability.md`, with no
provisional category.

The decisions below settle what the handover left open as proposals. Where they differ from sections 4, 6
and 7 of the issue (names, script, templates, checks), the decisions below win. The issue's code sketches
stay a review aid, not a patch.

### General constraint

- **D-11 — Human-maintainable code:** The maintainer stated for the whole phase: "produced code must be
  human maintainble and easy to understand". This restates the project's Developer Maintainability rule as a
  phase acceptance condition. Prefer the plain, readable solution; keep the backend a few ordinary classes
  and private helpers that can be read in one sitting. When a plan or implementation needs lifecycle
  classification, view cloning, source replay, signed recovery, per-method exemptions or other general
  machinery, stop and report the conflict instead of building it.

### Names that freeze at 1.0

- **D-12 — Destination class:** `BulkFormViewPermissionRequired`, a single public class. No plain
  `BulkFormView` twin: an ungated bulk write endpoint contradicts D-03. This replaces the sketch's
  `BulkFormView` everywhere (code, checks, docs, examples, stability inventory).
- **D-13 — Source mixin:** `BulkSelectionMixin`, replacing the sketch's `BulkMixin`. It adds selection
  controls only and never processes a POST.
- **D-14 — Templates and data attributes follow the existing layout:**
  - `crud_views/view_bulk_form.html` (destination page) and `crud_views/view_bulk_form.content.html`
    (review and form)
  - `crud_views/snippets/bulk_toolbar.html` (source toolbar)
  - `crud_views/columns/bulk_select.html` (table checkbox)
  - `crud_views/snippets/message/bulk.html` (default success message)
  - Data attributes use the `data-cv-bulk…` prefix. The word "simple" appears in no public name: no
    `bulk_simple/` folder and no `data-cv-simple-bulk`.
- **D-15 — Other names stay as proposed:** `cv_bulk_actions`, `cv_bulk_max`, `cv_bulk_confirm`,
  `cv_bulk_has_permission(obj)`, `cv_bulk_check(obj)`, `cv_bulk_objects`, `BulkConfirmForm`, the POST fields
  `cv_bulk_ids`, `cv_bulk_blocked_ids` and `cv_bulk_stage`, the module `crud_views.lib.bulk`, and the class
  keys `bulk:card-cell` and `bulk:card-select`. The one exception is `cv_bulk_label`, dropped by D-20.
  — **Reversibility:** costly — D-12 to D-15 enter `docs/development/stability.md` as stable public API;
  after 1.0 a rename needs the deprecation and migration policy.

### Toolbar controls

- **D-16 — Buttons in both modes:** The toolbar shows one submit button per configured action with and
  without JavaScript. The sketch's action picker and Continue button are not built. The script only adds
  "Select this page", the selected count, and the disabled state of D-18.
- **D-17 — "Select this page" lives in the toolbar** for tables and cards alike: one control, one mechanism.
  The table's selection column header stays a plain "Select" caption with no header checkbox.
- **D-18 — Empty state:** With JavaScript the toolbar is always visible, shows "0 selected" and disables the
  action buttons while nothing is selected. Without JavaScript it is always visible with enabled buttons, and
  an empty submission gets the D-02 warning.
- **D-19 — Icons and label modes, bounded to the location floor:** The maintainer chose this over plain
  labelled buttons. Toolbar buttons render through the existing button leaf with the destination's action
  icon and a label mode for a new `bulk` location. Only the location floor is configurable (the existing
  `CRUD_VIEWS_LABEL_MODE_DEFAULTS` chain: project over theme over package), default `both`. No per-action
  maps on view, ViewSet or setting, no `primary`/`secondary`/`tertiary`/`danger` variants, and one button
  class key.
  - D-03 still holds: the toolbar uses the leaf for rendering only. It must not route bulk buttons through
    the access-checking action pipeline; every configured action is shown and no permission hook or
    permission query runs while rendering.
- **D-20 — Label source:** Button text and tooltip come from the destination's existing action label and
  short action label; the icon comes from `cv_icon_action`. `cv_bulk_label` is dropped: one label mechanism
  and one name fewer to freeze. The review page header uses the action label too. The sketch's
  "Set cv_bulk_label" check and its `cv_header_template_code = "{{ view.cv_bulk_label }}"` change accordingly.

### Review page layout

- **D-21 — Plain names:** Listed records show `str(object)` as text, without links. The page holds the
  selection only in its hidden fields, so nothing on it leads away from an unconfirmed selection.
- **D-22 — Order:** Blocked and excluded records with their reasons go in a warning alert at the top, using
  the shared alert frame. Then the records to process, then the action form. The alert is absent when
  nothing is blocked.
- **D-23 — Show all records:** Every record is listed, with the count in the heading. No collapse, no
  threshold setting, no column flow.
- **D-24 — Two overridable snippets:** `crud_views/snippets/bulk/blocked.html` and
  `crud_views/snippets/bulk/eligible.html`, included by the content template. The hidden `cv_bulk_ids`,
  `cv_bulk_blocked_ids` and `cv_bulk_stage` fields render in the content template, outside both snippets, so
  a theme can restyle a list without touching the transport fields.

### Return after success

- **D-25 — Explicit success target:** `cv_success_keys` stays `None` on bulk destinations, as on create,
  update, delete and custom forms. Success goes to `cv_success_key`; a developer who wants the source used
  lists the origins, as the Archive example does. No bulk-only default and no new `"auto"` value.
- **D-26 — Origin system check:** A startup warning when a source offers an action whose destination does
  not accept that source's key as a cancel origin. It compares declared keys only and runs no hooks.
- **D-27 — Plain GET:** A GET on a bulk destination redirects silently to the source (the origin, else
  `cv_cancel_key`). No message.
- **D-28 — All-blocked page:** The way back is the form's Cancel button, rendered through the existing form
  button leaf with the same origin URL and label. No new string and no plain text link.

### Resolved after research (2026-11-19)

Research reported that D-19 cannot be built as written (`06.41-RESEARCH.md`, "Decision needed before
building: D-19 and the button leaf"). The maintainer decided the three points below; they are locked.

- **D-29 — Toolbar buttons use the existing form leaf (resolves D-19):** Bulk toolbar buttons render through
  `crud_views/tags/button/form.html` unchanged, as the `submit` form kind, with `formaction` passed through
  the leaf's extra attributes and the label mode stamped from the new `bulk` location floor. The action leaf
  is not extended and no `tags/button/bulk.html` leaf is added. D-19's "one button class key" under `bulk`
  is superseded: the buttons carry the `form:submit` class, and no bulk button class key or leaf path enters
  the 1.0 surface. Accepted cost: bulk buttons look like other form submit buttons and a theme cannot style
  them apart. The rest of D-19 stands: icon from the destination, `bulk` location floor default `both`, no
  per-action maps, no variants, and no access-checking pipeline while rendering (D-03).
  — **Reversibility:** cheap — a dedicated leaf can be added later without breaking this rendering.
- **D-30 — Only `bulk_review` becomes a stable template-facing name:** `bulk_review` and its fields
  (`objects`, `blocked`, and per item `pk`, `label`, `reasons`) are documented in the guide and listed in
  `docs/development/stability.md` as the override contract of the two D-24 snippets. `cv_bulk_form_id` and
  `cv_bulk_buttons` stay undocumented and internal.
  — **Reversibility:** costly — `bulk_review` freezes at 1.0 with D-12 to D-15.
- **D-31 — Header label through one read-only property:** The review page header shows the destination's
  action label (D-20) through one read-only, template-facing property (research spike name
  `cv_bulk_header`) used by a default `cv_header_template_code`. The standard header pipeline stays intact
  and a developer can still set their own template code. `cv_header` is not overridden.
  — **Reversibility:** costly — the property name freezes at 1.0.
- **D-32 — Six data attributes are stable:** `data-cv-bulk`, `data-cv-bulk-item`, `data-cv-bulk-all`,
  `data-cv-bulk-count`, `data-cv-bulk-action` and `data-cv-bulk-enhanced` are listed as stable in
  `docs/development/stability.md`. D-14 fixed only the `data-cv-bulk…` prefix; the maintainer confirmed the
  six names proposed during planning.
  — **Reversibility:** costly — the names freeze at 1.0 with D-12 to D-15.
- **D-33 — Toolbar buttons use the short action label only (narrows D-20):** Because the form leaf (D-29)
  takes one label string, a bulk toolbar button uses the destination's short action label for its visible
  text, its hidden text and its tooltip. The full action label appears only in the review page header
  (D-31). D-20's "action label and short action label" for the button is superseded for the button; its
  icon source and the dropped `cv_bulk_label` stand. The guide states this in its toolbar buttons section.
  — **Reversibility:** cheap — a dedicated leaf could show both labels later.
- **D-34 — Way back always has a target (amends D-27):** The way back from a bulk destination is the origin,
  else `cv_cancel_key`, else the success URL (`get_success_url()`) when no cancel target is accessible to the
  user. This applies to the plain GET redirect (D-27) and to the empty-selection and over-limit warnings
  (D-02), which share one helper. Cross-AI review cycle 1 flagged the third step as going beyond D-27's
  wording; the maintainer kept it so the redirect never lacks a target. The plans and the guide state the
  third step explicitly.
  — **Reversibility:** cheap — the fallback is one private helper.
- **D-35 — Bulk destinations do not call `cv_form_valid_process`:** The bulk execute path keeps its own
  order, because D-06 puts the eligibility check inside the transaction before the write: it calls
  `cv_form_valid` and `cv_form_valid_hook` directly inside `cv_get_atomic()`. An application override of
  `cv_form_valid_process` therefore does not run on a bulk destination; applications override
  `cv_form_valid` or `cv_form_valid_hook`. The guide and `docs/development/stability.md` state the
  exception and a test pins it. Raised by cross-AI review cycle 2; the maintainer chose documenting the
  exception over routing through the hook.
  — **Reversibility:** costly — the documented exception freezes at 1.0 with the hook listing.
- **D-36 — The all-blocked Cancel button uses the D-34 chain (extends D-28):** On the all-blocked page the
  Cancel button targets the origin, else `cv_cancel_key`, else the success URL when no cancel target is
  accessible to the user, so the page never lacks a way back. It stays the existing form button leaf with
  the existing label: no new string, no plain text link, no bulk-only control. A test covers an
  inaccessible cancel target with a distinct success target. Raised by cross-AI review cycle 2.
  — **Reversibility:** cheap — one private helper feeds the button.
- **D-37 — The lifecycle page notes the D-35 exception (extends D-35):** `docs/reference/request_lifecycle.md`
  gets a short note, one or two sentences, that bulk destinations keep their own execute order and do not
  call `cv_form_valid_process`, with a link to the bulk guide and a doc guard. The page's existing call
  chains and its advice for other form views stay as they are. All three reviewers raised the missing
  cross-reference in review cycle 4; the maintainer chose to add the note in this phase.
  — **Reversibility:** cheap — documentation only.
- **D-38 — Success message after a rollback follows the library limit (amends acceptance item AC-17):** The
  issue's sentence "a rerender or a rolled-back execution shows no success message" is narrowed. A bulk
  destination behaves like every other form view: `MessageMixin.cv_form_valid_hook` queues the success
  message inside the transaction. No success message is shown for a rerender, or for a failure before the
  message is queued (for example a raise in `cv_form_valid`). A raise after the message is queued, such as
  an override that calls `super().cv_form_valid_hook()` and then raises, rolls the writes back while the
  message may still be shown; `docs/reference/request_lifecycle.md` already documents that limit for all
  form views. A test pins the real outcome of that case and the guide points to the documented limit. The
  message is not moved to after the commit. Raised by cross-AI review cycle 5.
  — **Reversibility:** cheap — the message could be made commit-dependent later without breaking this.

### Claude's Discretion

- Example app label: `bulk_selection`. `bulk_actions` is taken by untracked leftovers of the 06.38 branch
  (see code context), and section 7.8 of the issue asks for a different label.
- Script text: the toolbar script creates no user-visible text. "Select this page" and the count come from
  server-rendered, translated markup that the script reveals and updates, as the existing scripts do.
- Check IDs, the names of the toolbar class keys under the `bulk` location, the exact wording of headings
  and messages, test organization and the split into plans.
- How the `bulk` location is registered in the label-mode and class-key machinery, within the bounds of
  D-11 and D-19. If registering a location turns out to need more than a small, explainable change, report
  it before building it.

### Established Patterns
- Every permission-required view is named `…PermissionRequired` (D-12 follows this).
- Templates are flat `view_<name>.html` plus `view_<name>.content.html`, with parts under `snippets/`,
  `columns/` and `table/`. The delete view keeps its record lists in `snippets/delete/` (precedent for D-24).
- `view_card.content.html` wraps each card in `view.cv_card_container_class` and calls `{% cv_card object %}`;
  the card checkbox goes in this wrapper, not in the card template.
- `view_list_table.content.html` is only `{% render_table table %}`; the toolbar is included around it.
- Scripts live in `src/crud_views/static/crud_views/js/` with tests in `tests/js/`. They take their text from
  markup and use `data-cv-*` attributes.
- Check IDs in use run up to `crud_views.E365` and `crud_views.W362`, and `crud_views_guardian.E001` is the
  only Guardian ID. The `viewset` IDs are not contiguous: `E260`–`E269`, `W270` (breadcrumb), `E280`–`E284`
  with `W280`, and `W290`–`W292` are in use; `271`–`279` are free in both severities (measured in `src/`
  on 2026-11-19). New checks take unused IDs.
- Example apps are self-contained folders in `examples/bootstrap5/` (`apps.py`, `seed.py`, `tests.py`,
  `urls.py`, `views.py`) registered through `examples/bootstrap5/project/features.py`, with reciprocal
  documentation links tested by `examples/bootstrap5/test_doc_links.py`.

<specifics>
## Specific Ideas

- Toolbar as chosen from the mockups: a first row with "Select this page" and "N selected", a second row
  with the action buttons (`[ Archive ] [ Assign owner ] [ Delete ]`), above the table or card grid.
- Review page as chosen from the mockups: header with the action label; a warning alert "1 record will be
  skipped" listing blocked records with their reasons; "To process: N" with the plain names; then
  `[ Confirm ] [ Cancel ]`.
- The application code a developer writes should read like the examples in section 6 of the issue, with the
  new names: `class ArchiveDocumentsView(BulkFormViewPermissionRequired)` and
  `class DocumentListView(BulkSelectionMixin, ListViewTableMixin, ListViewPermissionRequired)`.

</specifics>
