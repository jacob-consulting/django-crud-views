### Approved issue decisions (locked before this discussion)

D-01 to D-10 and the acceptance list in section 11 of `06.41-ISSUE-387.md` are the maintainer's decisions.
Read their full prose there; the lines below only index them and do not narrow them.

- **D-01:** Start from `main` with an opt-in selection mixin; destinations are ordinary action form views.
- **D-02:** Current-page selection; explicit `cv_bulk_max` (default 100) counted before loading records;
  oversized or empty selection gives a warning, a return to the source and no writes; a system check warns
  when a source's page size exceeds an offered action's limit.
- **D-03:** The toolbar shows every configured action with zero bulk-permission queries and no page scan.
  Admission first on submission; resolve only submitted IDs within ViewSet, parent and destination scope.
- **D-04:** Destination-owned `cv_bulk_confirm` (default `True`); full-page review only, no `cv_modal`;
  the skip, mixed-selection, input-form and all-blocked outcomes of the D-04 table.
- **D-05:** Blocked rows are informational; lost eligibility means no changes and a new confirmation; no
  stored or signed review record.
- **D-06:** One eligibility check per request, inside the configured transaction for any request that can write.
- **D-07:** Missing, out-of-scope and permission-denied records show one identical message without a label;
  a business-blocked record shows its name and the specific reason.
- **D-08:** Django ORM models on the default database with a single scalar primary key.
- **D-09:** Bulk delete is application code built on the new form view.
- **D-10:** Reference guide plus a dedicated Bootstrap example app (delete, archive, assign owner) over the
  same seeded documents, linked in both directions.

The issue's revision note also records five changes approved on 2026-11-19: explicit `cv_bulk_max`, no modal
review, warning-and-return for selection mistakes, a default success message, and reuse of the existing
origin mechanism for return. The API is listed as **stable** in `docs/development/stability.md`, with no
provisional category.

### General constraint

- **D-11 — Human-maintainable code:** The maintainer stated for the whole phase: "produced code must be
  human maintainble and easy to understand". This restates the project's Developer Maintainability rule as a
  phase acceptance condition. Prefer the plain, readable solution; keep the backend a few ordinary classes
  and private helpers that can be read in one sitting. When a plan or implementation needs lifecycle
  classification, view cloning, source replay, signed recovery, per-method exemptions or other general
  machinery, stop and report the conflict instead of building it.

### Names that freeze at 1.0

- **D-12 — Destination class:** `BulkFormViewPermissionRequired`, a single public class. No plain
  `BulkFormView` twin: an ungated bulk write endpoint contradicts D-03. This replaces the sketch's
  `BulkFormView` everywhere (code, checks, docs, examples, stability inventory).
- **D-13 — Source mixin:** `BulkSelectionMixin`, replacing the sketch's `BulkMixin`. It adds selection
  controls only and never processes a POST.
- **D-14 — Templates and data attributes follow the existing layout:**
  - `crud_views/view_bulk_form.html` (destination page) and `crud_views/view_bulk_form.content.html`
    (review and form)
  - `crud_views/snippets/bulk_toolbar.html` (source toolbar)
  - `crud_views/columns/bulk_select.html` (table checkbox)
  - `crud_views/snippets/message/bulk.html` (default success message)
  - Data attributes use the `data-cv-bulk…` prefix. The word "simple" appears in no public name: no
    `bulk_simple/` folder and no `data-cv-simple-bulk`.
- **D-15 — Other names stay as proposed:** `cv_bulk_actions`, `cv_bulk_max`, `cv_bulk_confirm`,
  `cv_bulk_has_permission(obj)`, `cv_bulk_check(obj)`, `cv_bulk_objects`, `BulkConfirmForm`, the POST fields
  `cv_bulk_ids`, `cv_bulk_blocked_ids` and `cv_bulk_stage`, the module `crud_views.lib.bulk`, and the class
  keys `bulk:card-cell` and `bulk:card-select`. The one exception is `cv_bulk_label`, dropped by D-20.
  — **Reversibility:** costly — D-12 to D-15 enter `docs/development/stability.md` as stable public API;
  after 1.0 a rename needs the deprecation and migration policy.

### Toolbar controls

- **D-16 — Buttons in both modes:** The toolbar shows one submit button per configured action with and
  without JavaScript. The sketch's action picker and Continue button are not built. The script only adds
  "Select this page", the selected count, and the disabled state of D-18.
- **D-17 — "Select this page" lives in the toolbar** for tables and cards alike: one control, one mechanism.
  The table's selection column header stays a plain "Select" caption with no header checkbox.
- **D-18 — Empty state:** With JavaScript the toolbar is always visible, shows "0 selected" and disables the
  action buttons while nothing is selected. Without JavaScript it is always visible with enabled buttons, and
  an empty submission gets the D-02 warning.
- **D-19 — Icons and label modes, bounded to the location floor:** The maintainer chose this over plain
  labelled buttons. Toolbar buttons render through the existing button leaf with the destination's action
  icon and a label mode for a new `bulk` location. Only the location floor is configurable (the existing
  `CRUD_VIEWS_LABEL_MODE_DEFAULTS` chain: project over theme over package), default `both`. No per-action
  maps on view, ViewSet or setting, no `primary`/`secondary`/`tertiary`/`danger` variants, and one button
  class key.
  - D-03 still holds: the toolbar uses the leaf for rendering only. It must not route bulk buttons through
    the access-checking action pipeline; every configured action is shown and no permission hook or
    permission query runs while rendering.
- **D-20 — Label source:** Button text and tooltip come from the destination's existing action label and
  short action label; the icon comes from `cv_icon_action`. `cv_bulk_label` is dropped: one label mechanism
  and one name fewer to freeze. The review page header uses the action label too. The sketch's
  "Set cv_bulk_label" check and its `cv_header_template_code = "{{ view.cv_bulk_label }}"` change accordingly.

### Review page layout

- **D-21 — Plain names:** Listed records show `str(object)` as text, without links. The page holds the
  selection only in its hidden fields, so nothing on it leads away from an unconfirmed selection.
- **D-22 — Order:** Blocked and excluded records with their reasons go in a warning alert at the top, using
  the shared alert frame. Then the records to process, then the action form. The alert is absent when
  nothing is blocked.
- **D-23 — Show all records:** Every record is listed, with the count in the heading. No collapse, no
  threshold setting, no column flow.
- **D-24 — Two overridable snippets:** `crud_views/snippets/bulk/blocked.html` and
  `crud_views/snippets/bulk/eligible.html`, included by the content template. The hidden `cv_bulk_ids`,
  `cv_bulk_blocked_ids` and `cv_bulk_stage` fields render in the content template, outside both snippets, so
  a theme can restyle a list without touching the transport fields.

### Return after success

- **D-25 — Explicit success target:** `cv_success_keys` stays `None` on bulk destinations, as on create,
  update, delete and custom forms. Success goes to `cv_success_key`; a developer who wants the source used
  lists the origins, as the Archive example does. No bulk-only default and no new `"auto"` value.
- **D-26 — Origin system check:** A startup warning when a source offers an action whose destination does
  not accept that source's key as a cancel origin. It compares declared keys only and runs no hooks.
- **D-27 — Plain GET:** A GET on a bulk destination redirects silently to the source (the origin, else
  `cv_cancel_key`). No message.
- **D-28 — All-blocked page:** The way back is the form's Cancel button, rendered through the existing form
  button leaf with the same origin URL and label. No new string and no plain text link.

## Summary

The issue's sketch (sections 7.1 to 7.4) composes with the bases on this checkout. A throwaway spike built
from it, with the CONTEXT names, ran the whole flow against the test project on Django 4.2.30 (crispy floor
2.0 / 2023.10), 5.2.19 and 6.1.2: toolbar with zero added queries, admission before item checks, review,
confirmed subset, skip, input form, eligibility loss, warning-and-return, plain GET, nested parent scope with
a deliberately broader destination queryset, and Cancel through the origin mechanism. The backend is small:
one module with a mixin, a form and a view of roughly 150 lines.

The spike also found six places where the sketch does not meet the approved behavior or the repository's
rules. Each has a small correction that was run in the spike (see
[Sketch corrections](#sketch-corrections-found-by-the-spike)). The two that matter most: the skip fallback
shows a **bound** form although the acceptance list requires an unbound review, and an out-of-range integer
ID raises `OverflowError` (HTTP 500) on all three Django series because Django's `__in` lookup has no range
guard.

One locked decision cannot be built exactly as written. **D-19 says toolbar buttons "render through the
existing button leaf", but neither existing leaf can render a native `formaction` submit button under a
`bulk` class key without a change.** The action leaf hard-codes `type="button"` and submits through
JavaScript; the form leaf can do it, but styles the button as `form:submit`. Registering the `bulk` location
is also wider than one line: it touches three existing tests and four documentation cells that are guarded
by tests. CONTEXT asks for exactly this to be reported before building, so it is the first open question.

**Primary recommendation:** Build `crud_views.lib.bulk` from the sketch with the six corrections, put the
checks on the two classes' own `checks()` classmethods (IDs `viewset.E271` to `viewset.E279`), render toolbar
buttons through the existing **form** leaf with the label mode stamped from the new `bulk` floor, and get the
maintainer's confirmation of that D-19 reading before the toolbar plan is executed.

### What the existing leaves emit

Spike output for one toolbar button, rendered through each leaf as it is today [VERIFIED: spike
`probe_leaf.py`, Django 6.1.2]:

```html
<!-- form leaf, cv_button_data(raw, "form") with cv_key "submit", mode "both" -->
<button type="submit" name="" value="" id="cv-bulk-archive"
    class="btn btn-primary x-bulk-action" data-cv-bulk-action="archive"
    formaction="/doc/archive/?cv_from=list&amp;cv_from_cancel=TOKEN"><i class="fa-regular fa-trash-can"
    aria-hidden="true"></i> <span>Archive</span></button>

<!-- action leaf, cv_button_data(ctx, "list") with cv_list_action_method "post" -->
<button type="button" class="btn btn-outline-primary btn-xs"
    data-cv-action="submit-form" data-cv-target="cv_form_x_archive_1"
    cv-key="archive"><i class="fa-regular fa-trash-can" aria-hidden="true"></i> <span>Archive</span></button>
```

- **Action leaf** (`crud_views/tags/button/action.html`): line 1 hard-codes the element type
  [VERIFIED: src/crud_views/templates/crud_views/tags/button/action.html:1]:
  `{% else %} type="button"{% endif %}`. A `type="button"` control never submits natively. Its POST path is
  the script hook `data-cv-action="submit-form"`, and that handler calls `e.preventDefault()` before it looks
  for the target form [VERIFIED: src/crud_views/static/crud_views/js/viewset.js:20-22]. The leaf has no
  `formaction`. It cannot give the no-JavaScript baseline of D-16.
- The action leaf is a documented theme override point. `docs/reference/buttons.md` ("Copied action leaf")
  publishes a complete copy for themes that contains the same literal `type="button"`. Adding `cv_type` and
  `cv_formaction` to that leaf's contract would make every theme that copied the recipe render dead bulk
  buttons. [VERIFIED: docs/reference/buttons.md, section "Copied action leaf"]
- **Form leaf** (`crud_views/tags/button/form.html`): emits `type="{{ cv_type }}"` and passes extra
  attributes through `{{ cv_flat_attrs }}` [VERIFIED: src/crud_views/templates/crud_views/tags/button/form.html:2-3],
  so `formaction` works unchanged. Its class is fixed to the `form` location:
  `class="{% cv_button_class 'form' cv_key cv_label_mode %}`, and `cv_key` must be a form kind
  [VERIFIED: src/crud_views/lib/button_classes.py:324]:
  `FORM_KINDS: frozenset[str] = frozenset({"submit", "cancel", "delete", "filter-submit", "filter-reset"})`.

### Options

| | Option A: existing form leaf (recommended) | Option C: new `tags/button/bulk.html` leaf | Option B: extend the action leaf |
|---|---|---|---|
| Matches "existing button leaf" | yes, unchanged | no, a new leaf | yes, but the leaf and `LEAF_KEYS` change |
| Native submit without JavaScript | yes | yes | only after the change |
| Button class | `form:submit` (Bootstrap `btn btn-primary`) plus an optional additive key | own key `bulk:action` | own key `bulk:<slot>` |
| New names to freeze | none for the button | leaf path, `bulk:action`, `bulk:hidden-label`, `bulk:icon-host` | two leaf-contract keys |
| Shared code touched | none | none | golden-tested, theme-copied leaf |
| D-20 "text and tooltip" | one string (the short label) for text, hidden text and tooltip | full label hidden, short label visible and as tooltip, like row actions | same as C |
| Tooltip marker | `data-cv-tooltip="form"` | `data-cv-tooltip="bulk"` | `data-cv-tooltip="bulk"` |
| Risk | bulk buttons share the look of every form submit button | more inventory edits (see below) | breaks copied theme leaves |

Option B is ruled out by the Developer Maintainability rule ("Preserve proven code paths") and by the copied
theme leaf. **Recommendation: Option A.** The toolbar is a `<form>` and its buttons are that form's submit
buttons, so the `submit` kind is accurate; D-28 already sends the all-blocked Cancel through the same leaf;
nothing shared changes and no button name is added to the 1.0 surface. Its cost is visible: with nothing
configured the toolbar is a row of primary buttons, and a theme can add classes to bulk buttons but cannot
restyle them apart from other form submit buttons. If the maintainer wants bulk-specific styling, Option C is
the fallback, at the inventory cost listed under [Pitfall 2](#pitfall-2-every-class-key-and-the-bulk-location-are-pinned-by-inventories).

Details that make Option A work, all verified in the spike:

- Pass `cv_name="cv_bulk_stage"` and `cv_value="review"`. The form leaf always prints `name` and `value`
  [VERIFIED: src/crud_views/templates/crud_views/tags/button/form.html:2], and an empty `name` is invalid
  HTML [CITED: html.spec.whatwg.org/multipage/form-control-infrastructure.html — "If the attribute is
  specified, its value must not be the empty string or isindex"]. Letting the button carry the stage removes
  the hidden `cv_bulk_stage` input from the toolbar and adds no POST field name.
- Pass `cv_label` (the short action label), `cv_id` (for example `cv-bulk-<key>`), `cv_icon`
  (`destination.cv_icon_action`), `cv_attrs={"formaction": url, "data-cv-bulk-action": key}` and
  `cv_label_mode=default_label_mode("bulk")`. A stamped `cv_label_mode` wins over the form maps
  [VERIFIED: src/crud_views/lib/view/button_data.py:308-317], so D-19's "floor only, no per-action maps" holds.
- Stamp `"label"` instead of the floor when the destination has no `cv_icon_action`. Otherwise an `icon`
  floor raises in strict mode with a message about `submit_icon` and `delete_icon` that would mislead here
  [VERIFIED: spike — `ValueError: form button 'submit' renders icon-only but its icon None is not available;
  set a usable icon (icon=, submit_icon, delete_icon or CRUD_VIEWS_ICONS)`].

## Sketch corrections found by the spike

Each row was reproduced, then the correction was run on Django 6.1.2 and 4.2.30.

| # | Sketch behavior | Evidence | Correction |
|---|---|---|---|
| 1 | With `cv_bulk_confirm = False` and a mixed selection, the review is rendered with a **bound** form. The acceptance list says "Review is read-only and leaves the action form unbound." | spike: `form bound on review: True`. Cause: `self._bulk_stage = "execute" if skipped else stage` is set before the selection is checked, so `get_form_kwargs` keeps `data` | Check the selection first, then decide the stage, then build the form. See [Destination lifecycle](#pattern-2-destination-lifecycle). After the correction: `form bound on review: False` |
| 2 | An integer ID outside the 64-bit range passes `_read_ids` and the scoped query raises `OverflowError: Python int too large to convert to SQLite INTEGER` (HTTP 500) | spike on 4.2.30, 5.2.19 and 6.1.2. Django guards `exact`, `gt`, `lt` lookups (`IntegerFieldOverflow`) but not `__in`. `field.clean()` is no portable fix: it rejects the value on 6.1.2 and accepts it on 4.2.30; `connection.ops.integer_field_range("BigAutoField")` is `(None, None)` on 4.2.30 | Catch `OverflowError` where the scoped queryset is evaluated and raise `BadRequest`. After the correction: `out-of-range id: 400` |
| 3 | `extra_columns` alone does not put the selection column first | spike: `sketch as written (extra_columns only), Table: ['id', 'name', 'cv_bulk_select', 'actions']` | Pass `sequence` too. See [Table column](#pattern-3-table-selection-column) |
| 4 | Translatable text written as template code in a Python string (`"{% load i18n %}{% translate '…' %}"`) is never extracted | `makemessages` does not templatize `.py` files [VERIFIED: django/core/management/commands/makemessages.py:81-85, `return file_ext != ".py"`] | Use snippet files (the core convention under `snippets/header`, `paragraph`, `action`, `message`) or wrap the code in `gettext_lazy`, as `crud_views_workflow` does |
| 5 | The all-blocked page renders a plain `<a>` | superseded by D-28 | Hand the template a private cancel-only form; `{% cv_render_form %}` then prints only Cancel. See [Pattern 5](#pattern-5-all-blocked-page-without-a-template-tag) |
| 6 | An execute request whose records have all become blocked adds the "selection changed" error to a form the template then does not render | sketch 7.4 and 7.6 read together: `{% if bulk_review.objects %}{% cv_render_form %}` | Treat "nothing eligible" like the skip fallback: render the all-blocked page before validation. ## Architectural Responsibility Map

| Capability | Primary Tier | Secondary Tier | Rationale |
|------------|-------------|----------------|-----------|
| Selection controls (checkboxes, toolbar) | Frontend Server (template rendering) | Browser (progressive enhancement) | Native form submission is the baseline; the script only adds "Select this page", the count and the disabled state (D-16, D-18) |
| Choosing the destination | Browser (native `formaction`) | — | The source never processes a POST (D-13); the clicked button's URL is the destination |
| Admission (may this user enter the action?) | API / Backend (destination `dispatch`) | — | Existing `CrudViewPermissionRequiredMixin` and ancestor guard run on the real endpoint (D-03) |
| Scoped resolution of submitted IDs | API / Backend (destination view) | Database | ViewSet queryset ∩ destination queryset ∩ structural parent scope (D-03) |
| Item permission and business eligibility | API / Backend (application hooks on the destination) | — | `cv_bulk_has_permission`, `cv_bulk_check` are application code (D-03, D-07) |
| Confirmation state | Browser (hidden fields of the review form) | API re-checks | No stored or signed review record (D-05) |
| Execution and transaction | API / Backend (existing form lifecycle hooks) | Database | `cv_form_valid` in `cv_get_atomic()` (D-06) |
| Return navigation | API / Backend (existing origin mechanism) | Browser (query string) | `cv_get_link_url`, `cv_get_cancel_url`, `cv_success_keys` (D-25 to D-27) |
| Configuration validation | API / Backend (Django system checks at startup) | — | No hooks, forms or querysets run at startup |

## Architecture Patterns

### System Architecture Diagram

```text
 Browser: list or card page (source, GET)
   |  BulkSelectionMixin: checkbox per row/card (form="cv-bulk-selection"),
   |  toolbar <form method="post"> with one submit button per configured action
   |  each button: formaction = cv_get_link_url(destination, key)   <- carries cv_from + signed query state
   v
 POST cv_bulk_ids=..., cv_bulk_stage=review  ---->  destination URL (a registered view of the same ViewSet)
   |
```

### Pattern 1: Source mixin without permission work

**What:** The mixin builds toolbar data from class-level facts only.
**When to use:** always; this is D-03.

[VERIFIED: src/crud_views/lib/view/base.py:1099-1117]. `cv_get_action_short_label(context)` renders a snippet
from `ViewSet.get_meta()`, which reads `model._meta` only [VERIFIED: src/crud_views/lib/view/base.py:637-643].

```python
# verified in the spike (labels and URLs); the cv_button_data call is Option A of the D-19 decision
```

### Pattern 2: Destination lifecycle

**What:** `post()` overrides `CrudViewProcessFormMixin.post` because the transaction must open before the
selection check (D-06), while the base opens it only around `cv_form_valid`
[VERIFIED: src/crud_views/lib/views/mixins.py:33-64].
**Hook order to preserve and pin with a test:** `_cv_check_nested_write` → `cv_post_hook` →
`cv_form_is_valid` → (`cv_form_invalid_hook`, `cv_form_invalid`) or (`cv_form_valid`, `cv_form_valid_hook`,
`transaction.on_commit(cv_on_commit)`) → `cv_form_valid_redirect`.

```python
# corrected sketch; verified in the spike on Django 4.2.30 and 6.1.2
def _bulk_context(self, review):
    # nothing eligible: only Cancel (Pattern 5); built directly, an application get_form() may expect its own fields
    form = self.get_form() if review.objects else _CancelOnlyForm(cv_view=self)
    return self.get_context_data(form=form, bulk_review=review)

def _bulk_execute(self, candidates, excluded, *, skipped):
    self._cv_check_nested_write()
    with self.cv_get_atomic():
        review = self._review_selection(candidates, excluded)  # the one check of this request, inside the transaction
        self.cv_bulk_objects = review.objects
        unchanged = bool(review.objects) and review.ids == candidates
        if not review.objects or (skipped and not unchanged):
            # nothing eligible, or the first look at a mixed selection: unbound form, nothing written
            self._bulk_stage = "review"
            return self.render_to_response(self._bulk_context(review))
        context = self._bulk_context(review)
        self._cv_check_nested_write(context)
        self.cv_post_hook(context)
        valid = self.cv_form_is_valid(context)
        if not unchanged:
            context["form"].add_error(None, _("The eligible selection changed. Review it and confirm again."))
            valid = False
        if not valid:
            self.cv_form_invalid_hook(context)
            return self.cv_form_invalid(context)
        self.cv_form_valid(context)
        self.cv_form_valid_hook(context)  # MessageMixin adds the success message here
        transaction.on_commit(partial(self.cv_on_commit, context), using=self.cv_get_db_alias())
    return self.cv_form_valid_redirect(context)
```

The review-stage request without skip uses the same two helpers outside a transaction:
`review = self._review_selection(…)`, `self.cv_bulk_objects = review.objects`, `self._bulk_context(review)`.

Facts the plan can rely on:

- The `not review.objects` branch must come before validation. Without it an execute request whose records
  have all become blocked reaches `add_error` on the unbound cancel-only form and fails (spike:
  `AttributeError: '_CancelOnlyForm' object has no attribute 'cleaned_data'`). With it the response is the
  all-blocked page (spike: `status: 200 | submit present: False | cancel present: True`).
- The non-field error added with `add_error(None, …)` is displayed by `{% cv_render_form %}` on crispy 2.7
  and on the 2.0 / 2023.10 floor (spike: `error text rendered: True` in both). No template addition is needed.
- `render_to_response` returns a lazy `TemplateResponse`; the template renders after the `with` block, so
  labels and form querysets are read outside the transaction. That is read-only work. [ASSUMED: Django
  `TemplateResponse` renders after the view returns; not measured here]
- `cv_form_invalid` sets status 422 only for modal requests [VERIFIED: src/crud_views/lib/views/mixins.py:92-100];
  bulk destinations never are (`cv_modal_supported = False`).
- A success message is added inside the transaction by `MessageMixin.cv_form_valid_hook`
  [VERIFIED: src/crud_views/lib/views/mixins.py:144-148]. An exception raised in `cv_form_valid` happens
  before that line, so a rolled-back execution adds no success message.

### Pattern 3: Table selection column

**What:** django-tables2 appends `extra_columns` after the declared columns and orders only by `sequence`
[VERIFIED: .venv/lib/python3.12/site-packages/django_tables2/tables.py:318-346].
**Constraints:**

- `crud_views.lib.table.Table` adds `("...", "actions")` only when no `sequence` keyword is passed and no
  `Meta.sequence` is declared [VERIFIED: src/crud_views/lib/table/table.py:30-34]. If the mixin passes
  `sequence`, it must restate that default.
- A `Meta.sequence` is expanded at class creation, so `table_class._meta.sequence` is a complete list
  without `"..."` (spike: `PBTable._meta.sequence after class creation: ['title']`).
- Naming a column the table does not have raises at render: `KeyError: 'actions'` (spike, a
  `TableWithViewContext` without an actions column). Append `"actions"` only when
  `"actions" in table_class.base_columns`.

```python
# verified in the spike: Table -> ['cv_bulk_select', 'id', 'name', 'actions'];
# a table with Meta.sequence -> ['cv_bulk_select', 'title']
def get_table_kwargs(self):
    kwargs = super().get_table_kwargs()
    if not self.cv_bulk_actions:
        return kwargs
    table_class = self.get_table_class()
    sequence = kwargs.get("sequence") or table_class._meta.sequence
    if not sequence:
        sequence = ("...", "actions") if "actions" in table_class.base_columns else ("...",)
    column = tables.TemplateColumn(
        template_name="crud_views/columns/bulk_select.html", verbose_name=_("Select"), orderable=False
    )
    kwargs["extra_columns"] = [("cv_bulk_select", column), *kwargs.get("extra_columns", ())]
    kwargs["sequence"] = ("cv_bulk_select", *(name for name in sequence if name != "cv_bulk_select"))
    return kwargs
```

`table.view` is available in the column template because `TableWithViewContext` stores it
[VERIFIED: src/crud_views/lib/table/table.py:15-20]; the spike rendered `form="cv-bulk-selection"` from
`{{ table.view.cv_bulk_form_id }}`.

`manage.js` is the model: an IIFE with an init guard, listeners bound before visibility changes, text that

```javascript
// untested skeleton; names are discretion
(function () {
    if (globalThis.__cvBulkInit) return;
    globalThis.__cvBulkInit = true;

    function init(form) {
        const items = () => [...document.querySelectorAll("[data-cv-bulk-item]")].filter(box => box.form === form);
        const all = form.querySelector("[data-cv-bulk-all]");
        const count = form.querySelector("[data-cv-bulk-count]");
        const actions = [...form.querySelectorAll("[data-cv-bulk-action]")];
        const refresh = () => {
            const boxes = items();
            const selected = boxes.filter(box => box.checked).length;
            all.checked = boxes.length > 0 && selected === boxes.length;
            all.indeterminate = selected > 0 && selected < boxes.length;
            all.disabled = boxes.length === 0;
            actions.forEach(button => { button.disabled = selected === 0; });
            count.textContent = String(selected);
        };
        // bind first, then reveal: a failed setup leaves the plain, working toolbar
        document.addEventListener("change", event => { if (event.target.matches?.("[data-cv-bulk-item]")) refresh(); });
        all.addEventListener("change", () => { items().forEach(box => { box.checked = all.checked; }); refresh(); });
        globalThis.addEventListener("pageshow", refresh);  // restored form state after back navigation
        form.querySelectorAll("[data-cv-bulk-enhanced]").forEach(el => { el.hidden = false; });
        refresh();
    }

    const start = () => document.querySelectorAll("[data-cv-bulk]").forEach(init);
    document.addEventListener("DOMContentLoaded", start);
    if (document.readyState !== "loading") start();
})();
```

`pageshow` fires after back and forward navigation, including restores from the back/forward cache, and is
widely available [CITED: developer.mozilla.org/en-US/docs/Web/API/Window/pageshow_event].

### Anti-Patterns to Avoid

- **Routing bulk buttons through the action pipeline** (`cv_get_context`, `cv_resolved_actions`,
  `{% cv_list_action %}`): runs `cv_has_access` per button and breaks D-03.
- **Replacing the two-queryset intersection with a manager lookup**: a destination `get_queryset()` broader
  than the ViewSet queryset would then escape parent scope. The spike used `Book.objects.all()` on a nested
  destination and still got `eligible: ['A1']`, `blocked: ['This item is unavailable for this action.']`.
- **Silently dropping unknown IDs**: D-07 needs one row per submitted ID.
- **`select_for_update()` in `get_queryset()`**: the review request runs outside a transaction.
- **Hard-coded `btn` classes in templates, Python or the script**: a test scans all shipped files
  [VERIFIED: tests/test1/test_button_classes_templates.py:126-138].
- **Building user-visible text in the script**: CONTEXT discretion; text is translated server markup.
- **Inspecting MROs or method bodies in checks**: ruled out by section 7.7 of the issue.

## Common Pitfalls

### Pitfall 1: Mixin order is silent when wrong
**What goes wrong:** `class X(ListViewTableMixin, BulkSelectionMixin, ListViewPermissionRequired)` renders
the toolbar but no checkboxes.
**Why it happens:** `ListViewTableMixin.get_table_kwargs` returns `{"view": self}` without calling `super()`
[VERIFIED: src/crud_views/lib/views/mixins.py:302-303], so a mixin placed after it is never reached.
**How to avoid:** document "first base class" in the guide and the docstring; add a test with the correct
order. Checks must not inspect the MRO (issue section 7.7).
**Warning signs:** toolbar present, `name="cv_bulk_ids"` absent from the page.

### Pitfall 2: Every class key and the `bulk` location are pinned by inventories
**What goes wrong:** adding one class key fails four tests.
**Why it happens:** the table is frozen on purpose.
**How to avoid:** for each new key update `EXPECTED_KEYS` and the two literal counts in
`tests/test1/test_button_classes.py` [VERIFIED: tests/test1/test_button_classes.py:144-146,

`{% cv_button_class 'bulk' '<slot>' %}` in a template must be a default key

**Warning signs:** `test_default_table_is_complete` fails.
**Note:** mode keys such as `bulk:action:icon` are not accepted by `crud_views.W362`, which knows only
variant locations and form kinds [VERIFIED: src/crud_views/lib/button_classes.py:335-350]. Do not read a mode

### Pitfall 3: Script inventories
**What goes wrong:** a new core script fails five tests.
**How to avoid:** add `"bulk": self.get_js("bulk.js")` to `CrudViewsSettings.javascript()`
[VERIFIED: src/crud_views/lib/settings.py:339-351] and update: the key list in

then loads on every page, like the others, and must do nothing without a `[data-cv-bulk]` form.

### Pitfall 4: `hidden` loses against Bootstrap display utilities
**What goes wrong:** an element meant to appear only with JavaScript is visible without it.
**Why it happens:** Bootstrap 5.3.3 has `[hidden] { display: none !important; }` at line 594 and
`.d-flex { display: flex !important; }` at line 7364; equal specificity, the later rule wins
[VERIFIED: bootstrap@5.3.3/dist/css/bootstrap.css fetched this session].
**How to avoid:** put `hidden` on an element without a `d-*` display class (wrap if needed), as the manage
page does with its `form-check` label.
**Warning signs:** "Select this page" visible with scripts disabled.

### Pitfall 5: The card checkbox can be painted over by the card
**What goes wrong:** the quarter of the checkbox that overlaps the card is hidden.
**Why it happens:** `.card` is `position: relative` with an opaque background
[VERIFIED: bootstrap.css lines 4400, 4407]; the sketch puts an absolutely positioned checkbox **before** the
card, and positioned boxes without a z-index paint in document order. [ASSUMED: CSS painting order; not run
in a browser this session]
**How to avoid:** include `z-1` in the `bulk:card-select` default (`.z-1 { z-index: 1 !important; }` exists
in 5.3.3). Check in a browser. `.form-check-input` also carries `margin-top: 0.25em`.
**Warning signs:** a clipped checkbox corner.

### Pitfall 6: Enter on a checkbox may submit to the first action
**What goes wrong:** a keyboard user presses Enter on a selection checkbox and the first configured action
receives the selection; with `cv_bulk_confirm = False` it runs at once.
**Why it happens:** implicit submission clicks the form's default button, "the first submit button in tree
order whose form owner is that form element" [CITED: html.spec.whatwg.org/multipage/form-control-infrastructure.html].
Whether browsers treat Enter on a checkbox as implicit submission is browser behavior. [ASSUMED]
**How to avoid:** make the first submit button in the toolbar form a hidden, disabled one
(`<button type="submit" disabled hidden></button>`). The specification fires the click only when the default
button "is not disabled", so implicit submission becomes inert while clicks on real buttons still work.
Verify in a browser before relying on it.
**Warning signs:** a browser check where Enter on a row checkbox navigates.

### Pitfall 7: `cv_bulk_max` above about 990 needs a Django setting
**What goes wrong:** a large page is rejected with HTTP 400 before the view runs.
**Why it happens:** `DATA_UPLOAD_MAX_NUMBER_FIELDS` defaults to `1000` and raises `TooManyFields`
[CITED: docs.djangoproject.com/en/5.2/ref/settings/#data-upload-max-number-fields].
**How to avoid:** document it beside `cv_bulk_max` in the guide.

### Pitfall 8: ViewSet names are global
**What goes wrong:** the example app fails at import.
**Why it happens:** `guardian_demo` already registers a ViewSet named `"document"`
[VERIFIED: examples/bootstrap5/guardian_demo/views.py:21-23, `name="document",`], and registration rejects a second
one [VERIFIED: src/crud_views/lib/viewset/__init__.py:206-211].
**How to avoid:** name the example ViewSet differently, for example `bulk_document`; URL names follow the
ViewSet name.

### Pitfall 9: The example project has seven inventories
**What goes wrong:** the example test suite fails after adding the app.
**How to avoid:** besides the app folder, edit `project/settings.py` (`INSTALLED_APPS`), `project/urls.py`,
`project/features.py` (one `Feature` with `docs=`), `project/seeding.py` (`ensure_developer_read_access`
lists models explicitly), `project/tests.py` (`test_grouping_matches_spec` pins every group's app list),
`project/test_developer.py` (the developer's exact permission set), `test_i18n.py` (`EXAMPLE_APPS`; model
names, field names, choices and table headers must be `gettext_lazy`) and `locale/de/LC_MESSAGES`
(`test_no_empty_or_fuzzy_msgstr`). Every page named in `Feature.docs` must contain a `!!! example` box linking
to `https://django-crud-views-demo.onrender.com` + `reverse(feature.url_name)`
[VERIFIED: examples/bootstrap5/test_doc_links.py:117-145].

### Pitfall 10: A cancel button needs JavaScript unless the theme chose a link
**What goes wrong:** on the all-blocked page, Cancel does nothing with scripts disabled.
**Why it happens:** the stock cancel is `<button type="button" data-cv-cancel-url="…">`, navigated by
`viewset.js` [VERIFIED: src/crud_views/static/crud_views/js/viewset.js:37-44]; `form:cancel-tag` is
`"button"` by default [VERIFIED: src/crud_views/lib/button_classes.py:92].
**How to avoid:** this is the existing behavior of every form in the package and matches D-28 as written.
State it in the guide; the no-JavaScript acceptance item concerns submission from the source.

### Pitfall 11: Translated Guardian check message
**What goes wrong:** the acceptance item "Every deliverable in section 7.8 exists" requires a German
translation of the Guardian warning, but no check message in the repository is translated today
[VERIFIED: no `gettext` import in `src/crud_views/checks.py`, `src/crud_views_guardian/checks.py`,

**How to avoid:** use `gettext` (not lazy) inside the check function, add the entry to
`src/crud_views_guardian/locale/de/LC_MESSAGES/django.po`, compile with polib. `tests/test1/test_i18n.py`

### Pitfall 12: Test ViewSets and goldens

**How to avoid:** declare dedicated ViewSets in a new `tests/test1/app/views_bulk.py` over the existing

## Open Questions (RESOLVED)

All five questions are answered: the first three by the maintainer in `06.41-CONTEXT.md` ("Resolved after
research", D-29 to D-31), the last two by the phase plans. No question is open.

1. **Which leaf renders toolbar buttons (D-19)?**
   - What we know: no existing leaf renders a native `formaction` submit under a `bulk` class key; the form
     leaf works unchanged with `form:submit` styling; a new leaf gives bulk-specific styling at the cost of
     one leaf path and three keys.
   - What's unclear: whether "existing button leaf" or "one button class key [of the bulk location]" matters
     more to the maintainer.
   - Recommendation: Option A; confirm with the maintainer before the toolbar plan runs. The backend,
     checks, review page, example app and guide do not depend on the answer.
   - **RESOLVED (D-29):** Option A. Toolbar buttons render through the existing form leaf
     `crud_views/tags/button/form.html` unchanged, as the `submit` kind with the `form:submit` class and the
     label mode stamped from the `bulk` floor. No bulk leaf and no bulk button class key is added.

2. **Are template-facing helper names part of the stable surface?**
   - What we know: templates cannot read underscore names, so the toolbar needs names such as
     `cv_bulk_form_id` and `cv_bulk_buttons`, and the review needs `bulk_review` (with `objects`, `blocked`,
     item `pk`, `label`, `reasons`). D-15 does not list them. `stability.md` calls undocumented context
     variables internal.
   - Recommendation: document `bulk_review` and its fields in the guide as the override contract of the two
     D-24 snippets (a theme that overrides them must read something); keep `cv_bulk_form_id` and
     `cv_bulk_buttons` undocumented and internal. Ask if in doubt, because Phase 7 freezes the list.
   - **RESOLVED (D-30):** only `bulk_review` with `objects`, `blocked` and per item `pk`, `label`, `reasons`
     is documented and listed as stable. `cv_bulk_form_id` and `cv_bulk_buttons` stay undocumented and
     internal.

3. **How does the header show the action label (D-20)?**
   - What we know: `cv_header` renders `cv_header_template(_code)` with `cv_get_meta()`; `viewset.E110`
     requires one of the two to be set; `cv_get_action_label(context)` takes an argument and cannot be called
     from template code.
   - Options: (a) override the `cv_header` property to return `self.cv_get_action_label(self.cv_get_view_context())`
     and keep a default `cv_header_template` snippet so `E110` passes; (b) a read-only property used by a
     default `cv_header_template_code` (spike used `{{ view.cv_bulk_header }}`: `header: Archive selected`).
   - Recommendation: (b) with one extra template-facing name, because the standard header pipeline stays
     intact and a developer can still set `cv_header_template_code`. Same caveat as question 2.
   - **RESOLVED (D-31):** option (b). The read-only property `cv_bulk_header` is used by a default
     `cv_header_template_code`; `cv_header` is not overridden.

4. **Default paragraph text and context actions of the review page.**
   - What we know: `viewset.E110` also requires a paragraph; `CustomFormNoObjectView` inherits
     `cv_context_actions = crud_views_settings.create_context_actions`, whose default is `["home", "create"]`

   - Recommendation: a `snippets/paragraph/bulk.html` default, and `cv_context_actions = ["home"]` on the

   - **RESOLVED (plan 06.41-01, task 06.41-01-01):** the recommendation is planned as written. The
     destination class sets `cv_paragraph_template` to `crud_views/snippets/paragraph/bulk.html` and

5. **Is the Guardian warning really to be translated?**
   - What we know: section 7.8 and the acceptance list say yes; no other check message is.
   - Recommendation: follow the acceptance list (Pitfall 11).
   - **RESOLVED (plan 06.41-09, task 06.41-09-02):** yes. The collector builds the warning and its hint with

### Applicable ASVS Categories

| ASVS Category | Applies | Standard Control |
|---------------|---------|-----------------|

### Known Threat Patterns for this feature

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Forged `cv_bulk_ids` naming records outside the user's scope (IDOR) | Elevation of Privilege | resolve only through `ViewSet.get_queryset(view) ∩ get_queryset() ∩ _scope_child_queryset`; never a bare manager lookup |
| Direct POST with `cv_bulk_stage=execute`, skipping the review | Tampering | accepted by design (D-05); the same checks run inside the transaction |
| Promoting a blocked record by moving its ID between the two fields | Tampering | reasons and eligibility are rebuilt on the server; nothing posted is trusted |
| Probing for the existence of records | Information Disclosure | identical text and no label for missing, out-of-scope and denied (D-07) |
| Oversized submissions | Denial of Service | count against `cv_bulk_max` before parsing or loading; Django's `DATA_UPLOAD_MAX_NUMBER_FIELDS` |
| Out-of-range or malformed IDs causing a server error | Denial of Service | `BadRequest` (correction 2) |
| Cross-site request forgery on either POST | Spoofing | Django CSRF middleware; token in the toolbar form and the review form |
| Script injection through record names or reasons | Tampering | template autoescaping; `alert_data` escapes items [VERIFIED: src/crud_views/lib/messages.py:35-42] |
| Open redirect through the return URL | Spoofing | URLs are built with `reverse()` plus a signed, bounded query; a bad token falls back to `cv_cancel_key` [VERIFIED: src/crud_views/lib/view/cancel.py:111-148] |
| Object permissions bypassed in a `GuardianViewSet` | Elevation of Privilege | `crud_views_guardian.W002`; documented in `guardian.md` |
| Record changes between check and write | Tampering | the library takes no locks; the guide carries the `select_for_update` recipe |
| Side effects on GET | Tampering | GET only redirects (D-27) |

## Project Constraints (from CLAUDE.md)

- **Developer Maintainability is a hard design constraint.** Prefer the simplest bounded solution; preserve
  proven code paths; prefer self-contained, opt-in additions; account for hidden state, extra abstractions
  and extra queries on existing paths; simplify or narrow when a proposal becomes too complex to explain.
- Commands: `task dev`, `task test` (nox matrix Python 3.12 to 3.15 × Django 4.2, 5.2, 6.0),
  `pytest tests -n auto`, `task format`, `task check`, `task build`, `task docs`.

  so; do not interrupt a running verification to change the worker count.
- Tests live in `tests/test1/`; fixtures are named `cv_<model>`, `user_<model>_<permission>`,
  `client_user_<model>_<permission>`.
- All `CrudView` class attributes use the `cv_` prefix. Permission mapping: list and detail → view,
  create → add, update → change, delete → delete.

- Core must not import Guardian; settings live in `crud_views/lib/settings.py`.

  a feature entry, not a breaking one.

  dropped, so declare the new attributes as plain class attributes.
