### WR-01: Bulk review heading ignores the configured semantic heading level

**Severity:** WARNING

**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/templates/crud_views/snippets/bulk/eligible.html:2`

**Issue:** The new eligible-record snippet emits a literal `<h3>`. The existing heading contract states that content headings follow `CRUD_VIEWS_HEADER_LEVEL` at one level below the page heading, retaining their visual size through the heading class registry (`docs/reference/theme.md:241`; `src/crud_views/templatetags/crud_views.py:385–405`). For a project using a page heading level of 4, the bulk review subsection still renders as h3, incorrectly moving upward in the document outline and bypassing the registered visual class. This affects accessible heading navigation and the supported theme setting, rather than being a preference about appearance.

**Reproduction/evidence:** Initialize Django using `tests.test1.conftest.pytest_configure()`, set the shared `crud_views_settings.header_level` to 4 (the same object the heading tag reads), set `CRUD_VIEWS_BUTTON_CLASSES` to `{"heading:size-3": "theme-size-three"}`, and render the eligible snippet with a review whose `objects` contains one record. Compare it with the existing heading tag around the same text:

```html
<!-- Actual new bulk snippet -->
<h3>To process: 1</h3>
<!-- Existing cv_heading level=3 under the same settings -->
<h5 class="theme-size-three">To process: 1</h5>
```

Both outputs were obtained with the installed Django 5.2 test environment. The settings object was changed in the isolated probe because it captures the configured header level; this is equivalent to starting the application with that header setting.

**Fix:** Load `crud_views` in this snippet and use the existing tag, preserving the default h3 and current translated text:

```django
{% load i18n crud_views %}
{% cv_heading level=3 %}{% blocktranslate with count=bulk_review.objects|length %}To process: {{ count }}{% endblocktranslate %}{% endcv_heading %}
```

Add a focused rendering assertion for an overridden header level and heading size class, alongside the unchanged default heading. No new setting or template API is needed.

### WR-02: Counted bulk messages render plural wording for one record

**Severity:** WARNING

**Files:**

- `/home/alex/projects/alex/django-crud-views/examples/bootstrap5/bulk_selection/views.py:69`
- `/home/alex/projects/alex/django-crud-views/examples/bootstrap5/bulk_selection/views.py:90`
- `/home/alex/projects/alex/django-crud-views/examples/bootstrap5/bulk_selection/views.py:122`
- `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/bulk/__init__.py:349`

**Issue:** The example destinations override the correctly pluralized core success message with fixed plural strings. Selecting one eligible document is supported, including when other selected records are blocked, but the resulting messages are grammatically incorrect. The core oversize-selection warning has the same defect when the valid configured `cv_bulk_max` is 1. Catalog synchronization alone does not correct it because the strings have no count-based singular/plural alternatives.

**Reproduction/evidence:** With `PYTHONPATH=src:examples/bootstrap5:.` and `DJANGO_SETTINGS_MODULE=project.settings`, initialize Django, import the three example destination classes, and render each `cv_message_template_code` through `django.template.Template` with `view.cv_bulk_objects=(object(),)`. The executed probe produced:

```text
DeleteDocumentsView: 1 documents deleted.
ArchiveDocumentsView: 1 documents archived.
AssignOwnerView: Owner assigned to 1 documents.
```

For the warning, set a destination's `cv_bulk_max` to 1 and POST two IDs with `cv_bulk_stage=review`. The fixed plural expression at line 349 produces `Select at most 1 records.` Existing `tests/test1/test_bulk_return.py:238–240` explicitly asserts that incorrect sentence, so the current return-path coverage preserves the defect rather than detecting it.

The example literals were prescribed by plan 11 and its translation work; this is a copy defect carried from the plan, not evidence that the implementation deviated from it. Fixing singular forms does not change the approved interaction or message lifecycle.

**Fix:** Give the three application-owned success messages count-aware singular/plural templates, using `{% blocktranslate count count=view.cv_bulk_objects|length %}…{% plural %}…{% endblocktranslate %}` in small message templates, or an equivalent existing message hook with `ngettext`. Change the core limit warning to:

```python
ngettext(
    "Select at most %(max)d record.",
    "Select at most %(max)d records.",
    self.cv_bulk_max,
) % {"max": self.cv_bulk_max}
```

Synchronize the example guide snippets and affected PO/MO catalogs. Assert singular and plural output in English and German for both example success messages and the configured limit warning; update the existing assertion that pins the incorrect singular sentence. Preserve the default core success template and current execution/message lifecycle.
