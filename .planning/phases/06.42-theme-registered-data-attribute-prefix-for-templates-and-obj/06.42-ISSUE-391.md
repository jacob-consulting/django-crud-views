## Problem / motivation

Four shipped templates and one script write Bootstrap's data-API attribute prefix literally:

| File | Attributes |
|---|---|
| `crud_views/templates/crud_views/tags/actions_menu_toggle.html` | `data-bs-toggle="dropdown"`, `data-bs-popper-config` |
| `crud_views/templates/crud_views/snippets/language_selector.html` | `data-bs-toggle="dropdown"` |
| `crud_views_object_detail/templates/crud_views_object_detail/layouts/tabs-vertical/object_detail.html` | `data-bs-toggle="pill"`, `data-bs-target` |
| `crud_views_object_detail/templates/crud_views_object_detail/layouts/accordion/group.html` | `data-bs-toggle="collapse"`, `data-bs-target`, `data-bs-parent` |
| `crud_views_object_detail/static/crud_views_object_detail/js/tabs.js` | trigger selector `[data-bs-toggle="tab"\|"pill"\|"list"]` |

A theme built on a Bootstrap fork that renamed its data API (CoreUI 5 reacts only to `data-coreui-*`) gets row
menus, the language selector, vertical tabs and accordions that silently do nothing. A downstream CoreUI theme works around
it today with four template copies that differ from upstream only in the prefix (drift-tested), its own
`coreui-tabs.js` plus a wrapper around `cv.initObjectDetailTabs`, and an app-order system check,
because the copies only win when the theme is listed before `crud_views` / `crud_views_object_detail` in
`INSTALLED_APPS` (tracker U11).

Goal: a theme sets the prefix once and needs none of those copies. Stock Bootstrap output stays byte-identical.
Developer maintainability is a hard constraint: this stays on the UI library's own data API and the proven
`tabs.js` path; it adds no adapter-driven initialization and no Django setting.

## Proposed solution

One theme-registered data-attribute prefix (default `bs`), read by a template tag in the four templates and by
`tabs.js` through `#cv-config`. The approved contract is recorded in `gsd-handover` below.

## Alternatives considered

1. **Prefix for templates and `tabs.js` (U1 + U2) — selected by the maintainer.** Removes every CoreUI override and
   script for this gap, keeps Bootstrap's data API and the existing tabs contract.
2. **Prefix for templates only (U1).** Smaller, but the theme keeps `coreui-tabs.js` and its
   `cv.initObjectDetailTabs` wrapper, the most delicate part of the workaround.
3. **crud_views-owned markers (`data-cv-*`) initialized through `cv.adapters` (U1 + U2 + U3).** Library-neutral,
   but moves dropdowns and accordions off the data API on the stock theme, needs a new dropdown adapter and
   re-implements accordion parent behaviour — changes proven paths. Not selected.
4. **Bundle U8, a `register_theme()` helper.** The tracker suggested filing it with U1. Not selected: it fixes no
   defect (the browser pass found every registration working), adds a pre-1.0 public API whose shape (parameters,
   relation to the five existing calls, workflow filtering) would need its own decisions, and U1 does not depend on
   it. Revisit when a third theme exists or a registration bug appears.

## gsd-handover

Carry these approved decisions and the acceptance criteria into GSD planning. Filing this issue does not create a
phase, schedule work, or authorize implementation.

### D-01 — Bounded scope: U1 + U2

Make the data-attribute prefix configurable for the four templates and `tabs.js` listed above, nothing more.
Out of scope: app-owned `data-bs-*` markup (e.g. host-app `[data-bs-toggle="tooltip"]`, which `tooltip.js`
deliberately leaves alone), a dropdown adapter (U3), the adapter namespace (U4), `--bs-*` CSS properties (U5),
a `register_theme()` helper (U8), and crispy-bootstrap5 (U6, third party). No new Django setting.

### D-02 — Registration API

`register_data_prefix(prefix: str)` in `crud_views.lib`, called from a theme's `AppConfig.ready()` next to
`register_button_classes()` / `register_icon_library()`. Default `bs`. The name was proposed by the assistant and
approved with the design.

- The prefix follows the theme's JS library, so there is no `CRUD_VIEWS_*` setting and no project-level override.
- Validation at call time: lowercase name matching `^[a-z][a-z0-9]*(-[a-z0-9]+)*$` (e.g. `bs`, `coreui`); anything
  else raises. Exact exception type is the builder's call, consistent with the other `register_*` functions.
- Repeated calls: last call wins, like the other registries; document it.

### D-03 — Templates

A simple tag `{% cv_data_prefix %}` (in the `crud_views` library) returns the registered prefix. The four templates
write `data-{% cv_data_prefix %}-toggle`, `-target`, `-parent`, `-popper-config`. A tag rather than a context
variable, because it works identically in inclusion-tag contexts and in separately rendered object-detail groups.

- With the default prefix every rendered page is byte-identical to today (existing golden tests unchanged).
- Update the two layout-pack recipes in `docs/reference/object_detail_layout_packs.md` (tabs-vertical, accordion) and
  the `actions_menu_toggle` example in `docs/reference/action_menus.md` to use the tag; mention it where
  `docs/reference/theme.md` and `docs/reference/buttons.md` name `data-bs-toggle`.

### D-04 — `tabs.js` and `#cv-config` (U2)

`cv_config.html` gets one attribute on `#cv-config`, `data-data-prefix` (exact attribute name is the builder's call)
carrying the registered prefix. `tabs.js` builds its trigger selector from it at each `initObjectDetailTabs` /
dispose call, not at script load (the config element may follow the script), falling back to `bs` when
`#cv-config` or the attribute is absent.

Everything else in the documented tabs contract (`docs/reference/javascript.md`, "Object-detail tabs";
`object_detail_layout_packs.md`) is unchanged: only `data-cv-od-tabs` tablists, marked root and nested-tablist
boundaries respected, repeat-safe, init on DOMContentLoaded / ready document / `cv:modal:loaded`, dispose on
`cv:modal:unload`, missing adapter or `Tab` is a no-op, malformed adapter entries throw, no show / focus.

### D-05 — Acceptance and documentation

- Default prefix: existing Python, golden and JS tests pass unchanged.
- With `register_data_prefix("coreui")`: the four templates render `data-coreui-*` and no `data-bs-`;
  `#cv-config` carries `coreui`; `tabs.js` (vitest) initializes `data-coreui-toggle="pill"` triggers inside
  `data-cv-od-tabs` and ignores `data-bs-*` ones.
- Invalid prefixes are rejected with a test per rule.
- Docs: a theme reference section on the prefix (when a fork needs it, the one-line call); CHANGELOG `### Added`
  entry. Not breaking, so `docs/migrating-1.0.md` is untouched.
- Downstream note, not upstream work: once released, the CoreUI theme can delete its four overrides,
  `coreui-tabs.js` with its `cv.initObjectDetailTabs` wrapper, and its app-order system check (U11).

### Left to the builder

Module placement of `register_data_prefix`, exception type, the `#cv-config` attribute name, test file layout.
