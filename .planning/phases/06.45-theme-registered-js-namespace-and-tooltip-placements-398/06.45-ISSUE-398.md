# Issue #398: Theme-registered JS namespace and tooltip placements (U4)

Source: https://github.com/jacob-consulting/django-crud-views/issues/398
Captured: 2026-11-21

**Date:** 2026-11-21
**Status:** design approved by the maintainer on 2026-11-21; issue handover, not implementation authorization.
**Scope:** CoreUI theme upstream finding U4 (default adapter namespace fixed to `globalThis.bootstrap`) together with
the tooltip placement wrapper that keeps a theme script alive next to it. U3 and U8 are explicitly out of scope.
This document does not schedule a phase or authorize product implementation.

## Problem / motivation

`cv.adapters` defaults to `cv.bootstrapAdapters(() => globalThis.bootstrap)`
(`src/crud_views/static/crud_views/js/adapters.js`). A theme built on a Bootstrap fork that exposes its components
under another global (CoreUI 5: `window.coreui`; Tabler: `window.tabler`) ships its own script just to repoint the
namespace, loaded after `adapters.js` and before first use:

```js
Object.assign(cv.adapters, cv.bootstrapAdapters(() => globalThis.coreui));
```

Both downstream themes (CoreUI and Tabler) also wrap `cv.adapters.tooltip.init` in that same script, identically
except for the attribute name: toolbar tooltips (`location === "context"`) open below the buttons so they do not
cover the page header, unless the trigger sets its own placement:

```js
const init = cv.adapters.tooltip.init;
cv.adapters.tooltip.init = (el, options = {}) => {
    if (options.location === "context" && !el.hasAttribute("data-coreui-placement")) {
        el.setAttribute("data-coreui-placement", "bottom");
    }
    init(el, options);
};
```

`tooltip.js` already passes `{location}` to `tooltip.init`; the stock adapter ignores it. The wrapper has to know the
library's data-attribute name (`data-coreui-placement`, `data-bs-placement`), so a namespace value alone would not
remove the theme script.

Goal: a theme registers its namespace and its tooltip placements in `AppConfig.ready()` and ships no adapter
script. Stock Bootstrap behaviour is unchanged.

## Proposed solution

Two theme registrations, both carried to the browser in `#cv-config` next to the data prefix from #391, and read by
`adapters.js` at call time. The approved contract is recorded in `gsd-handover` below.

## Alternatives considered

1. **The theme registers placements per location — selected by the maintainer.** Stock Bootstrap keeps its default
   placement; a theme states what it wants in one call; the per-trigger attribute still wins.
2. **Upstream makes "context → bottom" the default for every theme.** No new API, but stock Bootstrap toolbar
   tooltips would move, which breaks the "stock unchanged" rule #391 kept. Not selected.
3. **Namespace only, placement stays in the theme.** Smallest change, but the theme script remains, so the goal is
   missed. Not selected.
4. **Bundle U8, a `register_theme()` helper.** Not selected, same reasons as in #391; this adds two more
   registrations, so revisit U8 when a third theme exists.

## gsd-handover

Carry these approved decisions and the acceptance criteria into GSD planning. Filing this issue does not create a
phase, schedule work, or authorize implementation.

### D-01 — Bounded scope

Namespace registration and per-location tooltip placements, nothing more. Out of scope: a dropdown adapter (U3), a
`register_theme()` helper (U8), app-owned `[data-bs-toggle="tooltip"]` markup (left to the host app, as
`tooltip.js` documents), any change to the five adapter entries other than `tooltip.init` and the namespace
resolver. No new Django setting: both values follow the theme's JS library, like the data prefix.

### D-02 — `register_js_namespace(name: str)`

In `crud_views.lib`, next to `register_data_prefix()`. Default `bootstrap`. The value is the name of the global the
library's bundle defines (`coreui`, `tabler`). It stays separate from the data prefix: the two differ for Bootstrap
(`bs` / `bootstrap`) and only coincide for CoreUI.

- Validation at call time: a plain JS identifier, `^[A-Za-z_$][A-Za-z0-9_$]*$`; anything else raises `ValueError`
  without changing the previous registration (same contract as `register_data_prefix`).
- Repeated calls: last valid call wins.

### D-03 — `register_tooltip_placements(placements: dict[str, str])`

In `crud_views.lib`. Maps a `data-cv-tooltip` location (the values `tooltip.js` documents: `context`, `list`,
`card`, `card-order`, `formset`, `object-detail`, `form`, and `""` for a bare marker) to a placement (`top`,
`bottom`, `left`, `right`, `auto`). Default `{}`: no placement is set and the library default applies.

- Validation at call time: unknown location or placement raises `ValueError`, previous registration unchanged.
- Repeated calls: the last valid call replaces the whole mapping (no merge); document it.
- CoreUI and Tabler call `register_tooltip_placements({"context": "bottom"})`.

### D-04 — `#cv-config` and `adapters.js`

`cv_config.html` gets two attributes, emitted always like `data-data-prefix`: the namespace and the placements as
JSON (exact attribute names are the builder's call).

- **Namespace:** the stock adapters resolve the namespace on every call, from `#cv-config` when the element and
  attribute are present, else `bootstrap`. Reading at call time, not at script load, keeps the existing guarantees:
  the config element may follow the script and the bundle may load deferred. A theme that still assigns
  `cv.adapters` entries itself keeps working (today's `Object.assign` pattern is unchanged).
- **Placement:** `tooltip.init(el, {location})` looks the location up in the registered mapping. With a match, and
  when the trigger has no `data-{prefix}-placement` attribute (prefix from #391's `data-data-prefix`, fallback
  `bs`), it passes `{placement}` to `Tooltip.getOrCreateInstance(el, …)`. Without a match it behaves exactly as
  today. The transition guard and `hide` / `dispose` are unchanged. Missing or malformed JSON is treated as `{}`.
- Whether placement is applied through the instance config or by setting the data attribute is the builder's call,
  as long as an explicit attribute on the trigger wins.

### D-05 — Acceptance and documentation

- Defaults: existing Python, golden and JS tests pass; stock Bootstrap tooltips and adapters behave as today.
- Python: validation tests per rule for both functions; `#cv-config` renders the registered values.
- vitest (`tests/js/adapters.test.js`, `tooltip.test.js`): namespace resolved from `#cv-config` at call time (config
  inserted after script load counts), fallback to `bootstrap`; placement applied for a registered location, not for
  an unregistered one, not when `data-{prefix}-placement` is present (checked with prefix `bs` and `coreui`).
- Docs: `docs/reference/theme.md` (a fork's two calls, replacing the adapter-script recipe), the adapter section of
  `docs/reference/javascript.md`; CHANGELOG `### Added`. Not breaking, so `docs/migrating-1.0.md` is untouched.
- Downstream note, not upstream work: once released, the CoreUI theme deletes `coreui-adapters.js` and its asset
  bundle registration and adds the two calls; the Tabler theme can do the same with `tabler-adapters.js`.

### Left to the builder

Module placement of the two functions, the `#cv-config` attribute names, how placement reaches the library (config
vs. attribute, see D-04), test file layout.
