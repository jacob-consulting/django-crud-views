# Issue #399: Bulk toolbar: show only the actions the viewer can enter (C10, amends #387 D-03)

**Source:** https://github.com/jacob-consulting/django-crud-views/issues/399
**Captured:** 2026-11-21
**State at capture:** OPEN

**Date:** 2026-11-21
**Status:** design approved by the maintainer on 2026-11-21; issue handover, not implementation authorization.
**Scope:** theme-tracker finding C10 (AdminLTE and CoreUI demos): the bulk toolbar offers actions the viewer cannot
enter. This amends decision D-03 of #387. C11 (danger variant for bulk buttons) is out of scope.
This document does not schedule a phase or authorize product implementation.

## Problem / motivation

`BulkSelectionMixin.cv_bulk_buttons` renders every key in `cv_bulk_actions`. The destination's permission is first
checked on submission. In the Acme Roasters demo, Kim (group Roasters: `roast_order`, no `change_order`) sees
"Cancel orders" on `/orders/`, selects orders, presses it and gets a 403.

This is the documented contract, not a defect: #387 D-03 says "Show every action configured for that source.
Rendering the toolbar performs zero bulk-permission queries and never scans the page for an eligible record", and
`docs/reference/bulk_actions.md` repeats it. Every other control of the package follows the destination's
`cv_has_access` and `cv_action_enabled` when it renders; the bulk toolbar is the one exception.

Bulk actions (#387, PR #392) are unreleased, so the contract can still change without a migration.

Goal: the toolbar offers an action only when the viewer can enter its destination. The part of D-03 that protects
list rendering stays: no page scan, no per-record check.

## Proposed solution

The source evaluates each configured destination's own entry gate once per request (model permission, then state
hook) and renders the actions that pass. A source with no action left renders as if it had none configured. The
approved contract is recorded in `gsd-handover` below.

## Alternatives considered

1. **Filter by default, with the rule every other button uses — selected by the maintainer.** No new public name;
   a destination with a custom gate overrides `cv_has_access`, as it already must for its context buttons.
2. **The same plus an opt-out flag on the source.** One more name frozen at 1.0 for a case 1 covers. Not selected.
3. **Model permission only, ignoring `cv_action_enabled`.** A destination disabled by its state hook would stay
   visible and answer 403. Not selected.
4. **Opt-in flag, D-03 stays the default.** Considered first, for fear the check could hide a usable action under
   Guardian. Dropped: a bulk destination is the core class in a `GuardianViewSet` too, its entry gate is the model
   permission, and object grants only enter through `cv_bulk_has_permission` on submission.
5. **Hide an action when no record on the page is eligible.** Needs a per-row check on every list render, which
   D-03 rules out for good reason. Not selected.

## gsd-handover

Carry these approved decisions and the acceptance criteria into GSD planning. Filing this issue does not create a
phase, schedule work, or authorize implementation.

### D-01 — Amendment of #387 D-03, bounded

Replaced: "Show every action configured for that source" and "zero bulk-permission queries", together with D-19's
note that bulk buttons must not pass through an access check while rendering. Kept unchanged: no scan of the page
for eligible records, no call of `cv_bulk_has_permission` or `cv_bulk_check` while rendering, no object-permission
(Guardian) check while rendering, and everything D-03 says about submission. The destination remains the only
authority: a direct POST by a user who cannot enter still gets the ordinary permission response.

### D-02 — The rule

An action is offered when its destination passes, for `request.user`, in this order:

1. `cv_has_access(user, None)`;
2. the state hook through `_cv_action_enabled_for_rendering(user, action_obj, source_view)`, where `action_obj` is
   `None`, or the parent object when the ViewSet has a parent. The state hook runs only after access has passed.

This is what `_cancel_target_available` in `lib/view/base.py` already does for a non-object destination; reuse or
share that logic rather than writing a third variant. A hidden action leaves no markup (no disabled button).
The configured order is kept.

### D-03 — One effective list per request, no new public name

The source computes the offered actions once per request. Every consumer reads that one result: `cv_bulk_buttons`,
the `{% if view.cv_bulk_actions %}` tests in `view_list_table.content.html` and `view_card.content.html`, the card
checkbox cell, and the `cv_bulk_select` column in `get_table_kwargs`. The class attribute `cv_bulk_actions` stays
the configured tuple, and the system checks (`E271` to `W275`) keep reading it. The per-request list is private:
this issue adds no public attribute, setting or flag.

With no action left, the page renders exactly as a source with `cv_bulk_actions = ()`: no toolbar, no select
column, no card checkboxes. An empty page with at least one offered action keeps its toolbar, as today.

### D-04 — Custom gates and what the toolbar does not promise

A destination that overrides `has_permission` more generously than its model permission must also override
`cv_has_access`; this is the existing contract for context and list buttons and now applies to the toolbar.
Document it in the bulk reference. There is no opt-out.

The toolbar is a display rule, not authorization. An offered action can still be refused on submission, for example
by a farther ancestor's write rule; a user with the model permission but no object grant on any selected record
gets the all-blocked review. Both are unchanged.

### D-05 — Cost

One `cv_has_access` and at most one state-hook call per configured action per request; nothing per row. On a
top-level source this adds no SQL (Django caches the user's permissions): the existing comparison of query counts
with and without `cv_bulk_actions` stays and must still pass. For a nested source, report the measured count in
the plan; it must not grow with the number of rows or actions.

### D-06 — Acceptance and documentation

- `tests/test1/test_bulk_source.py`: `test_table_page_renders_actions_without_permission_work` and its card twin
  are rewritten: item hooks must still not run, `cv_has_access` now runs once per action, query counts stay equal.
- New, for table and card: a user lacking one destination's permission sees the others, in configured order; a
  user lacking all sees no toolbar, no select column and no checkbox, byte-identical to `cv_bulk_actions = ()`;
  a destination whose `cv_action_enabled` returns `False` is hidden; in a nested ViewSet the state hook receives
  the parent; an overridden `cv_has_access` is honoured.
- Unchanged and still passing: admission, scope, review and execution tests, including the 403 for a direct POST.
- Docs: `docs/reference/bulk_actions.md` (the sentence in "Selection on tables and cards", and the scope and
  permissions section with D-04's two paragraphs), the bulk section of `docs/reference/guardian.md` (the model
  permission decides visibility; object grants are not consulted while rendering). CHANGELOG: amend the unreleased
  #387 entry. No `docs/migrating-1.0.md` entry, because the feature is unreleased.
- Downstream note, not upstream work: in the AdminLTE and CoreUI demos Kim no longer sees "Cancel orders"; the
  direct-POST test `test_roasters_may_not_cancel` keeps passing.
