# Cross-AI Plan Review — Phase 06.46

Both plans are sound in their core mechanism, but neither is ready to execute as written. Plan 01 breaks two in-repo example tests that no task owns and no gate runs. Plan 02 breaks a registry inventory test that its own task does not run.

I read the source directly and ran no tests or builds. Every claim below about runtime behaviour is traced from code, not observed. I could not read the installed Guardian or Django packages (outside the allowed directory), so two points are marked as open questions.

## 06.46-01

### Summary

The plan filters bulk actions through the existing Cancel gate, caches the result per view instance, and bridges it to templates through a context key. The mechanism is correct and small. The gaps are an unowned regression in the Bootstrap example, an unresolved template contract for theme overrides, and an unqualified SQL claim.

### Strengths

- **The gate is the right one.** `_cancel_target_available` checks access first, short-circuits on denial, and passes the parent to a non-object nested destination (`src/crud_views/lib/view/base.py:76-88`). Bulk destinations declare `cv_object = False` (`src/crud_views/lib/bulk/__init__.py:207`), so they take exactly the D-02 branch.
- **Calling the module function directly loses nothing.** The `_cv_cancel_target_available` overrides live only on Guardian mixins (`src/crud_views_guardian/lib/mixins.py:115-119`, `257-262`, `439-461`). A core bulk destination does not inherit them.
- **Nested parent lookup adds no query.** `_cv_cancel_parent_object` (`base.py:976-988`) calls `cv_get_parent_object`, which reuses the parent the ancestor guard already resolved (`base.py:1177-1182`).
- **Either consumer can run first.** The mixin sits before `ListViewTableMixin`, and the context chain is cooperative (`src/crud_views/lib/views/mixins.py:269-270`, `337-338`), so a lazy cached property is the right shape. `cached_property` on a view has precedent (`base.py:1223`).
- **The test blast radius inside `tests/test1` is correctly scoped.** `test_bulk_source.py` is the only module there that expects a view-only actor to see the toolbar. The flow, return, i18n, execution and scope modules use change-capable clients on change-gated actions (for example `tests/test1/test_bulk_flow.py:322-323` grants the change permission explicitly).
- **The fixture choice is right.** The delete client inherits change and adds delete (`tests/test1/conftest.py:329-367`), matching the four table actions.

### Concerns

- **HIGH — Two in-repo example tests encode the old contract and will fail; no task owns them and no gate runs them.**
  - `examples/bootstrap5/bulk_selection/tests.py:88-100` (`test_view_only_user_sees_toolbar_but_cannot_enter_actions`) reads each button's `formaction` through `self.destination()`, which indexes `[0]` at line 48.
  - `examples/bootstrap5/project/test_developer.py:51-68` does the same at line 65 for the view-only developer account.
  - After task 01-01 both raise `IndexError`, because the buttons are gone.
  - These run in the `examples` nox session (`noxfile.py:208-219`), not under `pytest tests`.
  - Plan 01's `files_modified` (`06.46-01-PLAN.md:7-11`) and plan 02's final gate (`06.46-02-PLAN.md:202`) both miss them.
  - D-06 excludes the downstream AdminLTE/CoreUI demos, not this upstream example.

- **MEDIUM — The context key is called private, but theme overrides must use it, and nothing tells them so.**
  - The guide tells authors that an overridden list or card content template must include the toolbar snippet (`docs/reference/bulk_actions.md:89-91`). The snippet is in the stable override contract (`docs/development/stability.md:81-82`).
  - An override that copies today's `view.cv_bulk_actions` guard, or includes the toolbar unconditionally, will render an empty toolbar form and card checkboxes for a viewer with no offered action. The table select column disappears, because `get_table_kwargs` reads the cached tuple.
  - That is the D-03 inconsistency, on the kind of theme that raised C10.
  - The plan labels the key "private implementation plumbing" (`06.46-01-PLAN.md:75`, `:99`). Task 02-03 (`06.46-02-PLAN.md:159`) does not say which condition an override should test.
  - The key also shares its spelling with the class attribute. `cv_bulk_actions` (effective) and `view.cv_bulk_actions` (configured) would sit in one template namespace with different meanings.
  - The bridge is also a second channel that can drift. A render path that skips the mixin's `get_context_data` gets a select column without a toolbar. `tests/test1/test_bulk_flow.py:433-437` already renders the content template from a hand-built context.

- **LOW — "Top-level SQL stays equal" is stated without its precondition** (`06.46-01-PLAN.md:25`).
  - `cv_has_access` ends in `user.has_perms` (`base.py:1341`). It is free only if something earlier in the request loaded the user's permissions.
  - E273 allows a source with no permission check of its own (`bulk/__init__.py:59-64`); the checks fixture builds one from plain `ListView` (`tests/test1/test_bulk_checks.py:53-55`).
  - On such a page I expect the first gate call to load the permission cache: a constant cost, not per row or action. This is inferred from Django's backend, not measured.
  - Open question: whether Guardian's backend looks up its anonymous user on a model-level check. The test project sets `ANONYMOUS_USER_NAME=None` (`tests/test1/conftest.py:128`), so its tests could not show it.

- **LOW — Per-class spies will double-count.** `BulkPublisherArchiveNowView` and `BulkPublisherRenameView` subclass `BulkPublisherArchiveView` (`tests/test1/app/views_bulk.py:253`, `269`, `235`). If the base is patched first, the "original" captured for a subclass is the base spy. One call then records twice and breaks "exactly one access per key" (`06.46-01-PLAN.md:101`).

### Suggestions

- Add both example test files to task 01-01. Rewrite them to assert the buttons are absent for the view-only actor, then POST to the reversed destination URL and keep the 403 assertion. Add the examples suite to the phase gate.
- Decide the template contract explicitly. Two workable options:
  - Keep the bridge, give it a name distinct from the class attribute, and document the guard in the paragraph at `bulk_actions.md:89-91`.
  - Drop the bridge: make `cv_bulk_buttons` a cached property and guard the three template conditions on `view.cv_bulk_buttons`. That uses a name the stock snippet already reads, needs no `get_context_data` override, and leaves one channel. I lean towards this one under the maintainability rule.
- Qualify the SQL claim to permission-required sources, or add one test on a plain `ListView` source and record the number.
- Capture all original hooks before patching any class, or spy once on the shared base and key by `cls`.

### Risk Assessment

**MEDIUM.** The product change is small and reversible, and the mechanism is verified. The risk is in what the plan does not touch: a deterministic example-suite failure and an undocumented template contract for themes.
