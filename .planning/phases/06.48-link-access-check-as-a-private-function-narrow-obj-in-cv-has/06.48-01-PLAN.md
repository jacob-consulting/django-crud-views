## Known limits this plan freezes (pre-existing, not changed in stage 1)

Two mechanisms exist on the unchanged tree and stay as they are in this phase: changing either would change a
rendered result (issue #407 acceptance rule "the rendered result is the same as before"), and the maintainer
decided on 2026-11-23 to keep both in stage 1 (D-34 for L1, D-35 for L2; `06.48-CONTEXT.md`, "Known limits kept
in stage 1"). This plan freezes today's answer of each, so that plans 02 to 07 cannot move it unnoticed. Plan 02
states both in full.

- **L1, the list-page overwrite, D-34** (`src/crud_views_guardian/lib/mixins.py` lines 328 to 356 at `dbf1e6c4`). On a
  nested Guardian list page, `GuardianQuerysetMixin.cv_get_context` resolves the key of every context action that
  has no object against the page's own ViewSet: the `key_target` of the configured button when it has one, else
  the action key. When that key is registered there as a Guardian create, `cv_access` and `cv_action_enabled` are
  replaced by the result for the page's own create. The condition does not look at the button class. A
  `ParentContextButton(key_target="create")` on a grandchild list page, and a `SiblingContextButton` configured
  under the action key `create`, therefore show the page's own create result, while URL and label stay those of
  the button's real target.
- **L2, the actor rule on a nested Guardian create under a model-provider parent, D-35**
  (`src/crud_views_guardian/lib/views.py` lines 339 to 344 and 382 to 385, `src/crud_views/lib/viewset/__init__.py`
  lines 507 to 509 at `dbf1e6c4`). The link is answered by Guardian's inactive-actor rule and the parent provider.
  A core parent answers `user.has_perm`, so an anonymous actor is denied unless an authentication backend grants
  the parent permission to anonymous users; then the link shows, and the request refuses the click.

Create `tests/test1/test_link_access_matrix.py`. It records, for one cell at a time, what the user would see, as one of four strings: `hidden`, `enabled`, `disabled:permission`, `disabled:state`. The private helper `_outcome(raw)` produces that string from a ctx dict by calling `cv_resolve_action`: `None` gives `hidden`, a dict with `cv_disabled` true gives `disabled:` followed by its `cv_disabled_reason`, any other dict gives `enabled`. A navbar child item has no ctx dict; its outcome is `enabled` when the item is present in the built navbar data and `hidden` otherwise. Match the child item itself: the bar of `permission_routes` also holds an owner item, so an empty or non-empty bar says nothing about the child item. An exception is never an outcome (addresses review concern A2-01): `_outcome` catches nothing, so a cell that raises stops the capture run and fails the committed test with its traceback. No scenario of this matrix expects an exception. If a cell raises on the unchanged tree, do not freeze it: repair the scaffold when that is the cause, otherwise stop and return a checkpoint that names the case id and the exception. The allowed values of `cells` are therefore a closed set: the four outcome strings, `True` and `False` (the filter cells of task 02), and `page:` followed by a three-digit status code. URLs and primary keys are never part of the outcome.

A case id is the string `control/composition/page/target/actor/state/mode` (section "Case ids and cell counts" above). The private helper `_case_id` builds it from its seven parts and is the only place that joins them.
