## Decisions taken by this plan (concept 12.5, "open for the planner")

- **Name, module, signature.** `_link_access` in the new module `src/crud_views/lib/link_access.py`. A new module
  keeps the two gate modules byte-identical, which turns D-14 into a one-line `git diff` check. The signature is
  the interface of concept 5.1 and nothing more: the target class, the user, the target's own object, the known
  ancestors nearest first, and one optional keyword for the rendering view. There is no keyword that switches
  parent gating off: under D-31 no stage-1 call site needs one, so D-16 holds for every target.
- **How step 2 is satisfied for the nested Guardian create (D-32, locked by the maintainer).** The function asks
  the target class for the nearest parent gate and own permission through one private classmethod,
  `_cv_link_permission`. Its `obj` is only ever the target's own object; the parent arrives separately. A nested
  Guardian create answers it with `cv_create_has_access(user, rendering_view, parent)` and nothing else: package
  links do not call `cv_has_access` on a nested Guardian create. `cv_has_access(user, None)` stays `False`.
  Consequence for projects, carried to the Breaking entry in plan 08: an override of `cv_has_access` on a nested
  Guardian create no longer affects package links; the rule belongs in `cv_create_has_access`.
- **Why a per-target seam, measured against the maintainability rule.** The three definitions of the child-link
  adapter are three different rules, and two of them belong to Guardian (a stricter actor rule, and the
  queryset-only exception). The seam keeps each rule in the class that owns it today and replaces the adapter one
  for one, with a corrected contract. Core names no Guardian hook. One place states the order.
- **Where the rendering view goes (D-17).** The function hands it to exactly one callee, the target's
  `_cv_link_permission`. Of its three implementations only the nested Guardian create uses it, for
  `cv_create_has_access`, the one hook that already accepts a view. `_higher_ancestor_gates` takes no view and
  calls the provider with `view=None`, as `_immediate_parent_access` does today for a child link. The first draft
  forwarded the view to that provider call; that is removed.
- **The `rendering_view` each site hands over.** Each site keeps what the provider call receives today, so no
  Guardian checker and no access-trace owner changes: nothing at the navbar (and, in plan 04, at the child button
  and the card child action; in plans 05 and 06, at pages of the target's own ViewSet), the list view on the
  nested Guardian list page.
- **Deferred half of D-04.** Filling the ancestor list from the higher ancestors the request resolved waits for
  stage 2 or 3 (D-26). The function already gates whatever it is handed.

  <action>
Create `src/crud_views/lib/link_access.py`. Follow the header convention of `src/crud_views/lib/ancestor_db.py`: a module docstring that states the rule (parent gates, then own permission, then state; built from the request gate's pieces; private; decides links only, never a request), then `from __future__ import annotations`, then imports. Import the gate module as a module (`from crud_views.lib import ancestors`) and reach every one of its helpers as an attribute of that module at call time, never through a name bound at import; import `_check_nested_auth` from `crud_views.lib.ancestor_db`. Define the three constants `_LINK_ALLOWED`, `_LINK_PERMISSION`, `_LINK_STATE` with the values `"allowed"`, `"permission"`, `"state"`.

`_link_permission(target, user, obj=None, known_ancestors=(), *, rendering_view=None)` answers steps 1 and 2 as a bool, in this order. The target is nested when `target.cv_viewset.has_parent`; a top-level target ignores the list. The parent is `known_ancestors[0]` for a nested target with a non-empty list, else `None`. Per D-16 return `False` when the target is nested and the parent is `None`. This holds for every target, with or without an own object; the function has no keyword that relaxes it (D-31). When the target is nested and more than one ancestor was handed over, return `False` if `_higher_ancestor_gates` does. Then narrow the object per D-11 and D-15: the own object is `obj` when `target.cv_object`, else `None`. Return the bool of `target._cv_link_permission(user, own, parent, rendering_view=rendering_view)`. That call is the only place the function hands the rendering view to (D-17).

`_higher_ancestor_gates(target, user, known_ancestors)` gates the handed levels above the nearest one, as the request does. It takes no view. Take `chain = ancestors._walk_ancestors(viewset)` and `selected = ancestors._selected_gates(viewset, chain)`. The levels to gate are the indexes in `selected` that are at least 1 and below both `len(known_ancestors)` and `len(chain)`. With no such index return `True`. Per D-18 return `False` for an actor who is not both authenticated and active. Read the pair once with `ancestors._operation_requirements(target)`. Walk the indexes from the highest to the lowest (outermost first, the order of `_authorize_ancestors`); for each take the key (`nearest` or `higher` half as `selected` says), call `_check_nested_auth(target, actor=user, model=<ancestor ViewSet model>, obj=<handed object>, provider=ancestors._effective_provider(<ancestor ViewSet>))`, resolve the permission with `ancestors._permission_name(viewset, <ancestor ViewSet>, key, ancestors._registered_key(target))` and call the ancestor ViewSet's `_ancestor_has_permission(user, permission, <handed object>, view=None)`; the first `False` returns `False`. The provider receives no view, as it does today for a child link (D-17). No stage-1 call site hands over more than one ancestor (D-26), so this body runs past its first return only in the unit test of plan 03; say so in the docstring.

`_link_access` takes the same arguments as `_link_permission` and returns one of the three constants. `_LINK_PERMISSION` when `_link_permission` is false. Otherwise the action object per D-13, mirroring `cv_get_action_object`: `obj` when `target.cv_object`, else `known_ancestors[0]` for a nested target, else `None`. Call `target.cv_action_enabled(user, action_obj)` directly, never one of the two state adapters; a false answer returns `_LINK_STATE`, otherwise `_LINK_ALLOWED`. `_link_ctx(outcome)` returns a dict with `cv_access` true unless the outcome is `_LINK_PERMISSION`, and `cv_action_enabled` true unless it is `_LINK_STATE`. Nothing in this module sets an attribute on the user, a view or a class, and nothing is memoized (D-20). Nothing in it calls a ViewSet's `get_queryset` or a view's `cv_get_parent_object` (D-04, D-05).

In `src/crud_views/lib/view/base.py` add the classmethod `CrudView._cv_link_permission(cls, user, obj, parent_obj, *, rendering_view=None)` next to the existing child-link adapter, which stays untouched in this plan because the child button and the card still call it. When the ViewSet has a parent: import `_effective_provider` and `_immediate_parent_access` from `crud_views.lib.ancestors` inside the method body (as the existing adapter does), return `False` when `_immediate_parent_access(cls, user, parent_obj)` is false (called without a rendering view, as today), then return `False` unless the actor is authenticated and active or the immediate parent's effective provider is `"none"`.
