## Decisions taken by this plan (concept 12.5, "open for the planner")

- **Name, module, signature.** `_link_access` in the new module `src/crud_views/lib/link_access.py`. A new module
  keeps the two gate modules byte-identical, which turns D-14 into a one-line `git diff` check.
- **How step 2 is satisfied for the nested Guardian create.** The function asks the target class for the nearest
  parent gate and own permission through one private classmethod, `_cv_link_permission`. Its `obj` is only ever the
  target's own object; the parent arrives separately. A nested Guardian create answers it with
  `cv_create_has_access(user, rendering_view, parent)` and nothing else: package links no longer call
  `cv_has_access` on a nested Guardian create. `cv_has_access(user, None)` stays `False`. Consequence for projects,
  carried to the Breaking entry in plan 06: an override of `cv_has_access` on a nested Guardian create no longer
  affects package links; the rule belongs in `cv_create_has_access`. Rejected: also calling an overridden
  `cv_has_access(user, None)`. It needs override detection, and the default answer `False` would hide every link of
  an override that calls `super()`.
- **The `rendering_view` each site hands over.** Each site keeps what the provider call receives today, so no
  Guardian checker and no access-trace owner changes: nothing at the navbar (and, in plan 03, at the child button
  and the card child action; in plan 04, at context buttons, row actions, the parent button, the card action and
  the filter), the list view on the nested Guardian list page.
- **`gate_ancestors` keyword.** It defaults to `True`, the final behaviour. Sibling-page sites pass `False`, because
  sibling-page links to core targets carry no parent gate today and get none in this phase; gating them is stage 3.
  With `False` the parent is still required wherever it is used: by a target without an own object (its state
  object, and for a nested Guardian create its whole rule).
- **Deferred half of D-04.** Filling the ancestor list from the higher ancestors the request resolved waits for
  stage 2 or 3 (D-26). The function already gates whatever it is handed.
