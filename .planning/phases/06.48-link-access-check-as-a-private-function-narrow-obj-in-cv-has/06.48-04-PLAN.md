## How a page hands over the parent (D-27)

One rule, in one place. `_page_ancestors(rendering_view, target, page_obj)` returns the ancestor list a page hands to
the check:

- empty for a top-level target and for a target with an own object: in stage 1 nothing in a non-gating call uses
  the parent of an object target;
- otherwise the target class decides through `_cv_link_page_parent(rendering_view, page_obj)`:
  - `CrudView`: the ancestor of the target's parent ViewSet that this request resolved, read with
    `_resolved_ancestor`. No query. `None` when the view never ran the ancestor guard.
  - `GuardianCreateViewPermissionRequired`, nested: the same, but only when the page object is an own child of a
    single-foreign-key nesting. A page without an object, an unrelated object and a `ManyToMany` own child hand over
    nothing. These are the documented `False` answers, kept on purpose. The child list page is the one page without
    an object that hands over its URL parent, and it does so itself in `GuardianQuerysetMixin.cv_get_context`.

Consequences, all carried to the migration note in plan 06:

- A nested list or create control rendered by a view that resolved no parent (a custom or non-CRUD view, or a test
  view that never ran the guard) is denied, where the foreign-key walk or a database lookup answered before.
- A parent instance passed as `obj` to `cv_get_context` on a child page no longer stands for the parent.
- Not changed: `ParentContextButton` still obtains the parent object, which is the own object of its target, from
  `cv_get_parent_object()`.
