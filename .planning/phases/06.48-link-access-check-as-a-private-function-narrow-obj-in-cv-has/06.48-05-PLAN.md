## How a site on a page of the target's own ViewSet decides (D-31)

Six sites render a control for a target in the page's own ViewSet, or one level up: `ContextButton`, the actions
by view key (context actions and row actions), `ParentContextButton`, `SiblingContextButton`, the non-child card
action and the `cv_context_has_permission` filter. This plan changes the first two; plan 06 the other four. All
six follow one rule.

**1. Ask the target whether the check decides it here.** `target._cv_page_link_ancestors(rendering_view,
page_obj)` answers `None` for "no, use your own code path", or the ancestor list to hand to the check.

- `CrudView`: `None`, always. In stage 1 no core target is decided by the check from such a page.
- `GuardianCreateViewPermissionRequired`, nested: a tuple. It holds the parent the request resolved from the URL
  (`_resolved_ancestor`, no query) when the page object is an own child of a single-foreign-key nesting. It is
  empty in every other case, and the check then denies under D-16: a page without such an object (a child list or
  create page, the filter on a child list page, a sibling button, which passes no object), an unrelated object, a
  `ManyToMany` own child, and a view that resolved no parent. The decisions behind these answers are listed below
  (D-27, D-33, D-16). The child list page is the one page without an object whose create control still shows: it
  hands over its URL parent itself in `GuardianQuerysetMixin.cv_get_context` (plan 02).
- `GuardianCreateViewPermissionRequired`, top-level: `None`, like every core target.

**Decisions behind the empty tuple.** Four answers for the create of a nested Guardian ViewSet stay denied, and
each rests on a locked decision in `06.48-CONTEXT.md`. D-27 keeps the two documented ones: the `ManyToMany` child
page, and the `cv_context_has_permission` filter on a child list page. D-33 keeps two more: the create control on
the nested Guardian create page itself (this plan), and a `SiblingContextButton` to a nested Guardian create
(plan 06). For all four the seam hands the check no parent, D-16 denies, and `cv_create_has_access` is not asked,
although the request did resolve the parent on the create page and on a sibling page. That is why D-28 reads
"every package control that links to a nested Guardian create and is shown today". The rendered result is the
one of today; D-33 notes that it can be relaxed after 1.0. A view that resolved no parent is denied under D-16
alone.

Why a seam and not one helper in core: a helper would have to recognise the nested Guardian create by the name of
its hook, which puts a Guardian name into core, and it would have to repeat the rule about own children and
`ManyToMany` nesting that `_cv_guardian_create_parent` already owns. The seam keeps both in the Guardian class
where a developer looks when a create button misbehaves. The core default is two lines that say what stage 1 does
not do. Stage 3 removes the seam when these sites send every target through the check.

**2. A tuple: the check decides.** The site stamps `_link_ctx(_link_access(target, user, None, known))`. No
rendering view is passed, so `cv_create_has_access` receives `None` and the provider no view, as today on these
pages. Permission comes before state, and a denied control carries `cv_action_enabled` `True` (not evaluated).

**3. `None`: today's code path, narrowed.** The site keeps its two calls in their order (state adapter first,
independently of permission, then `cv_has_access`) and changes only the objects:

- `cv_has_access` receives the page or row object when the target has an own object, else `None` (D-11, D-15).
- the state adapter receives `_page_action_object(rendering_view, target, page_obj)`: the page or row object when
  the target has an own object; for a nested target without one, the ancestor of the target's parent ViewSet that
  this request resolved (D-13, D-27); otherwise `None`.

**A view that resolved no parent** (a custom or non-CRUD view that did not run the ancestor guard, or a test view
built by hand): `_page_action_object` returns `None` for a nested target without an own object. Nothing
disappears. A nested core create still resolves its parent inside `CreateView._cv_action_enabled_for_rendering`,
exactly as today, so its hook still receives the parent. A nested list's hook receives `None` where it received
the page object before. A control for a nested Guardian create is denied there, where the foreign-key walk
answered before. Plan 08 carries both sentences to the migration note.

Recorded consequence (advisory finding FD-1 of review cycle 1). D-13 in `06.48-CONTEXT.md` states the action
object without an exception. The `None` a nested list's state hook receives on a view that did not run the
ancestor guard is not a new decision: it follows from D-04 and D-27 (a link never loads an ancestor to decide,
and the parent is the one the request resolved). It stays visible in truth 5 of this plan, in the docstring
table of plan 07 and in fact F2 of plan 08. This phase does not edit `06.48-CONTEXT.md`; whether the exception
is written down beside D-13 is the maintainer's call.

The list-page override of plan 02 matches any context button whose resolved key is the page's own create, not
only a plain `ContextButton` (known limit L1, stated in `06.48-02-PLAN.md`). This plan does not touch that
override, and `ContextButton.get_context` is not affected by the limit: its target is in the page's own ViewSet.

Consequences that are not changes: sibling-page links to core targets get no parent gate, as today
(`tests/test1/test_ancestor_costs.py` pins zero helper gates for a core create control); a create control on a
Guardian child object page no longer reads the parent row through the child's foreign key.
