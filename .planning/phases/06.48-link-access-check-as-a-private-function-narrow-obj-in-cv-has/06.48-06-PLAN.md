## What each site passes

The rule is the one of plan 05: ask `target._cv_page_link_ancestors(rendering_view, page_obj)`; a tuple goes to
the check; `None` keeps the site's two calls in their order with narrowed objects.

| Site | Object handed to the seam | `cv_has_access` receives (code path kept) | State adapter receives (code path kept) |
|------|---------------------------|--------------------------------------------|------------------------------------------|
| `ParentContextButton` | the parent object the button already looks up | that parent object for an object target, else `None` | that parent object for an object target; the grandparent the request resolved for a nested target without an own object; else `None` |
| `SiblingContextButton` | nothing: the button has no object of the sibling in scope | `None`, as today | the parent both ViewSets share, as the request resolved it; `None` for a top-level sibling |
| non-child `CardAction` | the card row | the row for an object target, else `None` | the row for an object target; the resolved parent for a nested target without an own object; else `None` |
| `cv_context_has_permission` | the view's current object, or nothing | that object for an object target, else `None` | not evaluated: the filter is permission-only |

For a nested Guardian create this gives, with the seam of plan 05:

- parent button one level below the create's ViewSet: the looked-up parent is an own child of the create, so the
  check receives the grandparent the request resolved and asks `cv_create_has_access(user, None, grandparent)`;
- create card action on a child card row, and the filter on a child object page: the check receives the URL parent
  the request resolved;
- sibling button, the filter on a child list page, a `ManyToMany` child page, the create page itself, a view that
  resolved no parent: the seam hands over nothing and the check denies (D-16). These controls are hidden today.
  The sibling button is documented as collection-only and checked a nested Guardian create with no object, which
  answered `False`; it stays hidden, and it stops calling `cv_has_access` of the create (D-32).

**Decisions behind the kept denials.** The filter on a child list page and the `ManyToMany` child page are the two
answers D-27 names. The sibling button to a nested Guardian create and the create control on the create page
itself are the two answers D-33 adds: the maintainer decided on 2026-11-23 to keep both hidden as today, although
the request resolved the parent on those pages. For them the check is handed no parent, D-16 denies, and
`cv_create_has_access` is not asked; D-28 is worded accordingly ("every package control that links to a nested
Guardian create and is shown today"). The decision can be relaxed after 1.0. Plan 08 publishes all four answers
(fact F9).

`ParentContextButton` keeps obtaining the parent object from `cv_get_parent_object()`: that object is the own
object of an object target and an input of the button's URL, not a parent passed to a hook.
