## What the documents must say

These are the facts; the wording is the executor's. Use plain language and the project's existing style (bold entry
title, issue number in parentheses, lines wrapped at 120).

| # | Fact | Decision |
|---|------|----------|
| F1 | `cv_has_access(user, obj)`: `obj` is only the target view's own object, and `None` for a view without one (list, create). The package no longer passes the parent at child links, nor the page object at context buttons, row actions, card actions, the parent button and the `cv_context_has_permission` filter. | D-11, D-15 |
| F2 | `cv_action_enabled(user, obj)`: a link passes the object the request passes: the view's own object for an object view, the immediate parent for a nested list or create, otherwise `None`. Before, a button passed the page object or nothing: a nested list reached from a child object page received that child, a top-level list received the page object, the parent button passed the parent object to a parent list. | D-13, D-29 |
| F3 | Order for a link: parent gate, then own access, then state. The state hook is not called when permission denies. In a ctx dict of a permission-denied control `cv_action_enabled` is `True`, meaning not evaluated; the rendered result is unchanged. A malformed parent policy now raises `ImproperlyConfigured` on the hosting page also for an actor whose own access is denied. | D-19, concept 5.2 |
| F4 | An override that read the **parent** from `obj`: on a nested Guardian create the rule goes to `cv_create_has_access(user, rendering_view, parent_obj)`. On any nested list or create a rule about the parent's state goes to `cv_action_enabled`, which receives the immediate parent. The parent's permission itself is checked by the package through the ancestor policy. | issue #407 |
| F5 | An override that read the **page object** from `obj` on a list or create target receives `None` now. A rule about the parent goes to `cv_action_enabled`; a rule that needs another object belongs on the action's own page. | issue #407 |
| F6 | Nested Guardian create: `cv_has_access` answers `False` for every argument, a parent instance and an own child included. `cv_create_has_access` is the replacement and still accepts a parent instance or a foreign-key own child. An override of `cv_has_access` on a nested Guardian create no longer affects package links. | D-25 |
| F7 | `cv_create_has_access` now decides every package control that links to a nested Guardian create: as before the create control of the child list page, and newly the child context button, the card child action, the object navbar child item, the parent button, and create controls on child object pages. `rendering_view` is the list view on the child list page and `None` everywhere else. An override must not assume `rendering_view` is set. | D-28 |
| F8 | On a page of the target's own ViewSet the parent is the one the request resolved from the URL, not the page object's foreign key and not `cv_get_parent_object()`. A nested list or create control rendered by a view that did not run the ancestor guard (a custom or non-CRUD view) is hidden. A parent instance passed as `obj` to `cv_get_context` on a child page no longer stands for the parent. | D-27, D-16, D-04 |
| F9 | Two answers stay `False` on purpose for the create of a nested Guardian ViewSet: the `cv_context_has_permission` filter on a child list page (the filter and the toolbar's create control disagree by rule; place the control), and a `ManyToMany` child page. The old reason, that the filter has no URL parent to work with, is removed. | D-27 |
| F10 | Unchanged limits: rendering checks only the immediate parent, so a link can stay visible where a farther ancestor denies the request; a queryset-only Guardian composition shows its child link without a parent check. The click is refused with 403. Sibling-page links to core targets still carry no parent gate. | D-26, D-30 |
