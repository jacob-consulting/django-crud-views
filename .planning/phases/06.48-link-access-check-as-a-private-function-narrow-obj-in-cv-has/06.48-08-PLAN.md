## What the documents must say

These are the facts; the wording is the executor's. Use plain language and the project's existing style (bold entry
title, issue number in parentheses, lines wrapped at 120). Do not claim more than a fact states: in particular the
order of F3 holds only for the controls it names.

| # | Fact | Decision |
|---|------|----------|
| F1 | `cv_has_access(user, obj)`: `obj` is only the target view's own object, and `None` for a view without one (list, create). The package no longer passes the parent at child links, nor the page or row object at context buttons, row actions, card actions, the parent button and the `cv_context_has_permission` filter. | D-11, D-15, D-29 |
| F2 | `cv_action_enabled(user, obj)`: a link passes the object the request passes: the view's own object for an object view, the immediate parent for a nested list or create, otherwise `None`. Before, a button passed the page object or nothing: a nested list reached from a child object page received that child, a top-level list received the page object, the parent button passed the parent object to a parent list or a top-level create, the sibling button passed nothing. One exception: on a view that did not run the ancestor guard (a custom or non-CRUD view) a nested list receives `None`. No core control disappears there. | D-13, D-29, D-27, D-36 (the exception) |
| F3 | Order. The links the package decides through its link check run parent gate, then own access, then state: child context buttons, card child actions, object navbar child items, and every link to a nested Guardian create. For these the state hook is not called when permission denies, and the ctx dict of a permission-denied control carries `cv_action_enabled` `True`, meaning not evaluated; the rendered result is unchanged. A malformed parent policy now raises `ImproperlyConfigured` on the hosting page also for an actor whose own access is denied, and such an actor now pays for the parent gate. Context buttons, row actions, the parent button, the sibling button and non-child card actions to every other target keep their order: state is evaluated independently of permission. | D-19, D-31, concept 5.2 |
| F4 | An override that read the **parent** from `obj`: on a nested Guardian create the rule goes to `cv_create_has_access(user, rendering_view, parent_obj)`. On any nested list or create a rule about the parent's state goes to `cv_action_enabled`, which receives the immediate parent. The parent's permission itself is checked by the package through the ancestor policy at child links, with one exception: a queryset-only Guardian composition (a list view built from `GuardianQuerysetMixin` without `GuardianParentPermissionMixin`) has no parent check at its child link (F10). Its `cv_has_access` override received the parent at the child context button, the card child action and the object navbar child item, and receives `None` now. A rule that read the parent there goes to `cv_action_enabled`, which receives the parent; a rule about the parent's permission needs the parent mixin. | issue #407, D-30 |
| F5 | An override that read the **page object** from `obj` on a list or create target receives `None` now. A rule about the parent goes to `cv_action_enabled`; a rule that needs another object belongs on the action's own page. | issue #407 |
| F6 | Nested Guardian create: `cv_has_access` answers `False` for every argument, a parent instance and an own child included. `cv_create_has_access` is the replacement and still accepts a parent instance or a foreign-key own child. | D-25 |
| F7 | `cv_create_has_access` is the only own-permission step of every package control that links to a nested Guardian create and is shown today; the controls that stay hidden without asking it are F9. `cv_has_access` of that view is not called for a package link, so an override of it no longer affects package links. The sites where the hook is asked: as before the create control of the child list page and the cancel target; newly the child context button, the card child action and the object navbar child item; and, where `cv_has_access` resolved the parent from an own child before, the create controls on child object pages (a context action, or a button with `key_target="create"`, on a detail, update or delete page), a create card action on a child card row, the parent button (with the exception F11 on a list page), and the `cv_context_has_permission` filter on a child object page. `rendering_view` is the list view on the child list page, the rendering view at the cancel target, and `None` at every other site. An override must not assume `rendering_view` is set. | D-28, D-32 |
| F8 | For a control that links to a nested Guardian create from a page of the create's own ViewSet, the parent is the one the request resolved from the URL, not the page object's foreign key and not `cv_get_parent_object()`. This includes the create control of the child list page: before, the list view passed the result of its `cv_get_parent_object()` to `cv_create_has_access`; an override of `cv_get_parent_object()` on the list view therefore no longer decides that control. The request-resolved parent does. On a view that did not run the ancestor guard that control is hidden, where the foreign-key walk answered before. A parent instance passed as `obj` to `cv_get_context` on a child page no longer stands for the parent. Core targets are not affected. | D-27, D-16, D-04 |
| F9 | Answers that stay denied on purpose for the create of a nested Guardian ViewSet. Two are documented today (D-27): the `cv_context_has_permission` filter on a child list page (the filter and the toolbar's create control disagree by rule; place the control), and a `ManyToMany` child page. Two are hidden today and stay hidden (D-33): a `SiblingContextButton`, which stays collection-only for this target, and the create control on the nested create page itself. None of the four asks `cv_create_has_access`, so an override of that hook cannot show them. The old reason, that the filter has no URL parent to work with, is removed. | D-27, D-33, D-16 |
| F10 | Unchanged limits: rendering checks only the immediate parent, so a link can stay visible where a farther ancestor denies the request; a queryset-only Guardian composition shows its child link without a parent check. The click is refused with 403. Sibling-page links to core targets still carry no parent gate. | D-26, D-30, D-31 |
| F11 | Unchanged limit of the nested Guardian list page (known limit L1). For every context action without an object, the list view resolves the button's `key_target`, or the action key when the button has none, in its own ViewSet. When that key is a Guardian create of the page's own ViewSet, the shown access and state are those of the page's own create. This also holds for a `ParentContextButton` whose `key_target` is `create` and for a `SiblingContextButton` configured under the action key `create`: on such a list page they show exactly when the page's own create control shows, while their link goes to their real target, whose request decides the click. On object pages the parent button follows the parent ViewSet's create (F7); the limit applies to list pages only. Nothing about this changed in this release. | D-34 (issue #407: same rendered result) |
