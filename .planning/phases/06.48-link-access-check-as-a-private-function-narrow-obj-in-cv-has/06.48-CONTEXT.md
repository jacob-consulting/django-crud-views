<domain>
## Phase Boundary

Stage 1 of the approved concept "One link access check, shared grants". The phase delivers:

- the link check as one private function: parent gates, then own permission, then state, built from the pieces the
  request gate already uses (concept 5.1, 5.2);
- the package call sites that pass a parent as `obj` today, core and Guardian, moved to that function;
- `obj` in `cv_has_access` narrowed to the target's own object, and the object passed to `cv_action_enabled` for a
  link aligned with the request's `cv_get_action_object`;
- one `### Breaking` entry in `CHANGELOG.md`, the matching entry in `docs/migrating-1.0.md`, and the affected
  reference pages.

Two public hooks change meaning. No new public name is added. Affected packages: `crud_views` (core) and
`crud_views_guardian`.

The maintainer explicitly assigned phase number 06.48. It lands before 1.0 freezes both hooks. The concept states
that this is a real piece of work on the 1.0 path, not a one-line change.

</domain>

<decisions>
## Implementation Decisions

The maintainer approved the concept on 2026-11-23. A planner does not reopen these decisions; a decision changes
only when the maintainer says so. Decision numbers are the concept's own (section 12.1). Decisions tagged
`[informational]` are settled but are delivered by a later stage or bind nothing in stage 1; they are listed so the
planner does not contradict them.

### Decisions this phase implements or must honour

- **D-04:** A link checks the ancestors it is handed plus those the current request already resolved
  (`_cv_ancestor_state`). It never loads an ancestor only to decide a link. (Concept 5.3) In this phase D-26
  limits it: the function gates every level it is handed and loads none, and the call sites hand over the
  immediate parent only. The "plus those the request already resolved" half is deferred and is not a requirement
  of this phase.
- **D-05:** Links do not consult ViewSet querysets. A link to an ancestor that a ViewSet queryset filters out
  (archived, soft-deleted) is accepted; the failure is a refused click. (Concept 5.4)
- **D-06:** No stand-in or fake view instances, for any purpose. (Concept 2, 8.3)
- **D-07:** The check's ancestor-list interface is fixed now, so that `force_full_hierarchy_check` can be added
  later without changing it. The flag itself is not built in this phase. (Concept 5.1, 8.2)
- **D-10:** Manage page, `cv_access` and `cv_manage_view` change only if something there needs fixing. Their
  published JSON formats stay as they are. (Concept 9)
- **D-11:** `obj` in `cv_has_access` is narrowed to the target's own object before 1.0. (Concept 5.6)
- **D-12:** Because D-11 cannot ship alone, the core of the link check is pulled forward to before 1.0 as a private
  function, and the package's child-link and create call sites move to it in the same change. (Concept 5.6, 9)
- **D-13:** The object passed to `cv_action_enabled` for a link follows the request's `cv_get_action_object`: the
  target's own object for an object view, the immediate parent for any nested view without an own object (list and
  create alike), otherwise nothing. It lands with D-11. (Concept 5.2)
- **D-14:** The request gate is not rewired. The link check is assembled from the gate's existing building blocks.
  Gate order, 404 versus 403, login redirects and trace recording stay exactly as they are. (Concept 5.5)
- **D-15:** A target without an own object (list, create) receives `None` in `cv_has_access`. (Concept 5.6)
- **D-16:** A nested target whose immediate parent is not known is denied. Only ancestors above the nearest may be
  absent, and are then unchecked. (Concept 5.2)
- **D-17:** The check takes no view. The real rendering view may be passed through to hooks that already accept
  one (`cv_create_has_access`), or nothing on a non-CRUD page. It is never fabricated. (Concept 5.1)
- **D-18:** Step 1 keeps the signed-in-and-active rule for protected ancestry and `_check_nested_auth`.
  (Concept 5.2)
- **D-19:** State is evaluated only after parent gates and own permission have passed. (Concept 5.2)
- **D-20:** Decisions (the answer per view and object) are not stored anywhere. This phase adds no cache and no
  memoization of answers. (Concept 7)

### Maintainer decisions taken during planning (2026-11-23)

Research (`06.48-RESEARCH.md`, "Open Questions" 1 to 5) found that existing tests and reference pages pin behaviour
the decisions above change. The maintainer answered each question on 2026-11-23, before the planner ran. These
decisions are numbered after the concept's D-24 and are recorded in the concept document as section 12.6.

- **D-25:** Request-gate expectations in the ancestor suites stay untouched. Assertions on link helpers in
  `tests/test1/test_ancestor_helpers.py` and `tests/test1/test_ancestor_resolution.py` (direct
  `cv_has_access(user, parent)` or `cv_has_access(user, own_child)` on a nested Guardian create, and the private
  adapters called by name) are rewritten to the narrowed contract, and the plan lists each rewritten line.
  `cv_has_access` on a nested Guardian create fails closed for a parent argument; `cv_create_has_access` is the
  replacement. This reads the acceptance criterion "the existing ancestor suites pass without edits to their
  expectations" as covering the request gate, not link helpers. (Research Open Question 1)
- **D-26:** Stage-1 call sites hand the check the immediate parent only, as today. The function itself gates every
  level it is handed, proven by a direct unit test with a two-level ancestor list. Handing over the higher
  ancestors the request resolved (the second half of D-04) waits for stage 2 or 3, and the plan records that. The
  pinned cost tests and the documented "visible link, 403 on click for a farther ancestor" stay as they are.
  (Research Open Question 2)
- **D-27:** On a sibling page, the check takes the parent from the parent the request already resolved from the
  URL, not from the page object's foreign key. An explicit condition keeps the two documented `False` answers: the
  `ManyToMany` child page, and the `cv_context_has_permission` filter on a child list page. Neither may change
  silently. (Research Open Question 3)
- **D-28:** A project's `cv_create_has_access` override also governs child context buttons, card child actions and
  object navbar child items, which bypass the hook today. The `### Breaking` entry and the migration note state
  this. (Research Open Question 4)
- **D-29:** `ParentContextButton`, the state argument of `SiblingContextButton` and the non-child card action are
  narrowed in this phase as well: argument narrowing only, with no parent-gate step for them. The documented
  meaning of `obj` is then true for every package caller at the 1.0 freeze. (Research Open Question 5)

- **D-30:** The documented Guardian queryset-only exception is kept: the link shows while the request answers 403.
  Confirmed by the maintainer on 2026-11-23 after a review of D-25 to D-29. (Research Open Question 6)

The maintainer reviewed D-25 to D-29 against the concept on 2026-11-23, kept all of them, and had them recorded in
the concept document as section 12.6 and in issue #407.

### Consequences of D-25 to D-30 the plan must carry

These follow from the decisions and are not decisions themselves. The doc passages were checked against the tree
on 2026-11-23; test line numbers in the research were not re-checked.

- D-25: the own-child argument is the planner's to settle within D-11; research recommends that `cv_has_access`
  on a nested Guardian create answers `False` for every argument (its option G1). Either way,
  `docs/migrating-1.0.md` "Nested Guardian create access" (the bullet "A parent instance works as before", and the
  checklist entry that links to it) and the input table in `docs/reference/guardian.md` ("What the create access
  helpers accept") are rewritten, not appended to. The change is from allowed to denied.
- D-26 and D-30: a child link can stay visible where a farther ancestor, or a queryset-only composition, denies
  the request. The click is refused with 403, as documented today. External reviewers may report this; concept
  12.6 states that it is accepted for stage 1.
- D-27: `docs/reference/context_buttons.md` gives "the filter has no URL parent to work with" as the reason for the
  two `False` answers. That reason no longer holds and is reworded: the two answers are kept on purpose. On a child
  list page the filter and the toolbar's create control then disagree by rule. A view without a resolved parent (a
  custom or non-CRUD view) is denied under D-16, where the foreign-key walk answered before; the migration note
  names this.
- D-28: `cv_create_has_access` exists only on the Guardian create view. Its `rendering_view` is documented as the
  list view instance (`docs/reference/guardian.md`, and the docstring in `src/crud_views_guardian/lib/views.py`).
  At the three new sites it is a different view, or `None` if the plan keeps today's `view=None` to hold costs and
  trace output. An override that reads `rendering_view.request` could raise there. The Breaking entry states what
  an override receives at those sites. The rendered result is unchanged only for the default hook, which stays one
  parent gate.
- D-29 with D-25: a narrowed site that reaches a nested Guardian create with `None` would get `False`.
  `ContextButton`, row actions and `ParentContextButton` therefore go through the check for that target; narrowing
  alone would hide a button that shows today.
- From "the rendered result is the same as before": sibling-page links to core targets carry no parent gate today
  and get none in this phase (research, "Two kinds of stage-1 site"). Gating them is stage 3.
- `docs/migrating-1.0.md` "Child-link parent permissions" (near the top of the file) describes the old order, own
  access first, and is outdated by this phase. The research's documentation table does not list it.

### Settled, not delivered by this phase

- **D-01 [informational]:** Approach B: a shared Guardian checker plus one link check, delivered in the stages of
  concept section 9. This phase is stage 1 only.
- **D-02 [informational]:** The request gate always reads grants fresh. A revoked permission takes effect on the
  next request.
- **D-03 [informational]:** A cross-request cache may serve link rendering only, never the gate. Specified, not
  built.
- **D-08 [informational]:** Business rules split in two: cheap state rules (`cv_action_enabled`) run for links and
  requests and are never cached; expensive checks run only on the action's page. Delete gets no new hook.
- **D-09 [informational]:** The shared Guardian checker lives on the user object. Stage 2 (#385).
- **D-21 [informational]:** A denied breadcrumb item renders as plain text, not as a link. Stage 4.
- **D-22 [informational]:** `force_full_hierarchy_check` is built at the first real case, not in the first version.
- **D-23 [informational]:** If the cross-request cache is ever built, it is opt-in, holds grants only, and is
  invalidated by one global permission counter plus a short timeout.
- **D-24 [informational]:** The delete preview stays the only place that maps a model to a ViewSet. The link check
  never derives a ViewSet from a model.

### Stage 1 constraints (concept 12.2, issue #407)

These are not numbered decisions, but the plan must satisfy each of them.

- Nested Guardian create: a direct call to `cv_has_access` on a nested Guardian create must never start answering
  "allowed" without a parent check. This covers the template filter, `SiblingContextButton` and project code that
  calls the hook directly. A test pins it: a direct `cv_has_access(user, None)` on a nested Guardian create does
  not answer "allowed".
- `cv_create_has_access(user, rendering_view, parent_obj)` stays the documented hook for parent-based create rules
  and keeps being called, with the real rendering view or nothing.
- The request gate, its order, its responses and its trace recording are unchanged. The existing ancestor and
  access-trace suites pass without edits to their request-gate and trace expectations. Link-helper assertions in
  the ancestor suites are the exception D-25 allows, each rewritten line listed in the plan.
- Golden files under `tests/test1/golden/` stay byte-identical, or the plan names each intended markup change.
- Query counts in `tests/test1/test_navbar_costs.py` and `tests/test1/test_ancestor_costs.py` are unchanged, or
  each change is explained. They are pinned before and after.
- The check is private and is not added to the 1.0 stability inventory.

### Acceptance criteria (issue #407)

- Every package call site that passed a parent as `obj` goes through the link check; none calls `cv_has_access`
  with a parent object.
- For each affected control (child context button, card child action, object navbar child item, Guardian child
  create on list and detail pages), the rendered result is the same as before for every actor in the authorization
  matrix: anonymous, inactive, superuser, model permission, direct grant, group grant.
- A test pins the nested Guardian create constraint above.
- A test shows that `cv_action_enabled` receives the same object for a link as for the request, for an object
  view, a nested list and a nested create.
- The request gate's order, responses and access-trace output are unchanged.
- Golden files and the two cost suites hold as stated under the constraints.
- `CHANGELOG.md` has the `### Breaking` entry for both hooks and `docs/migrating-1.0.md` has the matching
  migration note, including the case of an override that read the parent or the page object from `obj`.
- The plan records which of the three private adapters were removed and which remain for stage 3.

## Existing Code Insights

Taken from concept section 3 and 5.6. Line references there are `main` @ `7c8e0177` and were not re-verified for
this capture; the researcher confirms each against the current tree.

### Request gate (unchanged by this phase)

- `CrudView.dispatch` → `_cv_ancestor_guard` → `_authorize_ancestors` (`src/crud_views/lib/ancestors.py`), then
  `CrudViewPermissionRequiredMixin.has_permission` (`src/crud_views/lib/view/base.py`) for the view's own
  permission and `cv_action_enabled`.
- `cv_get_action_object` (`base.py`) defines which object the request passes to `cv_action_enabled`.

### Building blocks the link check reuses

- `_selected_gates`, `_operation_requirements`, `_permission_name`, the provider's `_ancestor_has_permission`,
  `_check_nested_auth` and `_immediate_parent_access` in `src/crud_views/lib/ancestors.py`.
- `src/crud_views/lib/view/visibility.py` consumes the three outcomes: allowed, denied by permission, denied by
  state.

### Link path today

- Class methods `cv_has_access(user, obj)` and `cv_action_enabled(user, obj)`, plus the three private adapters
  named above.
- Known sites that pass a parent as `obj`: `_cv_child_link_has_access` in `base.py`; the Guardian child create's
  `cv_has_access` cases 3 and 4 and its `_cv_child_link_has_access` (`src/crud_views_guardian/lib/views.py`); the
  Guardian queryset mixin's `_cv_child_link_has_access` (`src/crud_views_guardian/lib/mixins.py`).
- Other link consumers (stage 3, not moved in this phase unless they pass a parent): the context button classes in
  `src/crud_views/lib/view/buttons.py`, row actions in `base.py`, card actions in `src/crud_views/lib/views/card.py`,
  the object navbar in `src/crud_views/lib/navbar.py`, the cancel target, the bulk toolbar, and the
  `cv_context_has_permission` filter in `src/crud_views/templatetags/crud_views.py`.
- Guardian pieces on this path: `GuardianQuerysetMixin.cv_get_context` rewrites `cv_access` and
  `cv_action_enabled` for a child create rendered on a list page; the create views' adapter overrides resolve the
  parent from the rendering view (`src/crud_views/lib/views/create.py`, `src/crud_views_guardian/lib/views.py`).

### Observations that shape the plan

- Buttons pass the page object or nothing to `cv_has_access` and `cv_action_enabled` for targets without an own
  object today; D-13 and D-15 change that, which is why both hooks appear in the Breaking entry.
- Context buttons and row actions evaluate state before permission today; D-19 fixes the order inside the check.
- A nested Guardian create has no permission of its own and answers `False` for an empty `obj` today.
