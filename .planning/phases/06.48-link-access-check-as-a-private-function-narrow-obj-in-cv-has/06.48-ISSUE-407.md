# Issue #407 snapshot

**Title:** Link access check as a private function; narrow obj in cv_has_access and cv_action_enabled before 1.0

## Problem

The package decides in about ten places whether a link or button to a view is shown. Each place calls `cv_has_access` and `cv_action_enabled` itself, and the `obj` argument means "the target's own object", "the parent" or "nothing" depending on the caller. Three private adapters exist only to bridge those meanings, and each new consumer has had to work out again how to call the checks (#312 and #318 came from two of them getting it wrong).

Both hooks are public and are about to be frozen for 1.0. This issue fixes their meaning before the freeze.

## Amendments (2026-11-23)

Planning research found that existing tests and reference pages pin behaviour the settled decisions change, and that the concept cannot hold two of its statements at once in stage 1: a link also checking the higher ancestors the request resolved (D-04, sections 5.1 and 5.3), and "the rendered result is the same as before" with the pinned gate counts. The maintainer decided:

The consequences for documentation and for the Breaking entry are listed in section 12.6.

## Scope

In:

- The link check as a private function: parent gates, then own permission, then state, built from the pieces the request gate already uses (concept sections 5.1 and 5.2).
- The call sites that pass a parent today, core and Guardian, moved to it.
- `obj` in `cv_has_access` narrowed to the target's own object, and the object passed to `cv_action_enabled` aligned with the request's `cv_get_action_object` (D-11, D-13, D-15). This includes `ParentContextButton`, the state argument of `SiblingContextButton` and the non-child card action, as argument narrowing only (D-29).
- One `### Breaking` entry in `CHANGELOG.md`, the matching entry in `docs/migrating-1.0.md`, and the affected reference pages.

Out:

- The shared Guardian checker (#385, stage 2).
- The remaining link consumers, the breadcrumb and the site menu (stages 3 to 5).
- Any cache, and the full-hierarchy flag (concept section 8).
- Any change to the request gate (D-14).

## The constraint that must not be missed

A nested Guardian create has no permission of its own; its whole rule is the parent rule, which it receives through `obj` today, and it answers `False` for an empty `obj`. Once `obj` no longer carries the parent:

**A direct call to `cv_has_access` on a nested Guardian create must never start answering "allowed" without a parent check.** This covers the template filter, `SiblingContextButton` and project code that calls the hook directly.

How the own-permission step is satisfied for such a view is the planner's to decide (concept section 5.6). `cv_create_has_access(user, rendering_view, parent_obj)` stays the documented hook for parent-based create rules and keeps being called.

## Acceptance criteria

- Every package call site that passed a parent as `obj` goes through the link check; none calls `cv_has_access` with a parent object.
- For each affected control (child context button, card child action, object navbar child item, Guardian child create on list and detail pages), the rendered result is the same as before for every actor in the authorization matrix: anonymous, inactive, superuser, model permission, direct grant, group grant.
- A test pins the constraint above: a direct `cv_has_access(user, None)` on a nested Guardian create does not answer "allowed".
- A test shows that `cv_action_enabled` receives the same object for a link as for the request, for an object view, a nested list and a nested create.
- The request gate's order, responses and access-trace output are unchanged; the existing ancestor and access-trace suites pass without edits to their request-gate and trace expectations. Link-helper assertions in the ancestor suites may be rewritten to the narrowed contract, each rewritten line listed in the plan (D-25).
- Golden files under `tests/test1/golden/` are byte-identical, or the plan names each intended markup change.
- Query counts in `tests/test1/test_navbar_costs.py` and `tests/test1/test_ancestor_costs.py` are unchanged, or each change is explained.
- `CHANGELOG.md` has the `### Breaking` entry for both hooks and `docs/migrating-1.0.md` has the matching migration note, including the case of an override that read the parent or the page object from `obj`, and the reach of a `cv_create_has_access` override (D-28) and the `cv_has_access` override that no longer affects package links to a nested Guardian create (D-32).
- The check is private and is not added to the 1.0 stability inventory.
- The plan records which of the three private adapters were removed and which remain for stage 3.

## Affected area

`crud_views` (core) and `crud_views_guardian`. Two public hooks change meaning; no new public name.
