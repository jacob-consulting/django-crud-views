## Summary

The concept's code inventory is accurate, and the building blocks exist with stable signatures. The work is larger
than the concept's site list suggests for one reason the concept does not spell out: **existing tests and reference
pages pin four properties that the locked decisions deliberately change**. A plan that does not name these in
advance will meet them as "regressions" during execution.

1. **The hook receives the parent** (changed by D-11). Pinned in about ten places, e.g.
   `access.assert_called_once_with(actor, parent)`.
2. **Own access is asked before the parent gate** (changed by the concept's step order, 5.2). Pinned by "own denial
   skips parent work" assertions and by three reference pages.
3. **State is evaluated independently of permission** (changed by D-19). Pinned by "the create state hook was not
   consulted" assertions that run for permission-denied actors too.
4. **`cv_has_access` on a nested Guardian create answers the parent rule when handed a parent or an own child**
   (cases 3 and 4). Pinned by direct calls in five test files, **one of which is
   `tests/test1/test_ancestor_helpers.py`**, a member of the "18 ancestor suites" that the acceptance criteria say
   pass "without edits to their expectations".

Point 4 is a real conflict between two acceptance statements and needs the maintainer's word before planning locks
(Open Question 1). The same file also calls `_cv_child_link_has_access` and `_cv_action_enabled_for_context`
directly, which bears on which adapters can be removed.

Three further findings constrain the design more tightly than the concept does:

- **One provider call per link, on the immediate parent only.** `tests/test1/test_ancestor_costs.py` asserts that no
  identical gate runs twice in a request, that a Guardian list page with a create button makes exactly one helper
  gate, that a **core** create button makes none, and that every helper gate is on the immediate parent. A generic
  step 1 followed by `cv_create_has_access` (whose default runs the same parent gate) breaks this. So does handing
  the request's higher ancestors to the check at these sites.
- **The `view=` argument of each provider call is observable.** It selects the Guardian checker (a fresh one for
  `None`, the view-local one otherwise) and it is the access-trace recorder's owner key. Changing it at a call site
  changes query counts and can change trace output.
- **The three `_cv_child_link_has_access` definitions are three different rules**, two of them Guardian-specific
  (a stricter actor rule, and a documented exception for queryset-only compositions). Core cannot import Guardian,
  so a per-target private seam must survive stage 1 in some form.

**Primary recommendation:** Add one private function that owns D-16, the D-13 action object and the D-19 order, and
let it ask the target class for the permission part through **one** private classmethod seam whose `obj` argument is
only ever the target's own object and whose parent arrives as a separate argument. The nested Guardian create
answers that seam with `cv_create_has_access(user, rendering_view, parent)`; its `cv_has_access` keeps answering
`False` for `None`. Stage-1 call sites hand the check exactly the immediate parent they hand today. Sibling-page
sites must not start gating core targets (see "Two kinds of stage-1 site"). Before any production edit, commit a
characterization matrix of the rendered outcome per control and actor on the unchanged tree, and keep it green
across the refactor. Plan the first production task as a tracer: the function, one parent-in-hand site and the
Guardian create from one sibling page, then a full-suite run whose failures are reconciled against the expected set
in this document before the remaining sites are moved.

### D-13 alignment today (planner item for AC-4)

`cv_get_action_object` returns `self.get_object()` for object views, `self.cv_get_parent_object()` for **any**
nested view without an own object, else `None` [VERIFIED: src/crud_views/lib/view/base.py:568-575]. Its docstring
says "the parent for child create-views", which understates the code: a nested list also gets the parent.

| Target kind | Request passes | Link passes today | Aligned? |
|-------------|----------------|-------------------|----------|
| Object view (detail, update, delete, action) from a row or its own page | own object | own object | yes |
| Nested create from a parent page (child button, card child action, navbar) | parent | parent (page object is the parent) | yes |
| Nested create from a sibling page | parent | parent, through the create adapters `create.py:36-75` and `guardian/views.py:305-313` | yes |
| Nested list from a parent page | parent | parent | yes |
| **Nested list from a sibling object page** (`home` on a child detail page) | parent | **the page's child object** | **no** |
| **Top-level list from an object page** (`home` on a top-level detail page) | `None` | **the page object** | **no** |
| **Nested sibling list** (`SiblingContextButton`) | parent | **`None`** | **no** |
| **Parent list from a child page** (`ParentContextButton`) | `None`, or the grandparent | **the parent object** | **no** |

### Two kinds of stage-1 site: parent in hand, and sibling page

This distinction is not in the concept and decides how the sites can share one function.

| | Parent in hand (A2, A3, A4) | Sibling page (A8, A9, A10, A11, A12) |
|---|---|---|
| Where the parent comes from | The page object or a card row **is** the target's parent | The page is in the target's own ViewSet (or one level below); the parent is an ancestor the page's guard resolved |
| Parent gate today, core target | **Yes**, with the target's nearest key (#380) | **None.** `cv_has_access(user, page_obj)` only |
| Parent gate today, nested Guardian create | Yes, once, through case 3 | Yes, once: `cv_create_has_access` on a list page, case 4 on an object page |
| Documented | "check the supplied immediate parent" | "Sibling links and ordinary row actions keep their existing behavior" [CITED: docs/reference/context_buttons.md:206-208, docs/reference/nested.md:590-592] |
| Pinned | `spy.assert_called_once_with(actor, parent)` throughout | `helper_gates = 1 if provider == "guardian" else 0` [VERIFIED: tests/test1/test_ancestor_costs.py:262] |

Consequence: if a sibling-page site sends **every** nested target through a check whose step 1 gates the parent, a
core create button on a nested list starts requiring the parent's Write key, and the default `home` button on a
nested update page starts requiring the parent's Read key. Both are the stage-3 behaviour, both change rendered
results, and the first breaks the pinned `helper_gates = 0`. In stage 1 only the nested Guardian create needs its
parent rule from a sibling page.

Three ways to keep that boundary, for the planner to choose from:

| Option | How | For | Against |
|--------|-----|-----|---------|
| **S1. Explicit stage-1 keyword** (recommended) | The function takes a keyword-only argument that says whether the handed ancestors still need their gates. It defaults to gating, the final behaviour. Sibling-page sites pass the non-gating value with a comment naming stage 3. The Guardian create's seam ignores it, because its parent rule is its permission. | One function for all Tier A sites; the temporary limitation is visible and greppable; stage 3 deletes the last use and the signature of concept 5.1 remains | One extra keyword until stage 3. D-16 then applies at sibling sites, so a view without guard state denies (Pitfall 7). |
| S2. Predicate at the site | Sibling-page sites call the check only for a target that is a nested Guardian create, selected the way Guardian code selects it today: `getattr(target_cls, "cv_permission", None) == "add" and hasattr(target_cls, "cv_create_has_access")` [VERIFIED: guardian/mixins.py:339-342] | Smallest behavioural footprint; every other sibling link keeps its exact path | A Guardian hook name appears in core, in four places unless one helper holds it; the sites are not really "moved" |
| S3. Gate sibling links now | Send all nested sibling targets through the gating check | The concept's end state | Pulls stage 3 forward; changes rendered results for core projects; changes `test_ancestor_costs.py`. Out of scope. |

### Pattern 1: one function, one per-target seam (recommended)

**What:** The function owns everything that is the same for every target: D-16, the D-13 action object and the D-19
order. The target class owns the permission part through one private classmethod whose inputs are fixed: `obj` is
only ever the target's own object, the parent is a separate argument.

**When to use:** every Tier A site in stage 1.

**Example** (a proposal to show shape; names and constants are `[ASSUMED]`, the planner decides them):

```python
# src/crud_views/lib/link_access.py  (illustrative, not existing code)
from crud_views.lib import ancestors

ALLOWED, DENIED_PERMISSION, DENIED_STATE = "allowed", "permission", "state"  # last two match visibility.py:19


def _link_access(target, user, obj=None, ancestors_known=(), *, rendering_view=None) -> str:
    """One link decision: parent gates, own permission, state (concept 5.2). Stores nothing (D-20)."""
    parent = None
    if target.cv_viewset.has_parent:
        if not ancestors_known:  # D-16: a nested target without its immediate parent is denied
            return DENIED_PERMISSION
        parent = ancestors_known[0]
    own = obj if target.cv_object else None  # D-11 / D-15
    if not target._cv_link_permission(user, own, ancestors_known, rendering_view):  # steps 1 and 2
        return DENIED_PERMISSION
    action_obj = own if target.cv_object else parent  # D-13, mirrors cv_get_action_object
    if not target.cv_action_enabled(user, action_obj):  # step 3, only now (D-19)
        return DENIED_STATE
    return ALLOWED
```

The seam's three implementations replace today's three `_cv_child_link_has_access` definitions one for one:

- `CrudView`: nested and gating requested: `ancestors._immediate_parent_access(cls, user, parent)` and the D-18
  actor rule; then `cls.cv_has_access(user, obj)`. The sketch above omits the stage-1 gating keyword of option S1
  for brevity.
- `GuardianQuerysetMixin`: its stricter actor rule and the queryset-only exception; otherwise `super()`.
- `GuardianCreateViewPermissionRequired`, nested: `cls.cv_create_has_access(user, rendering_view, parent)`.
  Top-level: `super()`.

Why this shape, measured against the maintainability rule:

- One place to read the order. Each Guardian difference stays in the Guardian class that owns it, where it is today.
- No hidden state, no new public name, no query added to an existing path.
- The seam is the existing adapter with a corrected contract, not an extra abstraction layer.

### Pattern 2: stamping the outcome into the existing ctx keys

`cv_resolve_action` and every template read `cv_access` and `cv_action_enabled`. The check's three outcomes map onto
them without touching `visibility.py`:

| Outcome | `cv_access` | `cv_action_enabled` |
|---------|-------------|---------------------|
| allowed | `True` | `True` |
| denied by permission | `False` | `True` (not evaluated, D-19) |
| denied by state | `True` | `False` |

Stamping `True` for "not evaluated" keeps the most existing assertions green (several tests assert
`ctx["cv_action_enabled"] is True` for a permission-denied create, e.g.
[CITED: tests/test1/test_guardian_parent_none.py:788]). It changes the cases that today record `False`/`False`
(Pitfall 1). `None` would be more literal but fails those `is True` assertions.

### Pattern 3: stage-1 call sites hand over the immediate parent, as today

The check accepts a list (D-07) and must gate every level it is handed (D-04). In stage 1 each Tier A site passes a
one-element list. See Open Question 2 for the evidence that passing the request's higher ancestors now would break
pinned expectations.

### Anti-patterns to avoid

- **A generic parent gate followed by `cv_create_has_access`.** The hook's default runs the same immediate-parent
  gate, so the provider is called twice. `test_ancestor_costs.py` forbids it (Pitfall 2).
- **Making `cv_has_access(user, None)` return `True` for a nested Guardian create.** Forbidden by the locked
  constraint.
- **Keeping a Guardian override that calls `cls.cv_has_access(user, parent_obj)`.** It satisfies the tests and
  fails AC-1 ("none calls `cv_has_access` with a parent object").
- **Deciding step 2 from `cv_get_requirement()["kind"] == "none"`.** That method describes gates for the manage
  page; a project that overrides `has_permission` flips it to `"custom"` [VERIFIED: guardian/mixins.py:420-437],
  which would silently hide create links that show today.
- **Calling `cv_get_parent_object()` from a link site without a guard state.** It falls back to a database read
  (D-04).
- **Building a stand-in view to satisfy `view=`.** `_ancestor_has_permission` needs the keyword; pass `None`
  (D-06).
- **Rewriting `_immediate_parent_access`.** It is called by `cv_create_has_access`, by the Guardian cancel target
  and directly by `test_ancestor_helpers.py` and `test_ancestor_auth_databases.py`. Compose it; do not replace it.

## Common Pitfalls

### Pitfall 1: D-19 reverses a property that tests pin on purpose

**What goes wrong:** Tests that assert the state hook was consulted fail for permission-denied actors.
**Why it happens:** Today state is computed first and independently ("state is independent of permission",
[VERIFIED: guardian/mixins.py:353]). D-19 evaluates it only after permission passes.
**Known pins:**
- `_assert_hook_saw_only_parent` requires a non-empty call list and runs with `create_grant=False`
  [CITED: tests/test1/test_guardian_parent_none.py:742-746, 773-794].
- `assert mx.state_calls["book"], "the create state hook was not consulted"` runs for the `denied`, `other_parent`
  and `global_change` conditions [CITED: tests/test1/test_authorization_matrix.py:1065].
- `data["cv_action_enabled"] is enabled` and `state.assert_called_once_with(actor, parent)` for anonymous and
  inactive actors [CITED: tests/test1/test_guardian_child_link_visibility.py:726, 733].
- `test_create_rendering_entry_points_keep_parent_and_adapter` expects `_cv_action_enabled_for_context` to be called
  for child-card and child-button entries [CITED: tests/test1/test_core_nested_create_state.py:112-150].
**How to avoid:** List these as intended expectation changes in the plan, each with the decision that causes it.
The visible result (`cv_resolve_action`) does not change, because permission denial already wins.
**Warning signs:** A failing assertion whose message mentions "state hook was not consulted".

### Pitfall 2: more than one provider call per link, or a call above the immediate parent

**What goes wrong:** `tests/test1/test_ancestor_costs.py` fails without any query count changing.
**Why it happens:** The suite pins events, not budgets [VERIFIED: tests/test1/test_ancestor_costs.py:157-178, 255-266]:
- `assert len(set(measured["gates"])) == len(measured["gates"])  # no identical gate twice in one request`
- `assert len(rest_gates) == helper_gates` with `helper_gates = 1 if provider == "guardian" else 0`
- `assert all(gate[1] == ancestors_outer_first[-1] for gate in rest_gates)  # helpers: immediate parent only`
**Consequences for the design:**
- The nested Guardian create gets exactly one gate. A generic step 1 plus the hook's default is two.
- A **core** create button on a nested list makes **zero** ancestor gates today. Routing core sibling links through
  a generic step 1 would make one. So sibling-page sites must reach the parent rule only for targets that have one
  today (the Guardian create), not for every nested sibling target. See "Two kinds of stage-1 site".
- In the depth-3 chain, handing the check the request's higher ancestors would add gates on Publisher and Book.
**How to avoid:** Pattern 1 and Pattern 3. Run this suite after every task that touches a call site.

### Pitfall 3: the `view=` argument changes costs and the access trace

**What goes wrong:** Guardian query counts drop on some pages, or traced pages record different steps.
**Why it happens:** `_request_checker` returns a fresh checker for `view is None` and a view-cached one otherwise;
the recorder keys steps by owner and deduplicates "once per owner and identical report"
[CITED: src/crud_views/lib/access_trace.py:67-85], and the Guardian gate uses
`view if view is not None else object()` as that owner.
**What each site passes today:**
- child link, card child action, navbar child item: `view=None` (`base.py:535`, `guardian/views.py:385`)
- Guardian list-page create: the list view (`guardian/mixins.py:352` into `guardian/views.py:344`)
- cancel target: the rendering view (`guardian/mixins.py:450`)
**Pinned:** `expected = (0 if composition == "plain" else 4) + (4 if vocabulary == "cold" else 0)` plus two for a
cold actor [VERIFIED: tests/test1/test_navbar_costs.py:157-159]; the comment at lines 44-45 states "These
class-level admissions create fresh Guardian checkers; no persistent rendering-view checker is involved."
`docs/reference/context_buttons.md` documents the same limitation [CITED: 229-230].
**How to avoid:** Keep each site's `view=` value in stage 1. Reusing the view-local checker is stage 2's gain and
must not leak in unannounced.

### Pitfall 4: `parent_spy` only sees calls made through a module attribute

**What goes wrong:** Dozens of `spy.assert_called_once_with(actor, parent)` assertions fail although behaviour is
right.
**Why it happens:** `parent_spy` monkeypatches `_immediate_parent_access` on three modules: `crud_views.lib.ancestors`,
`crud_views_guardian.lib.mixins` and `crud_views_guardian.lib.views`
[CITED: tests/test1/test_guardian_child_link_visibility.py:615-630]. A new module that does
`from crud_views.lib.ancestors import _immediate_parent_access` at import time holds the original function and is
invisible to the spy.
**How to avoid:** Call it as `ancestors._immediate_parent_access(...)` through the module, or import it inside the
function body as `base.py:533` does today. The spy also requires the signature
`(view_class, user, parent_obj, *, rendering_view=None)` and exactly one call per rendered link.

### Pitfall 5: the template filter is documented and pinned as answering the parent rule

**What goes wrong:** `view|cv_context_has_permission:"create"` turns `False` on Guardian child pages.
**Why it happens:** It passes the page object, and a Book on its detail page resolves to its Publisher through case 4.
`docs/reference/context_buttons.md` says so [CITED: 602-607]; `_render_permission_filter(response) == str(permitted)`
pins it [CITED: tests/test1/test_authorization_matrix.py:1064], as do
`tests/test1/test_guardian_parent_none.py:796, 819, 835` and `tests/test1/test_authorization_templates.py:602`.
**How to avoid:** Treat the filter as a Tier A site. It needs the permission part of the check with the ancestors
taken from `view`. Two documented cases "stay `False`" today, a child list page and a `ManyToMany` child page
[CITED: docs/reference/context_buttons.md:609-617]; see Open Question 3 before changing either.

### Pitfall 6: the step order of the concept reverses today's child-link order

**What goes wrong:** Tests that assert "own denial skips parent work" fail, and a misconfigured parent policy now
raises on pages where the link was simply hidden.
**Why it happens:** Today `_cv_child_link_has_access` asks own access first and returns before the parent gate
[VERIFIED: base.py:530-532]. The concept fixes the order as parent gates, then own permission (section 5.2).
**Known pins:** `spy.assert_not_called()` after an own denial in `test_plain_child_link_errors`
[CITED: tests/test1/test_guardian_child_link_visibility.py:484-488] and in
`test_preservation_create_policy_once` [CITED: 874-875];
`test_query_denied_actors_and_custom_do_no_permission_work` asserts zero queries for a custom own denial
[CITED: 1254-1269]; `events == ["access"]` in the navbar test [CITED: tests/test1/test_navbar_permissions.py:126].
The same order is documented: "Own-access denial stops there" (`context_buttons.md:187-188`), "Own denial
short-circuits parent work" (`nested.md:587`), "Own denial skips parent work" (`card-list-view.md:327`).
**How to avoid:** This follows from approved input, so it is an intended change. Name the tests and the three doc
passages in the plan. The boolean result is identical for a correctly configured project; what changes is query
cost for own-denied actors and the misconfiguration case.

### Pitfall 7: unbound views in tests have no resolved parent

**What goes wrong:** D-16 denies links in tests that build a view with `RequestFactory` and set `kwargs` by hand.
**Why it happens:** Such views never ran the guard, so `_cv_ancestor_state` is absent. Example:
`test_preservation_ordinary_row_and_sibling_actions` sets `host.kwargs` and expects a sibling link to be allowed
[CITED: tests/test1/test_guardian_child_link_visibility.py:1004-1010].
**How to avoid:** Parent-page sites (A2, A3, A4) hold the parent in hand and do not need guard state. Sibling-page
sites (A8, A9, A11) need the rendering view's resolved parent; decide explicitly what they do without one, and do
not fall back to `cv_get_parent_object()`'s database read. Leaving `SiblingContextButton` out of stage 1 avoids this
test entirely.

### Pitfall 8: a second meaning sneaks back in through the create adapters

**What goes wrong:** D-13 holds for the moved sites, but a remaining consumer still reaches
`CreateView._cv_action_enabled_for_rendering`, whose last fallback is
`get_object_or_404(parent.viewset.model, pk=kwargs[arg])` [VERIFIED: src/crud_views/lib/views/create.py:66-74].
**How to avoid:** The check calls `target.cv_action_enabled(user, action_obj)` directly. Do not route the check's
step 3 through the adapters.

### Pitfall 9: Resource targets

**What goes wrong:** A Resource ViewSet may be a nested leaf; its "objects" are not model instances.
**How to avoid:** Keep using `_immediate_parent_access` and `_check_nested_auth`, which already serve Resource
leaves. Add one Resource leaf to the characterization matrix if a child link can target one.

### Pitfall 10: doc-pinning tests

**What goes wrong:** Editing a reference page breaks a test that reads it.
**Why it happens:** `tests/test1/test_ancestor_docs.py` (an ancestor suite, 34 tests) reads `nested.md`,
`guardian.md`, `CHANGELOG.md` and `migrating-1.0.md` by section and asserts phrases and anchors; `test_bulk_docs.py`
reads `guardian.md` and `card-list-view.md`; `test_card.py` executes a fenced recipe from `card-list-view.md`.
**How to avoid:** Keep existing anchors (`#what-the-create-access-helpers-accept`,
`#parent-to-child-collection-links`, `#nested-guardian-create-access`, `#child-link-parent-permissions`,
`#visible-links-and-buttons`). Run the `*_docs.py` tests and `mkdocs build --strict` after every doc task.

```python
def _cancel_target_available(target, user, obj, rendering_view):
    """Evaluate the concrete destination's access and state hooks, including overrides."""
    target_obj = obj if target.cv_object else None
    if not target.cv_has_access(user, target_obj):
        return False
    if target.cv_object:
        return target._cv_action_enabled_for_rendering(user, target_obj, rendering_view)
    action_obj = None
    if target.cv_viewset.has_parent:
        action_obj = rendering_view._cv_cancel_parent_object()
        if action_obj is None:
            return False
    return target._cv_action_enabled_for_rendering(user, action_obj, rendering_view)
```

All six questions were answered by the maintainer on 2026-11-23. The answers are locked decisions in

1. **Does "the existing ancestor suites pass without edits to their expectations" cover `test_ancestor_helpers.py`
   and `test_ancestor_resolution.py:749, 771`?**
   - What we know: the concept counts 18 `test_ancestor_*.py` files as covering the request gate. Two of them
     assert link-path helpers: direct `cv_has_access(user, parent)` and `cv_has_access(user, own_child)` on a nested
     Guardian create, `_cv_child_link_has_access`, `_cv_action_enabled_for_context` and
     `_cv_action_enabled_for_rendering`.
   - What is unclear: read literally, the criterion forbids G1 and forbids replacing `_cv_child_link_has_access`.
     Read by intent (the request gate is unchanged), those helper assertions may be rewritten against
     `cv_create_has_access` and the check.
   - Recommendation: ask the maintainer before planning locks. Proposed wording: "Request-gate expectations in the
     ancestor suites are untouched. In `test_ancestor_helpers.py`, assertions on link helpers are rewritten to the
     narrowed contract; each rewritten line is listed in the plan." If the answer is no, plan G2 and keep all three
     adapter names callable.

2. **Do stage-1 call sites hand the check the higher ancestors the request already resolved (D-04)?**
   - What we know: D-04 says a link checks what it is handed plus what the request resolved. Doing that at the
     Guardian list-page create site breaks `test_ancestor_costs.py:175` ("helpers: immediate parent only") and adds
     gates in full-cascade mode; `test_ancestor_helpers.py:254-265` and `295-300` pin "never a farther ancestor" for
     helpers; `test_plain_child_link_farther_ancestor` pins a visible link with a 403 on click
     [CITED: tests/test1/test_guardian_child_link_visibility.py:499-562]; four reference pages document it.
     Without stage 2's shared checker, each extra Guardian gate costs queries.
   - What is unclear: whether D-04's positive half binds stage-1 call sites, or only fixes what the function does
     with a longer list.
   - Recommendation: the function gates every level it is handed, proven by a direct unit test with a two-level
     list; stage-1 call sites pass one level. Record in the plan that extending the lists waits for stage 2 or 3.
     If the maintainer wants the stricter links now, the plan must list the changed expectations above.

3. **For sibling-page sites, is the parent taken from the page's resolved URL parent, or from the page object's
   foreign key as today?**
   - What we know: the concept points to resolved ancestors. Today case 4 walks the FK and **denies a `ManyToMany`
     child page**, which the docs call a deliberate non-feature of 1.0 [CITED: docs/reference/guardian.md:270-282].
     Using the URL parent would allow that link, and would let the filter answer `True` on a child list page, where
     the docs say it stays `False`.
   - Recommendation: use the resolved URL parent, because it needs no query and matches the request; then either
     keep the two documented `False` cases by an explicit condition, or name both as intended changes with their doc
     edits. Do not let them change silently.

4. **Does a `cv_create_has_access` override now governing child buttons, card child actions and navbar items need
   the maintainer's explicit yes?** Today those three paths bypass the hook. Recommendation: yes, and state it in
   the Breaking entry; it is the consistency the issue asks for.

5. **How far does Tier B go in stage 1?** B1 and B2 are named by D-15. B3 (`ParentContextButton`), B4
   (`SiblingContextButton` state argument) and B5 (non-child card action) are the same kind of narrowing in classes
   the concept lists under stage 3. Recommendation: include B3 to B5 only as argument narrowing, with no step 1, so
   the documented hook meaning is true for every package caller at the freeze; or leave them and say so in the
   migration note. The first option is small and removes a caveat.

6. **Should the queryset-only Guardian exception survive?** The link shows while the request answers 403. Keeping
   it preserves AC-2 and the documented exception; removing it is a behaviour change. Recommendation: keep it in
   stage 1.

### Known threat patterns for this change

| Pattern | STRIDE | Standard mitigation |
|---------|--------|---------------------|
| A public hook starts answering "allowed" without the parent check (the nested Guardian create) | Elevation of privilege, at the presentation layer | `cv_has_access(user, None)` stays `False`; a named test with an actor who holds the parent grant; the filter and `SiblingContextButton` covered by the same test |
| A link shown that the request refuses | Information disclosure (the existence of an action) | Accepted and documented limit for higher ancestors; the request gate is authoritative. Do not widen what is shown: every Open Question above is resolved toward "same or stricter". |
| A link hidden that the request allows | Denial of service, usability | The characterization matrix |
| A cached answer granting access | Elevation of privilege | D-20: nothing stored. Anti-goal of the concept. |
| A state rule ending up in a cache | Tampering | D-20; the state hook is called on every decision |
| Authorization records read from another database | Tampering | `_check_nested_auth` stays on every gate path |
| An inactive or anonymous actor passing through a provider shortcut | Elevation of privilege | Keep D-18 and Guardian's stricter rule; `_guardian_ancestor_has_permission` denies both before any shortcut |
| A stand-in view passed to a hook | Spoofing of request context | D-06: pass the real view or `None` |

The reviewer brief (concept section 13) defines what counts as a finding. The two most relevant classes for the
plan check: a direct hook call that now answers "allowed" where it answered "denied", and a project override that
changes behaviour without a migration note.
