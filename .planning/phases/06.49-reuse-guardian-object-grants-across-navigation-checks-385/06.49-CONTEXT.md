<domain>
## Phase Boundary

Deliver stage 2 of the approved link-access concept: reuse Guardian grants through one checker on the user
object, replacing the existing checker construction sites. Each destination still evaluates its own permission
and action-state rules. Document the checker lifetime and measure the query savings.

Phase 06.49 follows shipped stage 1 (06.48, issue #407, PR #409) and precedes Phase 7. This is execution order;
the concept describes stage 2 as independent of stage 1. The maintainer's 2026-11-24 decision to plan this now
supersedes the earlier post-1.0 deferral of Roastery finding 37.

</domain>

<decisions>
## Implementation Decisions

The D-01–D-09 identifiers below are local to this phase. References to concept decisions identify the original
approved decisions; these summaries do not replace the concept.

### Authority and bounded implementation

- **D-01:** Use `superpowers/specs/2026-11-23-link-access-check-design.md` at commit `4b65990f` as the authority:
  section 12.1 supplies settled decisions, 12.3 supplies stage-2 scope, and 12.7 supplies the later amendments.
  Section 12.7 supersedes the older “to verify” items in 12.3. The concept prevails over the issue snapshot.
  Follow section 13's defect-focused reviewer brief; do not reopen approved architecture or broaden scope.
- **D-02:** One small helper in `crud_views_guardian` returns the user's `ObjectPermissionChecker`, creating it
  on first use and storing it on that user object (concept D-09). Replace all four existing construction sites
  and the view-local `_cv_guardian_ancestor_checker`. Existing hooks already receive the user; no rendering-view
  plumbing, temporary view exposure, fake views, or hook-signature changes are needed.

### Access behavior and lifetime

- **D-03:** Share loaded grants only, never per-view/object decisions (concept D-20). Each destination retains
  its permission rules and evaluates its action-state hook after permission passes. Preserve anonymous,
  inactive, superuser, direct-grant, group-grant and model-fallback outcomes except for D-04 below. The shipped
  link check, request gate structure, queryset filtering, and published access-trace output remain unchanged.
- **D-04:** Apply concept D-37: a second check of the same object in one request uses grants already loaded
  during that request. Changed grants are seen from the next normal request. In the workflow-refusal case,
  the transaction has unwound and no write follows the scoped reload: render the form with its error once
  more; the next request answers 403. Add no fresh-checker exception, flag, or bypass. Change only the
  `permission` cases of the identified workflow test; preserve its `scope` and `action` cases and scoped-reload
  assertions. If planning finds another repeated-object check, name it and apply D-37 there too.
- **D-05:** Document that the checker follows the Python user object's lifetime. Normal requests receive
  distinct users/checkers; retaining the same user in tests, a shell, or a background task retains its loaded
  grants, as Django's model-permission cache does. The lazy-user wrapper question is answered by the prior
  probe. Anonymous-user compatibility was established by reading; add the direct-hook regression test required
  by section 12.7. `get_objects_for_user` neither reads nor fills the checker and keeps its existing filtering.

### Measurements, tests and documentation

- **D-06:** Apply concept D-38: add a pinned before/after query count for a Guardian list page with row actions.
  Update the navbar cost table and affected navbar, ancestor and child-link count pins from measurements.
  `prefetch_perms` remains outside this phase; its future inclusion depends on the new measured row-action cost.
  The issue's Roastery totals of 20 or 18 queries are projections, not promised results or timing evidence.
- **D-07:** Carry every section-12.7 probe finding into the plan. The probe's failures are known adaptation
  points, not permission to weaken unrelated assertions:

  | Finding | Required planning treatment |
  | --- | --- |
  | F-01 | Exempt the chosen checker attribute by name in `test_no_decision_is_stored`; retain the remaining assertions against stored decisions. |
  | F-02 | Apply D-04 to the workflow-refusal permission cases and retain scope/action behavior. |
  | F-03 | Update the five affected child-link query pins using measured figures. |
  | F-04 | Re-measure the 80 isolated navbar cases; the probe observed 4 queries becoming 2 or 0. Ancestor costs may remain unchanged. |
  | F-05 | Re-fetch the user after changing grants in child-collection parity and cancel-permission tests; preserve their expected outcomes. |
  | F-06 | Express request isolation through distinct users and their checkers, replacing assertions about the retired view-local checker. |
  | F-07 | Update the lifetime/cost passages in the navbar and context-button references and the Guardian ancestor module docstring. |
  | F-08 | Locate construction sites by symbol; the current mixin sites are at lines 153 and 210, ancestor sites at 67 and 70. |

- **D-08:** Preserve the stage-1 decision matrix and access-trace contracts. The prior discarded probe found
  them unchanged; this is historical evidence, not verification of this phase. Its delete and bulk paths were
  not audited by reading, so do not claim that they were. The plan must identify any additional D-37 cases it
  finds. Update the documented checker lifetime and measured costs. No `### Breaking` entry is expected;
  if planning discovers a need for one, stop and report the concrete case. The repository requires a matching
  `docs/migrating-1.0.md` update for any approved Breaking entry before 1.0.

### Maintainability and exclusions

- **D-09:** Follow the repository's developer-maintainability constraint: a small helper and bounded call-site
  replacements, with understandable tests and explicit lifetime documentation. This phase excludes Django
  caches, cross-request caching, cached access/state decisions, `prefetch_perms`, link-check redesign, stages
  3–5/top-level navigation, and unrelated manage-page optimizations.

### Planner discretion within the approved handover

Choose the helper's module/name, checker attribute name, imports, focused test organization, row-action cost
fixture, and documentation placement within the boundaries above. These are implementation details, not newly
approved behavior. The probe's `_cv_guardian_checker` name is evidence, not a newly frozen public API.

## Existing Code Insights

### Reusable Assets

- `src/crud_views_guardian/lib/ancestors.py`: `_request_checker` currently constructs a fresh checker without a
  view and otherwise keeps a `(user, checker)` tuple on the view. `_guardian_ancestor_has_permission` consumes it.
- `src/crud_views_guardian/lib/mixins.py`: `GuardianObjectPermissionMixin._check_object_perm` and `cv_has_access`
  each construct a checker after the existing actor/model-fallback branches. These and the two ancestor branches
  are the four construction sites confirmed during the scout.
- `tests/test1/test_navbar_costs.py`, `tests/test1/test_ancestor_costs.py` and
  `tests/test1/test_guardian_child_link_visibility.py` provide existing count pins.

### Established Patterns

- Actor admission, default-database guards, model fallback, object permission and action-state evaluation have
  separate responsibilities. Replace checker construction while retaining these boundaries and trace events.
- The core remains separate from the optional Guardian app; existing Guardian imports are local to the paths
  that need them. Keep the addition bounded to that integration.
- `tests/test1/test_link_access_matrix.py` and `tests/test1/link_access_matrix_baseline.json` characterize the
  shipped link decisions. `tests/test1/test_access_trace*.py` cover trace behavior; they are regression evidence
  to retain, not formats to redesign.

### Integration Points

- `src/crud_views/lib/link_access.py` reaches Guardian through the existing ancestor and own-permission hooks;
  it needs no new checker argument or rendering-view bridge.
- `src/crud_views_workflow/lib/views.py`: refused transitions reload the scoped object for error rendering;
  `tests/test1/test_workflow_review.py` contains the D-37 case.
- `tests/test1/test_link_access.py`, `tests/test1/test_cancel_permissions.py` and
  `tests/test1/test_ancestor_boundaries.py` contain the assertions identified by F-01, F-05 and F-06.
- Guardian list filtering remains independent. Measure row-action checks through a real Guardian list page
  without introducing page-wide grant prefetching.

<specifics>
## Specific Ideas

The motivating example is the Roastery customer's four-item navbar: a user with view permission may see Details
while Edit remains hidden. Sharing that customer's loaded grants must not share the two destinations' decisions.
The reported warm-request baseline was 26 total queries with the navbar and 18 without it. The projected savings
and discarded probe inform planning; neither is a fresh measurement from this phase.

The maintainer selected option 1, “Capture the approved handover as phase context,” after the scout found no new
substantive decision. No additional concern or capability was added in this discussion.

</specifics>
