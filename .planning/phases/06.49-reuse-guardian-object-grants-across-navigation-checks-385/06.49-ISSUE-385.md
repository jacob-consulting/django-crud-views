# Issue #385 snapshot

**Captured:** 2026-11-24, after the stage-2 amendments D-37 and D-38 (body verbatim below; issue comments: 0)

## Problem

Each object navbar item that consults Guardian for the same owner can trigger a fresh pair of queries for that owner's user and group grants. The Roastery demo measured **26 queries with its four-item customer navbar and 18 with it switched off** on a nested order list. This was the second request, with caches warm, for a user with object grants. The navbar was built once. The eight extra queries were four repetitions of the same two grant lookups.

Sharing the loaded grants within the navbar would bring the projected total to **20**, saving **6 of 26 queries (23.1%)**. If the page has already loaded those grants for the same user and customer, reusing its checker could bring the projected total to **18**, saving **8 of 26 (30.8%)**. These are projections for this fixture. The response-time impact is unmeasured.

Reported in Roastery finding 37. The object navbar originated in #381. The theme follow-up is tracked in #384.

## gsd-handover

Updated 2026-11-24. This issue is **stage 2** of the approved concept [One link access check, shared grants](https://github.com/jacob-consulting/django-crud-views/blob/4b65990f/superpowers/specs/2026-11-23-link-access-check-design.md). The link is pinned to commit `4b65990f` on the branch `feature/link-access-check-design`; `main` does not have the stage 1 and stage 2 amendments yet. Section 12.1 lists the settled decisions, section 12.3 gives this stage's scope and constraints, and section 12.7 amends them after stage 1 shipped (#407, PR #409). A planner starts there and does not reopen those decisions.

The maintainer approved the following.

1. **This stage is planned now.** The maintainer decided this on 2026-11-24, after stage 1 shipped (#407, PR #409). It replaces the earlier decision to defer item 37 until after 1.0.
2. **The shared Guardian checker lives on the user object** (concept D-09), reached through one small helper in `crud_views_guardian`. The four places that build a checker today use it, and the view-local ancestor checker is replaced by it. This settles the placement that this handover previously left open.
3. **No Django cache in this issue.** The request gate always reads grants fresh, so a revoked grant takes effect on the next request (D-02). A cross-request cache may serve link rendering only; it is specified in the concept's section 8.1 and decided again after a real menu has been measured (D-03).
4. **Preserve each destination's permission and action-state checks.** Share the loaded Guardian grants for a user and object. Each item must still apply its own permission rules and, after permission passes, its own action-state hook. For example, a user with view permission can see Details while Edit stays hidden.
5. **Only grants are shared, never decisions** (D-20). The answer for a view and object is recomputed from the shared grants each time.

Starting points are unchanged: the existing view-local Guardian ancestor checker, the measured-cost table in `docs/reference/navbar.md`, and `tests/test1/test_navbar_costs.py`.

Section 12.7 records a probe of this stage against the shipped stage 1 (findings F-01 to F-08) and two maintainer decisions of 2026-11-24. Nothing is left open or to verify.

- **D-37:** a second check of the same object in one request uses the grants that request already loaded. A grant changed during a request is seen from the next request on. This is the one stated exception to "every access decision is unchanged" and affects the workflow reload after a refused transition (F-02).
- **D-38:** loading the grants for all rows of a list or card page in one step (`prefetch_perms`) is not part of this issue. This issue adds a pinned query count for a Guardian list page with row actions, before and after; the one-step loading is decided afterwards on that figure.
- **Answered:** an attribute kept on `request.user` works through Django's lazy user wrapper (probe) and for the anonymous user (by reading; the plan adds one test). `get_objects_for_user` list filtering does not interact with the checker.
- **For the plan:** the stage 1 test `test_no_decision_is_stored` contradicts D-09 and is adjusted (F-01); F-03 to F-08 list the further tests, count pins and documentation passages to update.

Superseded from the earlier handover: passing the rendering view through access hooks, and exposing it temporarily during a navbar access check, were considered as ways to reach a request-scoped checker. Keeping the checker on the user object makes both unnecessary. The top-level navigation is the concept's stage 5 and has its own design; it is no longer a prerequisite for deciding the placement.
