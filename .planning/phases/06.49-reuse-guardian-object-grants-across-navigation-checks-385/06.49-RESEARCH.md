## Summary

Use the approved one-user/one-checker helper and replace only checker acquisition. The current four constructor expressions are two own-object sites and two branches of the ancestor accessor. Existing permission selection, actor checks, default-database validation, model fallback, state evaluation, and trace recording remain their present callers' responsibilities. There is no reason to change the link checker or pass another view through hooks. [VERIFIED: src/crud_views_guardian/lib/mixins.py:141-212; src/crud_views_guardian/lib/ancestors.py:61-105; superpowers/specs/2026-11-23-link-access-check-design.md:432-469]

The important work is demonstrating the lifetime contract and preserving meaningful assertions when tests reuse Python users. Guardian already stores all grants for an object in its checker; sharing that checker makes repeat checks reuse the grant set while every target still asks its own permission. D-37 intentionally permits same-request grant staleness, including the workflow refusal reload. Next-request denial requires a new normal request user, not clearing an attribute on a long-lived test user. [CITED: https://django-guardian.readthedocs.io/en/stable/api/core/; VERIFIED: superpowers/specs/2026-11-23-link-access-check-design.md:569-609]

### Guardian internals and user lifecycle

Installed-source evidence is distinct from public documentation. The inspected package was Guardian 3.5.2 in the cached Django 6 environment. Its checker initializes “self._obj_perms_cache: dict = {}”, loads user/group permission querysets on an object-cache miss, and keys by “return ctype.id, force_str(obj.pk)”. Therefore equivalent ORM instances of one model/PK share grants; different models/PKs do not share a grant entry. Preserve the existing database guards rather than adding another cache key scheme. [VERIFIED: installed guardian/core.py:56-82,151-192]

Django's installed AuthenticationMiddleware assigns “request.user = SimpleLazyObject(lambda: get_user(request))”. LazyObject attribute assignment forwards through “setattr(self._wrapped, name, value)”. Store/retrieve with normal getattr/setattr, not mutation of the wrapper's __dict__. This independently supports the prior probe's lazy-user finding; no new probe was implemented. [VERIFIED: installed django/contrib/auth/middleware.py:18-40; installed django/utils/functional.py:287-296; superpowers/specs/2026-11-23-link-access-check-design.md:596-609]

For direct anonymous hooks Guardian's get_identity maps an AnonymousUser through get_anonymous_user, then constructs a normal checker. Attach the checker to the caller's anonymous user, not to a global anonymous actor. The installed version supports an optional anonymous-identity cache; therefore describe the saved lookup as dependent on Guardian configuration rather than promising one database query for every anonymous construction universally. Do not change that configuration. [VERIFIED: installed guardian/utils.py:68-86,129-152; installed guardian/core.py:56-63]

Django's documented model-permission cache similarly lives on a user instance. Re-fetching creates a new permission lifetime; refresh_from_db does not clear that cache. Tests that represent separate requests must use separate users or Client requests. [CITED: https://docs.djangoproject.com/en/6.0/topics/auth/default/#permission-caching]

## Common Pitfalls

- **A reused test user masquerades as another request.** Re-fetch after changing grants where the test models a new lifetime; do not erase the shared attribute globally in fixtures. Keep explicit stale-same-user tests. [VERIFIED: F-05 source references above; CITED: https://docs.djangoproject.com/en/6.0/topics/auth/default/#permission-caching]
- **A warm model cache is called a warm Guardian cache.** Navbar measurement runs after a real request; whether that request loaded owner grants differs by page/fixture. Preserve the retained checker when measuring incremental navbar work and report its priming. [VERIFIED: tests/test1/test_navbar_costs.py:34-61,119-138]
- **Lower counts are accepted without SQL attribution.** ContentType state can change independently of grants. The stage-1 receipt documents six queries in a combined run versus seven in a fresh process solely because of ContentType warm-up. Compare like-for-like SQL categories and retain both observations if encountered. [VERIFIED: .planning/phases/06.48-link-access-check-as-a-private-function-narrow-obj-in-cv-has/06.48-COST-BASELINE.md:570-587]
- **Constructor import moves break mocks.** Keep import-time behavior deliberate and retarget private-seam mocks without changing public trace expectations. [VERIFIED: tests/test1/test_access_trace_guardian.py:49-69,239-263,508-530]
- **D-37 is weakened by a workflow-only bypass.** Keep scoped reloading and state checks; only grant freshness changes for the already-loaded object. [VERIFIED: concept:571-584]
- **Documentation says every Guardian permission call is shared.** Backend has_perm and queryset shortcuts are independent; only the package's four constructors are replaced. [VERIFIED: installed guardian/backends.py:113-114; installed guardian/shortcuts.py:671-776]
- **Accidental stage-3 behavior change.** Do not reorder ordinary state hooks, change link parent lists, add queryset probes, or make the helper public. [VERIFIED: context D-09; src/crud_views/lib/view/base.py:939-945]

## Code Examples

~~~python
def _get_guardian_checker(user):
    checker = getattr(user, "_cv_guardian_checker", None)
    if checker is None:
        from guardian.core import ObjectPermissionChecker

        checker = ObjectPermissionChecker(user)
        user._cv_guardian_checker = checker
    return checker
~~~

The constructor and has_perm APIs are documented by Guardian; the proposed attribute/name above is intentionally new. The helper should neither decide access nor know about view/state rules. [CITED: https://django-guardian.readthedocs.io/en/stable/api/core/]

## State of the Art

This phase changes the application's ownership of an existing library object; it does not require adoption of a new API. Guardian documents instance-cached object grants, and Django documents instance-cached model permissions. Use those mechanisms with the explicitly documented retained-user cost.
