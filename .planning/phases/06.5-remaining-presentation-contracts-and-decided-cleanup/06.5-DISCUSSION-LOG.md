## Heading customization

### Question 1: How should alternative themes control heading sizing?

Options presented:

1. Theme-configurable sizing (recommended)
2. Keep compatibility classes
3. Follow semantic level

**Final selection:** Theme-configurable sizing: keep Bootstrap defaults, but let themes replace or omit sizing classes without copying the heading template.

### Question 2: Where should host-based heading icon classes go?

Options presented:

1. On the title-bearing element (recommended)
2. On a dedicated icon wrapper

**Final selection:** On the title-bearing element: heading for plain titles, button for accordion/tab titles. Element-based libraries render one child icon instead. Preserve visible title text and avoid duplicate icons.

### Question 3: Should themes style heading icons uniformly or by location?

Options presented:

1. Shared default with location overrides (recommended)
2. One shared style only
3. Separate styles per location

**Final selection:** Shared default with optional page, modal and group overrides.

### Question 4: How should existing custom heading templates migrate?

Options presented:

1. Preserve working overrides
2. Require immediate migration

**Final selection:** Require immediate migration: establish one heading contract before 1.0; incompatible custom templates must update. Ship tested migration examples and document breaking changes.

**History/clarification:** User initially selected preserve working overrides, then explicitly reopened this question and changed the answer to option 2. Immediate migration supersedes the earlier choice; do not retain compatibility as a locked requirement.

## Tabs and accordion IDs

### Question 1: Should tab and accordion IDs also support external links and application scripts?

Options presented:

1. Internal IDs only (initially recommended)
2. Optional stable IDs

**Final selection:** Optional stable IDs: generate collision-free IDs by default and allow application-supplied stable component/group identifiers for Selenium tests, links and scripts. Applications must ensure uniqueness across repeated components, including page/modal coexistence.

**History/clarification:** User initially chose internal IDs, reopened the question, asked whether stable IDs for Selenium favor option 2, then explicitly selected option 2. Optional stable IDs supersedes the initial choice. The Selenium suite is an explicit consumer requirement.

### Question 2: How should keyboard navigation work in vertical tabs?

Options presented:

1. Activate as focus moves (recommended)
2. Activate explicitly with Enter or Space

**Final selection:** Arrow keys move focus and immediately activate the corresponding tab/panel. Start with the first tab and its panel selected.

### Question 3: What should happen when application-supplied IDs collide?

Options presented:

1. Report a clear configuration error (recommended)
2. Automatically add suffixes

**Final selection:** Report a clear configuration error for collisions detectable during rendering. Document application responsibility for uniqueness across separately rendered page/modal components. Do not silently add suffixes that change supplied stable IDs.

### Question 4: How should copied tab and accordion templates migrate?

Options presented:

1. Immediate migration (recommended)
2. Temporary compatibility

**Final selection:** Immediate migration before 1.0 to the new shared ID and selection context, with tested examples for updating copied templates.

## Removed alias behavior

### Question 1: What should happen when application code still supplies CardAction.no_label?

Options presented:

1. Clear migration error (recommended)
2. Normal unknown-field handling, potentially silently ignoring the keyword

**Final selection:** Reject the removed keyword with a clear migration error explaining label_mode as the replacement, including label_mode="icon" for icon-only actions. Reject presence even when its value is False; do not silently ignore stale configuration.

**History/clarification:** User selected clear migration error. Assistant clarified that presence with False also fails; user then selected next area. Removal itself and obsolete template cv_no_label rejection-guard cleanup were already decided and were not reopened.

## Badge styling

### Question 1: What should alternative themes receive for badge styling in 1.0?

Options presented:

1. Semantic values plus existing classes (recommended)
2. Existing classes only; defer semantic values

**Final selection:** Expose resolved semantic color and pill state alongside existing classes so themes can map native styling. Preserve Bootstrap output by default.

### Question 2: Should semantic badge colors preserve arbitrary string names?

Options presented:

1. Allow custom color names (recommended)
2. Restrict to standard names

**Final selection:** Allow custom color names. Pass through the resolved name; themes map supported names to their styling. Do not introduce a standard-name-only restriction.

### Question 3: What happens when a color map has no match or a color function returns None?

Options presented:

1. Render the ordinary value (recommended)
2. Render a neutral badge

**Final selection:** Preserve current behavior: render the ordinary value without a badge when no color resolves.

### Question 4: Should an explicit property template override a resolved badge?

Options presented:

1. Preserve badge precedence (recommended)
2. Explicit property template wins

**Final selection:** Preserve existing badge precedence over property template=. Themes customize badges through their badge template, now receiving semantic color and pill values.
