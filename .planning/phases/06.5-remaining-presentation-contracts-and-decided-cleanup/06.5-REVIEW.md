### CR-01: BLOCKER — Browser-close failure skips termination and reaping of the fixture server

**File:** `/home/alex/projects/alex/django-crud-views/tests/browser/presentation.cjs:446-455`
**Classification:** BLOCKER
**Related contract:** PRES-06; plan 08 owned-process cleanup; T-06.5-17 (medium security threat, same finding).

**Issue:** Browser and server cleanup run inside one try block. If `browser.close()` rejects, or its
five-second bound expires at line 447, execution jumps to the catch before the SIGTERM at line 449 and before
awaiting `childExit`. Recording a failed result and assigning `process.exitCode = 1` does not terminate the
still-referenced child process or its pipes. The fixture can remain listening on its port and the Node runner
can remain alive after writing its failure report. This breaks cleanup precisely on the failure path where
the bounded browser close is intended to protect the runner.

**Evidence:** Executed the current source's verbatim cleanup block in a Node VM with controlled browser and
child stubs, separately exercising a rejected close and the timeout path. Both produced
`childKillCalls: []`, no `serverExit` or `reaped` result, `status: "failed"`, and exitCode 1. No real fixture
or browser was launched by this reproduction. The current test file tests port rejection but does not
exercise this cleanup failure.

**Fix:** Make fixture termination and reaping unconditional with respect to browser-close success: use
independent guarded cleanup steps or put server cleanup in a finally belonging to browser cleanup. Preserve
the browser error and unsuccessful run status while still sending SIGTERM, using the existing bounded wait
and SIGKILL fallback, and recording the actual server exit/reaping result. Add failure-path regressions for
both close rejection and timeout; assert that server shutdown and reaping still execute and that cleanup
errors never turn the report into a pass. Keep the normal success and early-startup cleanup paths working.

### WR-01: WARNING — Heading icon reference publishes the wrong registry defaults

**File:** `/home/alex/projects/alex/django-crud-views/docs/reference/icons.md:204-207`
**Classification:** WARNING
**Related contract:** PRES-01/PRES-06; exact heading configuration and migration reference.

**Issue:** The reference says `heading:icon-inline` defaults to an empty string, that group host/inline
overrides ship as `{name_class}`/`me-2`, and that page/modal inherit the shared defaults. The shipped
registry has the opposite layout: shared inline is `me-2`, page/modal inline keys explicitly contain empty
strings, and group override keys are absent. This is not just equivalent wording about the final appearance:
presence decides fallback, and theme authors can inspect/copy these public registry entries when extending
or restoring styling. The page disagrees with the implemented API and the canonical table in
`docs/reference/buttons.md`.

**Evidence:** Imported the checkout's `DEFAULT_BUTTON_CLASSES` in the configured Django 5.2 environment.
Its heading entries are six size keys, shared host `{name_class}`, shared inline `me-2`, and empty
`heading-page:icon-inline`/`heading-modal:icon-inline` entries. Neither group override is present.
The producer is `src/crud_views/lib/button_classes.py:16-25`; layer-first presence lookup is at 184-195.

**Fix:** Correct these reference lines to describe the actual shared defaults and the two shipped empty
page/modal inline overrides. Describe group host/inline and page/modal host overrides as addressable but
absent by default. Keep the documented layer-first precedence and suppression behavior. Do not change
production defaults to match the incorrect prose.

### WR-02: WARNING — Heading reference claims an optional level that the parser requires

**File:** `/home/alex/projects/alex/django-crud-views/docs/reference/templates.md:49`
**Classification:** WARNING
**Related contract:** PRES-01/PRES-06; executable heading migration contract.

**Issue:** The new parameter description says `level` has “default 5”. It is a required argument:
`cv_heading` explicitly raises when `level` is absent. Following the claimed default and omitting the
argument prevents a copied template from compiling, including when a global header level is configured.

**Evidence:** In the checkout's configured Django 5.2 environment, compiling
`{% load crud_views %}{% cv_heading %}Title{% endcv_heading %}` raises
`TemplateSyntaxError: cv_heading requires level=`. The required-argument check is in
`src/crud_views/templatetags/crud_views.py:410-411`; the existing bad-arguments regression already covers omission.

**Fix:** State that `level` is a required integer literal from 1 through 6, and remove the nonexistent
default. Keep the actual parser and required `level=` in the published recipes; do not introduce a new
implicit default as a documentation repair.
