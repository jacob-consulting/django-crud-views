<domain>
## Phase Boundary

Deliver stage 3a of the approved link-access concept: move the remaining package link consumers onto the
shared private check, supplying known ancestors aligned to the actual target and evaluating permission
before state. Preserve the Guardian exceptions assigned to stage 3b, including their explicitly documented
partial narrowing when higher-ancestor gates become reachable in this stage.

Consumers: context, parent, sibling and child buttons; actions by view key in context and table rows; card
own and child actions; navbar owner and child items; the permission-only `cv_context_has_permission`
filter; core Cancel; and the bulk toolbar.

Phase 06.49 provides stage 2's shared Guardian checker. Implement 3a (#412), then 3b (#413), then 3c (#414),
before the 1.0.0 freeze. Those three issues supersede #411. The code baseline is
`feature/link-access-check-design` at `e444bbfc`; implementation PRs target that feature branch.
This discussion captures context only; research, plans, implementation and verification remain pending.

</domain>

### Authority and carry-forward rules

  It prevails if the issue or this summary differs. Sections 12.1, 12.6 and 12.7 still apply except where
  section 12.8's "Amends" column supersedes them. Do not treat stage-1 deferrals as permanent restrictions.
- D-39–D-44, D-52 and D-55 are settled stage-3a input. D-45–D-51 and D-53–D-54 describe later stages and do not
  authorize their implementation here. Reviewers follow section 13: concrete defects with evidence,
  without reopening the approved architecture or broadening scope.
- Follow `CLAUDE.md`'s developer-maintainability rule. Prefer a bounded helper and understandable
  call-site migrations; preserve proven paths outside the enumerated changes. Share Guardian grants
  through the existing user-owned checker, never permission/state decisions. Preserve its documented
  user-object lifetime and normal fresh-request behavior.
- Keep request-gate order, authorization responses, login redirects, access trace, and published
  `cv_access` / `cv_manage_view` formats unchanged. Configuration errors remain errors, not hidden links.
  Do not load ancestors solely to decide a link, fabricate views, consult ViewSet querysets for link
  membership, or introduce caches/prefetch. Cancel retains its existing parent-resolution hook exception.

### Settled concept decisions for stage 3a

- **D-39 — Delivery:** Stage 3 is three ordered issues: consumers (3a), Guardian exceptions (3b), public
  function (3c), all in milestone 1.0.0. PRs target `feature/link-access-check-design`; stage issues close
  when that branch merges to `main`.
- **D-40 — Consumer routing and rendering view:** Every in-scope package consumer uses the check for
  every target, including Guardian targets. Pass the real rendering view only when it belongs to the
  target's own ViewSet, otherwise `None`; `cv_create_has_access` never receives another ViewSet's view.
  Guardian object/list targets gain the parent and higher-ancestor gates the request already runs.
  Preserve D-30, D-33 with D-27, D-34, D-35 and nested Guardian Cancel until 3b, subject only to the
  documented higher-ancestor consequences below.
- **D-41 — Ancestor alignment:** Supply the immediate parent and every higher ancestor the request has
  already resolved, nearest first and aligned with the target's declared ancestry. An unknown level is
  `None`; it is not gated and cannot shift a farther object into its position. On the target's own
  ViewSet page, use guard state rather than `cv_get_parent_object`. For a child link, use the object/row
  its URL is built from as immediate parent, followed by aligned guard state. A missing immediate
  parent denies a nested target even if the rendering view did not run the guard. Cancel alone follows
  D-42. Add no public context API.
- **D-42 — Cancel's parent:** Use `cv_get_parent_object` through the existing
  `_cv_cancel_parent_object`. A guarded request reuses its resolved parent without a query; a view
  without guard state retains the hook's existing lookup. Only the built-in lookup's missing row is
  "unavailable"; a project override and its exceptions remain honored. Higher ancestors come only
  from guard state. For D-40, use the request-bound copy `cv_get_cancel_url` already creates.
- **D-43 — Bulk toolbar:** Call the check directly for the destination on the same ViewSet, like a
  context button. The toolbar no longer uses the cancel helper.
- **D-44 — Permission filter:** `cv_context_has_permission` runs ancestor gates and own permission only.
  It never calls the state hook and may return true for a permitted action that state disables.
- **D-52 — Bulk returns:** GET, warning-POST and all-blocked-page Cancel returns follow the new Cancel
  eligibility. Keep origin, fallback, success URL order; the chosen `Location` may change.
  Authorization responses and login redirects do not change. This applies again in 3b.

- **D-55 — Navbar child items:** The retained nested Guardian create exception belongs only to the
  existing page seam and list rewrite. Navbar child items use neither and always receive the aligned
  ancestor chain, including when rendered on the create target's own ViewSet page. The navbar item
  and context create button may therefore differ until 3b. This amends D-40.

### Guardian boundaries that must survive 3a

- A nested Guardian create still receives only the immediate parent where a consumer consults the
  retained page seam (context buttons, actions by view key, card own actions and permission filter on
  its own ViewSet pages), or where the list-page rewrite applies. Child buttons, card child actions
  and navbar child items receive aligned higher ancestors. Navbar child items do so on every page,
  including the target's own ViewSet pages (D-55); do not extend the exception to the whole page.
- On a nested Guardian list/card page, the key-based rewrite still overwrites a parent/sibling button
  whose key resolves to that page's create with the create result (L1).
- A queryset-only composition still skips the immediate-parent gate. Its higher ancestors are gated
  in 3a for links and for Cancel to a queryset-only nested list, whose path delegates to the core check.
- The anonymous nested-create exception (L2) survives where no higher level is gated. Where a higher
  gate is reached, it denies anonymous/inactive actors in 3a. Do not apply 3b's wider actor-rule change.
- Cancel through `GuardianParentPermissionMixin` retains its separate path and immediate-parent-only
  gate. It can therefore differ from a button to the same target on a higher ancestor until 3b.
- Do not change `GuardianQuerysetMixin._cv_link_permission` or `cv_get_context`, the Guardian create
  `_cv_link_permission` or `_cv_page_link_ancestors`, or the three Guardian
  `_cv_cancel_target_available` overrides. Preserve the state adapters and their overrides until 3b.
  Do not make a general rule that every Guardian exception is unchanged: the two partial narrowings
  above are approved consequences of the shared higher-ancestor gates.

### Required behavior and migration record

Carry all eight issue behavior changes into the plan and documentation:

1. Context/parent/sibling buttons, actions by view key and card own actions stop calling the state hook
   after permission denial. Cancel, bulk and navbar owner items already follow permission-first order.
2. Core and Guardian object/list targets gain the immediate-parent and known higher-ancestor gates,
   with the retained Guardian exclusions above. With default policies, parent `view` without `change`
   removes child update/delete/create links and the bulk toolbar; those requests already answer 403.
3. Missing guard state makes nested-target links unavailable, except Cancel's hook-based parent path.
   Reachable shapes include create/form pages, Resource leaves, non-CRUD views and direct calls;
   nested list/object views with a request and no guard state already raise before rendering.
4. Bulk toolbar eligibility comes directly from the shared check.
5. Bulk return URLs can change with Cancel eligibility, without changing return priority or auth responses.
6. Every consumer on the target's own ViewSet page supplies its rendering view to `cv_create_has_access`,
   including object pages and row/card actions; other ViewSets continue to supply `None`.
7. Cancel to a nested object target now asks for the parent: no query with guard state, one existing lookup
   without it. Missing built-in parent rows mean unavailable; custom-hook exceptions propagate.
8. Core nested-create button state and parent-button objects use guard state instead of the parent hook.
   Projects using that hook to annotate/rescope parents move the customization to the parent ViewSet queryset.

Remove `_page_action_object` and the second branch at each migrated call site. Keep
`_cv_page_link_ancestors` with its Guardian create override; its core default now means use the aligned
list. Keep `_cv_action_enabled_for_context` and `_cv_action_enabled_for_rendering` plus their overrides:
the remaining production rendering-adapter caller is nested Guardian Cancel. Rewrite tests that name
the removed helper or observe migrated consumers through the rendering adapter to use public hooks,
and list the changed tests. The issue's named files are a starting inventory, not an exhaustive list.

### Acceptance and evidence

The nine acceptance criteria in the issue snapshot apply in full. In particular:

- Cover every consumer, and list every remaining production `cv_has_access` and `cv_action_enabled`
  call with the reason it remains. Prove permission-before-state separately at each changed site and
  prove the filter never evaluates state, including a permitted-but-state-disabled action.
- Exercise the default two-level parent `view`-without-`change` denial, including bulk and request 403.
  For three levels, use non-default operation pairs or an `actions` entry so the target actually needs
  a stricter far-ancestor permission than the page. Cover every consumer for core and Guardian
  object/list targets; pin the Guardian create seam/rewrite and nested Guardian Cancel exclusions.
  Explicitly deny the D-55 navbar child-create item on its own ViewSet page when its higher gate fails.
- Prove cross-ViewSet ancestor alignment with Guardian objects at their own levels; an unknown level
  stays `None`. Cover missing guard state, Cancel's built-in missing-parent behavior and custom-hook
  exception propagation, and the same-ViewSet-or-`None` rendering-view rule.
- List each changed stage-1 matrix cell with its reason. Changes only move toward permission denial
  (enabled/state-disabled to permission-hidden/disabled); no cell becomes more available. Preserve
  request-gate, ancestor and access-trace expectations. List necessary private-helper observation
  rewrites explicitly; do not conceal a behavioral change as a test adaptation.
- Measure before/after costs for navbar, context buttons, row/card actions, Cancel and bulk toolbar.
  Report gate calls separately from permission queries. Preserve prior-stage receipts as historical
  evidence; existing numbers do not certify this phase. Broad pytest runs use multiple workers per
  repository policy; choose focused runs and query pins during planning.
- Publish one `### Breaking` entry in `CHANGELOG.md`, matching `docs/migrating-1.0.md` guidance and
  affected reference pages. Golden files remain byte-identical unless one of the eight approved
  behavior changes explains the difference. Configuration errors at rendering remain observable;
  a missing own permission key still denies.

### Planner discretion

query-count pins are open to the planner. No new product decision was delegated in this discussion.
If planning finds a newly skipped gate, new exception, ancestor fetch or request-response change,
bring that concrete case to the maintainer before adopting it.
