## Problem

Stage 1 (#407) introduced the private link check and stage 2 (#385) the shared Guardian checker. Most package consumers still decide a link themselves: several evaluate state before permission, none runs a parent gate for a target on its own ViewSet's page, and child links hand over the immediate parent only. This issue moves every consumer to the check. The Guardian exceptions of stage 1 are ended in stage 3b; 3a narrows two of them only where the shared higher-ancestor gates reach them, as listed below.

| Bulk toolbar | `src/crud_views/lib/bulk/__init__.py:112` | Calls the check directly (D-43). |

Two rules hold at every site:

- **Ancestors** are aligned with the target's declared ancestry (D-41). For a target on the page's own ViewSet they come from the guard state of the rendering view; for a child link the immediate parent is the object or row its URL is built from, followed by the guard state. Cancel alone takes its immediate parent from the `cv_get_parent_object` hook.
- **The rendering view** is handed to the private function when it belongs to the target's own ViewSet, and `None` otherwise (D-40). For Cancel that is the request-bound copy `cv_get_cancel_url` already builds.

Not touched here, and left for 3b: `GuardianQuerysetMixin._cv_link_permission` and `cv_get_context`, the Guardian create view's `_cv_link_permission` and `_cv_page_link_ancestors`, the three Guardian `_cv_cancel_target_available` overrides, and the two state adapters they still use.

## Behaviour changes

| # | Today | After | Who notices |
| --- | --- | --- | --- |
| 1 | The three button classes, actions by view key and the card own action run the state hook although permission denies (`buttons.py:114, 188, 296`, `base.py:941`, `card.py:86-89`). | Permission first; the state hook is not called after a denial. Cancel, the bulk toolbar and navbar owner items already work this way. | A `cv_action_enabled` override with side effects or cost. |
| 2 | A nested target on its own ViewSet's page, or reached by a parent or sibling button, gets no parent gate; a child link gates the immediate parent only. | The immediate parent and every resolved higher ancestor are gated, for core targets and for Guardian object and list targets. | With the default policies: a user with `view` but not `change` on the parent loses the child's update, delete and create links and its bulk toolbar. The clicks are refused today. |
| 3 | A link to a nested target is decided without a known parent on a view that has no guard state. | Denied, except Cancel (D-42). The shapes that can reach this are create and form pages, Resource leaves, non-CRUD views and direct calls; a nested list or object view without guard state raises before it renders. | A project view that overrides `dispatch` without calling `super()`. |
| 4 | The bulk toolbar is decided by the cancel helper. | Decided by the check. | As row 2. |
| 5 | Bulk return redirects use today's Cancel eligibility. | They use the new one; the `Location` can change, the order origin, fallback, success does not (D-52). | A user who may run a bulk action but not open its cancel target. |
| 6 | `cv_create_has_access` receives its rendering view from the create button of the nested list or card page and from Cancel, and `None` from every other site. | It receives the view from every site on a page of its own ViewSet, so also from object pages and from row and card actions, and `None` from pages of other ViewSets as today. | A project override that uses `None` to detect "not the list page". |
| 7 | Cancel to a nested object target does not ask for the parent (`base.py:82-83`). | It asks, as Cancel to a nested list does. No query on a guarded request; one lookup on a view without guard state; an exception from a project override of `cv_get_parent_object` reaches this path. A missing parent stays "unavailable" and does not become a 404. | A project that overrides `cv_get_parent_object`. |
| 8 | A core nested create button takes its state object, and the parent button its object, from `cv_get_parent_object` (`src/crud_views/lib/views/create.py:63-64`, `buttons.py:177-181`). | From the guard state. | A project whose override returns an annotated or rescoped parent; it moves that to the parent ViewSet's queryset. |

Guardian paths that do not yet follow row 2, on purpose; 3b ends each:

- A nested Guardian create is handed the immediate parent only, and gets no higher-ancestor gate, where a site consults `_cv_page_link_ancestors` (context buttons, actions by view key, card own actions and the permission filter, on the pages of the create's own ViewSet) or where the list-page rewrite applies. From a child button, a card child action and a navbar child item it gains the higher-ancestor gates in 3a. A navbar child item does so on every page that renders the navbar, the pages of the create's own ViewSet included (D-55), so on such a page the navbar item and the context create button can differ until 3b.
- On a nested Guardian list or card page, a parent or sibling button whose key resolves to the page's create keeps being overwritten with that create's result.
- A queryset-only composition keeps skipping the immediate parent. Its higher ancestors are gated from 3a on, for links and for Cancel.
- An anonymous user keeps getting the link to a nested Guardian create (L2) where no higher level is gated. Where one is gated, the higher-ancestor gates deny an anonymous or inactive user from 3a on.
- Cancel through `GuardianParentPermissionMixin` keeps its own path and gates the immediate parent only.

A configuration error on a target (a missing ancestor permission key, no operation requirements, authorization records on another database) is raised when the link is rendered, as it already is for child links. A missing own permission key denies, as today.

## Helpers

- Removed: `_page_action_object`, and the second branch at each call site.
- Kept until 3b: `_cv_page_link_ancestors` with its single Guardian create override (its core default now means "use the aligned list"), and `_cv_action_enabled_for_context` / `_cv_action_enabled_for_rendering`, whose last caller is the nested Guardian Cancel path.
- Tests that name `_page_action_object`, or that observe a migrated consumer through `_cv_action_enabled_for_rendering`, are rewritten to the public hooks and listed. Known so far: `tests/test1/test_link_access.py` (`_page_action_object`), `test_navbar_checks.py`, `test_navbar_templates.py`, `test_navbar_costs.py`, `test_cancel_state.py`, `test_cancel_permissions.py` and `test_bulk_source.py`. The list is a starting point.
- New: one private helper that returns the known ancestors aligned with a target's declared ancestry, read from the rendering view. No public context API.

## Acceptance criteria

- [ ] Each consumer in the scope table decides its links through the check. The closing summary lists every remaining production call to `cv_has_access` and `cv_action_enabled` with the reason it stays.
- [ ] For each site of row 1, a test shows that the state hook is not called when permission denies. For the filter, a test shows that it never calls the state hook and answers true for a permitted action that state disables.
- [ ] On a two-level core nesting with the default policies, a user with `view` but not `change` on the parent gets no update, delete or create link and no bulk toolbar on the child list page, and the requests answer 403.
- [ ] On a three-level nesting where the target asks a stricter higher-level permission than the page (a non-default pair or `actions` entry, because the defaults agree), a denied far ancestor denies the link at every consumer, for a core target and for a Guardian object and list target, and the request answers 403. A nested Guardian create at the sites that consult `_cv_page_link_ancestors` or the list-page rewrite, and Cancel through `GuardianParentPermissionMixin`, are excluded and pinned unchanged. A navbar child item to that create is not excluded: it is denied on the pages of the create's own ViewSet as well (D-55).
- [ ] With Guardian ancestors and a target on another ViewSet than the page (parent button, sibling button, navbar item from a deeper page), each gate is asked about the object of its own level. A level that is not known is `None` and shifts nothing.
- [ ] On a create or form view without guard state, links to nested targets are denied and Cancel still resolves its parent; a missing parent leaves Cancel unavailable. A project override of `cv_get_parent_object` is honoured by Cancel, and its exception is not swallowed.
- [ ] `cv_create_has_access` receives a view of its own ViewSet or `None`, never a view of another ViewSet.
- [ ] Every changed cell of the stage-1 matrix is listed with its reason. Each change moves towards a permission denial (from enabled, or from disabled by state, to hidden or disabled by permission); no cell becomes more available. Request-gate, ancestor and access-trace suites pass without an edited expectation.
- [ ] Query counts are pinned before and after for navbar, context buttons, row and card actions, Cancel and the bulk toolbar, with gate calls and permission queries reported separately. One `### Breaking` entry, `docs/migrating-1.0.md` and the affected reference pages agree. Golden files are byte-identical except where one of the eight changes above explains the difference.
