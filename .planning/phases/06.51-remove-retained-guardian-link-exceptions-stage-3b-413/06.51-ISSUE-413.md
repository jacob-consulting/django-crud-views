## Problem

Stage 1 kept several Guardian link behaviours on purpose so that it changed no rendered result: links that stay hidden although the parent is known, a link shown to an anonymous user, one composition that skips the parent gate, and a list-page rewrite that gives a button the result of a different view. After 3a every consumer runs the shared check, so these can now end.

### Stage 3a decisions that bind this stage

Copied from section 12.8 at commit `55dce6f6`. 3a implemented them; 3b keeps to them wherever it moves a consumer onto the check. For the Cancel move of D-48 that means: the immediate parent comes from the `cv_get_parent_object` hook through `_cv_cancel_parent_object` (D-42), the higher ancestors come from the guard state and stay aligned (D-41), and the rendering view is handed over only when it belongs to the target's own ViewSet (D-40). The core helper `_cancel_target_available` (`src/crud_views/lib/view/base.py:77-93`) already works this way.

| ID | Decision | From | Amends |
| --- | --- | --- | --- |
| D-40 | Every package call site moves to the check for every target, Guardian targets included: the four context button classes, actions by view key, card actions, navbar items, the `cv_context_has_permission` filter, core Cancel and the bulk toolbar. Each site hands its rendering view to the private function when that view belongs to the target's own ViewSet, and `None` otherwise, so `cv_create_has_access` only ever receives a view of its own ViewSet. This departs from S3-06, which handed the view over everywhere. A Guardian object or list target therefore gains the parent and higher-ancestor gates the request already runs. Guardian's own exceptions (D-30, D-33 with D-27, D-34, D-35 and the nested Guardian Cancel path) stay until 3b, except as the consequences below state. | review | D-28, D-29, D-31 |
| D-41 | D-04 is completed. A consumer hands the check the immediate parent and every higher ancestor the request has already resolved, nearest first and aligned with the target's declared ancestry. For a target on the page's own ViewSet the immediate parent comes from the guard state, not from `cv_get_parent_object`; for a child link it is the object or row its URL is built from. 3b is one pull request. Bulk return redirects follow the changed Cancel eligibility once more (D-52). Its commits follow four constraints:

- D-45 and D-50 land together. The rewrite is the only thing that gives the list-page create button its parent today, so removing it first would hide that button.
- D-49 lands with or before the Cancel move of D-48. Otherwise an override that answers true restores a Cancel link, because the create's class step is the hook alone (`views.py:387`).
- D-46 lands with or before D-45, so that no newly shown create link is shown to an anonymous user.
- The state adapters are removed after the Cancel move, which holds their last caller.

Not adopted (D-51): an ordinary link to a nested parent-only Guardian view built on a `...PermissionRequired` base still asks the inherited child model permission, which the request does not require. Document it as a known limit in `docs/reference/guardian.md`.

## Acceptance criteria

- [ ] One test per row of the table shows the new result on a real list, detail, create or card page, and the unchanged request response beside it.
- [ ] D-49, at a child button, the permission filter and Cancel: a custom `cv_create_has_access` that answers true does not show a link whose immediate-parent gate denies, and is not called in that case. One that answers false still hides the link.
- [ ] D-46, for a nested create under a model-permission parent with an anonymous-granting backend and under a provider-`none` parent: an anonymous user gets no link; an override that answers true without calling `super()` does not change that; a direct call to the default hook answers false. An inactive user, an inactive superuser included, gets no link. A nested Guardian object view under a provider-`none` parent denies an anonymous user who holds an anonymous-user grant. A top-level Guardian create is unchanged.
- [ ] D-45 and D-50: a parent button and a sibling button whose keys collide with the page's `create` show their own target's result. The plain create button on a nested Guardian list page is still shown to a user who passes its gates, and `cv_create_has_access` still receives the list view there. On a three-level nesting with a stricter higher-level key, the create control on the own ViewSet's list, detail and card pages is denied when the far ancestor denies.
- [ ] Guardian Cancel: actor rule, origin and fallback order, availability with an empty list and configuration errors are covered and unchanged. The `user` and `request` arguments of `cv_get_cancel_url` still select the actor and the bound view, shown through `cv_create_has_access` for a create target and through the result for the others. - [ ] Direct `cv_has_access` on a nested Guardian create still answers false for every argument.
