## Problem

After 3a and 3b every package link is decided by one private function. Project code has no documented way to ask the same question: a custom button, a dashboard or a table column can call the public hooks, but the parent gates are private, so it cannot decide a link the way the package does. This issue publishes the function. It changes no behaviour of the package.

## Scope

- A public function `check_link_access` that validates its inputs and then calls the private check.
- **Inputs:** the target view class, the user, the target's own object, and the known ancestors, nearest first, aligned with the target's declared ancestry. A list shorter than the ancestry, or `None` for a higher level, means "not known".
- **Answer:** allowed, denied by permission, or denied by state.
- **No rendering view.** The function passes `None` to `cv_create_has_access`. Package consumers use the private function and hand over a view of the target's own ViewSet where they have one.
- **No accessor for resolved ancestors.** A caller supplies what it has.
- The permission-only function stays private. `cv_context_has_permission` remains the public permission-only entry for templates.

### Input validation (D-54)

Validation runs before any decision, so it does not depend on the user or on grants. The function raises `ImproperlyConfigured`, with a message that starts with the function's name, for:

- an ancestor that does not fit its level, also when a nearer slot is `None`;
- an own object that does not fit the target;
- no own object for an object target;
- an own object for a target without one;
- more ancestors than the target has levels, every element counted, `None` included;
- any ancestor for a top-level target.

An object fits a level when it is an instance of that level's concrete model. A proxy, a multi-table child and a polymorphic subclass pass. For a Resource target, which has no concrete model, the own object is an instance of the Resource class. The private function is not changed.

## Documentation

- A reference section with the import path, the inputs, the three answers and the order parent gates, own permission, state.
- Three examples: an object target; a nested list or create; a caller outside a CRUD page that supplies its ancestors.
- What the state hook receives: the own object, the immediate parent for a nested target without one, otherwise `None`.
- The limits, stated plainly:
  - it decides a link and does not authorize a request, and it loads nothing;
  - a missing immediate parent denies, and a higher level that is not supplied is not checked;
  - on a CRUD page a project has `cv_get_parent_object` and nothing public for the levels above, so a custom button can differ from a package button where the target asks a stricter higher-level permission than the page;
  - membership is not checked: a child with another parent than its own is accepted, where the request answers 404;
  - it does not see ViewSet querysets, a project's `dispatch` or `has_permission`, or middleware;
  - a top-level Guardian list answers allowed for an anonymous user;
  - a nested Guardian target denies an anonymous or inactive user, whatever the grants and also under a parent with provider `none` (D-46).
- What can raise:
  - the input validation above;
  - an error in the declared ancestry, which can surface during validation with its own message;
  - `ImproperlyConfigured` from a gate that is reached, for a missing ancestor permission key or a view without operation requirements;
  - `ImproperlyConfigured` from a gate or from the own-permission step, for a user, an object or authorization tables on another database than `default`;
  - whatever a project hook raises.

  A missing own permission key does not raise; it denies.
- One sentence on the rendering view: a `cv_create_has_access` override that reads it can answer differently for this function than for a package button on the same page.
- The known limit of D-51, by reference to the section "Parent-only non-create limitation" in `docs/reference/guardian.md`.
- An entry in `docs/development/stability.md`. No provisional status.
- The 3b migration note for custom `ContextButton` subclasses (item 6 at `docs/migrating-1.0.md:169`, and the matching paragraph in `docs/reference/guardian.md`) now points here. The documentation tests that pin the old pointer are updated with it: `tests/test1/test_link_access_docs.py:74` and `:197`.
- Three sentences say that no public checker exists and are corrected: `docs/migrating-1.0.md:11-12`, `docs/reference/guardian.md:574` and `docs/reference/nested.md:627`. The part about a public ancestor accessor stays, because none is published (D-53). Line references in this issue are `feature/link-access-check-design` at `1d538046`.
- `tests/test1/test_link_access_docs.py::test_link_check_is_not_in_the_stability_inventory` (`:90`), which also pins the phrases "no public checker API" and "remain later work" in the migration note, is replaced by a test of the new entry.
