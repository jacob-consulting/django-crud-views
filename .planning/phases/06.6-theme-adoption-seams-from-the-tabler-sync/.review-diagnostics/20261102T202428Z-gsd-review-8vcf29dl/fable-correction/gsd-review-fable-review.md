## Reassessment of the three cycle 8 findings

**C8-A01, plan 10, out-of-tree write authorization. Withdrawn as a finding.** The original claim had two parts: that executor step 0b halts on any Edit/Write to an absolute path outside the worktree, and that plan 10 gives the executor no authorized write mechanism for the companion other than Edit/Write. The first part is true but narrower than I stated. Step 0b is scoped to Edit and Write tool calls, exists to catch paths built from the orchestrator's `pwd` that land in the main repo, and does not govern Bash. The second part is not supported by the plan text. Plan 10 never directs Edit or Write at a companion file. Its delivery mechanism is patch application through `git -C` against the verified companion root:

The gates also force the worktree bytes to exist and detect the two plausible wrong implementations. An executor that commits from the temporary index but never materializes the delta fails `10-01`'s probe, which must run from an isolated copy of the delivered bytes at `:153`, and fails `10-02`'s comparison of the real tree's bytes to the replayed candidate at `:183-186`. An executor that stages into the user's real index trips the original-index snapshot check at `:112-113`. An executor that reaches for the Edit tool in worktree mode is stopped by step 0b and falls back to the plan's named mechanism, which is the specified path anyway; in sequential mode step 0b is inactive. So the behavior is specified and fail-closed under both dispatch modes, and no forced sequential dispatch is needed. The premise of my finding, that Edit/Write was the write path, came from the `files_modified` inventory and the word "edit" at `:81` and `:142`, not from the action text.

One optional clarity refinement remains, and it is not a missing property: `:106-108` name the index-side `apply --cached` commands explicitly, while the worktree-side application at `:143`, `:148` and `:176` says "apply hunks" without naming `git -C ... apply`. A clause naming it would remove the last reason an executor might reach for Edit. Nothing fails without it.

**C8-A02, plans 06/07, the icon-mapping test flip. Withdrawn as a finding.** The concern was that the companion test `test_every_upstream_icon_name_is_mapped` fails on the pinned baseline and passes after plan 07's three mappings, and that the D-13 comparison might record this only as a vanished failure. Checked against the actual text, every execution behavior is present. D-13 at `06.6-CONTEXT.md:50-51` imposes three obligations: no new regressions, all phase scenarios pass, unrelated failures shown to predate the change. A failure that disappears belongs to none of those classes, so it cannot be misclassified as unrelated, and it cannot be a regression. The data needed to see it are mandatory: `06.6-06-PLAN.md:17-18` and `:264` record baseline failing node IDs, `:171-172` retain raw commands, exit codes and failing IDs and forbid relabeling a failure as a pass, `:99` makes the capture report actual failures. `06.6-07-PLAN.md:312-315` compares raw failing identities to the baseline and reproduces any ambiguous difference on both sides, and `:335` fails on any required scenario not passed or any unproven new failure. The flip itself is deterministic rather than hoped for: the full report established that core `DEFAULT_ICONS` minus companion `TABLER_ICONS` at the pinned revisions is exactly the three names, plans 01 through 05 and 08 add no core icon names, and `06.6-06-PLAN.md:192-193` independently rejects a missing or changed `icons.py` registration. The residual edge case, that this test still fails in replay and gets called "pre-existing unrelated", requires an unmapped core icon name that the phase does not introduce. What my finding asked for was a "fixed by phase" label in the report, which is derivable as baseline failures minus replay failures from records the plans already require. That is a presentation refinement, not execution behavior.

**C8-A03, plans 06/10, companion branch and the protected-branch guard. Withdrawn as a finding.** Branch capture is already required at `06.6-10-PLAN.md:89`, which lists top-level, HEAD, branch, porcelain status and index entries; `:91` forbids changing branches; `:112-113` requires HEAD and branch unchanged before the commit; `:113-114` gives the exact `git -C` commit command. The executor's protected-branch assertion is step 0 of the task commit protocol and reads `git rev-parse --abbrev-ref HEAD` in the executor's own cwd, which the plan keeps in core. The companion commit is explicitly not a task-commit-protocol commit: `:96-97` says the explicit companion commit satisfies the companion task commit and must not be duplicated in core, and `06.6-CONTEXT.md:194-198` authorizes ordinary local commits with no new gate. Under the user's stated precedence, an executor applying a core branch guard to the companion would be adding a gate the user has excluded. A sentence saying so would be an optional clarification; recording the branch name in `10-companion-delivery.json` is already implied by `:61-62` and `:196`. No executable property is missing.

Open questions from the full report stay open and stay non-findings. Whether the GSD commit tool honors `GIT_INDEX_FILE` could not be read; Node child processes inherit the environment by default, and in the worst case the tool stages only its named files into the real index, which is what it does today. The `worktree-path-safety.md` step 0c check before each `<automated>` command could not be read; every plan 10 verify command contains only core-relative paths and the literal operand `recorded`, so no external path token is present for such a check to reject. Whole-file staging of the already dirty `ROADMAP.md` and `STATE.md` in metadata commits is GSD-wide.
