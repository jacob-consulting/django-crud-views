# Phase 06.6 Plan 02: Theme label-mode defaults Summary

**Themes can register label-mode floors atomically; real form buttons and existing diagnostics resolve live project settings over theme over package defaults.**

## Accomplishments

- Added `crud_views.lib.view.label_mode.register_label_mode_defaults(defaults: dict[str, str]) -> None`. It accepts the existing context/list/card/form locations and label/icon/both modes, copies caller input, validates the entire mapping before changing state, and merges later values per key under a dedicated lock. A single global rebind publishes the complete mapping.
- Package defaults remain immutable: context=icon, list=icon, card=both, form=label. Themes affect the existing public resolver and actual crispy form-button renderer without project configuration.
- Live project overrides remain responsive to nested `override_settings`; missing keys fall through to theme then package. The private setting-free fallback prevents recursion when a malformed project setting coexists with a malformed owner map or entry.
- Explicit owner/view/button modes and owner-first whole-map selection remain intact. Unmapped kinds take the effective floor without merging lower owners' entries.
- E108 still reports malformed project settings even when a valid theme floor exists. Existing context/form W292 wiring follows effective floors, project and explicit mode overrides, and icon availability. Form checks are proven not to construct request-dependent forms.
- An independent autouse fixture restores theme state by rebind. The serial registration selection proves two consecutive tests remain isolated without requesting the fixture; warning dedup state remains separate.

Approved `06.6-UI-SPEC.md` label-mode requirements were applied. The plan's historical “no UI-SPEC exists” sentence is superseded by that approved contract. No template styling, visual redesign, owner API rename, package installation or companion modification was needed.
