## Session memory after Cancel

Question: Tab A cancels back to Adams after Tab B has stored Pratchett filters. What should later bare-list visits
remember?

| Option | Description | Selected |
|--------|-------------|----------|
| 1. Remember Adams (recommended) | Cancel acts like an ordinary list visit, updates session memory and clears remembered filters for an explicitly unfiltered origin. | Yes |
| 2. Keep remembering Pratchett | Restore Adams only for this return without updating session memory. | |

**User's choice:** "1"
**Notes:** Both alternatives preserved each form's captured destination independently. Selected behavior is D-07.

## No usable fallback destination: missing registration

Question: There is no usable origin and cv_cancel_key defaults to list, but neither list nor card is registered.

| Option | Description | Selected |
|--------|-------------|----------|
| 1. Require a valid fallback (recommended) | Report a clear configuration error with guidance to configure an existing destination. | Yes |
| 2. Hide Cancel | Render the form without Cancel. | |
| 3. Disable Cancel | Keep Cancel visible but unavailable. | |

**User's choice:** "1"
**Notes:** Missing developer-configured destinations are configuration mistakes, distinct from user permissions.

## No usable fallback destination: permission restrictions

Question: Try an accessible allowed origin, then the accessible configured fallback; if neither is accessible,
how should Cancel render?

| Option | Description | Selected |
|--------|-------------|----------|
| 1. Hide Cancel (recommended) | Keep the form usable without offering inaccessible navigation. | Yes |
| 2. Disable Cancel | Show the control but make it unavailable. | |
| 3. Keep the link | Let destination authorization reject the request, potentially showing a 403. | |

**User's choice:** "1"
**Notes:** Resolution is accessible origin, accessible fallback, then omission. A missing configured fallback still
has the separate configuration-error policy.

## Custom-template migration

Question: Existing templates may use `{% cv_context_url view.cv_get_cancel_key as url %}`. Should that pattern
remain supported with reduced behavior, or require immediate migration to the URL helper?

| Option | Description | Selected |
|--------|-------------|----------|
| 1. Keep existing templates working (recommended by assistant) | Stock controls adopt the full behavior; custom templates keep the old behavior until explicitly migrated. | |
| 2. Require immediate migration | Treat the old cancel-template pattern as unsupported in this release and document the breaking change. | Yes |

**User's choice:** "2"
**Notes:** The user selected immediate migration over the assistant's compatibility recommendation. The new helper
must support query restoration and permission-aware hiding. Removal of the underlying key-resolution method was
not separately requested or decided.
