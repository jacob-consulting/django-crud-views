### WR-01: Invalid allowed-key configuration aborts fallback diagnostics

**Classification:** WARNING  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/base.py:196-202`  
**Related file:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/cancel.py:39-42`

**Issue:** E252 deliberately rejects values other than `None`, `"auto"`, or a list of registered string keys, but the following E256 evaluation still sends invalid values through `effective_cancel_keys()` whenever the fallback is missing. For example, `cv_cancel_key="missing"` and `cv_cancel_keys=[{}]` cause `dict.fromkeys()` to raise `TypeError: unhashable type: 'dict'`. A noniterable value such as `42` fails similarly. The generator aborts instead of returning the actionable E252/E256 messages. `check_viewsets()` and `ViewSet.checks_all()` do not catch this exception, so the registered Django check cannot finish reporting configuration problems.

**Evidence:** A checkout-bound Django 5.2 Python probe set those two attributes on `AuthorUpdateView`, then evaluated `[m.id for c in AuthorUpdateView.checks() for m in c.messages()]`. It exited 1 at `base.py:201 → cancel.py:42` with the TypeError above. No source files were changed.

**Fix:** Validate the allowed-key shape before deduplication or route lookup in the diagnostic path. When E252 rejects the shape, skip deriving candidates from it (or treat it as zero usable origin candidates for E256), while preserving the E252 error and all other checks. Do not broadly catch unrelated application exceptions. Add a focused check regression with a missing fallback and malformed values such as `[{}]`, `[[]]`, and `42`; the check pass must return diagnostic messages without raising.

### WR-02: Create documentation recipe test always requests Delete

**Classification:** WARNING  
**File:** `/home/alex/projects/alex/django-crud-views/tests/test1/test_cancel_docs.py:94-99`

**Issue:** `test_custom_actions_recipe` uses the parametrized `key` to install the chosen recipe on its target form, then overwrites `key` in `for key in ("list", "card")`. At line 98 the value is always `"card"`, so every parameter combination requests the Delete endpoint. The two create cases patch the Create form but render an unmodified Delete form. They therefore cannot detect a broken published `CancelAwareActionsMixin` recipe or prove its create-page ownership and omission behavior.

**Evidence:** Calling the test body with `key="create"` and a recording client requested `/author_origin/example/delete/`. A second, in-memory pytest probe replaced the create recipe's `get_form_actions()` with an unconditional `AssertionError`; `test_custom_actions_recipe[create-True]` still reported **1 passed**. The probe modified only process-local objects, not source or documentation files.

**Fix:** Rename the destination loop variable and retain the parametrized key:

```python
for destination in ("list", "card"):
    monkeypatch.setattr(
        cv_author_origin.get_view_class(destination),
        "cv_has_access",
        classmethod(lambda cls, user, obj=None: allowed),
    )
path = "/author_origin/create/" if key == "create" else f"/author_origin/{author_douglas_adams.pk}/delete/"
```

Assert that the response uses the selected target view and the patched form class. Re-run both allowed/denied create and delete cases; an intentionally failing create recipe must fail the create case.
