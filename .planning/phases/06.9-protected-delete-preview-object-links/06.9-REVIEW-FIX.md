### CR-01: Class-level permission overrides advertise a detail destination that rejects the actor

**Status:** fixed: requires human verification
**Files modified:** `src/crud_views/lib/views/delete.py`, `tests/test1/test_delete.py`
**Commit:** `dd9470aab965384eee74adc3196cac2380062398`

**Applied fix:** The private protected-link adapter statically checks the effective `permission_required` and
`get_permission_required` against the stock core contract, including inherited declarations. It also checks the
`has_permission` inheritance chain against stock core and Guardian implementations: Guardian's parent method
can delegate to another inherited method. Unsupported policies yield `url=None` without evaluating descriptors,
calling `has_permission`, or dispatching a request. Existing visibility filtering, native detail GET authority,
destination state checks and Guardian policy remain in place. This is deliberately conservative certification,
not a new authorization API or an attempt to execute arbitrary application policies.

Eight regression cases cover direct and inherited string requirements, property requirements,
`get_permission_required` and `has_permission` overrides. Each demonstrates a native GET returning 403 while
the classmethod policy permits the actor, then checks that preview preserves the label as text and invokes no
permission/dispatch probe. Existing stock core and Guardian positive controls remain in the passing selection.

**RED:** All eight cases failed against the prior implementation at the URL-versus-None assertion, after the
native denied GET succeeded. **GREEN:** Protected selection across core, Guardian and database tests passed:
296 tests, four workers, Django 5.2.18, 15.61 seconds.

The status explicitly retains the fixer protocol's human-verification flag for a permission logic change;
passing regressions do not substitute for the independent review requested by the orchestrator.

### WR-01: Read-only regression does not exercise its modal or confirmed-blocked POST cases

**Status:** fixed
**File modified:** `tests/test1/test_delete_inspection.py`
**Commit:** `911d775b9f6b49dd0418ea4d99e17fb1577054a1`

**Applied fix:** Set the source class's `cv_modal` to the parameter, send `confirm=on` on POST, assert the actual
page/modal template and a valid POST form, and require 422 for the blocked modal POST (200 for page POST).
The existing SQL capture, provider/filter contract and model-delete sentinels remain. A write-phase sentinel and
explicit per-request row refreshes additionally check that blocked requests never enter deletion callbacks or
remove either row. Existing separate invalid-confirmation coverage remains unchanged.

**RED:** Adding the semantic assertions first produced two expected failures: page POST had an invalid form;
the modal case rendered `crud_views/view_delete.html` instead of `crud_views/modal/content.html`.
**GREEN:** Both corrected cases passed in 1.15 seconds. These tiny diagnostics ran serially to avoid worker
startup overhead; broad regressions use four workers.
