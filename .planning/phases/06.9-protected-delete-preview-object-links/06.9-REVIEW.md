### CR-01: Class-level permission overrides advertise a detail destination that rejects the actor

**Resolution:** CLOSED — independently verified at `911d775`; fixed by `dd9470a`.
The static guard at `delete.py:264-284` rejects direct/inherited requirements and uncertifiable permission
resolution or permission-check methods before destination instantiation or querying. It inspects descriptors
without executing them, checks the inherited `has_permission` chain (including Guardian delegation), and
retains stock core/Guardian eligibility. The eight new regressions and additional inheritance/descriptor
probes passed. Historical finding follows.

**Classification:** BLOCKER  
**File:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:263-270`  
**Related lines:** `/home/alex/projects/alex/django-crud-views/src/crud_views/lib/views/delete.py:347`;
`/home/alex/projects/alex/django-crud-views/src/crud_views/lib/view/base.py:1085-1090`.

**Issue:** The adapter rejects a `permission_required` override supplied through callback init kwargs, but accepts
the equivalent override declared on the registered detail class (including one inherited from an application
base class). Its subsequent `_cv_cancel_target_available()` call reaches core `cv_has_access()`, which checks
the ViewSet's `cv_permission` mapping and never reads the class's effective `permission_required`.
Django's real `PermissionRequiredMixin` does read that attribute. Consequently a visible blocker gets an
ordinary anchor even though the destination's native permission gate denies the same actor.

**Evidence:** Independently reproduced against the source checkout and cached Django 5.2 runtime with an in-memory
database: register a `DetailViewPermissionRequired` subclass for Contract with
`permission_required = "app.change_contract"`; grant its actor only `app.view_contract`. The adapter returned
`/review_protected/1/detail/`, while invoking that registered class's normal `as_view()` GET with the same
actor/PK raised `PermissionDenied`. No middleware, custom dispatch or custom object lookup was involved.
This is incorrect eligibility/navigation, not a demonstrated authorization bypass: the real request still denies.

The existing `test_protected_candidate_contract[permission-override]` tests only
`as_view(permission_required=...)` and therefore misses the class declaration case.

**Fix:** Extend the inspectability guard to the effective class permission policy, not only `view_initkwargs`.
For core permission-required destinations, conservatively return `None` when class-level/inherited
`permission_required` or permission-resolution overrides cannot be certified by the existing classmethod
policy. Alternatively evaluate the effective destination permission requirement through a narrowly defined
read-only check while preserving the independent state gate and Guardian policy. Do not call dispatch or
`has_permission()` as a probe, since those can repeat object/state work. Add class-level and inherited
override regressions with a native-denied actual GET, and retain positive controls for stock core/Guardian
destinations. The denied blocker must retain its readable label with `url=None`.

### WR-01: Read-only regression does not exercise its modal or confirmed-blocked POST cases

**Resolution:** CLOSED — independently verified at `911d775`; fixed by `911d775`.
The test now enables `cv_modal`, submits `confirm=on`, asserts valid POST forms and the actual selected
template, and requires 422 for confirmed blocked modal POST. SQL capture and deletion sentinels remain,
with a write-phase sentinel and explicit row refreshes added. Both corrected variants pass in the fresh
selection below. Historical finding follows.

**Classification:** WARNING  
**File:** `/home/alex/projects/alex/django-crud-views/tests/test1/test_delete_inspection.py:23-59`.

**Issue:** `test_protected_preview_read_only` parameterizes `modal`, but only sends `X-CV-Modal`; it never enables
`cv_modal` on the source class. The reused `PublisherCascadeDeleteView` has `cv_modal=False`, so both parameter
values render the full page. Its POST also sends no confirmation data. The form is invalid, and execution never
reaches the valid-form blocked-deletion branch. Therefore this test's captured-SQL and callback assertions can
pass without checking the modal rendering path or a confirmed blocked POST, despite claiming both.

**Evidence:** The existing two cases pass. Temporary runtime instrumentation, without editing source files,
observed `cv_modal=False` and `['crud_views/view_delete.html']` for every response, including the
`modal=True` requests whose header was `true`. Both POST responses had `form_data={}` and `valid=False`.
The real modal protection response sets status 422 at `delete.py:470-474`; this test instead requires 200
unconditionally. Other migration tests exercise modal/confirmed responses, but do not make this particular
SQL-capture regression exercise the states it claims.

**Fix:** Patch the source class's `cv_modal` to the parameter value; send `{"confirm": "on"}` for POST;
assert the selected full-page/modal template and 422 for confirmed blocked modal POST (200 for page POST).
Retain SQL, deletion-callback, provider and row-preservation assertions for those actual paths. Keep an
invalid-confirmation case separately if that behavior also needs explicit coverage.
