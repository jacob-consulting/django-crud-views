## 06.9-01

### Summary
A sound tracer-first plan that places the structured projection at the correct boundary (`delete.py:278`), reuses the exact cascade field names, and routes the blocker list through the existing caller-context `body_template` seam instead of `items`. The destination adapter composition is grounded in real hooks. The main weakness is that the "tracer" task bundles the full URL-hardening and init-kwargs policy logic whose tests only arrive in plan 02, which breaks the TDD ordering the plan itself declares.

### Strengths
- **Correct boundary.** Replacing only `context["protected_objects"] = list(related.protected)` (`delete.py:278`) and leaving `cv_filter_related_objects` (`delete.py:235-262`) and `RelatedObjects.protected: list` (`src/crud_views/lib/deletion.py:30-33`) untouched honours the CONTEXT rule that D-01 does not authorize collector/provider type changes.
- **Avoids the stringified-dict trap.** `messages.py:42` would `conditional_escape` a dict; the plan's `{% with items=protected_objects %}` + `body_template` mirrors `related_objects.html:17-19`, which `test_alerts.py:102` proves works.
- **One state evaluation.** Calling `SingleObjectMixin.get_object` explicitly with the destination queryset, then `_cv_cancel_target_available` once, sidesteps the double `cv_action_enabled` that `mixins.py:80` + `mixins.py:269` would otherwise produce.
- **Parent correctness.** Passing a destination-bound instance as `rendering_view` makes `mixins.py:257` resolve the *destination's* parent from the destination's kwargs via `base.py:1023-1035`, not the delete view's. This is the right fix for Pitfall 4.
- **Real tracer target exists.** `Contract` (`tests/test1/app/models.py:79-80`, `PROTECT` to `Publisher`) has `cv_contract` with `ContractDetailView` (`tests/test1/app/views.py:485-511`), nested under `cv_publisher`, so a core tracer needs no new fixtures.
- **Header-cache awareness.** "remove the X-CV-Modal header and stale cached headers" correctly anticipates that `request.headers` is a cached property over `META` (`base.py:68-70` reads `request.headers`).

### Concerns
- **MEDIUM — Tracer task is not thin; tests for its hardening live in plan 02.** 01-01's `<action>` implements scheme/authority/backslash/control-char rejection, `view_initkwargs` policy-override detection, script-prefix handling and query/fragment preservation. The behaviours that test those (`test_protected_target_binding`, `test_protected_target_error_boundaries`) are declared in 02-01's `<behavior>`. Under `tdd="true"` this means 01-01 ships untested branches, and the tracer gate (execute-plan tracer rule) re-runs only `-k protected_link_request_tracer`.
- **MEDIUM — Per-blocker query cost is unbounded and untested.** Inspection already loads every protected row (`deletion.py:138,175`). The adapter adds, per visible blocker: `resolve()`, a view instantiation, a `queryset.get()`, a Guardian `ObjectPermissionChecker(user).has_perm` (fresh checker per call at `mixins.py:94-97`, so no cross-row cache), and a state hook. For the motivating issue #307 case (a Project with many protected Tasks) a delete GET could issue several hundred queries. 01-02 names no query-count assertion; `grep` finds no `django_assert_num_queries` in any delete test today.
- **LOW — Un-migrated copies fail *visibly but silently*.** A copied `related_objects.html` that still passes `items=protected_objects` will not error; `messages.py:42` renders `str(dict)` escaped, which leaks the URL text into the alert. No test or check detects this. See suggestion below.
- **LOW — `SingleObjectMixin.get_object` raises `AttributeError`, not `Http404`, when neither pk nor slug kwarg is present.** An override URL that resolves to a detail route with unexpected kwargs would propagate `AttributeError`. The plan's "no encompassing exception catch" policy makes this a crash rather than text. Probably acceptable, but it should be a named case in the error-boundary test.

### Suggestions
- Move the URL-shape hardening, init-kwargs policy detection and script-prefix handling out of 01-01 into 02-01 next to their tests. Leave 01-01 as: hook → `resolve()` → `view_class.cv_key == "detail"` and registered-class check → `setup()` → destination queryset `get()` → identity → `_cv_cancel_target_available`.
- Add to 01-02 (or 02-02) a `django_assert_num_queries`-style bound: queries grow at most linearly with visible blockers, and zero adapter queries when `cv_link_related_objects` is off. Document the cost under "Collection cost and overrides" (`docs/reference/delete_view.md:195`).
- Consider a tiny entry object (`obj`, `url` attributes, `__str__` returning `str(obj)`) instead of a dict. Template `node.obj`/`node.url` works identically, D-01's "structured entries" is satisfied, and a stale copied template passing `items=protected_objects` degrades to the old label text instead of a dict repr. This is a planner choice; if dicts are kept for cascade parity, add a negative test documenting the repr failure mode.

### Risk Assessment
**MEDIUM.** The design is correct and source-grounded; risk comes from the tracer's scope and the unmeasured query cost.

## 06.9-02

### Summary
This is the plan that makes PDL-01 real: it separates source visibility (`cv_filter_related_objects`, `_PermittedPks`) from destination policy (`_cv_cancel_target_available` + queryset membership + alias identity) and tests the contrasts that actually differ in source. ### Strengths

Guardian visibility uses `_PermittedPks` with the *delete view's* `cv_guardian_accept_global_perms` (`src/crud_views_guardian/lib/views.py:57-61`), while destination access uses the *detail view's* flag (`mixins.py:85-98`). The "global source, strict target" case is a genuine divergence.
- **Alias identity is grounded.** `_world()` in `tests/test1/test_delete_databases.py:19-24` already creates colliding pk=41/71/81 rows on both aliases and `database_routes` (`tests/test1/conftest.py:137-168`) routes per request. Extending this to a destination lookup is straightforward.
- **Stale-preview honesty.** "Permission revocation after preview is enforced by subsequent real detail request" matches `test_guardian_protected_revocation_applies_next_request` (`test_guardian_delete.py:592`) precedent.
- **Parent-permission None case** maps to real code: `mixins.py:357-359` skips only the permission check; parent resolution still happens at `base.py:1035`.

### Concerns
- **MEDIUM — Guardian destination fixture is not reachable through the default hook.** `_REGISTRY` is an `OrderedDict` (`viewset/__init__.py:43`) iterated in registration order, and `cv_contract` (core, `tests/test1/app/views.py:485`) is registered at module import. Any test-local `GuardianViewSet(model=Contract)` registers later and is never selected by `delete.py:190-191`. There is also no Guardian-registered model that is a `PROTECT`/`RESTRICT` blocker today (Book→Publisher is `CASCADE`; `Royalty` has no viewset and deliberately no `view_` permission). So `test_guardian_protected_target_policy` must either override `cv_get_related_object_url` to the Guardian route or define an `isolate_apps` blocker model. The plan's "Keep supporting fixtures local" does not say which, and the override path also changes what is being tested (override eligibility rather than default routing).
- **MEDIUM — Guardian `cv_has_access` on a cross-alias row.** `ObjectPermissionChecker(user).has_perm(codename, obj)` (`mixins.py:94-97`) queries Guardian tables through default routing, not `obj._state.db`. `_PermittedPks._routes_match` exists precisely because of this (`views.py:93-131`). The plan's identity check (`_state.db` equality) runs *after* the fetch but the availability call uses the target's own `cv_has_access`, which does not have that topology guard. 02-02 should state explicitly whether a same-alias shard row may link when Guardian grants live on `default`, and test the colliding-actor case (`test_delete_databases.py:229-246` is the analogue for labels).
- **LOW — "Count target state hook calls: one per preview candidate"** must also assert the source delete view's own `cv_action_enabled` is not re-invoked by the adapter. `CrudViewPermissionRequiredMixin.has_permission` (`base.py:1072-1082`) already ran it once on the real request; a spy that counts the *target* class alone will not catch an accidental source re-evaluation.
- **LOW — Wave-2 parallelism with plan 03.** Plan 03-01 writes reference prose describing "destination access/state/queryset/parent/model/PK/alias checks" and the error-propagation limits while 02-01/02-02 are still correcting the adapter. The docs could describe behaviour 02 then changes. Plan 04 does not re-check docs.

### Suggestions
- In 02-01, name the Guardian fixture strategy: either (a) an `isolate_apps` model `GuardianBlocker` with `PROTECT` to `Publisher` and a `GuardianViewSet` + `GuardianDetailViewPermissionRequired`, registered only inside the test with registry restoration as `test_delete_migration_docs.py:44-192` does; or (b) an explicit `cv_get_related_object_url` override, with a comment that it is the override-eligibility path. Prefer (a) so the default hook is exercised.
- In 02-02 add a case: shard-routed target row + Guardian grants only on `default` → expected outcome documented (text), mirroring `test_guardian_other_alias_grant_never_reveals_colliding_label`.
- Spy on both source and target `cv_action_enabled` in the hook-count test.
- Make 03-02's "exact surface inventory" and the eligibility/limits paragraph a *post-02* step (move to 04-02 or add a 03→02 reconciliation line in 04's read_first).

### Risk Assessment
**MEDIUM.** The policy separation is correct; fixture reachability and the Guardian cross-alias `cv_has_access` path need explicit decisions before execution.
