## Policy order

Rendering first checks the effective permission declaration, before superuser/global/checker shortcuts. Then existing inactive/anonymous semantics apply. Ordinary nested access resolves the selected direct parent, evaluates its effective parent permission when resolvable, then delegates child access through super(). Never add an ancestor permission requirement.

Direct requests have a separate order (C1-H5/M10): retain existing composition validation, then the configured anonymous response or inactive PermissionDenied before declaration/parent loading; active actors, including superusers, get the deliberate configuration error before permissive permission shortcuts. GuardianParentPermissionMixin.has_permission explicitly guards the top-level create's add mapping before delegating to the core permission mixin, while dispatch preserves its actor prelude. Required parent declarations are validated before parent permission evaluation; nested parent-only create never validates a child-add declaration. Keep the standalone core assertion and migration hint unchanged. Use real client requests for each actor/configuration combination, including 403/404/redirect anonymous settings.

After declaration checks, obj=None takes D-10's existing ordinary view-access fallback before consulting even a matching frame. This preserves SiblingContextButton and ordinary list-toolbar semantics; _cv_cancel_parent_target_access still has its own explicit parent gate. With no matching rendering scope, resolve only from the supplied object, never ambient page kwargs. Missing/unscoped/null outcomes take D-09's child-access fallback. Test the real URL-free cv_context_has_permission template filter, sibling/no-object list calls and Resource permission maps. Missing declarations still deny, and unexpected resolution errors propagate. Do not treat fallback as certification.

When URL-only resolution contains coordinates but no loaded direct parent, request materialize_parent from the shared resolver using registered metadata and the original instance's database/router context. Reuse already materialized parent instances. A known direct parent remains permission-checkable even if an older ancestor is unavailable; do not turn full-chain unavailability into a new direct-parent bypass. Complete explicit scope may name an absent parent: recognized native absence follows D-09 for ordinary helpers while the destination request still rejects it. Custom managers/properties retain their errors.

Same-parent reuse and cost (C2-M02): retain the parent instance already resolved by _guardian_check_parent on that request's view as private _cv_guardian_resolved_parent evidence. A matching rendering frame may reuse it for materialization only after the shared resolver has selected the destination and its registered parent model/normalized identity/database context agree. Reuse an existing frame parent instance under the same checks. Never call cv_get_parent_object once per row merely to obtain this hint, never let page evidence replace actual higher ancestry, and never reuse page A's parent for row B or an equal PK on another database. If matching evidence is absent, retain normal shared resolution. This stores model evidence for one request, not permission results: evaluate the effective parent policy for each action with the existing checker lifetime. Before 03-02 introduces the parent gate, record configured-permission baseline SQL for same-parent list and distinct-parent card fixtures at N=1/4 with fixed detail/update actions. In 03-03 measure each workload separately, splitting row/page setup, relation loads, parent permission SQL and child permission SQL, including already-resolved versus absent page-parent evidence and cold versus preloaded row relations. Commit exact numeric counts plus per-row/per-action deltas; do not claim a zero permission-query delta or hide it in relation totals.

Nested create remains special (C1-H4): its class-defined cv_has_access bypasses the parent mixin, so explicitly read the matching selected collection resolution there for non-None inputs before falling back to _cv_guardian_create_parent. Page A / row B create checks A, and the state adapter from plan 02 uses the identical A instance. Without a scope, unresolved own-child/M2M/None inputs still deny. For the existing no-object list create correction, the private rendering adapter invokes cv_has_access(user, None) once and cv_create_has_access(user, rendering_view, parent_A) once, preserving both public override seams and using the latter result as before. Consolidate the old GuardianQuerysetMixin post-render correction into this one scoped assembly, so parent state is evaluated only once. On row/child paths, retain the existing hook selection and original object arguments. Explicit None policy skips permission evaluation only; no new child-add requirement.

Certified availability (C1-H1) has one mandatory owner: _cv_cancel_target_available retains its explicit parent gate. Read rendering_view._cv_cancel_parent_object once; None immediately returns False and never takes D-09 fallback. Bind that exact already-certified instance and resolved coordinates with parent_gate_owner=certified-adapter, evaluate _guardian_user_has_parent_perm once, then invoke target cv_has_access once with the original child and evaluate child state once. The cooperative parent mixin detects matching certified-adapter ownership and delegates child policy without reloading/evaluating the parent; a non-delegating custom cv_has_access cannot bypass the earlier explicit gate. The ownership flag is chosen before policy evaluation and stores no result. Collection/create branches retain their explicit parent checks. Plan 03 owns this seam; plan 04 runs afterward and is the required real-delete integration gate, never an issue postponed to plan 06.
