# Remaining 1.0 work before the theme-surface freeze

Analysis date: 2026-10-28. Source of truth: `introduce-gsd` at
`e443376020ae6830308793b19cd9939c04fe77ac`. This report proposes work; it does not implement it or change the roadmap.

**Recommendation: phase 7 should wait.** The reason is a bounded set of reproduced defects, including request paths
that bypass protection or authorization, conditional controls that bind to the wrong row, and broken shipped
object-detail tabs. These need correction before the final policy freezes the affected request, DOM and template
contracts. Add the requested #275 cancel-link option as phase 6.1, complete the separately decided `no_label` removal,
and settle heading host placement alongside the small presentation fixes. Keep the final stability-policy phase last.

**Do not require the full jQuery port for 1.0.** Its dependency is explicit and compatible with a non-Bootstrap theme.
Fix current formset authorization and modal initialization independently. Do not reopen phase 6, rename the decided
label-mode attributes, or repeat implemented parent/global permission fixes. Treat conditional purge as the documented
opt-in aggregate capability unless the maintainer deliberately changes that policy.

### #275: optional native cancel navigation

The requested addition is a focused presentation capability, not a change to form validation or permission policy.
Current `CrispyFormMixin.get_cancel_button_kwargs()` obtains the existing cancel destination and passes it through
`data_cv_cancel_url` (`src/crud_views/lib/crispy/form.py:67–83`); the form normalizer exposes `cv_cancel_url` and the
stock leaf emits a button. `viewset.js:37–43` handles navigation by intercepting the marker's click. A custom leaf
can already render a link, but must then maintain its own label-mode/icon markup. The missing convenience is choosing
the tag through the public theme configuration while retaining the library leaf.

Use the issue's proposed `form:cancel-tag` (`button` default, `a` opt-in), an explicit per-button `tag=` override,
and form-leaf `cv_tag` as the intended scope. Validate allowed values and normalize reserved attributes; merely
adding a key must not allow arbitrary tags or duplicate/conflicting href attributes. Only a cancel kind with a usable
cancel URL becomes a link; a control without that URL remains a button, including submit/delete payloads using cancel
styling. Keep the current URL-selection/safety policy upstream rather than recomputing destinations in the theme.

Acceptance must cover default markup compatibility, theme/project/per-button precedence, no-URL fallback, all three
label modes, host/element icons, escaped URL/extra attributes, and supported disabled semantics. Anchor output retains
id/classes/accessible label and applicable extra attributes, but omits button-only type/name/value and the
`data-cv-cancel-url` interception marker. Keeping that marker would undermine native modified-click navigation, even
if ordinary clicks still reach the same URL. Verify navigation without core scripts, keyboard activation, modified/
middle-click behavior, no submit/reset side effects, and modal/full-page destinations with a minimal non-Bootstrap
fixture. `viewset.js` can remain unchanged because the anchor uses native navigation.

This follow-up refreshed the issue and checked source/test contracts; it did not implement the option or run new
runtime tests. Existing phase-6 tests establish the current button contract, not acceptance of the proposed link.
The option is additive with the button default preserved; document the new key, explicit override and leaf context,
including what custom form templates must adopt to honor it. If implementation changes existing defaults or behavior
beyond that scope, pair a Breaking entry with `docs/migrating-1.0.md` as usual.

### Heading-host probe and the precise missing work

With `detail -> ui:info` and a font library configured as
`{"class":"icon-{name}","placement":"host","standalone":"icon {name_class}"}`:

```html
<!-- Current stock cv_heading + cv_header_icon -->
<h5 class="modal-title"><i class="icon icon-info" aria-hidden="true"></i> Title</h5>
```

`get_icon_host_class("heading", "detail")` returns `''`. Adding the project class-table entry
`"heading:icon-host": "icon {name_class}"` and using the following public tags actually renders
`<h5 class="icon icon-info">Title</h5>`:

```django
{% load crud_views %}
{% cv_icon_class icon "heading" as host %}
{% cv_heading "header" level=5 class=host %}Title{% endcv_heading %}
```

A complete override also uses an element fallback when `host` is empty, combines existing heading classes, and
obtains the raw icon through the public view hook or group data. Thus the primitives are not absent. What is missing
is a consistent stock contract across page/modal/group titles. Test actual modal and all four icon-bearing layout
sites, mixed libraries, disabled/empty icon values, escaped classes and heading-level changes. This probe exercised
host output and existing tests exercise element headings; full stock dual-mode heading support remains acceptance
work. `cv_heading` currently also adds Bootstrap sizing class `hN` when changing levels: a CSS-only alternative theme
can define those compatibility tokens; native sizing-class remapping needs an explicit decision, not an accidental
promise that the tag has no Bootstrap conventions.

## 3. Guardian and inherited request paths

These are bounded findings, not a claim that every custom backend or mixin combination has been certified.
Severity reflects the demonstrated boundary. All six B1–B6 cases reproduced on current source with Django 4.2.30
and 6.0.9, using real Django Client request paths.

### B1 — High, confirmed: HTTP DELETE bypasses independent deletion protection

**Actor/configuration:** authenticated user with only per-object `delete_publisher` on the target; stock
`GuardianPublisherCascadeDeleteView` with documented `cv_check_delete_protection()` returning `["DENY-DELETION"]`.
No database PROTECT relation is needed for this reproduction.

**Requests/result:** POST `/guardian_publisher_cascade/<pk>/delete/` returns 200 and preserves the Publisher.
HTTP DELETE to the same URL returns 302 and deletes it. The existing `PublisherFormProtectedDeleteView`, whose
form clean raises a validation error, likewise preserves on POST but deletes on DELETE.

**Cause:** `src/crud_views/lib/views/delete.py:199–219` enforces form/protection in `post()` only. Inherited
`DeletionMixin.delete()` loads the object and deletes directly. Guardian's object grant/state check still runs, so
this is a bypass of an additional protection/confirmation boundary, not deletion without any object grant.
It also skips the library's form-valid processing/hooks/atomic boundary. Django documents this inherited
[DELETE behavior](https://docs.djangoproject.com/en/6.0/ref/class-based-views/mixins-editing/#deletionmixin).

**Disposition:** fix before freeze. Prefer explicitly disallowing DELETE unless maintaining a validated DELETE API
is intentional; otherwise route it through the complete library lifecycle. Test object denial, protection hooks,
form validation, rollback and hooks across allowed methods. Client probes disabled CSRF checks, but an actor allowed
to GET the confirmation page can obtain a token; CSRF is not the protection bypass.

**Theme:** supported presentation seams (form frame/leaf/alert), but backend behavior unsafe. No theme can repair an
alternate method. With a native form frame, denied/protected requests must still preserve the row. A behavior-changing
method restriction needs changelog/migration treatment; no new visual adapter is required.

### B2 — Medium to high depending form contents, confirmed: AJAX formset fragments skip object authorization

The supported composition used was:

```python
class ProbeUpdate(CrispyViewMixin, FormSetMixin, GuardianUpdateViewPermissionRequired):
    cv_viewset = GuardianViewSet(model=Publisher, name="probe_formset")
    cv_formsets = publisher_formsets  # existing books -> notes declaration
    form_class = PublisherFormSetForm
```

**Actor:** authenticated active user without Publisher/Book view/change/add grants. Ordinary GET
`/probe_formset/1/update/` returns 403. Adding `?template=books&pk=1&num=0` returns 200 JSON with `html` and `rows`.
A nonexistent endpoint object ID also returns 200. The stock fixture returns blank new-row fields, not existing row
values; that distinction matters.

**Demonstrated unauthorized data:** extend the inline Book form normally with
`reference = forms.ModelChoiceField(queryset=Contract.objects.all(), required=False)` and include it in the inline
layout. The same ungranted AJAX request returns `SECRET-CONTRACT-TITLE` in its choices. Authorized editors may need
those choices; an unrelated user denied the form must not receive them.

**Cause:** `src/crud_views/lib/formsets/mixins.py:37–44` returns the fragment before `super().get()`/object loading.
`src/crud_views_guardian/lib/mixins.py:31–58` intentionally admits authenticated users initially and relies on
`get_object()` for the replacement object gate. Child routes retain the parent gate but skip the target-child gate,
state check and object/parent relationship resolution. No unauthorized persistence via this GET was demonstrated.

**Disposition:** fix before freeze. Authorize the target and validate URL-parent/fragment coordinates before rendering
any fragment. Test missing/wrong-parent objects, state-disabled actions, grants/revocations and authorized fragments.
Keep `{html, rows}`, request coordinates, templates and `cv:formset:row-added` compatible where possible.

**Theme:** template/JS seams exist, but secure use requires backend correction. A theme must not filter the fragment or
copy permissions. After the fix, pair direct-denial assertions with a native formset override and widget initialization.

### B3 — Medium, confirmed: protected related-object labels leak through delete previews

**Actor/configuration:** only per-object delete Publisher, no view Contract; existing
`GuardianPublisherCascadeDeleteView` with `cv_show_related_objects=True`. Create a PROTECT-related Contract titled
`SECRET-CONTRACT-TITLE`. GET the delete page: 200 and the title is present while the guardian checker denies
`view_contract`.

**Cause:** `src/crud_views_guardian/lib/views.py:39–50` filters the cascade tree but passes `protected` unchanged.
Core `lib/views/delete.py:179–184` supplies those model instances to the template;
`templates/crud_views/snippets/delete/related_objects.html:5` renders their labels through the shared alert.
Existing tests cover cascade filtering and even preserve a synthetic protected list; they do not assert model-label
confidentiality on this path.

**Disposition:** fix before freeze. Filter individual protected objects before template context, with safe aggregate
placeholders or a separate blocked indicator. Hiding all labels must not falsely present deletion as unblocked.
Documented aggregate counts/model names are a separate intentional policy, not a newly alleged leak.

**Theme:** alert/tree leaves are usable, but input context is unsafe. Keep filtering library-owned; verify stock and
native alert frames with no/partial/full related view grants. Settle any safe-context changes before inventorying them.

### B4 — Medium, confirmed: parent permission `None` bypasses child-create action state

**Actor/configuration:** authenticated active user with no parent view/change or child add grant. Set both
`cv_guardian_parent_permission=None` and `cv_guardian_parent_create_permission=None`, a documented way to disable the
parent permission requirement. Set the create view's documented `cv_action_enabled` hook to return False.

POST `/guardian_publisher/1/guardian_book/create/`, `title=STATE-GATE-BYPASS`: 302 and row created under the URL parent.
The probe actor retained unrelated delete-Publisher/view-Author grants; they do not supply the required parent view/change or child add authority. The policy intentionally permits parent-permission-free creation; **skipping the independent state gate is the defect**.

`guardian/lib/mixins.py:233–234` returns before the no-object state check at 244; `has_permission:191–194` has already
bypassed the base create gate. Existing disabled-child-create tests use non-None parent permissions and pass.

**Disposition/theme:** fix before freeze, preserving the intentional None policy. Resolve the actual parent and check
state even when permission checking is off. Supported action leaves can show disabled state but cannot enforce it.
Test direct GET/POST, missing parents and native create controls; no new presentation API is needed.

### B5 — Medium in the affected backend configuration, confirmed: inactive list/detail disagreement

**Actor/configuration:** user with an object view grant, subsequently `is_active=False`, authenticated through Django's
`AllowAllUsersModelBackend` plus guardian's backend. GET `/guardian_author/` returns 200 with the granted secret row;
detail returns 403 and `ObjectPermissionChecker.has_perm` is False. An inactive superuser sees all list rows.

Default `ModelBackend` denies inactive authentication, so the default setup has an earlier safeguard. Django explicitly
supports [allowing inactive authentication](https://docs.djangoproject.com/en/6.0/topics/auth/customizing/#authorization-for-inactive-users);
that does not imply that these users acquire permission grants. Guardian's
[object checker](https://django-guardian.readthedocs.io/en/stable/api/core/#guardian.core.ObjectPermissionChecker.has_perm)
checks active status; the installed queryset helper does not apply the same check.

`guardian/lib/mixins.py:98–105,159–170,196–202` admits authenticated users and relies on that queryset helper.
**Disposition:** fix before freeze as a consistent backend gate. Test real inactive sessions, ordinary/granted/group/
superuser cases; default authentication alone would hide the defect. **Theme:** backend-only; tables/cards/native
lists must receive no unauthorized rows. Templates cannot restore the missing enforcement.

### B6 — Low/medium robustness, confirmed: documented parent-None policy crashes create controls

With the same None configuration but enabled creation, direct create GET is 200; child-list rendering and both create
access helpers raise `AttributeError: 'NoneType' object has no attribute 'split'`.
`guardian/lib/views.py:146–155,195–204` assumes a permission string despite dispatch supporting None.

**Disposition:** fix alongside B4 so visibility and dispatch share semantics. Missing parent resolution should remain
fail-closed; do not silently require a new child add permission. **Theme:** the public action leaf cannot repair
context construction without copying authorization. Presentation support is otherwise intact.

### B7 — Configuration inconsistency and diagnostics, not a confirmed escalation

`GuardianViewSet.cv_guardian_accept_global_perms` exists (`viewset.py:23`), but runtime mixins read a **view-class**
attribute; `GuardianViewSet.get_objects_for_user()` hardcodes strict fallback False (`:63–72`). Manage reports the
ViewSet flag (`views.py:231`), which can disagree with actual endpoints. Docs currently demonstrate the view-level
attribute (`docs/reference/guardian.md:92–98`), not a documented inheritance chain.

**Recommendation before freeze:** choose one truthful contract. Prefer preserving documented per-view behavior,
explicitly documenting the strict helper, and removing/clarifying the inert ViewSet knob while correcting manage's
effective-policy display. Alternatively define tested ViewSet→view precedence, acknowledging changed access. The
configuration display has public template seams but cannot manufacture missing effective-policy data.

Unknown/custom permission keys currently can reach `.get(...).split()` and produce 500s; this fails closed, with poor
diagnostics. Add focused configuration checks when touching these paths if inexpensive, otherwise defer additive checks
to 1.x. A malformed configuration is not evidence of a universal permission bypass.

## 4. Conditional groups and formsets

native DOM APIs and needs neither Bootstrap nor jQuery. Rendering still has crispy and DOM contracts that must be

### Precisely what another theme must override

- **Groups:** `ToggleGroup.template` defaults to `crud_views/conditional/toggle_group.html`; context is
  `cv_toggle_field`, `cv_toggle_css`, `cv_toggle_legend`, `cv_toggle_inner` (`conditional/layout.py:17,25–35`).
  Same-name template override or subclass template works. Actual temporary `<section class="custom-panel">` and
  native form-control rendering worked without Bootstrap JS. Keep `cv-data-toggle-group`, `cv-data-toggle-field`,
  and a real checkbox with its bound name. Checkbox CSS/switch appearance is replaceable; a div with role=switch
  and no checkbox is not currently the control protocol.
- **Crispy:** a non-Bootstrap form theme supplies its crispy pack/field/layout templates as appropriate. The server
  mixin itself is framework-independent; convenience forms and stock layouts use crispy. A minimal alternative
  field template was exercised, not a complete third-party pack. Custom form actions use the already completed
  public `get_form_actions()`/button-leaf path.
- **Formsets:** override `crud_views/formsets/formsets.html`, `formset.html`, `control.html`, or the documented layout
  template attributes. Normal rendering and AJAX use the same overrideable formset template. Keep `form.cv-form`,
  `.cv-formset-content`, `.cv-formset-row`, `.cv-formset-form`, `.cv-form-ctrl-*`, prefix/JSON attributes and management
  inputs. **Content and row selectors currently require div elements** (`formset.js:19–21`); changing their tag names
  requires core changes, not just CSS. Other wrappers and classes may change. Controls use public formset class keys,
  icon registry, accessible labels, delete-state class data and prefixes.
- **Template data:** formset templates reach XFormSet/XForm data while docs call rendering-tree machinery internal.
  Phase 7 must protect a documented data projection (prefixes, JSON, forms, management form, capabilities, helper
  data actually required by overrides) without declaring the implementation classes public. If a new facade is
  necessary, implement it before final inventory. Classifying all that context internal leaves no safe theme path.
- **Visibility:** native immediate `display:none`/restore plus library-owned disabled state needs no adapter.
  CSS can control visible layout and checkbox styling. **Managed exit animations or a UI-library visibility
  controller have no dedicated public interception seam**: core hides immediately and emits no transition event.
  A DOM observer/private wiring flag is not an adequate promised integration. If that is required for 1.0, add a
  small presentation-only callback/adapter before freeze while retaining binding/disabled/server ownership.
  Otherwise explicitly accept immediate native visibility for 1.0 and add animation hooks compatibly in 1.x.

These are distinct verdicts: ordinary native/CSS themes are supported with DOM constraints after correctness fixes;
arbitrary wrappers and managed animation are not automatically supported merely because toggle.js imports no Bootstrap.

## 9. Maintainer decisions actually needed

1. **DELETE endpoint policy:** recommend reject HTTP DELETE and retain the validated POST form workflow. Supporting
   DELETE is possible, but requires specifying how confirmation/protection/hooks work for it and testing equivalent
   semantics. Leaving inherited direct deletion is not an acceptable third option.

   behavioral DOM as the1.0 baseline, with the correctness/focus acceptance above. If a real downstream UI library
   must own visibility/exit animation now, approve a small presentation callback/adapter before freeze. It must not
   own disabled-state or authorization decisions.

   authors accept them. If the requirement is native variant/pill classes without parsing Bootstrap strings or
   compatibility CSS, add semantic resolved context now. The current implementation does not offer that capability.

   strict ViewSet helper, and truthful manage display; clarify/remove the inert ViewSet flag before1.0. Choose
   inheritance instead only with a specified precedence and tests, because it can broaden access.
