## Requirement across all tracks: usable by downstream themes

For **every feature, issue, finding, and proposed change**, answer: **Can a downstream theme customize its presentation and UI-library integration through supported public seams while preserving behavior, accessibility, and server-side security?** This is a required acceptance criterion throughout the analysis, not a separate optional review.

- Assess both the stock Bootstrap theme and a downstream theme using a different CSS/UI library, including one with no Bootstrap JavaScript. A successful Bootstrap render alone is insufficient evidence.
- Trace template selection and override paths, crispy template-pack assumptions, CSS/class keys, icon placement, JavaScript adapters, selectors, DOM attributes, lifecycle events, and asset/dependency loading where relevant. Distinguish styling defaults from classes or markup that carry behavior.
- Identify precisely what the downstream author must override or configure. Flag cases requiring private imports, package patches, replacement of core scripts, or copied permission/validation/business logic. Prefer supported presentation seams that retain library-owned behavior.
- Native DOM behavior can be theme-independent without an adapter. Require an adapter or another extension point only when a concrete downstream presentation or UI-library requirement needs it; explain the contract and compatibility cost.
- Give each item a theme-support verdict: supported with evidence, supported with documented constraints, gap requiring a public seam, or unverified. For backend-only work, explain why presentation is unaffected and verify that theme overrides cannot weaken its enforcement.
- Propose a focused way to validate each relevant contract using an existing downstream theme or a minimal temporary non-Bootstrap override/adapter fixture. State what was actually exercised versus what remains a recommendation; creating a new theme is outside scope.

Documenting a limitation is not by itself evidence that a feature meets the downstream theme requirement. Explain whether the limitation is acceptable or requires work before the final freeze, with the maintainer decision made explicit.

## Track A: conditional features and theme independence

Start with:

- `src/crud_views/lib/conditional/` (toggle sources, group validation/clearing, layout and conditional formset declarations).
- `src/crud_views/static/crud_views/js/toggle.js` and `adapters.js`.
- `src/crud_views/templates/crud_views/conditional/toggle_group.html`, formset templates/render tree, and `src/crud_views/lib/formsets/`.
- `docs/reference/conditional.md`, `javascript.md`, `theme.md`, `formsets.md`, and the conditional examples.
- `tests/test1/test_conditional*.py` and `tests/js/toggle.test.js`.

Initial observations: `toggle.js` uses native DOM APIs, inline `style.display`, and `disabled`; it does not directly call Bootstrap or jQuery. It listens for `cv:modal:loaded` and `cv:formset:row-added`. Its behavior is **not** delegated through `cv.adapters`, whose entries currently cover modal, tooltip, collapse, and alert. `ToggleGroup.template` names a package-owned overrideable template. These facts do not establish that the entire rendering stack is theme-independent, nor that a new adapter is needed.

Trace the complete feature from declarations to rendered HTML, events, client changes, validation, and persistence. Separate Bootstrap defaults in crispy/layout templates from behavioral coupling. Recommend whether the right public contract is native behavior, an adapter, a hook/event, template override, or documented constraints; explain the concrete theme use case for any new seam.

Explicitly assess whether downstream themes can change group/formset wrappers, checkbox styling, hidden/visible presentation, and optional animation without replacing validation or toggle ownership. Check whether inline `style.display`, disabled-state handling, selectors, or crispy assumptions prevent those changes. Verify the proposed theme path for initial content, modal content, and dynamically added rows, including accessible focus and disclosure behavior.

Probe likely edge cases rather than treating these as confirmed bugs:

- Repeated toggle names across formset rows: checkbox lookup currently scopes to the nearest form and permits suffix matches; does each group bind to the correct row?
- Re-enabling controls that were disabled for another reason; overlapping/nested groups; root-element handling during dynamic insertion; initialization retries and duplicate listeners.
- Multiple forms, prefixed forms, modal replacement, newly added nested rows, reset behavior, keyboard access, and focus when content is hidden.
- Management inputs must remain enabled when a formset is off; preserve the POST/re-render contract.
- JS-off and tampered POSTs; raw toggle coercion and cleaned-data timing; model validation, custom clean methods, empty-value clearing, files, and any supported field types with distinct save behavior.
- `skip` versus `purge`, queryset isolation, `commit=False`, transaction rollback, and forged formset IDs.

Important existing policy: conditional documentation explicitly says `purge` overrides `can_delete=False` / `edit_only=True`, and does not check per-row delete permissions, including under guardian. Existing tests cover queryset-limited purge and rollback when a sibling save fails. Decide whether this is an acceptable documented aggregate permission policy, an opt-in capability needing stronger controls, or a security defect under an actual supported configuration. Do not label the documented policy a vulnerability without defining the intended boundary and demonstrating the violation.

## Track B: adversarial guardian review

Start with `src/crud_views_guardian/lib/{mixins,views,viewset}.py`, `docs/reference/guardian.md`, guardian test helpers/fixtures, and `tests/test1/test_guardian*.py`. Follow inherited core behavior and MRO; do not stop at the guardian wrapper classes.

Initial observations: single-object access is checked in `get_object()`; list access is enforced through guardian-filtered querysets; parent access is checked in dispatch; top-level create and nested create have different permission policies. `has_permission()` deliberately bypasses model-level checks in some paths, so verify every supported execution path reaches its intended replacement gate. There is extensive existing regression coverage, including global/object permission fallback on parents (closed [#121](https://github.com/jacob-consulting/django-crud-views/issues/121)), anonymous behavior, child create-button visibility, card lists, and cascade-preview filtering. Coverage presence is not proof of security.

Build a permission matrix covering anonymous, inactive, authenticated without grants, user grants, group grants, global grants with fallback on/off, superusers, and revoked grants. Trace list/detail/create/update/delete/action and manage endpoints, parent-child combinations, modal requests, and dynamic formset requests. Verify supported authentication backend and guardian configuration semantics against installed versions and official upstream documentation when needed.

Specifically investigate:

- Direct URL and POST authorization independently of button visibility; disabled-action gates; alternate HTTP methods and custom hooks that could bypass object loading.
- Cross-parent IDs, parent/child queryset isolation, tampered foreign keys, inline formset IDs, and add-row endpoints that may leak data or mutate outside the authorized aggregate.
- Create permission semantics and consistency between `cv_create_has_access()` and actual dispatch, including `None` parent permission configuration and failed parent resolution.
- Agreement between ViewSet-level and view-level `cv_guardian_accept_global_perms`, helper methods, and parent checks.
- Anonymous/inactive/superuser behavior across list filtering and object checkers; permission caches and request boundaries.
- Manage-page exposure of permission holders/configuration and its access gate; related-object cascade previews, summaries and protected-object messages as possible metadata leaks.
- Delete, cascade, conditional purge, and workflow/action integration where supported. Distinguish intended parent/aggregate authority from per-row authority.
- Failure behavior for missing/custom permission keys and invalid configuration: fail closed, useful diagnostics, or unexpected 500s?

For each security finding, provide the actor's starting permissions, exact supported configuration, reachable request path, unauthorized read/write, and reproducible evidence. Separate confirmed vulnerabilities, defense-in-depth improvements, configuration hazards, performance issues, and uncertain hypotheses. A bounded review cannot certify that the integration is universally secure.

Apply the downstream theme requirement to guardian lists/cards, action visibility and disabled states, create controls, manage/configuration views, delete previews, permission-denied presentation, and supported modal/formset flows. Inspect guardian-owned templates as well as inherited core leaves. Verify that a theme can change markup, icons, classes and UI-library behavior through public seams without copying permission checks, exposing filtered objects, or relying on hidden buttons as the authorization boundary. Include direct-request denial alongside a representative themed render when validating security-sensitive presentation.
